## 3. Architecture notes

Everything below is the *behaviour the contract and `features.md` specify*, written in this repository's own
names, plus the facts measured on this host while rehearsing the unit (§6.1). Nothing here is a claim about the
reference product.

**Three processes, one boundary each (F§10.3, F§11).** The shell is an Electron application with a main
process, a preload script and a renderer that is the web app's own production build. The renderer is a plain
browser page: no Node, no Electron module, no file system. The preload runs with context isolation and
rendering sandboxing on, and copies exactly one object into the page — the desktop bridge — where every member
is a closure over an IPC channel rather than a reference the page could walk backwards through. The main
process is the only side that touches the disk, the settings record, dialogs and the operating system.

**One window that hides instead of closing.** The main window is loaded from a packaged file, never a URL. A
close request is cancelled and the window is hidden, so playback survives it; a real quit — `before-quit` from
any trigger — sets a flag that lets the next close destroy the window. A navigation away from the app's own
directory is cancelled before it happens and (only for `http:` and `https:`) handed to the operator's browser,
and a window the page tries to open is denied and handed over the same way. Autoplay is allowed because a
`?autoplay=1` hand-off is a script's decision rather than a user's.

**One instance per user-data directory.** The lock is requested before anything is created, keyed on the
user-data directory, which is what lets a test give a run its own directory and still launch the app twice. A
second launch that fails to take the lock exits immediately (exit code 0); this instance receives
`second-instance` and raises the `showMain` action.

**One action bus.** All nine triggers — the five shortcuts with a binding, the tray, the mini-player, the region
reader, the bridge's own window members, and a test — raise a single named action on Electron's `app` emitter,
and features subscribe by action. Nothing calls a feature directly.

**One validated boundary in both directions.** Channel names and payload schemas live in one module that both
the main process and the (bundled) preload import: an invoke is parsed before its handler runs, a push is parsed
before it is sent, and the preload parses what it receives before handing it to the page. A payload that does
not parse never reaches a handler and never reaches the page.

**The web app is the renderer, unmodified.** The shell consumes `apps/web/dist` — copied, not rebuilt — and the
hand-offs the shell owns are one boot feature on the web side: files the shell read are imported through the
ordinary import service, filed into the named folder (or `Inbox`), and the last one is opened playing; text is
imported into `Quick reads`, trimmed to its newest fifty, and opened playing. Both routes are the app's own.

**Measured on this host (Electron 45.3.1, xvfb, no window manager), before any deliverable was written:**

- a bare launch of the built shell (no `--no-sandbox`) dies at once with `SIGTRAP` and
  `FATAL:sandbox/linux/suid/client/setuid_sandbox_host.cc:172 The SUID sandbox helper binary was found, but is
  not configured correctly … chrome-sandbox is owned by root and has mode 4755`; Playwright's own Electron
  launcher passes `--no-sandbox` on Linux, which is why the suite's first launch works and a naked second launch
  does not;
- `shell.openExternal("https://example.org/")` resolves in about 15 ms, but it starts `xdg-open`, which starts
  `/opt/google/chrome/chrome` and does not return (measured: `timeout 8 xdg-open https://example.org/` exits
  124). After any such hand-off, Playwright's `ElectronApplication.close()` — the browser's own close command —
  never completes (measured: still pending after 20 s, and the case times out at 120 s), while the app's own
  `app.quit()` completes in about 0.5 s and Playwright's `close()` then resolves in 0 ms because the process is
  already gone;
- the renderer really is Node-free and Electron-free, and the window's title is `Lectern` both in the page and in
  the main process.

## 4. Lectern design

- [DESIGN] The renderer is `apps/web`'s production build, copied into `resources/web` by
  `scripts/copy-web.mjs`, which exits 1 with the path and the command that builds it when `apps/web/dist` is
  missing. Follows F§10.3's "consume the built `apps/web/dist`" and this contract's *Forbidden Actions* (no web
  source copied into the desktop app).
- [DESIGN] The preload is emitted as CommonJS (`out/preload/index.cjs`) with its dependencies bundled in, and
  the main process as an ES module. A sandboxed preload is not a module and may require nothing from
  `node_modules`, so both facts are forced by `sandbox: true` rather than chosen.
- [DESIGN] `ipc.ts` owns every channel name and payload schema and imports neither Electron nor any Node
  built-in, so the same module can be bundled into the preload and still be unit-tested with plain doubles. The
  outbound direction is validated by a table of channel → schema: a channel that is not in the table cannot be
  pushed on at all.
- [DESIGN] The settings record is one strict object written atomically (temporary file, then one rename) into
  the user-data directory, with `LECTERN_USER_DATA` overriding the whole directory. A file that does not parse,
  or that carries a field the record does not define, is answered with the defaults and left where it is —
  never partly trusted, never repaired in place.
- [DESIGN] `hotkeys.toggleMini` and `hotkeys.showMain` default to the empty string: F§10.3's hotkey list gives
  them no binding, and the tray and the mini-player (U-039) fill them in. The empty string is the record's own
  way of saying "unbound".
- [DESIGN] `captureRegion` raises its action and answers as soon as the request is on the bus, because the text
  it gathers arrives later on the `read-text` channel. F§10.3 does not say what the promise waits for; a
  promise that resolved when the capture completed would need the bridge to carry a second reply path this unit
  does not have.
- [DESIGN] The main window cancels a navigation to anything outside its own directory *and* hands `http:`/
  `https:` addresses to the system browser; the same helper backs `setWindowOpenHandler`, which denies every
  window the page asks for. Non-`http(s)` addresses are dropped without reaching the OS.
- [DESIGN] The end-to-end suite raises actions through `app.emit('lectern:action', …)` in the main process,
  which is the same call a hotkey or the tray makes; a global shortcut needs a window manager and a consent
  dialog, and a tray needs a desktop, neither of which this host has.
- [DESIGN] The suite's teardown ends the shell through its own quit path (`app.quit()`) and only then calls
  Playwright's `close()`. This is F§10.3's lifecycle — `before-quit` is what lets a window be destroyed — and it
  is what makes teardown deterministic on a host where a hand-off to the system browser leaves Playwright's own
  close command waiting.
- [DESIGN] The second launch in the suite passes `--no-sandbox` on Linux, exactly as Playwright's own launcher
  does for the first one. `launchApp()` keeps the contract's rule (`--no-sandbox` only when
  `LECTERN_E2E_NO_SANDBOX=1`) and the second-launch helper is where the platform's own requirement lives.

## 7. Deviation proposals

1. **The renderer's own navigation is the only hand-off the suite can observe.** F§11 asks that `http(s)` links
   open in the system browser, and on this host the OS handler is what makes the app's teardown stall for
   Playwright's close command (§6.1). The suite therefore asserts the refusal (the main process's
   `will-navigate` record with `defaultPrevented=true`, and the page still on its own file) and ends the shell
   through its own quit path. A contract that wanted the browser hand-off itself asserted would need a target
   and a host where a browser launch returns, or a bridge member that reports the hand-off — neither exists in
   F§10.3 today.
2. **`apps/web/src/boot.ts` is a registry this unit appends to, and the contract does not list a `Patch scope`.**
   The file is marked `(registry)` by U-027 (`spec.md:1109`), which is what `scripts/check-scope.mjs` allows a
   later unit to add a registry entry to; this unit adds exactly one entry (`[desktopIntegration]`) and no other
   line of the file changes. Proposed wording: name `apps/web/src/boot.ts` under *Patch scope* for every unit
   whose output bullet says "registered in `boot.ts`", so the permission is stated where the edit is.
3. **`docs/preflight.json` is rewritten by the fixed command's first step.** It is a tracked file of U-000's and
   the contract lists no way to write it, so it is restored to its committed content after the run and before
   the standing gates (the U-022 precedent). Proposed wording: add `docs/preflight.json` to AGENTS.md §5's
   always-writable row, or make `preflight.mjs` skip the write when `--phase` output is unchanged.
4. **`DEFAULT_HOTKEYS` leaves `toggleMini` and `showMain` unbound.** F§10.3's list of hotkeys does not include
   them, while its `DesktopSettings.hotkeys` record has a field for every action. An empty string is the
   design's answer; a contract that wants a binding will say so when the tray and the mini-player exist (U-039).
5. **One lockfile entry sits inside pnpm's minimum-release-age window.** `electron-builder@26.18.0` — a package
   this contract names — brings `electron-to-chromium@1.5.486`, published 2026-11-14T23:02:49Z, and the committed
   lockfile therefore fails pnpm's pre-script policy check: every `pnpm` invocation in the run prints
   `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION`, `Lockfile failed supply-chain policy check (663 entries)` and
   `[WARN] The install that runs before scripts failed …` above its own output, while the step itself exits 0 and
   the whole fixed command exits 0 (measured, §6.3). The installs this session made ran with
   `--config.minimumReleaseAge=0 --config.strictDepBuilds=false` on the invocation, which writes no file —
   `pnpm-workspace.yaml` stayed byte-identical (`sha256 193f4ebeb52b303fb4699dc1ec1cd03be4bc8067f2b08c3b9a2b097923167f70`,
   checked before and after). Proposed wording: name the package in `pnpm-workspace.yaml`'s
   `minimumReleaseAgeExclude` as an operator change, or give F§2.3 the toolchain versions the window permits, so
   the pre-script check stops failing on every run of every later unit.
