## 3. Architecture notes

**What a resolved payload is** — read from `dataParsers/ResolvingShareIntentDataParser.kt` and
`SharingRecords.kt` in the installed package, and from the typings in §5. Three shapes, distinguished by whether the
payload carries a `contentUri` and whether that URI is an address:

| Shared thing | `shareType` | `contentUri` | `contentType` | `value` |
|---|---|---|---|---|
| text | `text` | `null` | not set (typings allow `text`) | the text |
| an address (text that matches Android's web-URL pattern) | `url` | the resolved `http(s)` address after redirects | `website` for a page, `text` for plain text, `image`/`file`/`audio`/`video` by the resolved type | the address the reader shared |
| a file or an image | by MIME (`file`, `image`, `audio`, `video`) | `file:/…` — a **copy** the module made in this app's cache, named with `originalName` | by MIME (`file`, `image`, `audio`, `video`, and `website` for an `.html` file) | the `content://` URI the other app handed over |

Consequences that shaped the plan, all of them measured rather than assumed:

- The `content://` in a file share's `value` is the *other app's* grant, not a path this app can rely on later; the
  copy at `contentUri` is the readable one, and `clearSharedPayloads()` deletes it
  (`build/Sharing.d.ts`: "After it runs, the `contentUri` of a file shared into the app no longer points to a file").
- A shared **address** is resolved by an actual `GET` from the device before the screen sees it, so a share of a link
  can fail to resolve and answer through the hook's `error` instead of producing payloads.
- A shared **`.html` file** is labelled `website` even though its bytes are a local copy: the resolved-type vocabulary
  does not tell a web page apart from a web page *file*.
- Images arrive one payload each for `SEND_MULTIPLE`, so "one share of three photos" is three payloads with no field
  saying they are one intention; their order is the intent's own.

**The hook** — `useIncomingShare()` returns the raw payloads synchronously, an empty resolved list until resolution
finishes, `isResolving`, `error`, and `clearSharedPayloads()`. Two measured details matter to the screen:
`clearSharedPayloads()` sets both lists to `[]` (so the screen's own plan must not be read back out of the hook), and
`refreshSharePayloads()` returns early when the payloads are unchanged, so it cannot be used as a retry after a failed
resolution.

**The plugin's output**, read back from a real prebuild (a scratch copy of `apps/android`, §6.1):

```
<intent-filter android:autoVerify="false" expo-sharing-intent-filters="true">
  <action android:name="android.intent.action.SEND"/>
  <data android:mimeType="text/plain"/><data android:mimeType="application/pdf"/>
  <data android:mimeType="application/epub+zip"/>
  <data android:mimeType="application/vnd.openxmlformats-officedocument.wordprocessingml.document"/>
  <data android:mimeType="image/*"/>
  <category android:name="android.intent.category.DEFAULT"/>
</intent-filter>
<intent-filter android:autoVerify="false" expo-sharing-intent-filters="true">

```

Nothing else changes in the manifest for the shares: the module's own library manifest adds a
`SharingFileProvider` (`exported="false"`) and a `<queries>` block for `SEND`, and the plugin adds the
`share_into_scheme` string resource.

## 4. Lectern design

- [DESIGN] `planShare(payloads)` is pure and returns one action per shared item, in the order the platform reported
  them, with every image gathered into one `{ kind: "images", uris }` at the position the first image held
  (F§10.4's share sheet: "routes text, URLs, files, and images into the import pipeline"). Images are grouped because
  a multi-photo share is one intention and F§5.4 reads each image with the OCR engine; the `uris` are the **copies**,
  which are the only bytes this app may read.
- [DESIGN] The four roads are `classifyPastedInput`'s (F§10.4's pasted-text rules) where the payload is text, the
  hub's fetch where it is an address (F§7.2 — this device never holds that page), `importPickedFile` where it is a
  file (the same door U-049's picker uses), and `unsupported` for anything else — audio and video above all, which
  F§10.4 does not accept.
- [DESIGN] A file is importable when the hub reads its declared type **or** the extension it was shared under
  (F§5.4's six formats), because the declared type is a claim and the extension is the other claim; the hub decides
  from the bytes either way.
- [DESIGN] `app/+native-intent.ts` maps the share host to `/handle-share` and passes every other system path through,
  which is what expo-router's own `NativeIntent` contract describes; the host is parsed with string arithmetic rather
  than `URL`, because React Native's URL is a partial polyfill.
- [DESIGN] The handler screen plans before it imports: it lists one row per action, imports a text-only or
  address-only share as soon as the list appears (the contract allows it), and waits for the button whenever a file
  or an image is involved. Nothing reaches the hub without a row already on the screen; unsupported rows show their
  reason and are never sent. After the imports have read the copies it calls `clearSharedPayloads()`, because
  F§10.4 keeps no copies of shared files after an import — and it keeps its own plan and results in state, so the
  list survives the clear. A single resulting document opens the reader, several open the library.
- [DESIGN] The app config gains the `expo-sharing` plugin entry with Android receiving enabled and no iOS block
  (AGENTS.md §6, F§10.4's "expo-sharing config plugin with android.enabled: true"), the one file the contract's
  patch scope names besides the four outputs.

## 7. Deviation proposals

1. **A shared `.html` file is a file, not an address.** The contract's rules put "website → url" and "file with a
   supported MIME type or extension → file" next to each other, and the platform gives an `.html` *file* the resolved
   type `website` while its `contentUri` is a copy in this app's cache. The planner decides by whether the payload
   carries a fetchable `http(s)` address: a real website becomes a `url` action (the contract's rule holds for every
   payload that actually is an address), and an `.html` file becomes a `file` action for the hub to read — which is
   what F§5.4 does with it anyway. Filed for the operator to ratify or to narrow the rule in a patched contract.
2. **The install could not use `npx expo install`.** As U-045, U-047 and U-049 measured, its bare `pnpm add` dies on
   this repository's committed lockfile (`ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION`). The substitute
   `pnpm --filter @lectern/android add expo-sharing@~58.0.23 --config.minimumReleaseAge=0
   --config.strictDepBuilds=false` installs the version `expo@58.0.25`'s own `bundledNativeModules.json` names
   (`~58.0.23`) and F§2.3 pins (`58.0.23`): one package, 22 lockfile lines, no change to `pnpm-workspace.yaml`.
3. **F§5.4's six MIME types are declared twice.** `route-share.ts` cannot import `SUPPORTED_IMPORT_MIME_TYPES` from
   `import-service.ts`, because that module is not importable by the package's Node test program (§6.1). The two
   lists are the same six strings and both are named where they sit; the alternative — a shared module — needs a
   file outside this unit's scope.
