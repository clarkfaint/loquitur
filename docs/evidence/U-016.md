## 1. Questions

The contract names no inspection questions. The questions its *Required File Outputs* and *Pass/Fail
Verification Test* imply, and that this unit answers, are:

1. Which request does the adapter send for a synthesis, exactly, and to which path?
2. How are a voice id, a timestamp and a duration read out of the service's answer?
3. What does the adapter do when the service is down, when it does not have the voice, and when it never
   answers at all?
4. Does the adapter hold any knowledge of a voice list of its own?

## 3. Architecture notes

**Request shape.** One call is: `method`, `content-type: application/json`, and — for a synthesis only — a
JSON body of the six fields above, in F§6's order, with `speed` already clamped. The voice list is a `GET`
with no body and no content type. The address is `baseUrl` with its trailing slashes removed, then the path,
so a `baseUrl` with or without a trailing slash reaches the same paths.

**How the answer becomes a `SynthesisResult`.** `audio` (base64) is decoded to bytes; `timestamps` is mapped
one-to-one to `{ text: word, s: round(start_time · 1000), e: round(end_time · 1000) }`; an empty array
becomes `null`; and the duration is `max(readMp3DurationMs(audio), last token end)`. The container is always
`audio/mpeg`, because that is the `response_format` asked for.

**Timing math of the stub's audio.** A frame of the stub's header is MPEG-1 Layer III, 128 kbps, 44 100 Hz:
417 bytes and 1152 samples, i.e. 1152/44 100 s = 26.1224 ms. 100 frames are therefore 2612 ms and 50 frames
1306 ms, so a stub that divides its frame count by the requested speed answers exactly twice as fast at speed
2, and 2612/(1306·2) = 1.

**Failure behaviour.** Every way a request can fail converges on one error value: unreachable transport, an
HTTP status that is not `ok`, a body that is not JSON, a body that is not the expected shape, base64 that the
host cannot decode, audio with no readable frame, and a response that never arrives. The last one is a race
against a timer, and the timer also aborts the request; the abandoned request is caught so it cannot surface
later. No timeout leaves a pending handle behind.

## 4. Lectern design

- [DESIGN] **The transport is injected, defaulting to the host's `fetch`** (F§6's adapter is isomorphic).
  `KokoroRequest`/`KokoroAnswer` describe only the part of `fetch` this adapter uses — a URL, a method, JSON
  headers and body, a signal, and an answer with `ok`, `status` and `json()` — so a hub passes its own
  `fetch`, a test passes a stub, and no DOM or Node typing is needed. A host with no `fetch` at all is
  `ENGINE_UNAVAILABLE`, not a crash at construction.
- [DESIGN] **The host globals are declared locally** (`setTimeout`, `clearTimeout`, `AbortController`,
  `atob`). `lib` resolves to ES2022, which declares none of them, `@types/node` is absent and R10 forbids
  adding it, so each is declared with the exact signature used. `fetch` needs no declaration: it is read
  from `globalThis` as `unknown` and narrowed by `typeof`.
- [DESIGN] **`ENGINE_UNAVAILABLE` is the adapter's one code**, per the contract's *Required File Outputs*,
  and therefore covers a bad answer as well as an absent one. The message names the URL and the reason, so
  the two are still distinguishable to an operator.
- [DESIGN] **The engine speed is clamped, never refused** (contract's *Required File Outputs*); the clamped
  value is what appears in the request body, so the hub's cache key and the service's request agree.
- [DESIGN] **`Voice.lang` and `Voice.name` are derived from the service's own id.** F§6's `Voice` requires
  both and the service reports neither: `name` is the service's own voice id, and `lang` is the prefix before
  the first `_` (`af_heart` → `af`), which is the service's own language-and-gender code. Nothing about a
  particular voice is written down.
- [DESIGN] **The voice list is accepted in either envelope** — an object with a `voices` array, or a bare
  array of ids — because F§6 pins only the endpoint, not the envelope, and a wrong guess would be a silent
  empty picker rather than an error. The ids themselves are the service's.
- [DESIGN] **The two response schemas are not strict.** They are another project's payloads, and a field
  that this adapter does not read must not break synthesis; only `audio`, `timestamps` and `voices` are
  read, and a payload that lacks one of them is refused with the failing path in the message. Lectern's own
  records (U-014, U-015) stay strict.

## 7. Deviation proposals

1. **`lib` for this package.** `tsconfig.base.json` sets no `lib`, so the program is ES2022 alone and
   declares no `fetch`, timer, `AbortController` or `atob`; this unit declares the four it uses inside its own
   module. A host-typing decision for the whole repository (`"lib": ["ES2022", "DOM"]`, or an allow-listed
   host-globals declaration shared by the packages that reach a network) would be preferable to a local
   declaration per module, but both files that could carry it are outside this unit's writable set.
2. **The voice-list envelope.** F§6 names the endpoint and nothing about its envelope. This unit accepts both
   readings (§4). If the operator knows which one the container answers, pinning it in F§6 would let the
   adapter drop the union.
3. **`Voice.lang`.** F§6 requires a language tag per voice and the service reports none, so this unit derives
   it from the service's own id prefix. If the container exposes a language per voice, F§6 could name the
   field and the derivation could go.
