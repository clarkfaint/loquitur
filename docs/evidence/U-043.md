## 3. Architecture notes

**The state machine of one file.** F§10.3's watcher is one sentence — "chokidar watches configured folders
(default `~/Lectern/Inbox`) for `pdf, epub, docx, txt, md, html`; waits for writes to finish; never modifies the
watched files; imports through the web app's import pipeline; de-duplicates by `docId` and by a ledger of
processed files" — and it is six steps per file, in this order:

| # | Step | Where it happens |
|---|---|---|
| 1 | a file appears or changes below a watched folder | chokidar (`add` / `change`), which holds the event back until the write has settled |
| 2 | the path joins a queue, once, and the queue is drained one file at a time | `file-watcher.ts`'s own queue |
| 3 | the file is asked its size and modification time, and judged by its name and that size | `node:fs/promises` → `watch-model.ts`'s `isImportable` |
| 4 | a key of `path:size:mtime` is computed and looked for in the ledger | `watch-model.ts`'s `fileKey`, `shouldProcess` |
| 5 | the bytes are read and handed to the app as one import request (`Inbox`, `play: false`) | F§10.3's `lectern:import-request` |
| 6 | the key is recorded, newest first, and the ledger is capped at 5 000 | `DesktopSettings.processedFiles` |

The app is what turns the bytes into a document: F§5.4 decides the format from the bytes, the hub reads it
(`POST /v1/parse`), F§5.2's `docId` identifies it, and `apps/web/src/desktop/desktop-integration.ts` files it in
the folder the shell named. Nothing in the shell parses, hashes or stores anything, and **nothing writes to a
watched folder** — the shell only ever reads (`stat`, `readFile`).

**Two de-duplications, and they answer two different questions.** F§10.3 names both, and they are not
interchangeable:

- the **ledger** answers *has this shell read this file before?* Its key is the path, the size and the
  modification time together, so a file the operator has not touched is the same key and a file they have changed
  is a new one. It is what makes a restart quiet: the folder's contents are looked at when the watch begins, and
  every file already there is already in the ledger.
- the **`docId`** answers *does the library already hold this document?* It is the app's (`importFile` →
  `keep` → `store.getDocumentMeta`), and it is what makes the second copy of a file that has changed nothing new.
  Measured: the fixtures' `sample.txt` and `sample.md` are the *same* document under two names — both
  `cd670b281d074ae2eabdee8694a82aad` (§6.1 (a)) — so importing one after the other adds a ledger key and no
  library entry. A case that wants to see a *document* arrive must use a document of its own.

**Timing.** F§10.3 says the watcher "waits for writes to finish", which is chokidar's `awaitWriteFinish`: a file
is held until it has held still for `stabilityThreshold` (500 ms) and is asked about every `pollInterval`
(100 ms). One file is read at a time, so a folder dropped in at once is imported as a sequence of single
documents rather than a burst; the end-to-end case allows the contract's 30 s for two files and measured 6.7 s
and 11.9 s (§6.2).

**The section's layout.** F§10.1 renders every registered section as a titled block inside the settings screen
(`SettingsPage.tsx` maps `sections`), so the watched folders are one block: a list with one row per folder the
shell reports — the folder's own path, the words for its state, and, for a folder that came from the record, a
button that stops watching it — then one button that adds a folder, then one sentence for a failure if there is
one. Nothing renders at all in a browser, where there is no bridge.

**The ledger's arithmetic.** `processedFiles` is a flat list of keys, newest first, and the shell keeps the newest
5 000. Each reading of a file is one key, so the list's length is the number of readings and its *contents* are
what a restart reads. It is the one place a case can see "the shell looked at this file" for a file that produced
no new document, which is why the end-to-end cases read it (§6.2).

## 4. Lectern design

- [DESIGN] **The shell's own inbox is watched *beside* the record, and the record is never written to say so.**
  F§10.3's default is `~/Lectern/Inbox`, "created on first run", and the contract's *Forbidden Actions* allow
  exactly one folder the operator did not add. The obvious implementation — make the folder and add it to
  `settings.watchFolders` — was **rejected because it breaks a frozen unit's suite**: U-040's third case asserts
  that a shell whose only settings interaction was refused has *no* record at all
  (`apps/desktop/e2e/hotkeys.spec.ts:134` and `:141`, `expect(await recordHotkeys(userData)).toBeNull()`), and a
  start-up write of `watchFolders` would make that file exist. The shell therefore watches
  `settings.watchFolders ∪ {~/Lectern/Inbox}`, makes that folder on start-up, and writes nothing: a shell that has
  changed nothing still has no settings file, and U-040's case stays green (§6.3). §7 (1) proposes the contract
  say which of the two it wants.
- [DESIGN] **The folder's contents are looked at when the watch begins, and the ledger is what makes that safe.**
  `ignoreInitial: false` — a folder the operator points the shell at is a folder they want read, and F§10.3's own
  de-duplication is what stops the second look from being a second import. `followSymlinks: false` and `depth: 3`
  are the contract's own rules (a link out of a watched folder is not a file in it; three levels is where the
  shell stops looking), and both are chokidar options rather than a walk of this unit's own (§5).
- [DESIGN] **One file at a time, because the ledger is read-modify-written per file.** The record is the
  operator's, and `remember` reads it, extends it and writes it back for every file; two imports in flight could
  therefore each write a ledger missing the other's key. A single queue drains one file per turn, so the record's
  writes are serialised by construction, and a file that produces two events while it waits is processed once —
  its key is computed when it is read, not when the event arrives.
- [DESIGN] **A key is `size:truncated-mtime:path`, and the path comes last.** The three parts are what "the same
  reading of the same file" means; the time is truncated to whole milliseconds because that is the resolution a
  ledger can keep, and the path is last so no number can be read as part of it. A file whose *contents* changed
  is a new key and is read again, which is the difference between "untouched" and "changed" — and it is why the
  re-copied file in the contract's case adds nothing to the library while it does add a ledger key.
- [DESIGN] **The ledger is written after the hand-off, not before.** A hand-off that could not be made (a
  renderer that is gone, a window that never loaded) leaves the file unread rather than lost, and the app's own
  `docId` de-duplication is the second line F§10.3 names, so a file read twice costs a parse and not a duplicate
  document.
- [DESIGN] **A file that went away while it waited is not an error.** `stat` can fail with `ENOENT` for a file
  deleted between its event and its turn, which is an ordinary thing for a folder to do and not something the
  operator can act on; that ending is silent, and everything else is one line in the shell's log.
- [DESIGN] **The model is pure and takes the size as an argument.** `watch-model.ts` reads no disk and holds no
  clock: `isImportable(path, sizeBytes)` is handed the size the caller has just measured, so the whole of what a
  name and a size mean is testable without a filesystem, and the watcher around it is what the end-to-end case
  proves. Every surface the watcher touches outside itself (`watch`, `stat`, `read`, `makeDirectory`, `home`) is
  injected through `WatcherHost`, so the module imports no Electron and the shell's own surfaces are built in one
  place — the shape U-041 and U-042 used.
- [DESIGN] **Settings changes are applied as a diff, and the watcher's own write must not disturb it.** The
  watcher writes the ledger into the same record it reads folders from, so an `onChange` that restarted every
  watcher would tear its own watchers down on every import. `apply` compares the folders in force with the ones
  the record asks for and only adds what arrived and drops what left.
- [DESIGN] **The section lists what the *shell* reports, and offers removal only for the operator's folders.**
  F§10.3's `DesktopStatus.watchers` is the shell's own account — every folder, with the reason when one could not
  be held — while `DesktopSettings.watchFolders` is only what the operator asked for. The two differ by exactly
  one folder (the shell's own inbox), so the list is drawn from the status and the "stop watching" button is
  offered only where the record agrees. §7 (2) proposes F§10.3 say which folder is the shell's own.
- [DESIGN] **Subscribing comes before reading, and the status is published as part of the hand-off.** F§10.3's
  `onStatus` is a one-way push and the shell publishes its first status before any renderer exists, so a section
  that mounts late would wait for the next change; it subscribes first and then reads, and the shell re-announces
  its status while answering that read (the takeover U-040's feature makes). The watcher publishes on the same
  two paths U-040's feature does — into the store, and over `lectern:settings-status` — so a folder that fails
  to be watched is visible without a reload.
- [DESIGN] **The end-to-end cases read the library the way a reader does.** F§10.1's library screen reads the
  library once when it appears, so a case cannot watch a document arrive in an already-open screen: the cases
  leave the screen and enter it again, which is what makes a poll of it a poll of the reader's view. §7 (4)
  proposes the screen subscribe to the store instead.

## 5. API signatures relied on

`chokidar@6.0.0` — a new dependency this unit installs, so every member below was read from the installed
package rather than remembered (AGENTS.md R9). From `apps/desktop/node_modules/chokidar/index.d.ts`:

```ts
export declare function watch(paths: string | string[], options?: ChokidarOptions): FSWatcher;
export declare class FSWatcher extends EventEmitter<FSWatcherEventMap> {
  add(paths_: Path | Path[]): FSWatcher;
  unwatch(paths_: Path | Path[]): FSWatcher;
  close(): Promise<void>;
}
export interface FSWatcherEventMap {
  [EV.READY]: [];  [EV.ERROR]: Parameters<WatchHandlers['errHandler']>;
  [EV.ADD]: EmitArgs;  [EV.CHANGE]: EmitArgs;  [EV.UNLINK]: EmitArgs;  …
}
```

and from `chokidar/runtime.d.ts`:

```ts
export type Path = string;
export type EmitArgs = [path: Path, stats?: Stats];
export type WatchHandlers = { errHandler: (err: unknown) => void; rawEmitter: (ev, path, opts) => void };
export type AWF = { stabilityThreshold: number; pollInterval: number };
export type ChokidarOptions = Partial<BasicOptions & {
  ignored: Matcher | Matcher[];
  awaitWriteFinish: boolean | Partial<AWF>;
}>;
type BasicOptions = { persistent: boolean; ignoreInitial: boolean; followSymlinks: boolean; …
  alwaysStat?: boolean; depth?: number; atomic: boolean | number; };
```

Four consequences that decided the deliverable's shape:

1. The event listener is `(path: Path, stats?: Stats) => void` with `Path = string`, so the handler is
   `(path: string) => void` and no Buffer case exists to handle.
2. `awaitWriteFinish` is a *partial* `AWF`, which is why the two numbers are named constants rather than one
   object literal.
3. `error` carries `Parameters<WatchHandlers['errHandler']>`, i.e. `(err: unknown) => void` — an unknown, which is
   what `reasonFor` takes.
4. `chokidar@6.0.0`'s own manifest declares `"exports": { ".": { "default": "./index.js" } }` with **no** `types`
   condition; TypeScript resolves the sibling `index.d.ts` under `moduleResolution: "Bundler"`, and the file
   itself imports `node:events`, `node:fs` and `readdirp`, which compile because `skipLibCheck` is on (the U-006
   patch) and because `apps/desktop`'s program resolves `node:` specifiers through `electron@45.3.1`'s own
   `@types/node` dependency. `pnpm --filter @lectern/desktop run typecheck` is silent with the import in place
   (§6.2), which is the measurement.

`electron@45.3.1` — nothing new: the watcher imports no Electron at all, and the section uses the existing
bridge members (`settings.get`/`set`/`onStatus`/`pickFolder`, `DesktopStatus`, `DesktopSettings`) exactly as
`packages/ui-web/src/desktop-bridge.ts` declares them. `apps/desktop/electron.vite.config.ts`'s
`main.build.externalizeDeps: false` is why chokidar is bundled into `out/main/index.js` rather than required at
runtime — the packaging ships `out/**`, `resources/**` and `package.json` and no `node_modules` (§6.1 (b)).

### 6.2 Rehearsal in a copy of the repository (2026-11-15)

The fixed command was run whole — all six of its steps — in a `cp -a` copy of the repository
(`~/.hermes/cache/scratch/u043-repo`, 920 MB) with the deliverables copied in, before the official run. Its
numbers: **121** desktop unit tests in 7 files (20 of them this unit's `watch-model` cases), **50** web tests in
5 files, `tsc` silent, **197** modules to the web build (`0.67 kB` `index.html`, `8.44 kB` stylesheet,
`869.51 kB` script — one module more than U-042's 196, which is this unit's section), `copied 7 file(s) from
apps/web/dist into resources/web`, **149** modules to `out/main/index.js` (416.05 kB) and 121 to
`out/preload/index.cjs` (188.42 kB, unchanged) — and then **2 cases green in 20.0 s** (6.7 s for the arrival
case, 11.9 s for the restart case). The chain's exit code was 0.

Three findings came out of the rehearsal, and all three are in the deliverables or in the case that was wrong
about them:

1. **A file's second copy is a second *reading* and not a second document, and the case has to say which it is
   measuring.** The first version of the arrival case asserted that copying `sample.txt` in again left the
   library at two documents *and* the ledger at three keys; both are true, but the reason is not the watcher —
   F§5.2's `docId` is the same for the same text, so the app refuses the second import before the library sees
   it. The case now reads the ledger for "the shell read it again" and the library for "and nothing new
   appeared", and §6.1 (a) is the measurement behind it.
2. **The restart case's positive control was measuring the same de-duplication.** It copied `sample.md` in after
   `sample.txt` and waited for a third document; measured, `sample.md` *is* `sample.txt` (§6.1 (a)), so the
   library legitimately stayed at two. The control is now `article.html`, a document of its own, and the case
   asserts the ledger holds each key once and gained exactly one.
3. **A request that reaches the page is not a request that reaches the app, and only the shell's own record
   separates them.** A throwaway probe launched with the same user data showed the restart's watcher recording
   `sample.md` and pushing the import request, with the page's own listener receiving it — and no document. The
   cause was finding 2, not the hand-off; the probe is what made that a measurement instead of a guess, and it
   is why the delivered cases read the ledger (the shell's own account) beside the library (the app's).

## 7. Deviation proposals

1. **The contract's default folder cannot be watched the way the record works, without breaking a frozen unit.**
   The contract's `file-watcher.ts` bullet says the watcher "watches `settings.watchFolders`", and its *Forbidden
   Actions* say "the only default is `~/Lectern/Inbox`, created on first run" — which reads as: make that folder
   and add it to the record. That write would make `desktop-settings.json` exist on a shell that has changed
   nothing, and U-040's third case asserts exactly the opposite
   (`apps/desktop/e2e/hotkeys.spec.ts:134`, `:141`). This unit therefore watches the record's folders *plus* its
   own inbox and writes nothing (§4). Proposed: F§10.3 and the contract say which folder is the shell's own, so a
   later unit can tell whether "the default" means "added to the record on first run" (which needs U-040's case
   to change) or "watched beside the record" (which is what is built).
2. **`DesktopStatus.watchers` does not say which folders are the operator's.** F§10.3's status is
   `{ folder, ok, error? }[]`, and the shell has one folder nobody added; a settings section that offers a
   "stop watching" button has to compare the status with `DesktopSettings.watchFolders` to know which rows may
   have one. Proposed: a `removable` (or `source: 'operator' | 'shell'`) field on the status entry, so the
   section renders what the shell says rather than re-deriving it.
3. **`ignoreInitial` is a real decision the contract does not name.** "Waits for writes to finish" and "never
   modifies the watched files" are named; whether a folder's *existing* contents are read when the watch begins
   is not. This unit reads them (`ignoreInitial: false`), because F§10.3's ledger is what de-duplicates and a
   folder the operator adds is one they want imported. Proposed: the contract name the behaviour.
4. **F§10.1's library screen reads the library once when it appears**, so no end-to-end case can observe a
   document arriving in a screen that is already open — the case has to leave the route and enter it again. The
   same is true of the import screen's list. Proposed: the library screen subscribe to the store (it already
   re-reads after every action), which would also make the screen honest for a document that arrives from the
   shell, another tab, or a sync push (F§8.2).
5. **A document the hub refuses is not reported anywhere.** `handleImportRequest` logs a failure to the page's
   console and stops; a folder the operator pointed the shell at can therefore fail silently for as long as they
   do not open the developer tools. Proposed: F§10.3's `DesktopStatus` carry the last hand-off's outcome (or a
   count of refused files per folder), which the settings section could show beside the folder's state. This is
   the shell's half of a feature whose only visible artefact is a document that did or did not appear.
