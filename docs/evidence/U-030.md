## 3. Architecture notes

No behaviour of the reference product is described here, because nothing was observed. What follows is the
Lectern architecture this unit implements, read from `features.md` and the frozen units it builds on.

**What a `PdfAnchor` points at (F§5.1).** An anchor is
`{ sentenceIndex, wordIndex, page, itemIndex, charStart, charEnd }`: `page` is 1-based, `itemIndex` indexes
the page's text-item list *as `getTextContent()` returns it* — the raw array, before the hub parser drops the
empty items pdf-lib writes beside the text it draws — and `charStart`/`charEnd` are offsets inside that item's
own `str`. U-007 built them from provenance rather than from a second guess at the text: every character of a
block's text remembers the item and offset it came from, so a word's range maps onto exactly the characters
that drew it. Because the hub and this client call the same `getTextContent()` with **no arguments** on the
same `pdfjs-dist@6.5.438`, the two item lists are one list, and an anchor resolves to a span here by
arithmetic rather than by searching text.

**The text layer's shape.** `TextLayer` positions one span per item that carries a `str`, in the order the
items appear, skipping items that carry none (marked content), hanging the unpositioned ones on the container
and taking the page's layout from the viewport. Three of its conventions decide how this unit drives it:

- the whole layer is laid out in *unscaled* page units — `left`/`top` are percentages of the page box and the
  span's `font-size` is `calc(var(--text-scale-factor) * var(--font-height))`, where
  `--text-scale-factor = calc(var(--total-scale-factor) * var(--min-font-size))` and `--min-font-size` is
  measured by the class itself. `--total-scale-factor` is the one custom property the *viewer* normally sets
  and the class never does, so the view sets it to the scale it renders at;
- the container's own width and height are written as
  `round(down, var(--total-scale-factor) * <page width>px, var(--scale-round-x))`, a CSS expression this view
  replaces with `100%` of a page box whose px size it already knows from the viewport;
- `--scale-x` and `--rotate` are per span and are set by the class after it measures the text on a canvas, so
  no span width is ever computed here.

The span that an anchor's `itemIndex` names is therefore the *k*-th span, where *k* counts the items before
it that carry a `str` — the view builds that map once per page as the layer is created and keeps it, so a
new active word is a map lookup and a `Range`.

**Virtualization.** Every page of the document gets a box of its own size, in document order, so the
document's scroll height is right before anything is drawn. A page is *drawn* — canvas and text layer
created — only while its box intersects the viewport expanded by one page height above and below, which is
the contract's "visible pages plus one on each side". A page that leaves the window releases its canvas, its
text layer and its pdfjs page (`cleanup()`); a page that enters it is built again. The page carrying the
active word is always inside the window, because the view scrolls that page box into view when the word
moves to it and drawing follows from the box becoming visible.

**The highlight registry.** The active word is one range on the span its anchor names, limited to
`charStart…charEnd` inside it. The active sentence is one range per anchor of that sentence which lies on a
drawn page, because a sentence can run across two items or two pages. Both are registered under the frozen
names `lectern-sentence` and `lectern-word`, so the *same* two `::highlight()` rules that paint the reflowed
text paint the page view; the view injects those rules itself (in U-023's tokens) because R6 freezes
`packages/ui-web/src/styles.css`, and a reader who never mounted the text view must still see a highlight. A
sentence highlight for a page that is not drawn is not registered — a range cannot exist outside the DOM —
and the reader gets it back when they scroll to that page.

**Following the word.** On every frame, the view measures the active word's rectangles on the page that
carries it. A word whose top has left the band (30 %–60 % of the viewport) is scrolled to rest at 45 % —
F§10.1's own auto-scroll policy in `@lectern/ui-web`, reused as it stands, including its four-second
suspension after a scroll the reader makes by hand. When the word's page has not been drawn yet (a seek
across pages, or a restored position), the page box itself is brought to the middle of the viewport, which is
what makes the page enter the drawn window; the fine positioning follows the next frame.

**Clicking.** A click on the text layer is resolved through the same anchors rather than through a second
model: the caret-from-point API gives the node and the offset inside it, the span the node belongs to gives
the `itemIndex` the anchor names, and the anchor on that item whose `[charStart, charEnd)` contains the
offset gives the sentence and the word. An offset that falls between two anchored ranges (the whitespace a
word's anchor stops short of) takes the nearest anchor *before* it on the same item; a click that has no
anchor at or before it seeks nowhere rather than moving the reading backwards.

## 4. Lectern design

- [DESIGN] The page view renders at the scale it is handed, and the reader page hands it `1`. F§10.1 gives
  the PDF page view no zoom control and this contract lists none, so none is invented: the prop exists
  because the page box's size, the canvas's backing store and the layer's `--total-scale-factor` are all
  functions of it. See deviation proposal 1.
- [DESIGN] `rectsForAnchor` is the contract's own answer for "where is this anchor on the page"; its
  companion `rangeForAnchor` returns the `Range` itself, so the highlight registry, the scroll policy and
  the click resolver all resolve an anchor to a range exactly once, in one place. `rectsForAnchor` is the
  contract's `DOMRect[]` view of that same range. The extra export is listed as deviation proposal 2.
- [DESIGN] `indexAnchors` keys an anchor by `sentenceIndex:wordIndex`; the view builds the map once per
  document with `useMemo`, and the render effect keeps it in a ref so a frame's work never depends on React
  having re-rendered (F§5.6(d)'s per-frame sampling).
- [DESIGN] The page view is handed the document's *original bytes* and its anchors — the two blobs U-028's
  import wrote under `orig/<docId>` and `anchors/<docId>` — which the reader page reads through the frozen
  `BlobCache` (F§5.9). The parse is never repeated in the browser and playback keeps using the model from
  the hub: the contract's *Forbidden Actions* forbid both.
- [DESIGN] The anchors blob is validated with F§5.1's own `PdfAnchorSchema` from `@lectern/core` before a
  single anchor is used (AGENTS.md §7: a stored record is external input). A blob that is missing,
  unreadable, or holds anything that is not an anchor leaves the document in its text view — the page view
  is offered only for a PDF whose anchors are usable, so a broken blob degrades to "text only" rather than
  to a reader that cannot open the document.
- [DESIGN] The `Text / Pages` switch is a `<fieldset aria-label>` holding two `aria-pressed` buttons, the
  pattern the frozen `VoicePicker` uses for a choice between alternatives, and it is rendered only when the
  document is a PDF whose anchors are stored. Nothing else in the reader page changes.
- [DESIGN] The screen's rules — the page box, the canvas, the text layer and its two `::highlight()` rules —
  are injected as a `<style id="lectern-pdf-view-styles">` element in U-023's tokens, the pattern every
  other screen uses, because R6 freezes `apps/web/src/app.css` and `packages/ui-web/src/styles.css`.
- [DESIGN] Only pages inside the window are drawn, and a page that has never been in it is a plain box of the
  right size, so the work a document costs is bounded by the viewport rather than by its page count
  (the contract's *Forbidden Actions*: never more than the visible pages plus one on each side).

## 7. Deviation proposals

1. **F§10.1's page view has no zoom control, while the contract asks whether the reference product's
   highlight follows one.** `PdfPageView` takes `scale` as a prop and lays out the box, the canvas and the
   text layer from it, so the geometry is a function of the scale; this unit's reader page hands it `1`,
   because F§10.1 lists no zoom feature and the contract's *Required File Outputs* name no control for it.
   Proposed wording for F§10.1: “PDF page view: `pdfjs-dist` canvas + text layer, at a scale the page is
   handed”, and a later unit (or an operator patch) may add the control.
2. **`apps/web/src/reader/pdf-anchors.ts` exports one function beyond the three the contract names.**
   `rangeForAnchor` is the anchor → `Range` resolution that `rectsForAnchor`, the highlight registry and the
   click resolver all need; writing it three times, or having the page view do range arithmetic itself, would
   be the alternative. Proposed wording for the file's bullet: “`rangeForAnchor(textLayerSpans, anchor):
   Range | null` and `rectsForAnchor(textLayerSpans, anchor): DOMRect[]` (the same range, as rectangles)”.
3. **A sentence highlight cannot cover a page that is not drawn.** A registered range must live in the DOM,
   and the contract's *Forbidden Actions* cap what may be rendered, so a sentence running across two pages —
   or read while the reader is looking at another page — is painted only on the pages that are on screen.
   The text view (F§10.1's reflowed reader) has no such limit. Proposed wording for F§10.1: “highlights are
   painted on the rendered pages; a sentence that spans pages is painted per page”.
