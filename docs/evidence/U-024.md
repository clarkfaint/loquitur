## 3. Architecture notes

**The queue and its two elements.** One sink owns two `HTMLAudioElement`s created with `new Audio()`, `preload = "auto"` and `preservesPitch = true`. They are never appended to a document, so a page that hosts the sink is handed no media node. Each element is a *slot*: the slot carries the chunk metadata, a `token` that is bumped every time the element is reloaded, and a detach function for the two listeners it installs while a chunk is loaded. The token is what makes a late `ended` or `error` from a chunk that has already been cleared or replaced a no-op.

**Load, play and hand-over.** `enqueue` pushes onto a pending list and calls `fill()`, which loads pending chunks onto every slot that is neither active nor occupied (at most one when something is playing, both when nothing is), so the first chunk plays immediately after `play()` and the next one is already decoded. Only `play()` starts playback; `enqueue` merely loads bytes. On `ended` of the active slot:

1. `chunk-end` fires with that chunk's id;
2. the slot is unloaded (listeners detached, token bumped, source removed);
3. the other slot, if it holds a chunk, becomes active and `chunk-start` fires before `play()` is called on it;
4. `fill()` preloads the next pending chunk onto the slot that just emptied;
5. if the other slot was empty and nothing is pending, `queue-empty` fires once and the sink stops being "playing".

That ordering is exactly the sequence `runAudioQueueSinkConformance` asserts (`chunk-start`, (`chunk-end`, `chunk-start`)², `chunk-end`, `queue-empty`), and `queue-empty` is guarded by an `emptyReported` flag so it fires once per drain and again only after a new `enqueue`. `clear()` detaches both elements before pausing them, which is why no event escapes after it (the suite's second case asserts that).

**Rate.** `setRate` clamps into `[0.0625, 16]` (`maxRate = 16`, F§5.8) and writes *both* `defaultPlaybackRate` and `playbackRate` on both elements. Measured fact, and the one real bug this rehearsal caught: **`HTMLMediaElement.load()` resets `playbackRate` to `defaultPlaybackRate`**, so a chunk preloaded after a `setRate(2)` played at 1× — 696 ms for a 600 ms chunk instead of 300 ms, which pushed three chunks to 1476 ms. Writing both properties in `setRate` *and* re-pinning them after every `load()` fixed it; the same run then measured 1162 ms.

**Measured timings in Chromium 158.0.8127.18 (headless shell), 22 050 Hz mono WAV from the mock engine:**

| Case | Media | Wall |
|---|---|---|
| one chunk, rate 1 | 600 ms | 678 ms |
| one chunk, rate 2 | 600 ms | 393 ms |
| one chunk, rate 1 | 4 980 ms | 5 074 ms |
| three chunks, rate 2 (preload + two hand-overs) | 3 × 600 ms | 1 162 ms |

So the element's own start-up costs roughly 75–95 ms per chunk and a hand-over costs single-digit milliseconds on top of the media time divided by the rate; the rate itself is applied by the browser's pitch-preserving time-stretcher, which is why `preservesPitch` is left on.

## 4. Lectern design

- [DESIGN] Two elements, alternating, exactly as F§5.8 prescribes; the next chunk is preloaded onto the idle one at `enqueue` time rather than at hand-over time, which is what removes the gap from the sentence boundary.
- [DESIGN] `positionMs` is read from the element's `currentTime` (`Math.round(currentTime * 1000)`), so a pause freezes it for free and a `seekInCurrent` is one assignment; `clear()` empties `current()` because `active` becomes `null`, which is the shape the conformance suite expects.
- [DESIGN] A `play()` promise rejection is reported as the sink's `error` event *unless* it is an `AbortError` or the slot has since been reloaded — a `clear()` or a hand-over interrupts a pending `play()` by design and must not surface as a failure (the suite's `clear` case asserts that no event fires afterwards).
- [DESIGN] `MIN_RATE` is 0.0625 because a media element refuses a slower `playbackRate`; no user rate reaches it (F§5.6(e) starts at 0.5), so it only guards the API.
- [DESIGN] The harness page watches the `Audio` constructor with a `Proxy` before creating a sink. The sink keeps its elements out of the document (F§5.8), so this is the only way for `window.sinkProbe()` to read the element that is playing; the page mutates no DOM and attaches nothing to it.
- [DESIGN] `window` exposes four entry points (`runSinkConformance`, `sinkProbe`, `createSink`, `makeChunk`), not the two the contract names. `runSinkConformance` and `sinkProbe` are the contract's own; `createSink` and `makeChunk` exist because the contract's spec file also asserts the rate probe and the three-chunk wall time, and neither assertion can be expressed without a sink to drive and audio to enqueue.
- [DESIGN] `makeChunk(ms)` takes the text length from F§6's duration law (60 ms per letter or digit), so `makeChunk(600)` is ten characters and exactly 600 ms — the spec pins `[600, 600, 600]`, which is what makes the wall-time assertion meaningful.

## 7. Deviation proposals

- **The harness exposes four window entry points, not two.** `window.createSink()` and `window.makeChunk(ms)` are additions; without them the contract's own spec assertions (the `setRate(4.5)` probe and the three-chunk wall time) cannot be made, because `runSinkConformance()` creates and disposes its own sinks internally and `sinkProbe()` only reads. A future contract could name the four.
- **The spec file's wall-time case is the only place a rate change is measured with a preload in flight.** `setRate` now writes `defaultPlaybackRate` as well, which F§5.8 does not mention; without it a chunk loaded after a rate change plays at 1× on this platform. Worth a sentence in F§5.8's implementation note for `HtmlAudioQueueSink`.
- **`playwright.config.ts` sets `workers: 1` and `fullyParallel: false`** — not in the contract, but the wall-time assertions are timing measurements and a second worker's browser would contend for the audio thread.
