   "1.5× body size" that also clears "≥ 1.25× the page median", and a footnote that is both "in a smaller
   font" and below "0.85× the page median"?
3. What shape does a hyphenated line break take so that F§5.4's PDF rule ("a line ending in `-` followed by
   a lowercase start is de-hyphenated") can act on it, and what is the resulting word?
4. What does an EPUB 3 archive need to be *valid* as well as parseable by F§5.4's EPUB row: which entry
   must be first and how must it be stored, and which of `nav` and cover must exist in order to be
   *dropped*?
5. What must `doc.docx` contain so that F§5.4's DOCX row (`mammoth` → `convertToHtml`) produces a title,
   two headings, paragraphs and a real list rather than flat paragraphs?
6. What do F§5.5's OCR inputs require of `page.png` and `scanned.pdf` — a page of body text that rasterizes
   to a real image, a scanned PDF with **no** text layer so the "< 20 extracted characters" fallback fires,
   and no `PdfAnchor` anywhere?
7. Is the canvas "28 px sans-serif" requirement satisfiable and verifiable when the CSS generic family is
   resolved by the host's font database rather than named directly?

## 3. Architecture notes

**One source, seven artefacts.** `source/lighthouse.md` is parsed once into a small in-memory shape
(title, three chapters with their paragraphs, the three-item list, the block quote, the footnote) and every
other file is *derived* from it, which is what the contract means by "builds every file below from
`source/lighthouse.md`" — no artefact is hand-written a second time, so the fixtures cannot drift apart.

**Page geometry of `text.pdf`.** Letter, 612 × 792 points. F§5.4's bands are fractions of the page, so on
this page the top band is `y ≥ 792 − 0.08·792 = 728.64` and the bottom band is `y ≤ 63.36` (y measured from
the page bottom, as pdf-lib draws). The running header is drawn at `y = 750` and the running footer at
`y = 36`, both inside their bands. The body column starts at `700` and the last body line of a page stays
above `110`, which keeps every body line out of both bands. Five pages carry the same header text and a
`Page N` footer, so each appears on 5/5 pages: `5 × 10 ≥ 5 × 6` holds (the integer form of "at least 60%")
and the "minimum 3 pages" clause is cleared with room to spare. Digit substitution collapses `Page 1` … `Page 5`
into the single key `Page #`, which is the only reason the footer is detectable as *one* repeated line.

**The two font ratios are chosen so both F§5.4 tests decide.** Body text is 11 pt, so a chapter heading at
16.5 pt is exactly 1.5× the body size (the contract's wording) *and* clears "≥ 1.25× the page median" because
the median of a page dominated by body lines is the body size. The footnote is 8 pt: 0.727× the body size,
below both "smaller font" and "0.85× the page median" (`8 < 9.35`). The footnote is drawn at `y = 84` below a
0.7 pt horizontal rule at `y = 100`, so it is at the foot of the page but *outside* the bottom band (63.36) —
the fixture cannot be misread as a second footer, and F§5.4's second footnote arm ("below a horizontal rule")
is satisfied as well as the first.

**Pagination is balanced, not capacity-driven.** The wrapped body lines are distributed over exactly five
pages rather than filled page by page, because the fixture's shape is part of its contract ("5 pages") and
the source is ~750 words: a capacity-driven flow would leave the last pages empty. The footnote band is
reserved on the final page, and the page count is then read back from the written file, not assumed.

**The hyphenated break is produced by real line breaking.** A word that does not fit in the remaining column
width is broken at the last fitting hyphenation point of a small compound dictionary (measured with
`widthOfTextAtSize`, not guessed), so one body line ends in `light-` and the next begins with the lowercase
`house`. The joined word `lighthouse` is what F§5.4's de-hyphenation rule must produce, and it is recorded in
`expected.json`.

**`scanned.pdf` is an image and nothing else.** Two pages, each a full-page `drawImage` of a canvas render
(Letter at 200 DPI, 1700 × 2200, matching F§5.5's rasterization resolution), so the pages extract **zero**
characters, the "< 20 extracted characters" rule fires, and no `PdfAnchor` can exist.

**EPUB and DOCX are ZIP containers written by `fflate`** with a fixed modification stamp, so the committed
bytes are reproducible on any host and in any order. The EPUB's first entry is `mimetype`, stored
uncompressed, followed by `META-INF/container.xml`; the OPF's spine lists exactly the three chapter
documents, while `nav.xhtml` and the cover page exist in the manifest so that F§5.4's "`nav` and cover
documents are dropped" rule has something to drop. The DOCX carries `[Content_Types].xml`, the two
relationship parts, `word/styles.xml` (so `Title`, `Heading1`, `Heading2` are real styles rather than
formatting) and `word/numbering.xml` (so the list is a real numbered list that `mammoth` maps to `<ul>`/`<ol>`
instead of flat paragraphs).

**Canvas type resolution is pinned to what the host actually has.** Because the CSS generic `sans-serif` is
resolved by the platform font database (measured above: identical ink to Liberation Sans, and a *different*
count for an unknown family), the renderers ask `GlobalFonts` for the first available family from an ordered
sans-serif preference list and fall back to the default face, and the generated image is validated as
non-blank (ink counted) rather than trusted. This is the contract's "do not commit blank images" made
mechanical.

## 4. Lectern design

- [DESIGN] `source/lighthouse.md` is the single input; `generate.mjs` parses it once and renders all seven
  artefacts from that parse — follows the contract's `generate.mjs` bullet.
- [DESIGN] The footnote in the Markdown is a trailing paragraph whose text begins with the marker `1. `, and
  the document's *three-item list* is the `-` list inside chapter two. The Markdown reader (F§5.4) reads a
  `1.`-style line as a list item, so the marker is deliberately the F§5.4 footnote form
  (`^\d{1,3}[.)]?\s`) rather than a bullet that would merge the footnote into the chapter's list — follows
  F§5.4's footnote rule and the contract's "a three-item list … and one footnote".
- [DESIGN] `expected.json` carries exactly the contract's eight fields, defined as: `title` = the `#` title;
  `chapterTitles` = the three `##` headings in order; `firstSentenceOfChapter` = the first sentence of the
  first body paragraph *after* each chapter heading (not the heading itself); `headerText` = the running
  header drawn on every page; `footerPattern` = the footer with digits replaced by `#` (so `Page 1` and
  `Page 5` are one key); `footnoteStart` = the literal marker the footnote line begins with; `dehyphenatedWord`
  = the word the hyphenated break must yield with the hyphen removed; `pageImageWords` = the words rendered
  into `page.png`, in reading order.
- [DESIGN] `--check` performs every validation the contract names (magic bytes, non-zero sizes, PDF page
  counts, exit 0/1) **and** four that this unit's own artefacts make possible and that the contract's
  *Forbidden Actions* imply: that the header/footer text is really present in `text.pdf`'s inflated content
  streams with the expected font sizes, that `scanned.pdf` carries no text operators at all, that the PNG's
  IHDR really is 1240 × 1754 with ink on it, and that `expected.json` agrees with the files it describes.
  It builds into a temporary directory and never writes the committed tree in check mode.
- [DESIGN] Every ZIP entry is written with one fixed modification stamp (1980-01-01Z) because `fflate`
  refuses `mtime: 0` (measured) and because a reproducible archive is what makes a committed binary fixture
  reviewable — follows the contract's "commit the generated files".
- [DESIGN] `text.pdf` is drawn with the standard PDF fonts only (`StandardFonts.Helvetica` /
  `HelveticaBold`), which are built into every PDF reader and require no font file to be downloaded or
  embedded (contract: "Do not download fonts"; §4.4 of AGENTS.md: never embed reference assets).
- [DESIGN] `make-icons.mjs` draws the mark from primitives only — a rounded square plus three horizontal
  bars of decreasing length — using `roundRect` and `fillRect` on a fresh canvas per size, so the icon set
  shares one design language with no copied asset and no external font beyond the host's sans-serif face.
- [DESIGN] Only the three contract-named packages are installed, at exact versions (`pnpm add -E`): `pdf-lib`,
  `@napi-rs/canvas`, `fflate`. `@napi-rs/canvas` itself resolves a platform binary package
  (`@napi-rs/canvas-linux-x64-gnu`) — that is the named package's own optional dependency, not an additional
  Lectern dependency (R10).
- [DESIGN] Both scripts are plain Node ESM with no build step and no TypeScript, because the contract lists
  them as `.mjs` outputs and R5 allows no extra file (no `tsconfig.json`, no barrel) in this package — so the
  package declares no `typecheck` script and the standing `turbo run typecheck` gate stays scoped to
  `@lectern/core`.

## 7. Deviation proposals

- [DESIGN → contract] The contract requires "one word hyphenated across a line break in the PDF layout" but
  fixes no column width, so whether the break happens at all is a function of geometry. This unit makes it
  deterministic by choosing the column width and a compound word whose hyphenation point lands in the
  leftover space, and `--check` fails if the break is absent. Proposal: state the required column width, or
  accept "the break must exist in the generated file and be asserted by `--check`", which is what is
  implemented.
- [DESIGN → contract] The contract's `--check` bullet requires only magic bytes, sizes and PDF page counts.
  Those are satisfiable by a file that is the right *shape* but the wrong *content* (a 5-page PDF of nothing
  would pass). The four extra validations in section 4 close that gap. Proposal: fold them into the contract
  text so the next unit to touch fixtures is held to the same bar.
- [DESIGN → contract] `scanned.pdf` is rendered at 1700 × 2200 (Letter at 200 DPI) because F§5.5 names 200 DPI
  as the rasterization resolution for the scanned-PDF fallback; the contract does not name a resolution for
  this fixture. Proposal: record 200 DPI in the contract so `page.png` (1240 × 1754, i.e. A4 at 150 DPI) and
  `scanned.pdf` are visibly two different regimes rather than two arbitrary sizes.
- [DESIGN → operator] `@napi-rs/canvas` adds four platform binary packages to `pnpm-lock.yaml` (linux x64
  gnu/musl, win32 x64/arm64). They are the named package's own optional dependencies, so R10 is untouched,
  but the operator should expect them in the lockfile diff.
