## 3. Architecture notes

Everything below was measured on this host or read out of the installed packages in this session; the runs
themselves are in §6 and §7.

**Two interfaces carry the platform.** `SqlDriver` (`exec`, `run`, `all`, `transaction`, all asynchronous) is
the whole database surface a store may touch, and `BlobFs` (`write`, `read`, `remove`, `exists`, `uri`) is the
whole file surface a cache may touch. `packages/store-sql/src` therefore imports neither `expo-*`,
`react-native` nor `better-sqlite3` outside its `testing` directory (the contract's *Forbidden Actions*): the
package is the same program on Hermes, on Node under `vitest`, and on any platform that can supply a driver.

**The layout is F§5.9's entity set, one table each.** Version 1 creates `documents`, `models`, `folders`,
`bookmarks`, `progress`, `settings`, `outbox`, `meta`, `blob_meta` and the version table itself. Several
choices are worth naming because the interface leaves them open:

- **the version table is `schema_version`, a single row.** `migrate(driver)` reads it, applies nothing when the
  value is already 1, and otherwise creates the tables and writes 1 — so a second call is a no-op and a
  database written by an older build has one upgrade step to add;
- **the outbox is an auto-incrementing table, and insertion order is its order.** `seq INTEGER PRIMARY KEY
  AUTOINCREMENT` gives `pendingOps(limit)` a `LIMIT`-bounded read of the oldest rows and `ackOps` a delete by
  `opId`; the op's own identifiers are values, never SQL text;
- **a version stamp lives in `meta` under `version:<entity>:<id>`**, as JSON. F§5.9's ten tables have no
  versions table, and `meta` is one of them, so the last-writer-wins rule needs no store the layout does not
  already declare — the same reasoning U-026's IndexedDB store recorded for its own layout. The sync cursor
  lives there too, under `cursor`;
- **a mutation and its outbox row commit in one transaction.** `putDocument` writes the record, the model, the
  op and the stamp inside one `driver.transaction(...)` call; a record whose op is missing is a change no other
  device hears about, and an op whose record is missing is one they cannot apply;
- **the model is stored beside its metadata and never inside an op.** Ops carry records; a document's text
  travels as its own payload (F§8.2), so a device that applies a remote `document` op holds the metadata and
  waits for the file — which is why applying one leaves a model already on hand alone;
- **`documents` carries a folded copy of the title.** The library's text filter is a SQL predicate
  (`instr(titleFold, ?) > 0`) rather than a scan in JavaScript, and SQLite's built-in `lower()` folds ASCII
  only, so the column is written from JavaScript's `toLowerCase()` — one document's title, folded once, on the
  way in. The needle is folded the same way and travels as a parameter.

**Parameters, never concatenated values.** A query's *shape* is assembled from a fixed set of clauses
(`deleted = 0`, `folderId IS NULL`, `instr(titleFold, ?) > 0`) while every value — a docId, a title fragment, an
op id, an entity kind — is bound. `ackOps` builds its placeholder list from the count of the identifiers it was
handed; no identifier's text reaches the SQL string.

**The blob cache keeps bytes in files and metadata in the table.** `blob_meta(key, size, mime, lastUsed)` is
what `sizeBytes`, `evictLru` and `uri` read; the bytes are the `BlobFs`'s business, which is why the contract
forbids storing them in SQLite. Recency comes from the injected `now()` (as U-026's IndexedDB cache does), the
MIME type is kept beside the size because `uri` has to hand back a *playable* URI, and eviction deletes a row
and its file together.

**The Android side is a thin, honest mapping.** `expo-sqlite-driver.ts` implements all four driver members over
the asynchronous API (`execAsync`, `runAsync`, `getAllAsync`, `withTransactionAsync`); `expo-blob-fs.ts`
implements the file half over `expo-file-system`'s `File`/`Directory`/`Paths.document`, under a `blobs/`
directory, with each key mapped to one safe file name; `stores/index.ts` opens `lectern.db`, migrates it and
creates this installation's `deviceId` once with `expo-crypto`; `stores/diagnostics.ts` adds the two registry
entries that run the conformance suites on the device.

**Keys become file names by percent-encoding, not by hashing.** Every byte outside `[A-Za-z0-9._-]` is written
as `%XX` over the key's UTF-8 bytes, so the mapping is injective (two keys cannot collide into one file), human
readable in a log, and cannot escape the directory: `orig/<docId>` becomes `orig%2F<docId>` and a key of `..`
is escaped to `%2E%2E` by the guard that refuses a name of `.` or `..`.

**The diagnostics checks are the conformance suites, run on the device.** `library-store` and `blob-cache` run
`runLibraryStoreConformance` and `runBlobCacheConformance` against a **scratch** database and directory —
`lectern-u046-check-<n>` and `<document>/blobs-check-<n>/`, never the reader's own `lectern.db` — and delete
both when the run is over, whatever its outcome, so running diagnostics never costs the reader a document. Each
conformance case gets a fresh database and a fresh directory, because a case expects a store that holds
nothing (U-026's measured lesson: one shared database lets an earlier case's document appear in a later case's
unfiltered list).

## 4. Lectern design

- [DESIGN] The store talks only to `SqlDriver` and `BlobFs` (F§5.9's interface, split at the platform
  boundary). A platform difference is therefore a driver, not a branch: the same `createSqlLibraryStore` runs
  over `better-sqlite3` in a Node test and over `expo-sqlite` on a device.
- [DESIGN] Every record that crosses back out of the database is validated with F§5.9's own schemas
  (`DocumentMetaSchema`, `FolderSchema`, `BookmarkSchema`, `ProgressSchema`, `SettingRecordSchema`,
  `DocumentModelSchema`) and every incoming op with `OpSchema` before a field of it is compared — AGENTS.md
  §7's boundary rule, applied where the bytes arrive.
- [DESIGN] The bytes live in the app's own private document directory, under `blobs/`; no external storage and
  no storage permission is used or requested (the contract's *Forbidden Actions*, AGENTS.md §6).
- [DESIGN] The library's text filter is case-insensitive through the folded column rather than through SQLite's
  ASCII-only `lower()`, so a title that is not ASCII searches the way the reference store searches it.
- [DESIGN] `getStores()` is the app's one composition point: it opens `lectern.db` once, migrates it, reads (or
  creates) this installation's `deviceId` from the same `meta` table the stamps live in, and hands back the
  store, the cache and the identifier — so no screen builds a second connection.
- [DESIGN] The conformance suites are the diagnostics checks' whole content: `library-store` and `blob-cache`
  report how many cases held, and both run against a scratch database and directory that are deleted
  afterwards. F§5.9 calls the suites the measure of every implementation, and this is the only place they can
  run against the device's own SQLite and file system.

## 7. Deviation proposals

- `better-sqlite3`'s **declarations are absent from the program by construction**: the package ships no `.d.ts`
  of its own, and R10 forbids adding `@types/better-sqlite3`. The testing driver therefore reaches it through a
  `string`-typed dynamic import and describes the host API it uses as its own interface, which is the same
  boundary the hub's Node modules use; a patched contract could name the typings package instead.
- **There is no test file for the four Android modules, by design.** `apps/android/vitest.config.ts` collects
  `src/**/*.test.ts` in a Node environment, and `expo-sqlite`, `expo-file-system` and `expo-crypto` cannot load
  there; a screen or a service that reaches them is covered by the on-device diagnostics screen U-045 built,
  which this unit's `library-store` and `blob-cache` checks are the first real users of. The contract's fixed
  command runs the Android suite unchanged.
- **`apps/android/src/diagnostics/checks.ts` is U-045's file and is marked `(registry)` in U-045's contract**,
  so this unit appends to it and rewrites nothing: one import line and one spread into the exported array
  (`[coreSelfTest, hubHealth, ...storeChecks]`). That is the only earlier-unit file this unit touches, and
  §5's append-only class is what allows it. If the operator would rather every registry entry were a line of
  its own, a patched contract could say so.
- **`docs/preflight.json` is untouched.** This unit's fixed command does not run `scripts/preflight.mjs` (the
  contract's command is the seven steps quoted in §6), so the file U-022/U-038/U-045 had to restore after a
  phase run is not rewritten here at all — verified with `git status --porcelain`, which lists no such path.
- **(1) The blocker: one assertion in U-045's test file, and no file this unit may write can satisfy it.**
  `apps/android/src/__tests__/selftest.test.ts:207` asserts
  `expect(checks.map((check) => check.id)).toEqual(["core-selftest", "hub-health"])` — exactly two ids, in that
  order. The contract requires this unit to *register* `library-store` and `blob-cache` (its
  `apps/android/src/stores/diagnostics.ts` output, and its `Uses:` line names the registry), and U-052's own
  `verify-diagnostics.sh` passes only when `PASS core-selftest`, `PASS hub-health`, `PASS library-store`,
  `PASS blob-cache` and `PASS audio-sink` are all on the screen — so the registry must grow to five entries
  across U-046 and U-047. Measured: with the registry appended, the array is
  `["core-selftest", "hub-health", "library-store", "blob-cache"]` and that one case fails
  (`1 failed | 18 passed (19)`); every other step of the fixed command passes (§6.1). The registry file itself
  is append-only under §5 (`apps/android/src/diagnostics/checks.ts` is marked `(registry)` in U-045's contract),
  so the append is in scope; *the test file is not*, R6 freezes it, R11 forbids making a test pass by weakening
  it, and §2's verification cannot exit 0 from any file this unit may write. Two repairs, either of which is
  measured to close the unit (§6.3):
  1. extend that one assertion to the registry's real contents — a strengthening, not a weakening —
     `expect(checks.map((check) => check.id)).toEqual(["core-selftest", "hub-health", "library-store", "blob-cache"])`,
     with `Patch scope: apps/android/src/__tests__/selftest.test.ts` on a patched contract. U-047 adds
     `audio-sink` to the same registry and runs the same android suite, so it meets this assertion too and
     should be patched in the same breath;
  2. or assert containment of U-045's own two ids —
     `expect(checks.map((check) => check.id)).toEqual(expect.arrayContaining(["core-selftest", "hub-health"]))` —
     which leaves the registry free to grow and is what the registry file's own doc comment ("a later unit adds
     its own by appending one entry") describes.
  U-045's contract asked only that "every self-test case is `ok` under Node" (spec.md U-045's *Required File
  Outputs*), so nothing in the operator's contract text is contradicted by either repair.
- **(2) The platform modules are loaded when a driver or a cache is built, not when the module is imported.**
  The contract does not say this, and it is load-bearing: the diagnostics registry reaches
  `src/stores/diagnostics.ts`, and `apps/android`'s Node test program imports that registry — where
  `expo-sqlite` and `expo-file-system` (and, through them, `react-native`) cannot be parsed at all. Measured
  before the change: importing the registry from `vitest` failed with
  `RolldownError: Parse failure: Parse failed with 1 error: Flow is not supported` at
  `react-native/index.js:1:0`, which took five of the registry's cases down with it. `openExpoSqliteDriver` and
  `createExpoBlobFs` therefore `await import(…)` their platform module inside the factory, which is why
  `createExpoBlobFs` is asynchronous and why `deleteExpoSqliteDatabase`/`removeExpoDirectory` exist beside the
  driver and the cache for the scratch cleanup. After it, the registry imports cleanly in Node and only the
  device run loads SQLite — measured: `18 passed (19)` in the repository, `19 passed (19)` in the repaired copy.
