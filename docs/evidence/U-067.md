## 3. Architecture notes

**The cross-device flow (`scripts/e2e-cross-device.mjs`), in the order it proves things.** One hub is built in a
temporary directory with F§7.1's `LECTERN_ENABLE_MOCK=1` and U-062's mock endpoint as F§9's provider, and is
reached through `fetchFromFastify(readableApp(app))` — no socket, no port, no service. Two devices are then the
same four objects F§10.1/F§10.4 build per platform: `createMemoryLibraryStore` (F§5.9's records and outbox),
`createMemoryBlobCache` (F§5.9's bytes), `createCachingChunkSource` over the hub client (F§5.8's `ChunkSource`)
and `createSyncEngine` over `createSyncClient` (F§8.2's round). Device A parses the probe text through
`POST /v1/parse`, stores the record, and reads it aloud through `createPlayerController` driving `FakeSink` on a
`FakeClock`: the sink moves only when the run advances that clock, so "three sentences" costs no wall time while
every chunk behind it is a real `POST /v1/tts` and `GET /v1/tts/audio/<chunkId>` against the hub (measured: 6
synthesis requests and 6 downloads for the 3 sentences played, because F§5.7's prefetch window holds the current
sentence plus the next three). A bookmark and a reading position are written through the store, `syncNow()` runs
F§8.2's round, and the engine's own status is what proves the round really reached the hub (`pending 0`,
`state idle`, `lastSyncedAt` set). Device B is a second store with its own device id: one round gives it the
document record, the position and the bookmark, and — measured — **no document body**, because F§8.2 keeps the
model lazy; `ensureModel` is what fetches it, and the step asserts both halves (absent before, kept after).
Device B then opens its own player at the pulled position and plays, which is a resumed reading rather than a
fresh one. The summary is F§9's job: B requests it (`running`), `waitForSummary` polls to `done`, and A reads
the same `GET /v1/ai/summary/:docId?mode=brief` — the step compares the two results byte for byte rather than
trusting either. The backup is the last step: `GET /v1/admin/backup` is downloaded, gunzipped, and its members
are read out of the archive itself (512-byte headers, the `name` and octal `size` fields) so the check is
against the bytes the hub served, not against a promise in a log line. Every step prints one line and the first
failure exits 1.

**The release check (`scripts/release-check.mjs`).** One ordered list of steps, each carrying the command it
runs, and — for the steps that need something this host may not have — a function that answers whether it can run
at all. A step that cannot run is recorded `SKIPPED` with that reason instead of being silently dropped, and a
step that ran is `PASS` or `FAIL` with its exit code and its duration. The list is the contract's own order: the
three workspace tasks, the four guard scripts, each app's build and its end-to-end suite (the desktop suite under
`xvfb-run` on Linux), the four Android host checks, and `scripts/e2e-cross-device.mjs`; `--device` adds the four
device steps, `--docker` adds U-022's own three (`cp -n infra/.env.example infra/.env`, `docker compose … up -d
--build --wait`, `node scripts/smoke-engine.mjs --base http://127.0.0.1:8787`). The record is written to
`docs/release-check.json` after every step has been tried, so a failing run still leaves a report of what failed,
and the compose stack is brought down in a `finally` whatever happened.

**The device steps, and what they need before they can be trusted.** The harness's four scripts share `lib.sh`,
which starts the repository's own mock-engine hub on `127.0.0.1:8787` with `adb reverse tcp:8787 tcp:8787` and
drives the app with `adb` plus `uiautomator dump`. Two facts make a run nondeterministic unless they are dealt
with *before* the checks: the app keeps the reader's place per document, so a phone that inherits a nearly
finished document leaves U-052's frozen `verify-media-session.sh` reading "not playing" at the end of its own
window; and a freshly emptied app pulls the previous run's records straight back from the hub on its first round,
which restores the same progress record. The `device-prepare` step therefore runs `adb shell pm clear
dev.lectern.app`, removes the harness's gitignored `data/device-run/`, and clears the port reverses, in that
order, before any check — the practice U-052's close and U-061's run both record.

## 4. Lectern design

- [DESIGN] **The parity report is the F§4 table, one row per `IN` capability**, with the units that built it, the
  command that covers it and — for every row — the status that *this session's* `docs/release-check.json` reports
  for that command (`PASS`, `FAIL`, `SKIPPED` or `MANUAL`), then the blocked units, the unavailable inspections,
  every open deviation proposal from the evidence files, the two manual checklists with their recorded state, and
  F§14's known limits. A row whose covering step is `SKIPPED` on this host says so rather than reading as
  verified; a row that no automated command can cover is `MANUAL` and names the manual check that covers it.
- [DESIGN] **The two scripts stay dependency-free and run under plain `node`.** `scripts/` carries no dependency
  (R10), and the contract's fixed command invokes them as `node scripts/<name>.mjs`, so neither may need a
  loader, a runner or a build step. `e2e-cross-device.mjs` registers a two-line resolver with `node:module`'s
  `register()` — a relative specifier with no extension (or the `.js` a TypeScript source maps to) is answered as
  the `.ts` beside it — and Node 24's built-in type stripping then runs the workspace's own sources unchanged.
  Measured: `register("data:text/javascript,…")` needs no file of its own, so the script stays a single deliverable
  and the hook reaches the packages' own transitive imports too.
- [DESIGN] **The transport the two simulated devices share is one `fetch` that records what it was asked for**,
  so a step can assert not only that the reading advanced but that it advanced *because the hub served audio*: the
  play step counts `POST /v1/tts` and `GET /v1/tts/audio/…` and reads the chunk's own bytes back out of the
  device's blob cache. F§5.8's `ChunkSource` is the seam that makes this true — the sink never sees the hub, and
  the cache is what a reader plays from when the hub is gone.
- [DESIGN] **The `204` wrapper is one function, named for what it does, with the reason in place.** It is the
  only place this unit touches a frozen boundary, it changes nothing about the hub (the answer is still produced
  by the same route), and it is the same remedy U-058's suite already applies; §7 (1) asks the operator to decide
  whether the adapter itself should learn to read a null-body status.
- [DESIGN] **A step's prerequisite is probed, never assumed**, and every probe answers a *reason* rather than a
  boolean: `adb version` and a device in `adb devices -l` for the device steps, `docker version --format
  {{.Server.Version}}` and `docker compose version` for the compose steps, `which xvfb-run` on Linux for the
  desktop suite, and the app's own `node_modules/.bin/playwright` for the three browser suites. That is what
  makes `SKIPPED` mean "this host could not exercise it" rather than "nobody looked".
- [DESIGN] **The record is JSON the fixed command itself reads.** `docs/release-check.json` carries each step's
  id, label, command, status, exit code and duration, the run's flags and the serial of the phone it used when it
  used one — and the contract's own `node -e "…require('./docs/release-check.json')…"` step is what turns a
  recorded `FAIL` into a non-zero exit for the whole chain.

## 7. Deviation proposals

1. **`docs/release-check.json` is mandated by this contract's prose and is not one of its output bullets.** The
   *Required File Outputs* bullet for `scripts/release-check.mjs` ends "Writes `docs/release-check.json`", the
   fixed command's fourth step requires the file, and `docs/parity-report.md` is specified to quote "this
   session's `docs/release-check.json`" — but `node scripts/unit.mjs U-067 --json` answers four outputs and no
   `patchScope`, and `scripts/check-scope.mjs` builds its allowed set from the output bullets alone. Measured:
   with a generated `docs/release-check.json` in the tree, `node scripts/check-scope.mjs U-067` exits **1** with
   "1 changed path(s) outside this unit's scope → docs/release-check.json". The generated file is a run artifact
   of the release check — regenerated in full by `node scripts/release-check.mjs`, quoted in the report, and read
   by the fixed command's own `require` — so AGENTS.md §5's remedy for an out-of-scope change ("fixed by
   reverting the out-of-scope change, never by editing the checker or the contract") is applied literally: the
   file is written and read by the run, and removed from the tree afterwards, exactly as this unit's own
   `apps/android` harness keeps its run data under the gitignored `data/device-run/`. §6.3's log is the run's own
   output and `docs/parity-report.md` carries the step table the file held. **Proposed patch:** add
   `- \`docs/release-check.json\`` to *Required File Outputs* (or to a `Patch scope:` bullet) so the artifact may
   stay in the tree the fixed command generates it in.
   **Post-script (2026-11-18, closing session).** The blocker this file recorded is closed: the operator's
   `chore(spec)` `2f57cac` scoped the two desktop e2e library assertions, `desktop-e2e` exited 0 in both of this
   session's readings of the suite, and the contract's fixed command **exits 0** on its second attempt (§6.7) —
   the first attempt failed `web-e2e` on the intermittent case §7.2 documents, which cost no file change. This
   item's own proposal still stands: the generated `docs/release-check.json` remains outside this contract's
   output bullets, and §6.8 re-measured the scope gate's `exit 1` with the file in the tree
   (`1 changed path(s) outside this unit's scope`).
2. **A root script's access to the workspace's TypeScript sources is a design decision worth ratifying.** The
   contract's *Uses* line names `@lectern/core`, `@lectern/api-client`, `@lectern/server` and
   `@lectern/server/testing`, and the fixed command runs the scripts with plain `node`. The repository root
   declares no dependency (R10 admits none) and the packages' entry points are TypeScript sources with
   extensionless relative imports, so the scripts reach them by path and register a resolver for the extension
   (measured in §2). The alternative — adding four `workspace:*` dependencies and a lockfile churn to the root
   manifest — would make the root a workspace consumer, which nothing else in this repository does. Note for a
   later unit: if a root script ever needs a *third-party* declaration (`@types/node`), the same boundary the
   hub's own tests record applies here.
3. **The rehearsal's mirror is the recipe this unit used for a root script, and it is worth keeping.** A
   scratch directory holding `scripts/<candidate>.mjs` plus symlinks named `packages` and `apps` to the
   repository's own, and copies of `biome.json` and `.gitignore`, lets a root script be run and formatted exactly
   as it will be in the tree — the mirror's `node` resolves the candidates' imports through the symlinks to the
   repository's real files. R3's evidence-before-code order then holds with the candidates `cmp`-identical
   across the copy (measured for both files).
4. **The `204`-vs-`Response` boundary is U-021's, and this unit only works around it.**
   `packages/api-client/src/testing/fastify-fetch.ts` cannot carry a null-body status, so every caller of an
   endpoint that answers `204` — the library model upload today, anything `204`-shaped later — has to wrap the
   app first. A later unit could teach the adapter to answer `204` with an empty body and delete both wrappers.
   Filed as U-058's suite implicitly documents the same remedy, including in this session's fresh measurement.
