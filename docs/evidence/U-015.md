## 3. Architecture notes

**Chunk identity.** A chunk is named by everything that decides its audio: the engine, that engine's own voice id, the engine-side synthesis speed written to two decimals, and the text — joined with a NUL and hashed by `@lectern/core`'s pure-TypeScript SHA-256, truncated to 40 hex characters. The speed is normalized by `toFixed(2)` before hashing, so the reading speed the user hears (`sinkRate`) never enters a chunk id: only the speed the *synthesizer* was asked for does, and `planSpeed` keeps that at 1.0 for every user rate a 16× sink can serve.

**The two audio readers, and why they are hand-written.** F§6 forbids an audio encoding package, so both directions are arithmetic on the container's own fields. The WAV writer emits one canonical 44-byte header and computes every derived field (both chunk sizes, the `RIFF` size, `byteRate`) from the sample count, so a file whose header disagrees with its data cannot be produced; the WAV reader walks the chunk list once, following each chunk's declared size and word-alignment, and reads `byteRate` from `fmt ` and the byte count from `data` — which is why a `LIST` chunk between them changes nothing. The MP3 reader never decodes a frame: it skips an ID3v2 tag from its synchsafe size (plus a footer when the flag says so), then walks the frames with F§6's tables and both length formulas, summing `samples / sampleRate` per frame and rounding once at the end. Layer III only, as the contract says; a header with a reserved version, a bitrate index of 0 or 15, or a sample-rate index of 3 is not a frame, and a stream that never presents one is refused.

**The mock tone.** F§6's duration law is measured in *alnum characters*: `60 ms × alnum`, floored at 200 ms, then divided by `synthSpeed`. The writer derives the sample count from that duration and reads the duration back from the sample count, so the invariant `readWavDurationMs(audio) === durationMs` holds exactly for every text and every speed — the number the hub reports and the number a reader parses out of the WAV cannot drift. The tone itself is a 220 Hz sine at 22 050 Hz, mono, 16-bit.

**The timing path.** `synthesizeChunk` is where the TTS layer meets F§5.6. The chunk text is tokenized by `@lectern/core`'s `splitWords`, so a timing index is a word index in the tokenizer the document model is pinned to; an engine that reported tokens has them aligned by `alignEngineTimings`, which itself falls back to `estimateTimings` when fewer than half the words matched. The mock adapter deliberately derives its tokens *from* `estimateTimings`, so every mock chunk walks the alignment path rather than only the estimation path — and because its tokens equal its words, all of them match and the chunk reports `timingSource: "engine"`.

**Failures are per engine.** The registry asks every engine for its list at once and keeps the answers that arrived, validating each list against `VoiceSchema`; a backend that is down, throws, or answers a shape this design does not define contributes no voices and hides nobody else's. `resolve` refuses in three distinguishable ways — an id that is not an `engine:voice` pair, an engine nobody registered, and a voice the engine does not offer — each with the reason in the message rather than a silent `null`.

## 4. Lectern design

- [DESIGN] F§6's `Voice` is a strict zod schema and `Voice` is `z.infer` of it, so runtime validation and the compile-time type cannot drift (F§5.1's precedent, `@lectern/api-contract`'s rule).
- [DESIGN] `Voice.id` is `voiceIdFor(engine, engineVoiceId)` = `engine:voice`, and `parseVoiceId` splits at the **first** colon, so an engine whose own voice ids contain one (`piper:en_US-amy:low`) still parses. Text that is not such an identifier answers `null` rather than a half-parsed pair.
- [DESIGN] The engine interface's request and result are named types (`SynthesisRequest`, `SynthesisResult`) rather than two inline object types; the token shape is `@lectern/core`'s existing `EngineToken`, so the field names F§5.6(b) uses are shared with the alignment code rather than re-declared.
- [DESIGN] `SynthesizedChunk` returns `chunkId`, `audio`, `mime`, `durationMs`, `timings` and `timingSource` — the six things the hub's cache (F§7.3) and a client both need from one synthesis, with the timing source visible so a caller can tell estimated timings from engine ones.
- [DESIGN] An empty `engineTokens` array is treated exactly like `null` and estimated: F§6 says an empty array is what Kokoro answers for a language it cannot time, and `alignEngineTimings` would reach the same answer a step later. Both spellings are asserted in the test.
- [DESIGN] A malformed voice list is that engine's failure alone (validated inside the registry, per engine), which keeps one bad backend from emptying the picker.
- [DESIGN] Errors are plain `Error`s carrying a stable prefix (`UNKNOWN_VOICE`, `UNKNOWN_ENGINE`, `INVALID_WAV`, `INVALID_MP3`), following the parser codes' shape rather than inventing an error class this unit's contract does not name.
- [DESIGN] The mock voices are named `Mock A` / `Mock B` in language `en` — Lectern's own names, per §4.3; no real engine's voice catalogue is reproduced.
- [DESIGN] Both readers throw on bytes they cannot read rather than answering `0` or `NaN`, so a caller cannot mistake "not audio" for a zero-length chunk.

## 7. Deviation proposals

1. **F§6's `TtsEngine.synthesize` return type is written inline in the interface.** Implemented as a named `SynthesisResult` (with `SynthesisRequest`) so the hub, the adapters and the tests can name the same type; the field names and the `engineTokens: { text, s, e }[] | null` shape are unchanged, and the token type is `@lectern/core`'s existing `EngineToken`. Proposal: name the two types in the F§6 block.
2. **F§6 does not say what the mock engine's *voice* names and language are.** Implemented as `Mock A` / `Mock B`, `lang: "en"`. Proposal: state them, or state that an adapter may choose.
3. **F§6 fixes the mock tone's duration, sample rate and frequency but not its amplitude.** Implemented as a half-scale sine (0.3 × 32767). Proposal: leave it to the adapter, as done here; the duration law and the container are what other code can depend on.
4. **F§6 does not say whether the mock engine's `durationMs` is the computed duration or the one read back from the WAV header.** They are made equal (the sample count is derived first and the duration read from it), and the invariant is asserted in the test. Proposal: state that `durationMs` must agree with the audio the engine returns.
5. **F§6's `engineTokens` for a language Kokoro cannot time is an empty array, while `null` is the "no timestamps at all" spelling.** Implemented as the same path — both estimated — which is what `alignEngineTimings` reaches anyway once fewer than half the words match. Proposal: say in F§6 that an empty array is treated as `null` by the hub.
