## 3. Architecture notes

**The rule the hub applies (F§5.9, F§8.2).** One row per `(entity, entity_id)` in `records` holds the record
that won, stamped with the `(ts, deviceId)` that won it; `changes` is the log of accepted winners in the
order the hub accepted them; `seen_ops` is every `opId` the hub has seen. A push applies each op in turn —
if its `opId` is in the ledger it is skipped; otherwise the ledger records it, the stored stamp is compared
with `isNewer` (a greater `ts` wins, or an equal `ts` with the greater `deviceId` string), and a winner
writes `records` and appends one `changes` row. Every `opId` of the request is answered in `accepted`,
winners and losers alike. A batch is one transaction, so the `rev` a client stores as its cursor always
describes a batch whose changes it can also see.

**The paging invariant (F§8.2's pull).** `changesSince(rev, limit)` groups the log by entity, keeps each
entity's **latest** `rev`, orders those **ascending**, and answers at most `limit` of them, each as the
record that currently wins. The cursor is the last `rev` of the page and `more` says whether an entity's
latest change lies beyond it. Ascending order is what makes the cursor sound: everything whose latest `rev`
is ≤ `nextRev` has been answered, and everything above it has not. Worked example — `theme` changed at revs
3, 7 and 11, `font` at rev 9, `speed` at rev 12, `limit` 2: page one is `[font@9, theme@11]` (`nextRev` 11,
`more` true), page two is `[speed@12]` (`nextRev` 12, `more` false), and `theme` — three writes — appears
once, as the record that won rather than as the first or the last write. A page never answers the same
entity twice.

**What the hub does not store.** No document body is a row: F§8.4 keeps models and originals as files under
`{DATA_DIR}/library/{docId}/`, so the database holds records, the change log, the op ledger and (for later
units) the summary status table. The model is written exactly as the client uploaded it — gzipped JSON — and
is never parsed or re-encoded here.

**The document files' writes.** A model or an original goes to a temporary file in the document's own
directory and is renamed into place, so a reader finds the previous file or the complete new one and never a
half-written one. The original's mime type lives in a sidecar written **after** the bytes, so a sidecar that
exists always describes bytes that are already there. `removeDocument` removes the whole directory and is a
no-op when it is already gone.

**The schema (F§8.4).** Five tables, created by migration 1: `records(entity, entity_id, ts, device_id,
deleted, json)` with `PRIMARY KEY(entity, entity_id)`, `changes(rev INTEGER PRIMARY KEY AUTOINCREMENT,
entity, entity_id)`, `seen_ops(op_id PRIMARY KEY, received_at)`, `summaries(doc_id, mode, model,
prompt_version, status, json, updated_at)` and `schema_migrations(version)`. `migrate` reads the versions a
database has applied, runs each missing one inside its own transaction together with the row that records
it, and answers the highest version present — so a second call, a second connection and a restarted hub all
find nothing to do.

## 4. Lectern design

- [DESIGN] **The op's own stamp decides; the batch's `deviceId` is the fallback.** F§5.9's rule compares
  `(ts, deviceId)`, and the device that made an op stamped it — a hub that substituted the pushing device
  for it could reach a different winner than the devices holding the same ops, which is the divergence the
  rule exists to prevent. `applyOps(deviceId, ops)` therefore stamps a record with `op.deviceId`, and uses
  the batch's `deviceId` only for an op that carries none (`OpSchema`'s `deviceId` is a plain string, so the
  empty one is representable). This is also what lets one batch break a tie: two ops with the same `ts` and
  different device ids are decided by the ids (F§5.9), which a batch-wide stamp could never do.
- [DESIGN] **A pulled op is built from the record that won.** `changes` stores no record, so a page answers
  the current `records` row, re-validated through F§5.9's own `OpSchema` before it leaves (AGENTS.md §7's
  boundary rule): `deviceId` and `ts` are the winner's stamp, `kind` is `delete` when the stored tombstone
  flag is set and `put` otherwise, `record` is the stored JSON, and `opId` is derived from the change itself
  (`entity:entityId:rev`) because the hub keeps no winning op id — a client applies pulled ops through
  `applyRemote`, which reads the stamp and never the `opId`. A row this design could not have written is
  skipped rather than failing a whole page.
- [DESIGN] **Storage is opened when the hub is built, and closed with it.** `createHubContext` opens F§8.4's
  database, migrates it and builds the repository and the document files over the same data directory; a hub
  whose storage cannot be opened fails while it is built rather than failing a later request, and the app's
  `onClose` hook releases the connection (the contract's patch note). The data directory itself is created
  by `openDatabase`, because SQLite will not create a database in a directory that does not exist and
  F§7.1's default is a relative path a fresh checkout lacks.
- [DESIGN] **The host's modules are reached through `string`-typed specifiers**, with the part of their API
  this hub uses declared beside the code that uses it. This is forced, not stylistic: §2 measures that a
  static import of `better-sqlite3` resolves `@types/better-sqlite3`'s `/// <reference types="node" />` and
  breaks two frozen `packages/core` lines. The pattern is the one this package already uses for
  `node:fs/promises` (F§7.3's cache) and `@lectern/store-sql` uses for the same native addon; the installed
  declarations remain the truth for what the host offers and are quoted in §5.
- [DESIGN] **The document files' names.** `model.json.gz` (the gzipped model as uploaded), `original` (the
  bytes) and `original.json` (`{ mime }`) under `{DATA_DIR}/library/{docId}/`; F§8.4 fixes the directory and
  leaves the names open, and the sidecar is what lets the route that serves an original answer with the
  content type the file really had.
- [DESIGN] **The document id is refused before any path exists.** F§5.2's id — 32 lower-case hexadecimal
  characters — names a directory, so every method validates it first and refuses with F§7.2's
  `HubError("BAD_REQUEST", …)`; the closed code set has no document-specific code, and a refusal here is a
  client's malformed request, not a missing document.
- [DESIGN] **`changesSince` clamps its limit to at least one.** F§8.2's pull asks for a positive limit (the
  route's query schema enforces one), and a client that asked for none would otherwise be told `more`
  forever. The clamp makes progress regardless of what a caller passes.
- [DESIGN] **`summaries` carries a `(doc_id, mode)` primary key and two nullable provenance columns.**
  F§8.4 lists the columns; a row exists while its summary is pending, so `model` and `prompt_version` cannot
  be required, and one status per document and mode is what F§7.2's `GET /v1/ai/summary/:docId?mode=` reads.
- [DESIGN] **`ts` is stored with REAL affinity.** F§5.9's `ts` is a JSON number, not a whole second; SQLite
  keeps an integer that fits exactly and a fractional millisecond is not rounded behind a client's back.

## 7. Deviation proposals

1. **`@types/better-sqlite3` cannot enter this package's type program, so the hub declares the API it uses.**
   The contract names the typings package as a devDependency and it is installed and quoted in §5 — but its
   first line is `/// <reference types="node" />`, so *using* it statically puts Node's ambient types into
   `apps/server`'s program (which compiles `packages/core`'s sources) and two frozen lines there stop
   type-checking: `docx.ts:107` TS2740 and `ocr-tesseract.ts:143` TS2345, the same failure U-023 was blocked
   on. R6 freezes those files, this unit's *Patch scope* is `context.ts` and `app.ts`, and
   `apps/server/tsconfig.json` is not a *Required File Output*, so no file this unit may write can repair
   them. The delivered modules therefore reach `better-sqlite3` and the host's `node:` modules through
   `string`-typed specifiers and declare what they use — the boundary this repository already uses for
   `node:fs/promises` and for this same addon in `packages/store-sql`. Three repairs are measured and
   available to the operator: (a) repair the two frozen lines (a `Buffer`-typed view of the bytes), which is
   the only change that lets the typings be imported; (b) add `"types": []` or an equivalent program
   boundary to `apps/server/tsconfig.json`; or (c) drop the devDependency from the contract, since the
   delivered declaration is self-contained. Until then the devDependency is installed but never imported,
   and §5 is where its signatures are the truth.
2. **`better-sqlite3` is 13.2.0, not F§2.3's 13.1.1.** The lockfile already carried 13.2.0 for
   `packages/store-sql` (U-046, `DONE`), so installing 13.1.1 here would have put two copies of a native
   addon in one lockfile. 13.2.0 is installed, exact (`-E`), and one importer entry was added. A patched
   contract that prefers the ledger's 13.1.1 can say so.
3. **`applyOps(deviceId, ops)`'s `deviceId` is the fallback stamp** (§4). A contract that intends the
   pushing device to *override* each op's own `deviceId` would diverge from what the devices applying the
   same ops compute, so the op's own stamp wins; if the operator wants a mismatch refused instead, that is a
   one-line change here plus a test.
4. **The pull's cursor is ascending-by-latest-`rev`** (§3), and `nextRev` is the page's last `rev`. A route
   unit can rely on the invariant stated there; a contract that prefers the client to re-pull from `since`
   until `more` is false would still work with this implementation.
5. **A malformed document id answers `BAD_REQUEST`.** F§7.2's closed code set has no document-id code, and
   inventing one would fail every client's own copy of `ErrorBodySchema` (U-018's frozen `common.ts`). A
   patched contract could name the code.
6. **`summaries`'s primary key and nullable columns** (§4). F§8.4 lists the columns without constraints;
   U-058's routes are the first users, and this is where the choice is recorded in case it disagrees with
   that unit's contract.
