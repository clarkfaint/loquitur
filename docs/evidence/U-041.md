## 3. Architecture notes

**One capture chain per environment, and the environment decides it (F§10.3's selection-capture table).** The
shell chooses its provider once, at start-up, from the platform and the session:

| Environment | Chain, in order |
|---|---|
| Linux, X11 | the primary selection through Electron's own clipboard → `xclip -o -selection primary` → `xsel -o -p` |
| Linux, Wayland | `wl-paste --primary --no-newline` → the primary selection through Electron's own clipboard |
| Windows | save the system clipboard → `Ctrl+C` to the foreground window through PowerShell `SendKeys` → wait up to 400 ms for the clipboard to change → read → restore what was saved |

Wayland is decided before X11 and never by `DISPLAY` alone: a Wayland session sets `WAYLAND_DISPLAY`, and
`XDG_SESSION_TYPE` states it outright, while an X11 session under a wrapper such as `xvfb-run` sets `DISPLAY`
and nothing else. `win32` is Windows; anything else is treated as a Linux session and decided by those two
variables (§7 (4)).

**The chain is a list of candidates with three endings.** Each candidate either answers with text, or is *not
installed*, or runs and answers nothing:

- the first candidate whose answer is not blank wins, and nothing after it is asked;
- a candidate that is not installed contributes its package name to the error that is raised only if nothing
  answered at all;
- every candidate asked and answered nothing → `EMPTY` ("nothing is selected");
- every candidate that could have answered was not installed → `TOOL_MISSING`, naming the packages to install;
- a candidate that hung past its deadline → `TIMEOUT`.

On this host neither `xclip` nor `xsel` nor `wl-paste` exists, which is the reason the shell's own clipboard is
the first candidate on X11 rather than the last (F§10.3's own order).

**Timing, in the units the code uses.**

| Step | Number | Where it comes from |
|---|---|---|
| one command-line tool's deadline | 2 000 ms | the contract's *Forbidden Actions* |
| the Windows wait for the clipboard to change | 400 ms | F§10.3 |
| the Windows poll interval | 40 ms | this unit: ten polls over the 400 ms window, counted rather than timed, so the wait cannot be shortened by a slow first read |
| the text kept from one capture | 100 000 characters | the contract |
| the title the text is imported under | its first 60 characters | the contract |

**What the operator sees, in the order it happens.** A capture is a request, not a loop: nothing polls the
selection while the operator reads. The trigger (F§10.3's `Ctrl+Alt+R`, the tray, the mini-player) is one action
on one bus; the handler captures once, trims, caps, hands the text to the main window as a read request, shows
the mini-player — because the reading then belongs to a strip that stands in for the window — and, when the
capture failed, raises one desktop notification carrying the reason and does nothing else. It never writes to
the clipboard on Linux, never observes the keyboard, and never looks at the selection again until the operator
triggers it.

**The status line.** `DesktopStatus.selectionProvider` is F§10.3's field for "which provider this shell chose",
and it is the provider's own id: `linux-x11`, `linux-wayland` or `windows` — the environment `detectEnvironment`
answered, so a diagnostics screen can say which chain is in force without re-deriving it.

## 4. Lectern design

- [DESIGN] **The clipboard and the tools are injected, and nothing else is.** `SelectionClipboard`,
  `SelectionExec` and `SelectionSleep` are declared in `provider.ts`; the shell supplies one adapter each over
  Electron's `clipboard`, `node:child_process`'s `execFile` and a timer, and the unit tests supply fakes. This is
  what makes the whole chain — including the Windows round trip, which cannot run on this host at all — a unit
  test rather than a hope (F§10.3: "All commands run through an injected `exec` function so the logic is
  unit-tested without the tools installed").
- [DESIGN] **Commands are called with an argument array and a deadline, never through a shell.** `execFile` is
  the API used, its `timeout` is the contract's 2 000 ms, and the only place a string is passed to another
  program is PowerShell's own `-Command`, which is an argument of that array rather than a shell.
- [DESIGN] **A tool that is not installed is not an error while another candidate may answer.** The chain only
  reports `TOOL_MISSING` when nothing was installed at all, and its message names the packages, because the
  operator's next step is an install rather than a retry (the contract: "`TOOL_MISSING` names the packages to
  install").
- [DESIGN] **The Windows wait counts ten polls rather than reading a clock.** The window F§10.3 fixes is 400 ms
  and the interval is this unit's 40 ms; counting the polls makes the wait exact under a fake `sleep` and
  independent of how long a read takes, which is what AGENTS.md §7's determinism rule asks for.
- [DESIGN] **The saved clipboard text is restored in a `finally`.** Every path leaves the Windows clipboard as
  it was found — success, a timeout, a failed `exec`, and an empty result — so a read-aloud action can never cost
  the operator what they had copied (the contract's *Forbidden Actions*).
- [DESIGN] **The handler is a feature, and the shell's surfaces are one object.** `readSelectionFeature` is what
  `features.ts` appends — the registry U-038 marked — and it hands `useReadSelection` the same ctx every other
  feature gets plus the four surfaces; the unit test drives the handler with a stand-in ctx, so the send, the
  status publication, the notification and the mini-player's trigger are all asserted rather than inferred from
  a page.
- [DESIGN] **The mini-player is shown by raising its own action.** F§10.3's bus has nine actions and none of
  them is "show the mini-player"; the strip is made and shown by `toggleMini`, the action the tray and the
  hotkey already raise, and a shell that has just been asked to read a selection has no strip up yet (§7 (3)).
- [DESIGN] **The provider id is published when the feature registers.** `DesktopStatus` is F§10.3's own record
  and its `selectionProvider` is a string; the value is written once, from the environment the shell detected,
  and every later publish (U-040's own status announcements included) spreads the record it finds, so the field
  cannot be lost by a later feature publishing its own.
- [DESIGN] **A failed capture is reported, not thrown.** The action handler runs from an ordinary bus listener,
  where an exception has nowhere to go: the failure becomes a notification naming the reason, which is what the
  contract asks for and what a trigger with no page of its own needs.

## 6. Verification log

### 6.1 Rehearsal, before the deliverables (2026-11-15)

The contract's end-to-end case turns on one question this host can answer in isolation: whether Electron's
clipboard can put text on the X11 primary selection and read it back under `xvfb-run`, since the case writes the
selection from the main process and the shell's own provider reads it from the same process. A throwaway probe
outside the repository (`~/.hermes/cache/scratch/u041-probe`, an Electron app that writes and reads the
selection and has no window) answered it:

```
$ xvfb-run -a <repo>/.../electron/dist/electron --no-sandbox <probe>       # write, then read in one process
PROBE {"selectionType":"object","writeIsPromise":true,"readIsPromise":true,
       "selectionRead":"alpha bravo charlie delta echo","systemRead":"",
       "systemAfterWrite":"system clipboard text","selectionAfterSystemWrite":"system clipboard text"}
$ xvfb-run -a … <probe> read        # nothing ever wrote a selection
PROBE {"mode":"read","wayland":null,"session":null,"display":":99","selection":"","system":""}
$ xvfb-run -a … <probe> write ; xvfb-run -a … <probe> read   # a second process, after the writer exited
PROBE {"mode":"read",…,"selection":""}
$ xvfb-run -a … <probe> clear-read  # selection.clear() after a write, same process
PROBE {"mode":"clear-read",…,"selection":""}
```

Four consequences, all used by the case:

1. `clipboard.selection` is a real object with promise-returning `writeText`/`readText` (the installed types are
   the truth here, §5) and a round trip in one process works, so the case can write the text the shell is asked
   to read.
2. With nothing owning the selection — a fresh `xvfb-run` session, or a process that exited — a read answers
   `""`, which is exactly what the case's second half needs: no writer, no text, no document.
3. A selection **does not outlive the process that wrote it**: the second process read `""`, so a case cannot be
   contaminated by the previous case's text.
4. `selection.clear()` leaves `""` as well, so the empty case is explicit about it.

Also measured on this host, because they decide what the X11 chain really does here: `which xclip xsel wl-paste
powershell` names none of the four, so the injected clipboard is the only candidate that can answer on this
host, and the empty case ends in `TOOL_MISSING` naming `xclip`/`xsel` rather than in `EMPTY` (§7 (2)); the
session variables under `xvfb-run` are `DISPLAY=:99`, `WAYLAND_DISPLAY` unset, `XDG_SESSION_TYPE` unset, which is
the detection's X11 branch measured rather than assumed.

`pnpm-workspace.yaml` was byte-identical before this unit began
(`sha256 193f4ebeb52b303fb4699dc1ec1cd03be4bc8067f2b08c3b9a2b097923167f70`); no dependency is added by this

## 7. Deviation proposals

1. **The installed electron's clipboard is asynchronous and addresses the selection as an object.** F§10.3's
   table says "Electron `clipboard.readText('selection')`", and `electron@45.3.1` declares
   `readText(): Promise<string>` and `writeText(text: string): Promise<void>` with no type argument plus
   `readonly selection: Clipboard`, whose own members are the same promises (§5). The deliverable therefore
   reads the primary selection through `clipboard.selection.readText()`, and the case writes it through
   `clipboard.selection.writeText(text)`. The contract states the second call as
   `clipboard.writeText(text, 'selection')` in the case's own text, which the installed types do not accept.
   Proposed: word F§10.3's row and the case as "the selection clipboard object, or the type parameter where the
   pinned Electron still takes one".
2. **The channel the text is handed over on is spelled `lectern:read-text`.** The contract's output bullet says
   the handler sends "`reader:read-text`", and no such channel exists anywhere in the repository: `./ipc`'s
   frozen table (U-038) names the text hand-off `lectern:read-text` (`ipc.ts:55`), with
   `DesktopReadRequestSchema` as its outbound schema (151) and `onReadText` in the preload bound to it. Nothing
   this unit may write can add a channel — `ipc.ts` is a `DONE` unit's file and is not in this unit's scope — so
   the handler sends on the channel that exists. Proposed: correct the bullet to `lectern:read-text`.
3. **F§10.3 has no action for showing the mini-player.** The contract's bullet asks the handler to "show the
   mini-player", and the shell's only trigger for the strip is `toggleMini` (F§10.3's nine actions;
   `context.ts:44`, answered by U-039's feature). On a shell that has just been asked for a selection the strip
   is not up (it is made on the first trigger that needs it), so the toggle is what shows it — but a second
   selection read while the strip is already visible hides it instead. Proposed: an idempotent show on
   `DesktopWindows` (or a `showMini` action) so "show" means show.
4. **`detectEnvironment` has three answers and the shell can run on two platforms.** F§10.3's shell is Linux and
   Windows; the contract's union has no answer for a third platform. The deliverable treats `win32` as Windows
   and everything else as a Linux session decided by `WAYLAND_DISPLAY`/`XDG_SESSION_TYPE`, which is the branch a
   Linux host really takes and the one the unit test pins; a fourth environment would need a contract that names
   it.
5. **The missing-tool error is the one an empty selection produces on a host without the tools.** Because the
   chain reports `TOOL_MISSING` whenever nothing that could have answered is installed, an empty selection on
   this host (which has neither `xclip` nor `xsel`) is reported as "install one of these" rather than "nothing is
   selected". The distinction is real information — the clipboard could not be read at all — and the end-to-end
   case asserts the observable half of both (no document, one notification) rather than the wording. Proposed:
   if the order ever puts a tool ahead of the shell's own clipboard on X11, that host's empty case reads `EMPTY`
   instead, and the wording of the two is worth pinning in F§10.3.
