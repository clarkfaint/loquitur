## 3. Architecture notes

Generic names, own words. The platform is `expo-audio`'s **audio playlist**: one native queue object that holds an
ordered list of audio sources and plays them one after another without JavaScript being awake in between.

**The queue as a state machine.** The playlist has an index (which item is current), a count, a position inside the
current item, a rate, and a playing flag. It reports two things a sink can act on: a **track change** (an old index and
a new one, which the platform emits only when the two differ) and a periodic **status** (index, count, position,
duration, playing, loaded, buffering, and a flag that says the queue has just run to its end). Playback starts on
`play`, stops where it is on `pause`, moves inside the current item on `seek`, empties on `clear`, and a rate is applied
to the whole queue at once.

**Timing math.** Positions and durations are reported in **seconds** by the playlist and are whole **milliseconds**
everywhere in Lectern (F§5.6), so the sink multiplies by 1000 and rounds once. The rate the playlist accepts is bounded
by the platform: its own declared range is `0.1` to `2.0`, which is exactly F§5.8's `maxRate = 2` for this platform —
above 2× the split in `planSpeed` (F§5.6(e)) moves the rest of the speed-up into synthesis, so one cached chunk still
serves several rates.

**Why the queue lives natively.** The contract forbids driving sentence-to-sentence advance from JavaScript timers. The
native queue advances between items on its own, so a throttled or backgrounded JavaScript thread does not interrupt
playback; JavaScript only listens. That is also why the sink holds no timer of its own and why its events are
translated from the platform's own reports rather than polled.

**The end of the queue.** The platform emits **no** track change for the end of the last item — its own listener
suppresses an event whose two indexes are equal. The end arrives instead as a status report carrying the
just-finished flag, whose current index is still the last item. So the sink turns "a report whose current index is the
one it is already on" into the last chunk's end followed by one queue-empty, and it must do that **once**: the same
report can arrive more than once, and a sink that repeated itself would break the conformance suite's "queue-empty
fires once" case.

**What the platform does not have.** The playlist exposes no pitch-correction switch (only the single-item player
does), because its rate is applied by the platform's own time-stretcher, which keeps the pitch. So "pitch correction
left on" on this platform means: set the rate and nothing else — there is no flag to turn off, and this unit turns
none.

## 4. Lectern design

- [DESIGN] `queue-map.ts` is the pure half: a list of chunk ids in playlist order, the index the map believes is
  current, and one drain flag. `append` records a chunk and answers its index; `onTrackChanged(previousIndex,
  currentIndex)` answers **the events to emit** — a chunk ends when the map moves off it, a chunk starts when the map
  lands on one, an equal index means the chunk the map is on has finished (its end, then queue-empty, once), and a
  report naming an index the map holds no chunk for emits nothing; `reset` empties it; `currentChunk` answers the chunk
  the map is on, or `null` when nothing is playing. Keeping the decision out of the sink is what makes it testable
  under Node, where no native module exists (AGENTS.md §7's "no real clock, no device" rule).
- [DESIGN] `expo-queue-sink.ts` is the platform half and satisfies F§5.8's `AudioQueueSink` verbatim: `maxRate` is the
  setting `sinkMaxRate`'s default, `2.0`; `enqueue` adds a source to the native queue; the platform's track changes
  and its just-finished status become `chunk-end`, `chunk-start` and `queue-empty` through the map; `clear` empties the
  queue and the map; `setRate` writes the playlist's rate; `current()` reads the playlist's position; `dispose` takes
  the listeners off and destroys the queue. The platform module is loaded **when a sink is built, not when this module
  is imported**, so the diagnostics registry — which the package's Node test imports — never pulls `expo-audio` into a
  Node program. `createExpoBlobFs` (U-046) is the same shape for the same reason.
- [DESIGN] `audio-session.ts` holds F§10.4's two platform-wide declarations: `configureAudioSession()` sets background
  playback on and the interruption mode to do-not-mix (a reader's audio stops for a call and does not play under a
  video), and `setNowPlaying(sink, { title, subtitle })` hands the queue to the lock screen with previous and next
  enabled and both seek buttons off, which is F§10.4's "play/pause and previous/next sentence". Only one queue can own
  the lock screen at a time, so the module remembers the one it handed over and `clearNowPlaying()` — no argument, as
  the contract writes it — takes it back.
- [DESIGN] `audio/diagnostics.ts` registers the check `audio-sink` for the diagnostics screen (F§10.4: "the diagnostics
  screen runs the conformance suites on the device"). It runs F§5.8's own `runAudioQueueSinkConformance` against the
  real sink on a scratch blob cache, so the run is measured on the device's own audio stack and the reader's own cache
  and library are never opened — the pattern U-046's store checks established.
- [DESIGN] No JavaScript timer anywhere, no playback started by this unit, and no microphone: the sink plays only when
  the app calls `play()`, which happens from a reader's tap (F§10.4's background-audio rule, verified on a device in
  U-052).

redundant half of that contradiction is removed there: `RECORD_AUDIO` leaves `blockedPermissions` and the plugin's own

## 7. Deviation proposals

1. **`app.json`'s `blockedPermissions` and the fixed command's `RECORD_AUDIO` grep** — §6.1. This unit removes
   `android.permission.RECORD_AUDIO` from `blockedPermissions`, because the generated manifest carries the string
   whenever it is blocked and the contract's fixed command requires the string to be absent. If the operator would
   rather keep the directive, the repair is a patched command that ignores a `tools:node="remove"` entry (for example
   `! grep -q 'RECORD_AUDIO"' …`). Recorded rather than hidden; the microphone stays out of the manifest either way,
   and U-053's release-APK audit (F§10.4) is the check that would catch a regression.
2. **`createExpoQueueSink` is asynchronous** — the contract writes `createExpoQueueSink({ maxRate }): AudioQueueSink`,
   and the value it answers is one; the call itself is `async` because the platform module is loaded when a sink is
   built rather than when this module is imported (a static import of `expo-audio` would put it, through the
   diagnostics registry, into the Node test program, where `react-native` cannot be parsed — U-046's measured
   lesson). `runAudioQueueSinkConformance`'s factory accepts a promise, so the suite is unaffected.
3. **`clearNowPlaying()` takes no argument**, as the contract writes it, so `audio-session.ts` remembers the queue
   `setNowPlaying` handed to the lock screen. The platform allows one owner at a time, which makes that memory
   unambiguous.
