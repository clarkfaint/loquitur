## 3. Architecture notes

**One engine per app run, and it is the app's own composition.** U-058's `createSyncEngine` reads no platform
API — the store, the client, the clock, the socket factory and the online signal all arrive as arguments — so
this unit's job is to supply the four Android answers and nothing else: `AppState` for the foreground *and*
reachability signal, React Native's global `WebSocket` for F§8.3's feed, `fflate` for F§7.2's gzip container,
and `expo/fetch` for the transport. The service is built by `createSyncService(options)`, whose every platform
contact is a seam with the platform's own implementation behind it; `syncService` is the app's single instance
and `app/_layout.tsx` starts and stops it with the app.

**Where a round comes from on this platform.** F§8.3 gives an engine three clocks: a socket `changed`, a local
change, and the app coming back to the foreground. All three are here, plus one more (U-059's doorbell): a
one-second look at the outbox, because F§5.9's store raises no change event and the screens that write to it —
the importer, the library, an offline pin — are files frozen by the units that built them. The reader's own
progress is the one write this unit *can* announce, so `player-context.tsx` calls `notifyLocalChange()` directly
after each `setProgress`, and `syncNow()` is what a return to the foreground calls.

**No background work, and the reachability signal is the foreground one.** The contract forbids background
tasks, background fetch, notifications and boot receivers, and the honest Android answer to "may I run a round"
turns out to be the same question as "is the app in front of the reader": so `isOnline()` is `AppState ===
"active"`. A backgrounded app runs no round at all (F§8.3's own rule for the foreground pull, and the reason a
reader listening with the screen off is untouched by this subsystem — F§10.4's queue advances without
JavaScript). The service's only timer is the doorbell, and the engine's five-minute round is U-058's.

**The round trip the check measures.** The device's own check writes one F§5.9 `setting` record, which queues one
op in the real outbox, asks the engine for a round, and reads F§8.2's two facts back: `pendingOps` answers
nothing (the hub acknowledged it, so `ackOps` emptied the outbox) and `getCursor()` moved (the pull stored
`nextRev`). The outbox is drained in a bounded loop, because a device that has never synced holds every op it
ever wrote — up to F§8.2's 200 per round.

**The other half of the round trip is a second device.** The harness's `push-document.mjs` is that device: the
hub parses the probe text, the model is uploaded gzipped under its own `docId`, and one `document` op is pushed
with a `deviceId` of the script's own. The phone therefore receives a record *written elsewhere*, and the title
that appears in its library is the visible end of that.

## 4. Lectern design

- [DESIGN] **The switch is not an F§5.9 `setting` record.** It is this device's own property, kept beside the
  connection in the platform's secure store under `lectern.sync-enabled` (F§11's two values already live there,
  and React Native has no `localStorage`). A `setting` record is exactly what F§8 carries to the reader's other
  devices, and one device turning sync off must not turn it off on another. F§8's default is on.
- [DESIGN] **The connection's change is watched by the service, once, for its own life.** A reader who saves a
  hub in Settings expects sync to start; the watcher is one listener on U-045's `onConnectionChanged`, and
  `begin()` re-reads both the switch and the connection, so a save while nothing is running cannot start
  anything a stopped switch would not allow.
- [DESIGN] **`ensureModel` is called where F§8.2 says it is.** A `document` record can arrive from another
  device before its text does (F§8.2's lazy body), so `player-context.tsx` asks the service for the model only
  when the store has none, and only after the local read has failed — a document this device imported is
  untouched by the sync subsystem.
- [DESIGN] **The harness restarts the app inside the contract's window rather than waiting a round out.** The
  library reads F§5.9's store when it comes into focus (`useFocusEffect`), so a round that landed after the list
  had drawn is not visible until the screen re-reads; a fresh start both re-reads and runs F§8.3's start round.
  This is the app's own path, and it is why `verify-sync.sh`'s window is the contract's 30 s rather than longer.
- [DESIGN] **The check's probe setting is written to the reader's own store.** A scratch store would round-trip
  against the same hub and prove nothing about this app; the outbox and the cursor that F§8.2 moves are the
  reader's, so the record is too. It is one `setting` under the key `sync-roundtrip` holding the moment it was
  written.

None. Two things are worth recording for whoever reads this next, and neither asks for a contract patch:

1. A device unit that reads a *screen* has to be written around `useFocusEffect`: the library re-reads F§5.9's
   store when it comes into focus and not when the store changes underneath it, so `verify-sync.sh` restarts the
   app inside its own window instead of waiting for a round it cannot see. The window stays the contract's 30 s.
2. The switch's home (the secure store, §4) is a design decision this unit made rather than a place the contract
   names. If a later unit wants the reader's sync preference to *travel* between devices, that is a different
   decision and it needs its own contract, because it would make one device's off another device's off.
