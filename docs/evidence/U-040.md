## 3. Architecture notes

**One registration per action, and the state of each is the shell's own report (F§10.3).** Nine triggers are
bound to accelerators; five of them (the tray's two entries and the mini-player's own controls) have no default
accelerator at all. Each action's registration is one of three states, and the settings screen draws them as
they are: `registered` (the accelerator is held by this shell), `failed` (the accelerator is bound — by another
application, by an invalid string, or by nothing that accepts it), and `pending` (nothing is bound yet, or the
desktop has not answered). The state moves like this:

- an empty accelerator is never handed to the OS and stays `pending`;
- a string that does not name a modifier plus a key is refused before it reaches the OS and reads `failed`;
- otherwise the accelerator is handed over: a surface that answers synchronously moves straight to `registered`
  or `failed`, and a surface that reports the desktop's asynchronous resolution stays `pending` until it does;
- when the resolver reports, each accelerator awaiting it is asked whether it is held, and becomes `registered`
  or `failed`;
- changing one accelerator moves only that action's state; the actions around it keep theirs.

**A change is a diff, not a re-registration of everything.** Unbinding one action and binding another elsewhere
must not disturb the six the operator did not touch, and an action whose accelerator has not changed must not be
handed to the OS twice — a second `register` on an accelerator this shell already holds answers `false`, which
would misreport a working shortcut as failed. So a change unregisters every accelerator that is going away
before it registers any that is arriving; a swap (A takes B's accelerator while B takes A's) therefore works,
where a register-first order would fail one of the two.

**The order of a change.** `previous` and `next` are compared per action: a value that disappeared or changed
puts the *old* string in the unregister list, and a value that appeared or changed puts the *action* in the
register list. Everything else — including an action that had nothing and still has nothing — is in neither
list, and is not touched.

**What the settings screen shows.** One row per action, in F§10.3's own order: the accelerator as the capture
control (a read-only field that takes the next keystroke), and the live state beside it. A captured chord is
applied the moment the key is released — there is no separate save — so an invalid or already-held accelerator
is refused before anything is written: the field keeps the value that is really bound and one sentence says why
the attempt was declined. One button at the end of the section restores F§10.3's defaults.

## 4. Lectern design

- [DESIGN] **The portal's answer is read from the accelerators, not from the event's payload.** F§10.3 says the
  result of a portal-mediated bind arrives asynchronously, and this shell then asks the surface which of the
  accelerators awaiting it are held (`isRegistered`). No payload shape is invented, and the same code answers
  however the desktop words its answer. The installed Electron (see §5) reports no such event at all.
- [DESIGN] **The hotkey feature re-announces the status when the renderer reads the settings.** F§10.3's
  `onStatus` is a one-way push, and a page that subscribes after the last publish has no way to ask for it
  (`settings.get()` answers the record alone). The feature therefore answers that one channel itself — the
  pattern U-039 established for the player's channels — publishing the current status as part of the answer, so
  the settings screen's own read is the handshake. U-038's behaviour on that channel is preserved exactly.
- [DESIGN] **An action with no accelerator reads `pending`.** There is nothing to resolve, and calling it
  `registered` would claim the shell holds a shortcut it does not.
- [DESIGN] **A captured chord is spelled with Electron's full modifier names** (`Control`, `Alt`, `Shift`,
  `Super`) in that fixed order, while F§10.3 writes the defaults as `Ctrl+…`. Both are the same accelerator to
  the OS, and the capture uses the unambiguous spelling so what the operator pressed is what the record says.
- [DESIGN] **The key of a captured chord is read from the event's `code`** (`KeyP` → `P`, `Digit1` → `1`,
  `ArrowRight` → `Right`, `Space` → `Space`, `Escape` → `Escape`, `F5` → `F5`), falling back to the event's own
  `key` for anything else, because `key` follows the keyboard layout and the shift state while `code` is the
  physical key the operator means.
- [DESIGN] **Everything is unregistered on `will-quit`.** A shell that is quitting must not leave a chord held
  by a process that is gone, and the same handler releases the settings subscription.
- [DESIGN] **`hotkey-model.ts` is pure.** No Electron import and no clock: the defaults, the validator, the
  conflict finder and the diff are functions over plain records, which is what lets the shell's own unit tests
  drive them without an application.

## 7. Deviation proposals

1. **F§10.3's `registration-resolved` event does not exist in the installed Electron.** The contract's
   *Forbidden Actions* say "use the asynchronous resolution described in the installed Electron documentation",
   and the installed `electron@45.3.1` declares none: `interface GlobalShortcut` (line 8998) carries seven
   methods and no event members, does not extend an emitter, and mentions neither Wayland nor the portal. The
   deliverable therefore treats a surface as portal-mediated only when it offers an event API, and resolves the
   answer by asking the accelerators whether they are held; the asynchronous path is exercised by the unit test
   through an injected surface, and the real path cannot be reached on this host's Electron. Proposed: word
   F§10.3's sentence as the mechanism ("the result arrives asynchronously when the surface reports it") or raise
   the pinned Electron to a version whose types declare the event. `wayland: unverified`.
2. **The bridge has no member for the default table or for a status read.** F§10.3's `LecternDesktopBridge`
   offers `settings.get/set/onStatus/pickFolder` and nothing else, so the settings section carries its own copy
   of F§10.3's defaults (for the reset control) and its own copy of the two pure predicates
   (`validateAccelerator`, `findConflicts`), while `hotkey-model.ts` holds the shell's. Two copies of one table
   can drift. Proposed: publish the defaults and the status through `@lectern/ui-web` (or extend the bridge) so
   both ends read one table.
3. **A late subscriber cannot ask for the current status.** `settingsStatus` is a push and U-038's `settingsGet`
   answers the record alone, so a page that subscribes after the shell's first publish learns nothing until the
   next change. This unit re-announces from the read (see §4) rather than changing the frozen channel's request
   shape; proposed: F§10.3 could give the bridge a `status()` read.
4. **`toggleMini` and `showMain` have no default accelerator** in F§10.3's list, so they are stored as empty
   strings and read `pending` until the operator binds one; F§10.3 says the defaults are configurable but does
   not say what an unset one means in the status.
