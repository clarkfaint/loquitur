## 3. Architecture notes

**A container is read, never followed.** The bytes are a ZIP and every fact comes out of it: the container
file names the package document, the package document's manifest names resources and its spine orders
them, and each spine document is decompressed and mapped. No reference is ever resolved outside the
container — an `href` carrying a scheme (`http:`, `data:`), a protocol-relative `//host`, or enough `..`
segments to climb past the container's root is passed over instead of fetched — so a book cannot make the
hub read a file the book does not contain. This is F§5.4's *Forbidden Actions* applied to the one parser
whose input is a bundle of files rather than one.

**Reading order is the spine, and the manifest is not an order.** The manifest is a bag: it holds the
navigation document, the cover, the cover image and the chapters, in whatever order the producer wrote
them. Only the spine says what a reader encounters and in which sequence, which is why the parse walks
`spine`'s `itemref`s and looks each `idref` up in the manifest rather than mapping manifest items in
manifest order.

**Which documents a spine may contribute.** A spine entry contributes prose when all four of these hold:
its `itemref` names an item the manifest defines; the item is not the navigation document (EPUB 3's
`properties` token `nav` — the token is matched, not the string, so `properties="nav svg"` still counts);
the item is not a cover document; and its media type is a content type (`application/xhtml+xml`,
`text/html`, `image/svg+xml`). Anything else is passed over rather than failing the book, because a spine
that names an image or an item the manifest forgot is a producer's mistake, not a reason to refuse a
readable book. An entry the *container* does not hold is different: that book is broken, and the parse
fails with `INVALID_EPUB`.

**A navigation document is prose if it is mapped, and a cover is not text.** Measured on the fixture
(section 2): the navigation document maps to a heading `Contents` and three list items that repeat the
chapter titles, i.e. every title would be read twice in a book read aloud; the cover document maps to
nothing at all, because its only text lives in `head`. Both are dropped because F§5.4 says so, and the
second is the reason the rule can be stated without measuring it first.

**Two refusals, both before any mapping.** `INVALID_EPUB` covers a container that is not a ZIP, one without
`META-INF/container.xml`, one whose `rootfile`s name no package document the archive holds, and a spine
naming a document the container does not hold. `DRM_PROTECTED` covers an **encrypted content document**:
an OCF `CipherReference` URI (measured from the container's root, which is where OCF defines it) that
resolves either to a spine document or to a manifest item whose media type is a content type. A resource
that is neither — an obfuscated cover image, a font — is not a refusal, because rejecting any book with an
encrypted resource would refuse books whose text is perfectly readable. Nothing is ever decrypted: the
encrypted entries are **not** decrypted, and no document is parsed: the refusal happens as soon as the
manifest, the spine and `META-INF/encryption.xml` have been read, before a single spine document is
mapped. (The container's entries are inflated by `unzipSync` before that point, because which entries are
encrypted is only knowable by reading `encryption.xml`; what the refusal prevents is *reading* one as
prose.)

**Names are matched on their local part.** The container file and the OPF are XML, and section 2's probe
shows linkedom's XML tree reports one namespace for everything while keeping a prefix inside the element
name. Matching on the local part of the name is therefore both necessary (a `dc:` prefix) and sufficient
(a Dublin Core default namespace would drop the prefix) — and it never depends on the namespace a tree
claims. The `localName` member is read rather than `tagName`, because an HTML tree uppercases `tagName`
(the defect section 6 records).

**A chapter is already an article.** A spine document is parsed as HTML and its body is walked by
`html-map.ts` — the mapping F§5.4 asks for — and Readability is deliberately *not* run over it. EPUB
documents are chapter-sized and often shorter than Readability's threshold; asking an article extractor to
find the article again would let a short or unusually structured chapter be discarded, and there is
nothing in a chapter to extract: no navigation, no aside, no footer to strip.

**One tree, one MIME type.** The container file and the OPF are read as XML so that their elements keep
their document order and their names; the spine documents are read as HTML so that `html-map.ts` sees the
tree it was written for (U-006's `html.ts` gives a web page exactly that tree). Both come from the same
`DOMParser`, and the documents are built lazily inside the walk — nothing is parsed twice.

## 4. Lectern design

- [DESIGN] `packages/core/src/parsers/epub.ts` exports `parseEpub(bytes: Uint8Array): Promise<ParsedEpub>`
  returning `{ rawBlocks, title, lang }`, the shape the contract fixes. The container is decompressed
  synchronously (`unzipSync`) and the caller's array is only read — unlike pdfjs, which *transfers* the
  buffer it is given (U-007), fflate copies nothing out of it, so no defensive copy is taken and a
  `Buffer` argument works — follows the contract's signature and F§5.4's "Every parser returns `RawBlock[]`
  … and metadata".
- [DESIGN] The two refusals are a single exported error class, `EpubParseError`, carrying
  `code: "INVALID_EPUB" | "DRM_PROTECTED"`. F§5.4 names the codes and F§7.2's error envelope is
  `{ error: { code, message } }`, so the hub needs to branch on the *code* of a caught parser error rather
  than search a message for it; a caller can also tell a refusal apart from a bug with `instanceof`.
- [DESIGN] `title` is the OPF's `dc:title`, trimmed; when the package declares none, the first spine
  document that declares a `<title>` of its own supplies it, and `""` when none does — follows the
  contract's "title from OPF `dc:title`" and leaves `buildDocument`'s own title rule (first heading, then
  the first 60 characters) as the last resort it already is.
- [DESIGN] `lang` is the OPF's `dc:language`, trimmed, and `undefined` when the package declares none, so
  `buildDocument` applies F§5.1's `en` default rather than the parser inventing one.
- [DESIGN] Blocks are concatenated in spine order, each document mapped from its `body` (or, for a
  document that is a fragment rather than a whole XHTML file, from its root element) — follows F§5.4's
  "Each spine XHTML is mapped like HTML" and keeps U-006's walker as the only place block kinds are
  decided.
- [DESIGN] A cover *document* is recognised by the convention EPUB 2 established and EPUB 3 kept — an item
  whose manifest `id` or whose file-name stem is `cover` — and not by the `cover-image` property, which
  F§5.4's rule does not need: a resource the package marks as the cover image is an image, and an image's
  media type is already not a content type, so it can never contribute a block. The cover document's own
  text lives in `head` on the fixture, but the rule does not rely on that.
- [DESIGN] An OCF path reference is percent-decoded before it is matched against an entry name (a ZIP entry
  name is raw bytes while an OCF `href` is a URI), a fragment or query is dropped, and a reference that
  climbs past the container's root, or carries a scheme or a `//host`, is refused — the contract's "Do not
  follow external references or load remote resources", implemented as a resolver that returns `null`
  rather than as a fetch that is never called.
- [DESIGN] `packages/core/src/parsers/index.ts` gains one export line, inserted where the standing lint
  gate's `organizeImports` wants it (`./epub` before `./html`) — §5's append-only rule for a barrel, and
  the U-007 pitfall that a barrel line is an insertion rather than an append.
- [DESIGN] The module imports `fflate` and `linkedom` and nothing else — no `node:` specifier — so the
  Node-only parser needs no ambient Node types in the package's type-check program, which is the barrier
  U-006 hit and the operator's `chore(spec)` patch removed for the tests' sake (section 5).
- [DESIGN] `packages/core/tsconfig.json` is **not** touched: the delivered test is under
  `src/parsers/__tests__`, which the operator's patch excludes from the program, so the test may read the
  fixture with `node:fs` while `tsc` still checks the two delivered modules — the contract lists neither
  file, so this unit could not have carried the exclusion itself.

## 7. Deviation proposals

- [DESIGN → contract] **F§5.4 says "`nav` and cover documents are dropped" without saying how either is
  recognised.** Implemented as: the navigation document is the one whose manifest `properties` tokens
  include `nav` (EPUB 3), and a cover document is one whose manifest `id` or file-name stem is `cover`
  (the convention EPUB 2 established and EPUB 3 kept) — a `properties="cover-image"` resource needs no
  rule of its own, since an image is never a content type. Proposal: name the two markers in F§5.4 so a
  later parser (or the DOCX parser's cover page, if it has one) does not have to choose them again.
- [DESIGN → contract] **The fixture cannot prove the drop rule.** Its spine names the three chapters and
  neither the navigation nor the cover document (section 2), so the fixture alone would pass even if the
  parser mapped every manifest item. This unit pins the rule with a synthetic container instead (test 4),
  and the fixture's own assertion says plainly that the spine is what keeps the table of contents out.
  Proposal: have U-005's generator put the navigation and cover documents in the fixture's spine, or say
  in F§5.4 that the fixture pins spine order only.
- [DESIGN → contract] **The OPF and the container file are XML, and F§5.4 does not say so.** They are read
  with linkedom's `text/xml` document (the third MIME type its `DOMParser` declares) while a spine
  document is read as HTML, which is what the mapping wants. Note also that linkedom resolves no
  namespaces: every element of a parsed XML file reports the XHTML namespace, so names must be matched on
  their local part (section 2). Proposal: record both facts in F§5.4's EPUB row, since a later parser of
  an XML-based format (the DOCX package is a ZIP of XML as well) will meet exactly the same two.
- [DESIGN → contract] **An EPUB's XML files are decoded as UTF-8** (`strFromU8`), which is what OCF
  requires of them; a book whose XML declares another encoding is read as UTF-8 and will look wrong rather
  than fail. This unit does not detect the declaration. Proposal: state the assumption in F§5.4 so the
  dispatcher's later MIME sniffing does not have to guess what the parser does.
- [DESIGN → contract] **The contract's four test cases are a floor, not a ceiling.** Two of the four
  behaviours this unit had to get right — the title fallback and a percent-encoded `href` — are not in the
