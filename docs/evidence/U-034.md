## 3. Architecture notes

Inspection is unavailable, so nothing in this section is a claim about the reference product. The first part is
what the contract, F§10.2, F§5.7 and F§5.8 fix for *Lectern*; the second part is what this session measured about
the *browser* the extension runs in, because the contract's design assumes platform behaviour that has to be
checked rather than remembered (AGENTS.md §7, R9).

### 3.1 What Lectern's offscreen host is

- F§10.2 gives the extension four contexts and this unit builds the middle one. The **background service worker**
  routes messages, creates the offscreen document and tracks the active reading tab; the **offscreen document**
  (`AUDIO_PLAYBACK`) hosts `PlayerController`, `HtmlAudioQueueSink`, the api-client and the IndexedDB
  `BlobCache`, and is *the only context that plays audio or calls the hub*; the content script (U-035) extracts
  text and paints highlights; the popup is the connection form.
- The reason playback lives outside the worker is MV3's own lifetime rule: a service worker is terminated when
  idle, so nothing that must keep running — audio, a play loop, a queue — can live in it.
- The player this unit hosts is the frozen one. `createPlayerController` (U-013) is pure TypeScript over four
  injected boundaries (F§5.8): an `AudioQueueSink`, a `ChunkSource`, a `DocumentProvider` and a `Clock`. This unit
  supplies `createHtmlAudioQueueSink` (U-024), `createCachingChunkSource` over `createHubClient` (U-021),
  an in-memory provider holding the one document the session is reading, and a clock over `Date.now`.
- The relay is one hop in each direction (F§10.2): a `DocumentModel` extracted in a tab travels
  background → offscreen as `ext/read-document`; the player's `PlayerSnapshot` travels offscreen → background as
  `ext/snapshot` and is forwarded to the active tab and the popup. The offscreen document holds the document in
  memory only; nothing about a page survives the session (the contract's *Forbidden Actions*).

### 3.2 What this session measured about the platform

Measured, not assumed (R9). The instrument was a throwaway MV3 probe extension loaded into Playwright's bundled
`chromium-1254` through a persistent context, driven from the test's side by `serviceWorker.evaluate` and by an
extension page of the probe; each statement below is one observation from that probe, and none of it is evidence
about the reference product.

- [OBSERVED] **A service worker cannot deliver a message to its own `onMessage` listener.**
  `chrome.runtime.sendMessage` from the worker's own global scope, with the worker listening, rejects with
  `Error: Could not establish connection. Receiving end does not exist.` — and when an offscreen document is
  listening, that document answers instead while the worker's own listener never fires. So "the worker sends it"
  and "the worker receives it" are mutually exclusive for one message.
- [OBSERVED] **`chrome.runtime.sendMessage` is a broadcast to every extension context except the sender.** A
  message sent by an extension page was received by both the worker *and* the offscreen document; a message sent
  by the worker was received by the offscreen document and by extension pages. `chrome.tabs.sendMessage(tabId)`
  reaches the runtime listener of an extension page sitting in that tab as well as a content script.
- [OBSERVED] **An offscreen document has almost no extension API surface.** Inside the document,
  `Object.keys(chrome)` is `["loadTimes", "csi", "runtime"]`: `chrome.storage`, `chrome.tabs`,
  `chrome.offscreen` and `chrome.permissions` are all `undefined` (the manifest declares `storage`; it makes no
  difference). `chrome.runtime` — `sendMessage`, `onMessage`, `connect`, `onConnect` — is present, and so are the
  page's own capabilities: `Audio`, `indexedDB`, `URL.createObjectURL`, `fetch`.
- [OBSERVED] **A `chrome.runtime` port carries data in both directions from the offscreen document.** The
  document's `chrome.runtime.connect({ name })` fires the worker's `chrome.runtime.onConnect`, and
  `port.postMessage` works in both directions.
- [OBSERVED] **`chrome.offscreen.createDocument` and `chrome.runtime.getContexts` behave as the contract
  assumes**: after `createDocument({ reasons: ["AUDIO_PLAYBACK"] })`,
  `getContexts({ contextTypes: ["OFFSCREEN_DOCUMENT"] })` answers exactly one context whose `contextType` is
  `OFFSCREEN_DOCUMENT`; before it, zero.
- [OBSERVED] **Chromium does not load an extension in Playwright's default headless mode at all** (the
  `chromium_headless_shell` binary it launches then reports no service worker). With `channel: "chromium"` the
  full browser runs headless with the extension loaded, and everything above was measured that way — which is
  why the e2e fixture launches with that channel and the contract's command needs no `xvfb-run`.
- [OBSERVED] **A static import of `@lectern/server` inside `apps/extension`'s program pulls the frozen parser
  files in, and two of their lines stop compiling there.** `apps/extension`'s type-check program is WXT's
  generated one, `include: ["../**/*"]`, and `@types/node@26.6.6` *is* reachable inside it (measured with
  `tsc --listFiles`: `node_modules/.pnpm/@types+node@26.6.6/...`, reached through a referenced declaration), so
  a plain `import { writeFile } from "node:fs/promises"` resolves and type-checks — the earlier reading of this
  package as having no node types at all does not reproduce. The consequence runs the other way, though: a
  static `import { buildApp, loadConfig } from "@lectern/server"` adds `packages/core/src/parsers/**` and
  `@fastify/cors` to the program, whose `/// <reference types="node" />` makes `Buffer` a real type there, and
  `packages/core/src/parsers/docx.ts:107` (TS2740) and `ocr-tesseract.ts:143` (TS2345) come back — the same two
  frozen lines U-023 measured, in a different program. Both appear with the static import and both disappear
  without it; nothing else in the program is affected. The hub package is therefore reached from this unit's
  fixture through a *string-typed* dynamic import, which the compiler does not follow.
- [OBSERVED] **A test cannot grant the hub origin.** `chrome.permissions.request` from a page that has just been
  clicked at hangs on a native prompt nothing can dismiss (the promise was still pending after 3 s); the same
  call from the worker without a gesture rejects at once with `This function must be called during a user
  gesture`. What does make the origin reachable from an extension page is the hub's own CORS policy: U-019
  registers `@fastify/cors` with `origin: true` and `allowedHeaders` carrying `authorization`, and a fetch from
  an extension page to such a hub completed (preflight `OPTIONS`, then `200`, with the bearer header intact) with
  no host permission granted.

### 3.3 What 3.2 forces on this unit

The two platform facts with design consequences are the offscreen document's API surface and the broadcast
nature of `chrome.runtime.sendMessage`:

- The offscreen document **cannot read `chrome.storage`**, so "builds the hub client from settings" cannot be a
  storage read. The settings it needs — hub URL, token, voice, rate, furniture — are pushed to it by the worker
  over a `chrome.runtime` port, whose first message is also the readiness signal the worker waits for before it
  relays anything (a relay sent into a document whose script has not run yet would be answered by nobody).
- Because a page's message is broadcast, a copy of, say, an `ext/command` reaches the offscreen document whether
  or not the worker relays it, and a `toggle` executed twice cancels itself. The offscreen document therefore
  obeys a player instruction only when it arrives without a tab (`sender.tab === undefined`), which is exactly
  the background's own shape — the content script's and a page's copies carry their tab and are ignored, and the
  worker's relay is the one that acts.

## 4. Lectern design

- [DESIGN] `src/background/offscreen.ts` owns the document's life: `ensureOffscreen()` creates it only when
  `chrome.runtime.getContexts` shows none, and resolves once the document's port has connected, so a caller can
  rely on the document being ready to receive; `closeOffscreenLater()` schedules
  `chrome.offscreen.closeDocument()` 30 s after a stop or the end of a document, and a new reading cancels the
  pending close (the contract's *Forbidden Actions*, F§10.2).
- [DESIGN] The same module carries the one settings channel this platform allows:
  `OffscreenSettingsSchema` (a strict zod object: `hubUrl`, `token`, `voiceId`, `rate`, `skipFurniture`) and the
  port name, sent by `installOffscreenBridge()` when the document connects and again whenever
  `onSettingsChanged` fires — so a change reaches a live document without a reload (§3.3).
- [DESIGN] `src/background/session.ts` is `ReadingSession`: it remembers the one tab being read, relays
  `ext/read-document` and `ext/command` to the offscreen document and `ext/snapshot` to the active tab and the
  popup, and stops itself when that tab closes or navigates; a second tab's reading stops the first (the
  contract's own words). Its chrome surface is injected (`SessionPlatform`) so the unit test drives it with a
  fake, and the service worker builds the real one.
- [DESIGN] `entrypoints/offscreen/main.ts` is the host itself: it connects the port, validates what arrives,
  builds the hub client, the IndexedDB blob cache, the caching chunk source, the HTML audio sink and the
  controller over them, keeps the current document in memory behind a `DocumentProvider`, and re-builds the
  client and the chunk source when the settings change — behind a stable `ChunkSource` wrapper, so a settings
  change does not disturb a controller that is mid-document (F§10.2, F§5.8).
- [DESIGN] The offscreen document publishes `ext/snapshot` on every state change of the controller and, while
  the player is `playing`, samples the active word and publishes at most once every 50 ms — the contract's own
  rate — so a viewer sees the sentence advance even between state changes (F§5.7, F§6(d)).
- [DESIGN] The e2e rig is this unit's own: `e2e/global-setup.ts` starts a real hub (F§7.1's mock engine) and a
  static server for `e2e/pages/`, writes their addresses and the token to `e2e/.env.local` (gitignored, as
  `.gitignore`'s `*.local` already covers), and releases both; `e2e/fixtures.ts` launches
  Playwright's Chromium with the built extension loaded and exposes `serviceWorker`, `extensionId` and
  `configure()`; `e2e/offscreen.spec.ts` drives the whole flow (§3.2's measured delivery rules decide how).
- [DESIGN] `installReadingSession()` registers the four messages the session answers in `background/handlers.ts`'s
  registry *when it runs*, rather than adding them to that file by name: the file is U-032's, whose own frozen
  test asserts the declared registry refuses every type but `ext/get-status`, and the service worker's startup
  path is what makes a registration real (see §6.1, §7).
- [DESIGN] The hub package is reached from `e2e/global-setup.ts` through a string-typed dynamic import cast to a
  small declared interface (`loadConfig`, `buildApp`, `listen`, `close`), not a static one: a static import of
  `@lectern/server` adds the frozen parser files to this package's program and two of their lines fail there
  (§3.2, measured). Node's own built-ins (`node:fs/promises`, `node:os`, `node:path`, `node:http`, `node:url`)
  are imported normally, because they do resolve in this program.

## 7. Deviation proposals

- **The offscreen document cannot read `chrome.storage`.** The contract says `main.ts` "builds the hub client
  from settings" and "rebuilds the client when settings change", which reads as the same `chrome.storage.local`
  access the popup and the worker use. Measured (§3.2): inside an offscreen document `chrome` holds only
  `loadTimes`, `csi` and `runtime` — no `storage`. The settings therefore reach it over a `chrome.runtime` port
  owned by `background/offscreen.ts`, pushed on connect and on every change. Proposed wording for the contract:
  "builds the hub client from the settings the background pushes over its port, and rebuilds it when a new
  settings message arrives".
- **The service worker cannot send a message to itself, so the e2e's first message cannot originate in the
  worker.** Measured (§3.2): a worker's `chrome.runtime.sendMessage` rejects with `Could not establish
  connection. Receiving end does not exist.` when the worker is the only listener, and an offscreen document
  answers it when one exists — the worker's own `onMessage` never fires. The contract's spec line ("after
  `ext/read-document` … is sent from the service worker") is therefore unsatisfiable as written: nothing the
  worker sends can reach a handler *in* the worker, and with no offscreen document yet in existence the send has
  no receiver at all. `e2e/offscreen.spec.ts` sends the message from the extension's own popup page — an
  extension context that *can* reach the worker, and the context F§10.2 gives the job before U-035's content
  script exists — and then asserts that the worker relayed it to the offscreen document and that the offscreen
