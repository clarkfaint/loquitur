## 1. Questions

1. Which context performs the save, and how does a Save button that lives in somebody else's page reach a library
   that only the offscreen document can open?
2. What exactly is stored when the reader presses Save — and what must never be stored?
3. How does the widget learn that the page it is on is in the library, given that `./mount` (U-036) is frozen and
   hands it nothing but a `PlayerSnapshot`?
4. What makes a progress record belong to a document, what stops it being written twenty times a second, and what
   makes a pause land?
5. How does the reader's place reach the hub without a push per write?
6. Which package API does each step use, at the versions this repository installs (R9)?

## 3. Architecture notes

**Where a save happens.** The widget (a content script, inside the reader's page) is the only place the reader can
press; the offscreen document is the only context that owns a library. The message that joins them is the
extension's own protocol, `ext/save-page`, and it is the one message in this protocol that a *page* sends and the
offscreen document answers: a content script's `chrome.runtime.sendMessage` is a broadcast to every context of the
extension except the sender's (U-034's measurement), so the worker receives it too and refuses it with
`NO_HANDLER`, while the offscreen document — whose listener otherwise ignores anything carrying a tab, so that a
page's copy of an `ext/command` cannot cancel itself — acts on this one. The widget does not read that reply: the
worker's refusal is not the library's answer, and the answer that matters arrives with the next snapshot.

**What a save writes.** F§5.9's `DocumentMeta` for the page — `sourceKind: 'html'` (F§10.2 saves *pages*), the
title and the counts the `DocumentModel` itself carries, `sourceUri` from the model's `source.uri` when it has
one, `folderId: null`, `addedAt`/`updatedAt` from the caller's clock — and then the model, through
`putDocument`. Nothing else: no page markup, no cookies, no screenshot, no original bytes. The duplicate test is
F§5.9's own question (`getDocumentMeta(docId) !== null`) asked before either write, so a second press answers
`{ duplicate: true }` and writes nothing.

**How the widget knows.** The offscreen document publishes `saved` with every `ext/snapshot` it already
publishes, computed from the document it has in memory and the identifier it last saw in the library (asked once,
with one store read, when a reading starts — not on every 50 ms sample). The widget reads it from a raw
non-answering `chrome.runtime.onMessage` listener of its own and draws the button from it. A page in a private
window is offered no Save control at all.

**What throttles a place.** `recordProgress(store, engine, snapshot)` writes F§5.9's `Progress` only for a
document the library holds. While the player is moving (`playing`, `buffering`, `loading`) a write happens at most
once per `PROGRESS_INTERVAL_MS` (5 000 ms), and the throttle is the *record's own timestamp* — the store stamps
`updatedAt` with its own clock, and the next call compares against it — so the rule survives a reload of the
offscreen document rather than living in a variable that dies with it. A player that has settled (`paused`,
`ended`, `error`, `ready`) is written at once, which is what makes a pause land. The offscreen document calls it
at most once per distinct position (state, document, sentence, word), which is what keeps a 50 ms sample from
asking the store a question twenty times a second; the five-second rule itself is the module's.

**How a place reaches the hub.** F§5.9's store raises no change event, and U-058's engine schedules its round
`LOCAL_CHANGE_DELAY_MS` (2 000 ms) after `notifyLocalChange()`. `recordProgress` therefore announces the write
rather than pushing it: a burst of places becomes the one round F§8.2's debounce is for. A save is the other
case — a user action that should be visible at once — and it asks for `syncNow()`.

## 4. Lectern design

- [DESIGN] The save is answered by the offscreen document and nowhere else, because F§10.2 gives the library to
  that context and no other context can reach the hub.
- [DESIGN] `ext/save-page` carries nothing: the document being saved is the one the offscreen document is
  already reading, so a page cannot ask for another document to be stored.
- [DESIGN] `saved` travels on `ext/snapshot` as an optional boolean, so a snapshot from any context that does not
  know about a library is still a snapshot (and U-032's frozen message test stays true — §7 (1)).
- [DESIGN] A save with nothing loaded is `NO_DOCUMENT`; a save with no library (a hub the reader has not
  configured) is `NO_LIBRARY`. Both are refusals the widget shows by leaving the button as it was, because
  F§10.2's Save button has one state to report and it is the saved one.
- [DESIGN] A private window is offered no Save control: F§10.2's rule, enforced where the browser's own
  `inIncognitoContext` flag is readable.
- [DESIGN] `recordProgress` writes F§5.9's `Progress` and nothing else, and only for a document the library
  holds: a page nobody kept has no place worth remembering.
- [DESIGN] The library is the same `lectern` IndexedDB database, the same `LibraryStore` and the same identity
  (`getDeviceId`) the audio cache already uses, so the extension's saved pages and its cached audio are one
  installation's — F§5.9's implementations are shared across web, extension and desktop.

## 7. Deviation proposals

Never acted on without a patched contract.

1. **`saved` had to be optional on `ext/snapshot`.** The contract says the message "gains a `saved: boolean`
   field". Written as a *required* field it breaks two frozen tests that no file this unit may write can repair:
   U-032's `src/__tests__/messages.test.ts:43-56` builds a valid `ext/snapshot` without it and asserts
   `ExtMessageSchema.safeParse(...)` succeeds (`:82-87`), and U-037's `src/background/__tests__/session.test.ts:192`
   declares one as `ExtMessage`, whose inferred type would then require the field (`ext/snapshot`'s output type is
   `z.infer`). R6 freezes both files and R11 forbids weakening a test, so the field is
   `z.boolean().exactOptional()` — the same shape this protocol already uses for `ext/read-document`'s
   `startSentence`, and the same shape its own frozen test pins (`messages.test.ts:121-124` rejects an optional
   field present as `undefined`). Every producer in this repository sends it.
2. **The widget talks to the extension itself.** `src/content/widget/mount.ts` (U-036) is the only file that
   renders `Widget` and is not in this contract's *Patch scope*, so `saved` and the Save action could not arrive
   as props. A patched contract that added `apps/extension/src/content/widget/mount.ts` to the patch scope would
   let the widget stay purely presentational: `mount` already watches `ext/snapshot` and could pass
   `saved={message.saved ?? false}` and `onSave={() => void send({ type: "ext/save-page" })}` the way it passes
   `onCommand`.
3. **The worker refuses a save it is not asked to answer.** The widget's `chrome.runtime.sendMessage` reaches the
   worker as well as the offscreen document, and the worker has no handler for `ext/save-page`, so the promise the
   widget deliberately ignores resolves `NO_HANDLER`. The save is unaffected (the offscreen document answers the
   same broadcast), but a patched contract could register a one-line relay in the frozen
   `src/background/session.ts` — `"ext/save-page": (message) => relay(message)` — so that the reply a caller reads
   is the save's own.
4. **The private-window rule is enforced in the widget.** F§10.2's "do not save pages from private browsing
   windows" is checked where `chrome.extension.inIncognitoContext` is readable, which is a content script and not
   the offscreen document (U-036's measurements of both contexts). A stronger gate would need the flag relayed to
   the offscreen document with the settings; the contract's *Forbidden Actions* name no such mechanism, and
   `apps/extension/src/background/offscreen.ts` is not in this contract's patch scope.
