## 3. Architecture notes

### 3.1 The host, and how Docker is reached here

`docker --version` → 29.1.3; `docker compose version` → 2.40.3; the daemon is up (`systemctl is-active docker`
→ `active`). The client could not reach the daemon at first: `docker ps` → `permission denied while trying to
connect to the docker API at unix:///var/run/docker.sock`, while `/etc/group` holds `docker:x:107:user`
and this login session's own credentials do not (`id` lists 1000,4,24,27,30,46,100,101 — no 107). The operator
granted the group after the session started, so the group is available to a *new* shell and not to this one.
`sg docker -c '<command>'` switches into it without a password and without `sudo` (`sudo -n true` → `sudo:
interactive authentication is required`), and every Docker command in this unit ran that way. The command text
of the fixed verification test is unchanged; only the shell that carries the supplementary group differs.

Measured host limits, because this unit's whole risk is resource-shaped: `nproc` → 2; `free -h` → 3.3 GiB
total, 1.7–1.8 GiB available; `df -h /` → 30 GiB volume, and the free space fell from 8.2 GiB to 2.9 GiB when
the engine image was pulled, so disk — not CPU — is the binding constraint.

### 3.2 The engine: which release, and why not the newest

F§2.3 names the image (`ghcr.io/remsky/kokoro-fastapi-cpu`) and the two APIs (`GET /v1/audio/voices`,
`POST /dev/captioned_speech`), and the contract forbids a `latest` tag, so the tag had to be resolved and
pinned. The registry's own tag list (ghcr anonymous token + `/v2/…/tags/list`) holds `v0.1.0-pre` … `v0.10.0`;
`docker manifest inspect --verbose` sizes the amd64 images at 1.51 GB (v0.10.0), 1.52 GB (v0.9.2), 1.49 GB
(v0.8.1), 1.66 GB (v0.3.0) compressed.

The newest release is **not** usable, and this is the finding that decided the pin. U-016's adapter (frozen by
R6) reads the voice list with `z.union([z.array(z.string()), z.object({ voices: z.array(z.string()) })])`, i.e.
F§6's "voices come from the service" as *ids*. Measured on the real container:

| Tag | `GET /v1/audio/voices` | `POST /dev/captioned_speech` |
|---|---|---|
| v0.10.0 | `{"voices":[{"id":"af_alloy","name":…},…],"default_voice":…}` — 72 **objects** | present (`api/src/routers/development.py`) |
| v0.3.0 | `{"voices":["af_alloy","af_aoede",…]}` — **strings** | present (`api/src/routers/development.py`) |

The change is in the source at the tag, not inferred from behaviour: at v0.10.0 the route's own docstring says
it returns objects "by default so OpenAI-compatible clients … can render the full voice list. Pass
`?legacy=true` for the pre-0.3.x plain-string shape", while v0.3.0's `list_voices()` is typed
`-> List[str]` and the route returns `{"voices": voices}` with no parameter at all. U-016 requests the path
with no query string, so an object list makes the hub's own `/v1/voices` carry no `kokoro:` voice and the
contract's second smoke check could never pass. **Pinned: `ghcr.io/remsky/kokoro-fastapi-cpu:v0.3.0`**, digest
`sha256:d7df384acb57929f88a696d892c1a2e0c6b60fa934802ebec9a88626003b8e9a`, 1 658 435 489 bytes, built
2026-05-15 — the newest release whose default voice list is the shape F§6 describes.

Behaviour of that pinned release, measured on this host (`docker run -d -p 127.0.0.1:8880:8880`, 2 CPUs):

- Readiness: `/health` answers `{"status":"healthy"}` after ~40 s (poll every 5 s; the log shows `72 voice
  packs loaded` before it does). No GPU is present and none is needed.
- `POST /dev/captioned_speech` with exactly U-016's payload
  (`{"model":"kokoro","input":"Hello, world.","voice":"af_alloy","speed":1,"response_format":"mp3","stream":false}`)
  → HTTP 200 in **1.5 s**, `{"audio": <base64>, "audio_format": …, "timestamps": […]}`. The audio decodes to
  **27 308 bytes** beginning `49 44 33 04` (`ID3` v2.4) — the tag `readMp3DurationMs` already skips. The
  timestamps are **four**, one per engine token, punctuation included:
  `Hello 0.068–0.568, "," 0.568–0.655, world 0.655–1.593, "." 1.593–1.793` (seconds).
- So the words the hub's own tokenizer finds (`Hello`, `world`) are both matched by engine tokens with
  punctuation tokens in between — exactly the case U-012's `alignEngineTimings` looks ahead for.

### 3.3 The bundle, and the one defect the rehearsal caught

esbuild 0.28.2 bundles `apps/server/src/main.ts` to a 4.2 MB ESM file, and the four externals survive as
imports (`pdfjs-dist/legacy/build/pdf.mjs`, `@napi-rs/canvas`, `tesseract.js` — measured by grepping the
output; `better-sqlite3` is named external although nothing imports it yet). Bundling the hub's CommonJS
dependencies (`fastify`, `fastify-plugin`, `@fastify/cors`) into an ESM output **breaks at startup**, and only
running it shows that:

```
Error: Dynamic require of "node:path" is not supported
    at …/dist/server.mjs:11:9
    at fastify-plugin/lib/getPluginName.js (…/dist/server.mjs:54:33)
```

esbuild's CommonJS shim falls back to `require` only when one is in scope, and an ESM file has none. The fix is
a one-line banner — `import { createRequire as __lecternCreateRequire } from "node:module"; const require =
__lecternCreateRequire(import.meta.url);` — after which the same bundle prints `lectern hub listening on
0.0.0.0:8787`. The bundle is not "probably fine" until it has been started.

### 3.4 The production `node_modules` the image ships

`pnpm deploy --prod` is the contract's own suggestion and it produces a self-contained tree, but the default
layout is unusable from a bundle: the workspace packages become symlinks and their dependencies land in
`node_modules/.pnpm/node_modules/`, which is **not** on Node's resolution path from `dist/server.mjs`
(`pdfjs-dist`, `tesseract.js`, `fflate`, `linkedom` were all found there and none at the top level). With
`--config.node-linker=hoisted` the same deploy answers a flat tree — 100 top-level entries, **175 MB** — with
`pdfjs-dist`, `tesseract.js`, `@napi-rs/canvas`, `fflate`, `linkedom`, `mammoth`, `@mozilla/readability`,
`fastify` and `zod` all directly resolvable. `better-sqlite3` is absent because no package depends on it yet.

Two pnpm 12 policies have to be answered on every invocation that installs, and both were measured here:

- `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` — `@fastify/cors@11.4.3` (installed by U-019) sits inside the
  window. In the repository a plain `pnpm install` only warns, but `pnpm deploy` **fails**: `✗ Lockfile at
  …/pnpm-lock.yaml failed supply-chain policy check (127 entries in 6.4s)`.
- `ERR_PNPM_IGNORED_BUILDS` — `tesseract.js@7.0.0`'s postinstall. Here `pnpm deploy` also fails where a plain
  install only warns.

`--config.minimumReleaseAge=0 --config.strictDepBuilds=false` are per-run flags, so no file is written:
`pnpm-workspace.yaml` stayed byte-identical across the esbuild install
(`bc13db515b2a8009648c2f0691b561bfee1cb9365c68a0debaec521d3fe3ea29` before and after).

## 4. Lectern design

- [DESIGN] **One Dockerfile, three stages, hub last** (F§12). `build` installs with pnpm, bundles with
  esbuild and produces the production tree with `pnpm deploy --prod --config.node-linker=hoisted`; `piper`
  builds F§2.3's `piper-tts[http]` service; `runtime` is the hub image and is the default target, so
  `docker compose up --build` cannot accidentally build the wrong stage. The piper service asks for its stage
  by name (`target: piper`) behind a profile, so the fixed command never builds it.
- [DESIGN] **The runtime image holds only what runs.** It copies the deployed `node_modules` and the bundle,
  never the repository sources, and it runs as the base image's own unprivileged `node` user — never root, as
  the contract requires. `LECTERN_DATA_DIR=/data` is set in the image and the compose volume is mounted there,
  so F§7.3's cache and F§7.1's SQLite file live on the named volume.
- [DESIGN] **The health check is Node's, not curl's.** Measured: `curl` is *not* in
  `node:24.22.3-bookworm-slim` (`command -v curl` → nothing), so the `HEALTHCHECK` runs `node -e` against
  `/healthz`, the one route F§11 leaves unauthenticated. The kokoro service's check uses the `curl` the engine
  image does ship (`/usr/bin/curl`).
- [DESIGN] **The engine is pinned by tag and recorded by digest**, and the pin is the newest release whose
  voice list matches F§6 (§3.2). The image carries no published port: `hub` maps `8787:8787` and the engine is
  reachable only on the compose network as `http://kokoro:8880`.
- [DESIGN] **The smoke test asks the hub, never the engine.** It reads `LECTERN_TOKEN` from the environment the
  contract's command exports and takes `--base`, so it works against a container stack or a local hub
  unchanged; it prints one line per check and exits 1 on the first failure. The three assertions with a
  countable quantity are fixed in the script: `Hello, world.` is two words (F§5.3) and must be timed by the
  engine, the audio must exceed 1 000 bytes, and one sentence of text must parse as one sentence.
- [DESIGN] `infra/.env.example` carries the placeholder token and F§7.1's optional variables commented out;
  `infra/.env` is already ignored by `.gitignore`, so the command's `cp -n` cannot dirty the tree.

## 5. API signatures relied on

- `esbuild@0.28.2` — `apps/server/node_modules/esbuild/lib/main.d.ts`:
  `export declare function build<T extends BuildOptions>(options: SameShape<BuildOptions, T>): Promise<BuildResult<T>>` (line 557);
  `BuildOptions` carries `entryPoints?` (168), `outfile?` (124), `bundle?` (118), `external?: string[]` (132),
  `banner?: { [type: string]: string }` (164), plus the `CommonOptions` members `format?: Format` (21),
  `target?: string | string[]` (25) and `platform?: Platform` (29). The version is the registry's current one
  (`pnpm add -D -E` → 0.28.2), which the contract allows for a package F§2.3 does not list.
- `ghcr.io/remsky/kokoro-fastapi-cpu:v0.3.0` — measured on the running container, not from documentation:
  `GET /health` → `{"status":"healthy"}`; `GET /v1/audio/voices` → `{"voices": string[]}`;
  `POST /dev/captioned_speech` → `{"audio": string (base64), "audio_format": string, "timestamps": [{ word: string, start_time: number, end_time: number }]}`.
  These are the two endpoints and the one shape F§6 and U-016 already depend on.

## 7. Deviation proposals

1. **F§2.3's engine row names no tag, and the newest tags are incompatible with F§6.** Proposed wording: name
   `ghcr.io/remsky/kokoro-fastapi-cpu:v0.3.0` (or any release before the object-shaped voice list) as the
   pinned image, because U-016's frozen adapter reads voice ids and the route changed shape at v0.4.0. Without
   the pin the contract's own smoke check cannot pass.
2. **The `piper` profile's service image is not specified anywhere.** F§2.3 says Piper HTTP is "built from
   `piper-tts[http]` (`python3 -m piper.http_server`)" but `infra/Dockerfile.piper` is not a listed output, so
   the build lives in a `piper` stage of the one Dockerfile the contract does list. Proposed wording: say so.
3. **F§12 names profiles `piper` and `llm`; the contract's compose bullet names only `piper`.** The `llm`
   profile (an `ollama/ollama` service plus F§7.1's three LLM variables) is included, since F§12 is cited and
   the profile is off unless asked for.
4. **The fixed command's `docker compose` steps need the `docker` group in the invoking shell** on this host,
   because the session predates the operator's group grant (§3.1). The command was not edited; it ran inside a
   group-switched shell.
5. **`pdfjs-dist/*` accompanies `pdfjs-dist` in esbuild's external list.** The package is imported through the
   `pdfjs-dist/legacy/build/pdf.mjs` subpath, which a bare package name need not cover; the contract's intent
   (do not bundle the worker-based package) is what the pair implements.
6. **pnpm 12's supply-chain policy needs `--config.minimumReleaseAge=0 --config.strictDepBuilds=false` on every
   installing invocation** (§3.4), inside the image as well as on this host, or `pnpm deploy` exits 1.
