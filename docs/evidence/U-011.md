## 3. Architecture notes

**The decision chain.** One input, one question — *what are these bytes?* — answered in F§5.4's order. The bytes'
own signatures are asked first (`%PDF`, the eight PNG bytes, the three JPEG bytes, `RIFF` … `WEBP`, `PK` plus a
ZIP's entry list, and a document that opens with `<!doctype html>` or `<html>` after optional leading
whitespace). If none answers, the declared MIME type is asked, normalized to its bare type (parameters dropped,
trimmed, lower-cased) so that `text/plain; charset=utf-8` is the same evidence as `text/plain`. If that is silent
too, the file name's extension is asked. Only when all three are silent does the fallback run: the bytes are
decoded strictly as UTF-8, and text that decodes without a replacement character is text. Anything else is
`UNSUPPORTED_FORMAT`.

**Telling the two containers apart.** A ZIP's own signature is two bytes and both container formats share it, so
the archive is *listed*: `unzipSync` calls its filter once per entry, before any data is touched, and an entry the
filter declines is not expanded. The filter records the name and answers `false` for every entry, so the call
returns nothing and costs nothing but the central-directory walk. A `mimetype` entry means EPUB; a
`word/document.xml` entry means DOCX. An archive whose directory cannot be read is not identified, and the
refusal surfaces from the parser the remaining evidence selects — or as `UNSUPPORTED_FORMAT`.

**Failure mapping.** Nothing is swallowed and nothing is guessed at. A refusal this module made itself passes
through; an `EpubParseError` keeps its own code (`INVALID_EPUB`, `DRM_PROTECTED`); a `DocxParseError` keeps
`UNSUPPORTED_FORMAT`; and everything else — a library's own throw, a strict decode that met a byte it cannot
represent, a container that is not what it claimed — becomes `PARSE_FAILED` carrying the original message. The
document that carries no text is `EMPTY_DOCUMENT`, measured on the built model rather than on the raw blocks, so
whitespace-only input is refused by the same rule as an empty file.

**One model, one title rule.** Every branch hands `buildDocument` its raw blocks and its source, and the title
only when the parser found one: an empty parser title is not a title, so it is left out and F§5.1's own rule
applies — the first heading, else the first 60 characters of the first block. That is what names a scan (which
declares nothing and has no heading) after its first line, and what names both text artefacts after the heading
their own markup opens with.

**Anchors belong to a paged source.** The PDF branch is the only one that answers with `anchors`, computed by
`anchorsFor` over the word locations the PDF parser recorded; every other branch returns a document alone. A
scanned PDF is still a PDF, so it answers with an anchor list — empty, because OCR'd pages carry no text-layer
position.

## 4. Lectern design

- [DESIGN] `sniffFormat` implements F§5.4's precedence chain and its text fallback, and returns `null` only for
  bytes that are neither a format Lectern reads nor UTF-8 text; `parseDocument` calls the same resolution and
  refuses `null` with `UNSUPPORTED_FORMAT`. One oracle for "what is this?", one refusal.
- [DESIGN] A document's opening markup counts as a signature (`<!doctype html`, `<html`, case-insensitively,
  past leading ASCII whitespace). F§5.4's list names the binary formats because those are the ones a byte test
  settles, but the contract requires every fixture to be identified from its bytes alone, and the alternative —
  reading a web page as prose — contradicts the row that owns HTML. Recorded as a deviation proposal below.
- [DESIGN] The TXT / Markdown row is read with one reader, `parseMarkdown`, because the row gives both formats one
  set of rules (`#`…`######` open headings, list markers and `>` open list items and quotes, a blank line
  separates paragraphs, inline markers are stripped). `parseText` remains exported for a caller that knows its
  input carries no block markers, and the two renderings of one document read back as one document under this
  reading. Recorded as a deviation proposal below.
- [DESIGN] `source.mime` records the MIME type of the format the bytes actually are — the declared type only
  when the declared type is what identified the format. A caller's wrong claim is therefore never written into
  the model, which is what the contract's first *Forbidden Action* is about.
- [DESIGN] `source.kind` is `url` for markup that arrived at an address, and the address is recorded as
  `source.uri`; markup read from a file is `html` with no `uri`. F§5.1 has both kinds, and this is the difference
  between them.
- [DESIGN] An image without an OCR engine is `PARSE_FAILED` with a message that says an engine is needed: the
  format was recognised and the input was not empty, so the failure is the missing reader, not the format.
- [DESIGN] A scanned PDF without an engine is `EMPTY_DOCUMENT`: the PDF parser is F§5.5's own entry point, it
  yields no block for a page with an empty text layer, and the built model is what the refusal is measured on.
- [DESIGN] `pageCount` is recorded for PDFs only, and the anchors answer carries `PdfAnchor[]` for PDFs only —
  F§5.1's `pageCount` is for paged sources, and F§5.4 gives anchors to the text layer of a paged source.
- [DESIGN] The module exports its own types (`FormatHint`, `ParseDocumentInput`, `ParseDocumentDeps`,
  `ParsedDocument`, `ParseErrorCode`, `SniffedFormat`) so a caller never has to restate a shape it was given.
  Nothing in it is exported from the isomorphic entry: it lives under the parser entry, which F§7 keeps
  Node-only.

### What the rehearsal changed, and what it did not

The fixed command passed on its first run in the repository, and all twenty delivered tests passed on their first
run in the rehearsal. The four failing assertions that preceded the delivered files were one **decision of this
unit's**, not a defect in the frozen parsers: F§5.4's signature list names the binary formats and not a web page,
so a page with no hint at all was claimed by the text fallback and read as prose. Three other choices were settled
by measurement rather than assumption, and each would have failed **silently** — as wrong text rather than as an
error — if it had been guessed:

1. **What identifies a container.** `PK` alone is two container formats at once. The rehearsal proved that only
   the entry list tells them apart, and that `unzipSync`'s filter is called for every central-directory entry
   before its data is expanded, so the listing costs no inflation. A dispatcher that trusted the first two bytes
   would have read an EPUB as a DOCX and produced mammoth's refusal instead of the book.
2. **What an empty parser title means.** `parseImage` and `parseScanned` hand back `""` when their text declares no
   title. Passed to `buildDocument` as an empty string, F§5.1's fallback would be skipped and the document would
   be nameless; left out, the fallback names a scan after its first line. Measured on the two scans, both of
   which declare no title.
3. **What the text row's rules are.** F§5.4 gives TXT and Markdown one rule set. Reading `sample.txt` with the
   paragraph reader and with the row's full reader produces two different documents (18 blocks against 20, and a
   literal `# Lighthouse Notes` as the first block's text); the row's full reader makes the two renderings of one
   document come back as one document. Measured, not assumed.

## 7. Deviation proposals

1. **The markup signature.** F§5.4 lists signatures for the binary formats only. This unit treats a document that
   opens with `<!doctype html>` or `<html>` (case-insensitively, past leading whitespace) as a web page, because
   the contract's own test requires `article.html` to parse with `source.kind === "html"` when the caller gives
   no hint at all, and the text fallback would otherwise claim it as prose. If the operator wants the page to be
   identified only by a declared type or a name, the change is the one line in `magicFormat` and two fixture
   cases in the test — but the artefact then parses as `txt` with no hint, and the contract's test as written
   cannot pass.
2. **One reader for the TXT / Markdown row.** The row gives both formats one rule set, so `parseDocument` reads
   text with `parseMarkdown`; `parseText` stays exported for callers whose input is known to be marker-free
   (`importTextLocal`, F§10.4's Android path). If the operator intends `.txt` to be read as paragraphs only, the
   change is one call in `parseAsText`, and `sample.txt` then carries the literal title `# Lighthouse Notes`
   instead of its own heading.
3. **An empty parser title is not a title.** The dispatcher passes a parser's title to `buildDocument` only when
   it is non-empty, so F§5.1's fallback names a document whose parser found none — which is what names
   `scanned.pdf` after its first line. If the operator prefers an empty title to survive to the model, the change
   is `titleOf`'s one line.
