## 3. Architecture notes

The state machine this UI draws is F§5.7's, not an invention of this unit: `idle → loading → ready →
buffering → playing → paused → ended`, with `error` reachable from any state and a failure keeping the
position so `play` retries. The three transitions the reader's own controls drive are `play` (from `ready`,
`paused`, `ended` or `error`), `pause` (from `playing` or `buffering`) and `seek` (from anything but `idle`
and `loading`), and the contract's reader screen adds nothing to it.

**Highlight clock (F§5.6(d)).** `t = sink.current().positionMs + lookaheadMs`, with `lookaheadMs` 80 ms on
Android. The UI samples at most every 50 ms while audio is moving — 20 Hz, which is both F§10.4's reader
throttle and this contract's ceiling — and once per state change otherwise, so a restored or seeked position
is painted without playback having to start. Media time is independent of playback rate, so no rate correction
is ever applied to the sampled position.

**Highlight geometry.** F§5.1 stores, per sentence, its `charStart`/`charEnd` into the owning `Block.text`,
and per word the same pair. That makes the whole highlight a function of one string and three offsets: the
block's text is split into at most five runs (text before the sentence, text before the word, the word, text
after the word, text after the sentence), and the runs concatenate back to the block's own text exactly. A
block that does not hold the active sentence has no offsets to split on, so it is one plain run. This is the
one place where the Android reader differs in *mechanism* from the web reader: the DOM uses the CSS Custom
Highlight API over text nodes, and React Native has no range API, so the Android reader re-renders the active
block as styled `<Text>` runs instead.

**Progress (F§5.6(f)).** `fraction = (wordsBefore(sentenceIndex) + wordIndex) / wordCount`, and remaining time
at rate `r` is `remainingWords / (baseWpm · r)` minutes with `baseWpm` a running average of
`60000 · words / durationMs` over chunks played with the current voice, seeded at 170. Both numbers come from
`@lectern/core`'s own `progressFraction` and `remainingMs`; this unit only feeds them a position and the pace.

**Lock screen (F§10.4).** One media session owns the notification shade at a time, and the platform stops
audio that has none behind it after a few minutes. The metadata therefore has to follow the sentence being
read, and the controls are the ones U-047 already declares: play/pause and previous/next sentence.

## 4. Lectern design

- [DESIGN] **Control arrangement (F§10.4, contract's Forbidden Actions).** A fixed bottom bar in three
  stacked rows: a full-width progress line at the top, then one row carrying the time remaining, the speed
  button and the voice button, then the transport row — previous sentence, play/pause, next sentence — with a
  sleep-timer chip at its end. This is deliberately not a single centred transport strip: the reader's thumb
  reaches the transport first and the progress line is readable at a glance without covering text.
- [DESIGN] **Speed and voice are bottom sheets** (F§5.6(e), F§6): `SpeedSheet` offers F§5.6(e)'s five
  `RATE_PRESETS` as chips plus −/+ steps of `RATE_STEP` (0.05) reaching the whole 0.5–5.0 range; `VoiceSheet`
  groups F§6's voices by `lang` behind a text filter. Both are React Native `Modal`s — no UI kit, no icon font,
  no animation library (contract's Forbidden Actions).
- [DESIGN] **Both numbers are shown** (F§5.6(f)): the percentage, because a reader skimming wants the shape of
  the document, and the time remaining, because that is what decides whether to keep listening. The percentage
  is drawn as the bar's own fill.
- [DESIGN] **The active sentence is a background, the active word a stronger one**, in the theme's own
  `colors.sentence` and `colors.word` tokens (F§10.4) — the same two tokens the web reader paints with, so the
  two platforms agree.
- [DESIGN] **Tap target is the sentence, never the word.** Every sentence is one pressable run in its block,
  and the whole document is one run per sentence rather than one element per word; only the active block is
  further split, into the highlight runs of §3. This is the contract's first Forbidden Action made structural:
  a block's element count is proportional to its sentence count, and words never become elements.
- [DESIGN] **Skipped blocks are dimmed, not hidden** (F§5.4): furniture stays visible at 55 % opacity so a
  reader can see what is being passed over, while the player skips it. The web reader instead drops hidden
  furniture from its list; the contract asks for dimming here.
- [DESIGN] **Auto-follow with a manual-scroll override** (contract, and the web reader's own rule): the list
  follows the active block unless the reader dragged it within the last 4 s. Row offsets are measured through
  `onLayout` and the list is scrolled with `scrollToOffset`, not `scrollToIndex`, because a variable-height
  list cannot scroll to an index outside its render window.
- [DESIGN] **A document the library does not hold** renders a not-found state rather than an empty reader, and
  a hub that is not configured is reported through the bar's error line with its retry button (F§5.7's `error`
  state) instead of a silent no-op: `createClient()` refuses, and that refusal becomes the chunk source's own
  refusal, so the reader sees the sentence they can act on.

## 7. Deviation proposals

None acted on. Two notes for the ledger, neither requiring a contract change:

1. F§10.4's reader paragraph ("updates are throttled to 20 Hz") and this contract's Forbidden Action ("Do not
   update highlight state more often than 20 times per second") are the same number, and the implementation
   samples at 50 ms — exactly 20 Hz. No deviation.
2. The contract asks for skipped blocks to be *dimmed* while F§10.1's web reader drops them from its list. The
   Android reader follows the contract; the difference is recorded here so a later reader unit does not read
   it as an inconsistency.
3. **F§5.1's two offset kinds are not the same kind.** A sentence's `charStart`/`charEnd` are offsets into
   `Block.text`, but a word's are offsets into its `Sentence.text` — `packages/core/src/tokenizer.ts` says so in
   its own doc comment, and `packages/ui-web/src/highlight/locate.ts` composes them as
   `sentence.charStart + word.charStart`. `highlight-model.ts` does the same, and its tests assert the composed
   result against the model's own word text, so a later unit that assumes both are block-relative will fail
   there rather than in the reader.
4. The player bar's two F§5.6(f) numbers are resampled every 500 ms while audio is moving, not on the highlight's
   20 Hz clock: the cap F§5.6(d) and this contract's Forbidden Action set is about *highlight* updates, and the
   bar is not the highlight. The sentence-level position that drives the text is still published per change.
   Recorded so the 2 Hz is not read as an oversight.
