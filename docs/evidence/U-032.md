## 3. Architecture notes

Inspection is unavailable, so nothing here is a claim about the reference product. What the contract and F§10.2
establish about *Lectern's* extension is a design, and it is recorded as such:

- Four contexts, four responsibilities (F§10.2): a **background service worker** that routes messages, owns the
  context menu and the manifest's keyboard commands, creates the offscreen document and tracks the active
  reading tab; an **offscreen document** (`AUDIO_PLAYBACK`) that alone plays audio and calls the hub — it hosts
  the player controller, the audio sink, the api-client and the IndexedDB blob cache; a **content script** that
  builds a `TextMap` of the page's readable text, converts it to a `DocumentModel`, draws the two highlights and
  mounts the floating widget in an open shadow root; and the **popup**, which is the connection form.
- Manifest V3 fixes the shape of the declarations this unit writes: one service worker entry, an `action` with a
  popup document, a `permissions` list, `optional_host_permissions` for the hub origin, and a `commands` map
  whose values are suggested key bindings. MV3 service workers are terminated when idle, which is why F§10.2
  puts long-lived playback in an offscreen document rather than in the worker.
- The message protocol is Lectern's own (F§10.2, F§11). Every message is a discriminated union on `type`, so a
  handler is a lookup by that key and a message from a page or another extension cannot reach a handler by
  accident; every reply is `{ ok: true, data? }` or `{ ok: false, code, message }`, so a refusal is data and not
  a thrown error crossing a boundary.
- Keyboard commands are declarative in MV3: the manifest declares the bindings and Chrome delivers a key event,
  so the extension needs no key listener of its own.

## 4. Lectern design

- [DESIGN] `apps/extension/wxt.config.ts` declares exactly the manifest the contract lists — name `Lectern`, one
  original line of description, `permissions: ['activeTab', 'scripting', 'storage', 'offscreen', 'contextMenus']`,
  `optional_host_permissions: ['http://*/*', 'https://*/*']`, no static `host_permissions`, and four `commands`
  (`toggle-play` `Alt+Shift+P`, `read-page` `Alt+Shift+R`, `next-sentence` `Alt+Shift+Right`,
  `previous-sentence` `Alt+Shift+Left`) — because the hub origin is requested at run time (F§10.2, F§11).
- [DESIGN] Message handlers and startup features live in two registries (`background/handlers.ts`,
  `background/features.ts`) and `background.ts` only installs the router and runs the features, so a later unit
  adds a handler by appending one entry instead of editing the entry point (the contract's *Forbidden Actions*).
- [DESIGN] Settings live in `chrome.storage.local` under one key, validated field by field at every read, because
  a stored record can be edited by hand or written by an older version — the same boundary rule the web app
  applies to `localStorage` (F§10.1).
- [DESIGN] The extension's own vocabulary is Lectern's: the protocol types, the settings fields the contract
  names, and a description written for this project. No reference-product wording, identifier or key order is
  carried over.
