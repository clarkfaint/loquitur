## 3. Architecture notes

**One bus, two transports, and the shell holds both ends (F§10.1, F§10.3).** The reader's page *hosts* the
player: it publishes a snapshot whenever the player changes and runs every command a remote sends it. A
mini-player window or a second tab is a *remote*: it paints the snapshots it receives and answers with
commands. F§10.1 gives the bus two transports — a `BroadcastChannel` between tabs of one browser, and F§10.3's
bridge, one channel per direction, when `window.lecternDesktop` is present.

Measured on this host, in the shell the built application really is:

- the reader's page **has** the bridge (U-038's own suite asserts it), so the host publishes over the bridge and
  never on the channel;
- two windows of the shell **do** share a `BroadcastChannel` — a message posted in the main window's page was
  received in the mini window's page, the two being the same origin and the same storage partition;
- the shipped mini page **listens only on the channel**: `apps/web/src/mini/MiniPage.tsx` (U-029, frozen) builds
  its bus over `createBroadcastChannelTransport` unconditionally, while `apps/web/src/reader/use-player.ts`
  prefers the bridge when the bridge exists. Measured consequence, before any deliverable existed: a second
  window loading `#/mini` while the main window was playing showed "No document is open in a reader tab yet." —
  two ends of one bus, speaking different transports, with neither hearing the other.

That is the one join this unit has to make, and the shell is the only place both transports exist.

**One relay owns the player's two channels.** The shell answers the renderer on two player channels: the host
publishes its state on one and a remote sends commands on the other (F§10.3). A second handler on a channel
`ipcMain` already answers is refused, and there is no side-channel to listen on: measured, `webContents.on`
`("ipc-message")` recorded **nothing** while the reader published once a second, because the renderer reaches
the main process with `invoke` and only a handler sees an `invoke`. A channel therefore changes hands
explicitly — `removeHandler` and then `handle` — which is what the relay does before it answers either one, and
why the published state can go to three places (the main window's own echo, the mini-player, the tray) from one
place instead of two.

**The mini-player is a strip, not a window (F§10.3).** Frameless, a fixed 360×72 of content, always on top,
skipped in the task list, not resizable, and *shown inactive*: the last of those is what makes an
always-on-top window bearable, because bringing it up never takes the operator's typing away from the
application they are in. It loads the app's own build at `#/mini` — the same `index.html` the main window loads
— so the repository keeps one reader UI rather than two, and the page is a remote: it holds no document, no
player and no audio.

**State that a late remote cannot have.** F§10.1 defines no handshake, so a window that opens in the middle of a
reading has missed every change so far. Two things cover that: the relay keeps the last snapshot and hands it
over the moment a mini window's page is ready, and the host republishes its state once a second regardless of
whether it is playing (U-029's own beat), so a window that opens while the reading is paused is still told
where it is. Measured: a mini window's bridge recorded the sentence indexes `[0,1,1,1,1]` over about four
seconds, and the relay's own hand-over arrived before the first of them.

**Where the strip sits is remembered, and clamped (F§10.3).** The record keeps a position (`miniBounds`) and
never a size, because the size is fixed. Measured: the window opens at the primary work area's bottom-right
corner, a 24 px margin in from the edge (896,928 on this host's 1280×1024 display); `move` fires both when the
window is created and after `setBounds` (Linux emits no one-shot `moved` event, so a drag would otherwise have
to be polled), and the position is written once the window has held still for a moment.

**The tray is the shell's way back in (F§10.3).** Closing the app's window *hides* it, because playback is
supposed to outlive the window, so the tray — not the window's close button — is where the operator says they
are finished. Its menu has five entries and two labels that follow the shell's own state: Play or Pause from the
state the host published, and Show or Hide mini-player from whether the strip is up. Measured under `xvfb-run`
on this host: a `Tray` can be created from `resources/icons/32.png` (U-038's icon) and given a built menu, and
the five entries are `Play`, `Next sentence`, `Show Lectern`, `Show mini-player`, `Quit` with separators between
the three groups.

## 4. Lectern design

- [DESIGN] **The relay takes over both player channels** (`player:player-publish`, `player:player-send`) rather
  than adding a second path beside `context.ts`'s, and keeps the echo to the main window that U-038's own suite
  asserts. One module then owns the whole of the player's traffic, which is what the contract's relay
  description requires and what the tray's label needs (F§10.3).
- [DESIGN] **A page-side adapter joins F§10.1's two transports in the mini window.** F§10.1 says the bus uses
  the bridge when `window.lecternDesktop` exists; the frozen mini page uses the channel. Rather than leave the
  strip unable to hear the reading, the relay installs a small script into that window (once per load) which
  re-posts the bridge's snapshots onto the page's channel and forwards the page's commands back over the
  bridge. It holds no state and makes no decision, so the strip still has no player of its own (F§10.3's rule
  that all audio stays in the main window). §7 files the underlying wording.
- [DESIGN] **`showMain` hides the mini-player.** The reader's own window is then in front with the whole player
  bar in it, and the strip exists to stand in for that window. F§10.3 names both actions as the mini-player
  feature's, and this is the only thing the second one can usefully mean.
- [DESIGN] **The tray's entries raise actions instead of acting.** A tray click raises `togglePlay`,
  `nextSentence`, `showMain` or `toggleMini` on the one action bus (F§10.3), so a tray entry, a hotkey and the
  bridge's own `windows` members are the same trigger; only Quit is the tray's own, and it calls `app.quit()`.
- [DESIGN] **`faster` and `slower` step by a tenth from the published rate**, clamped to F§5.6(e)'s 0.5–5.0
  (`clampRate` from `@lectern/core`), and the step is rounded onto a tenth because the rate it is compared
  against is one. The rate comes from the last snapshot rather than from a number kept in the relay, so a
  shortcut pressed at 5× cannot walk past the end of the range.
- [DESIGN] **The menu is rebuilt only when a label would change.** The state arrives on every published
  snapshot (once a second while a document is being read), and replacing the menu of a tray the operator is
  looking at every second is not something to do.

## 7. Deviation proposals

1. **F§10.1's transport sentence is not what the mini page implements.** F§10.1 says the bus publishes "over
   `BroadcastChannel('lectern-player')`, or over the desktop bridge when `window.lecternDesktop` exists", and
   `apps/web/src/reader/use-player.ts` follows that exactly — but `apps/web/src/mini/MiniPage.tsx` (U-029) builds
   its bus over the channel unconditionally, so inside the shell the two ends of one bus never meet (measured,
   §3). `apps/web/src/mini/MiniPage.tsx` is a frozen file this contract does not list under `Patch scope`, so
   the shell joins the two transports itself, in the one place both exist (§4). Proposed: either a patch unit
   that makes the mini page prefer the bridge the way the reader does — which would retire the adapter — or a
   contract for this unit that names `apps/web/src/mini/MiniPage.tsx` in its patch scope.
2. **With no hub configured, the strip's page is the settings screen.** The mini window loads the app's own
   `#/mini`, and the frozen `App.tsx` redirects every route to `#/settings` while no connection is saved, so a
   strip opened before the app has been pointed at a hub shows the settings screen in a 360×72 window. Nothing
   is being read in that state, so nothing is wrong with the *reading*; the window is simply showing a page
   that has nothing to mirror. Proposed: exempt the `#/mini` route from that redirect in a patched contract, or
   accept it as the app's own rule.
3. **`showMain` means "hide the strip" here.** F§10.3 lists the action among the mini-player's, and does not say
   what it does to a window that is not the main one. Recorded as a design decision (§4) rather than a claim
   about the reference product; a contract that wants the strip to stay up while the main window is raised
   should say so.
