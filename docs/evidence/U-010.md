## 3. Architecture notes

**Two halves, split by what a platform can run.** F§5.5's `OcrEngine` interface and the grouping rule are
isomorphic: they name no library, no file and no `node:` module, so Android (which runs ML Kit on-device, F§10.4)
uses the same grouping rule as the hub. Everything that touches a library — tesseract.js, `@napi-rs/canvas`,
pdfjs's renderer — sits under `@lectern/core/parsers`, where `scripts/check-isomorphic.mjs` cannot reach it from
the isomorphic entry. The contract makes this a *Forbidden Action* ("Do not place `OcrEngine` or `groupOcrLines`
under `src/parsers/`"), and the guard measures it: the isomorphic walk is 12 modules and clean (section 2).

**The pipeline, end to end.** An image goes in as bytes; the engine decodes it itself (tesseract.js writes the
bytes into its own WASM filesystem and lets Leptonica sniff the format, so no image decoder is needed on the Node
side) and answers with lines; `groupOcrLines` drops the uncertain ones, orders the rest and joins them into
paragraphs. A PDF page whose text layer carries fewer than 20 characters is rasterized at 200 DPI — pdfjs draws
it onto an `@napi-rs/canvas` context — and then goes down the same route. That page's blocks carry `page` and no
anchor, because a scan has no text item to point one at (F§5.5).

**The paragraph rule, as arithmetic.** F§5.5 says "lines are grouped into paragraphs by a vertical gap > 1.5× the
median line height", which is two measurements that both have to be pinned: the *gap* is the whitespace between
one line's box and the next (previous `bbox[3]` to next `bbox[1]`), and the *line height* is the median of the
boxes' own heights, taken over the lines that survived the confidence filter. On `text.pdf` at 200 DPI that is
47–48 px of ordinary leading against a 54 px threshold and 55–238 px at a paragraph start — the rule reads that
page as eight blocks. On the tighter canvas render of `page.png` the same arithmetic gives 14 px of ordinary
leading against a 39 px threshold, with the fixture's own block break at 34 px — below the threshold, so that page
comes out as two blocks rather than five (section 2, section 7).

**One worker, per language, created once.** `createWorker` is async and has to be awaited, so a synchronous
factory cannot return one; the promise is memoized instead, keyed by language, and a creation that fails is
forgotten so the next call retries. Nothing in the engine is shared mutable state beyond that map, and `dispose`
terminates every worker it created.

**What the fallback must not do.** The contract's *Forbidden Actions* are all about reach: no run-time language
download (so `langPath` is a filesystem path — tesseract.js fetches only URL-shaped values), no cloud OCR (the
only engine is the local one), and no image pre-processing library (`@napi-rs/canvas` is the rasterizer the
contract names, and no filter is applied to the pixels). The page-level decision is on the *text layer*: a page
with a usable one is never rasterized, which keeps the ordinary PDF path — U-007's — exactly as it was.

## 4. Lectern design

- [DESIGN] `packages/core/src/ocr.ts` holds F§5.5's `OcrEngine` interface, the two numbers the spec writes into
  prose (`OCR_MIN_CONFIDENCE = 40`, `OCR_PARAGRAPH_GAP = 1.5`), the hub's OCR language (`OCR_LANG = "eng"`) and
  `groupOcrLines(lines: readonly OcrLine[]): RawBlock[]`. It imports **only a type** from `./builder`, so the
  isomorphic entry can export it (the contract's forbidden action, and F§5.4's "Android builds the document
  locally with `buildDocument`").
- [DESIGN] `OcrLine` and `OcrResult` are exported names for the shapes F§5.5 writes inline inside the interface
  (`{ text, bbox: [number, number, number, number], confidence }` and `{ lines }`), so `groupOcrLines`' parameter
  and the engine's answer have names without the interface being altered: `OcrEngine` is F§5.5's declaration
  verbatim, `id: string` and `recognize(image, opts: { lang: string })` included.
- [DESIGN] `groupOcrLines` drops a line whose `confidence < 40`, drops a line whose text is blank once its
  newlines are flattened, orders what is left by `bbox[1]` then `bbox[0]`, takes the median box height **of the
  surviving lines** (so a dropped line cannot move the threshold) and starts a new block when the whitespace to
  the previous line is strictly greater than `1.5 ×` that median. Every block is `{ kind: "paragraph", text }`:
  F§5.5 says nothing about recognising headings in a scan, so none is guessed at, and the lines of one paragraph
  are joined with a single space, since OCR text arrives with the engine's own newlines.
- [DESIGN] `groupOcrLines` takes one argument, as the contract writes it, so it cannot stamp a page number. The
  scanned-PDF path adds `page` to the blocks it gets back (`{ ...rawBlock, page }`), which is where F§5.1's
  `Block.page` is known; the image path leaves it off, because an image has no page number.
- [DESIGN] `packages/core/src/parsers/ocr-tesseract.ts` exports `createTesseractOcrEngine(opts?: { cacheDir?:
  string }): TesseractOcrEngine` where `TesseractOcrEngine extends OcrEngine` with `dispose(): Promise<void>` —
  the contract's signature, and the extra member it asks for. `id` is `"tesseract"` (F§5.5 names the adapter
  `TesseractOcrEngine`), the worker is created on the first `recognize` for a language and reused for every later
  call with it, and `dispose` terminates all of them; the engine stays usable afterwards and would create new
  ones rather than holding a disposed flag.
- [DESIGN] The language data is located with `new URL("4.0.0", import.meta.resolve("@tesseract.js-data/eng"))`
  — the platform's own resolver, so the path is right wherever the workspace is installed — and passed as
  `langPath`, which is the offline form tesseract.js's Node worker reads with `fs`. `4.0.0` is the directory the
  data package's own manifest names, and it is the full (LSTM + legacy) data the LSTM-only worker initialises
  from.
- [DESIGN] `cacheMethod` is `"write"` with `cachePath: opts.cacheDir` when the caller gives one (F§5.5's "language
  data cached under the data directory", which `LECTERN_DATA_DIR` is), and `"none"` with no `cachePath` when it
  does not — because tesseract.js otherwise defaults the cache to the process's **current directory** and would
  write `./eng.traineddata` beside whatever the caller was doing (section 2).
- [DESIGN] An `errorHandler` is passed to `createWorker` that ignores the message, because tesseract.js otherwise
  throws a rejected job out of its own message listener; the promise the caller awaits rejects with the same
  message, so nothing is swallowed — the failure just arrives where it can be caught (section 2).
- [DESIGN] The engine's answer is validated with zod before any of it is read: a schema over
  `data.blocks[].paragraphs[].lines[].{text,confidence,bbox}`, which strips everything else tesseract.js returns
  (symbols, choices, fonts, row attributes, TSV, HOCR) and turns `blocks: null` into no lines. A failure raises an
  exported `OcrEngineError` with `code: "OCR_RESPONSE_INVALID"`, mirroring U-008's and U-009's error classes, so
  the hub can branch on a code rather than on a message. `blocks` is `any` in tesseract.js's own declarations,
  which is exactly the case F§7's zod rule is for.
- [DESIGN] `packages/core/src/parsers/pdf-raster.ts` exports `rasterizePdfPage(bytes: Uint8Array, pageNumber:
  number, dpi: number): Promise<Uint8Array>` — the contract's signature. It copies the caller's bytes (pdfjs
  transfers the buffer it is given), opens the document for that one page, scales by `dpi / 72`, renders with
  `{ canvas: null, canvasContext, viewport }` and returns `canvas.toBuffer("image/png")`. One documented
  `as unknown as CanvasRenderingContext2D` bridge sits at that boundary, the same kind of single bridge U-006/U-008
  use for linkedom's parallel DOM; the page is cleaned up in a `finally` and the document destroyed in another.
- [DESIGN] `packages/core/src/parsers/image.ts` exports `parseImage(bytes: Uint8Array, ocr: OcrEngine):
  Promise<ParsedImage>` returning `{ rawBlocks, title }` (the contract's signature): bytes to
  `ocr.recognize(bytes, { lang: OCR_LANG })`, lines to `groupOcrLines`, and the title is the first block's text
  cut to **60** characters — the length `buildDocument`'s own title fallback uses (F§5.1), so an OCR'd document
  has a name without the parser inventing a rule of its own. The engine is always the caller's; the parser never
  creates one.
- [DESIGN] `packages/core/src/parsers/pdf.ts` gains exactly what the contract's patch note lists: an optional
  `ocr?: OcrEngine` on `ParsePdfOptions`, F§5.5's threshold as `OCR_MIN_CHARACTERS = 20` and its resolution as
  `OCR_RASTER_DPI = 200`, and one `ocrBlocks(...)` step per page that rasterizes only a page whose text layer
  carries fewer than 20 characters and only when an engine was supplied. Those blocks are `paragraph`s carrying
  the page and **no locations**, so `anchorsFor` produces nothing for them (F§5.5's "OCR'd pages carry no
  `PdfAnchor`"), and a scan read without an engine yields no blocks rather than an error. The U-007 tests for a
  text-layer page are untouched, and the module's header comment was corrected where it claimed no page is ever
  rendered.
- [DESIGN] `packages/core/src/index.ts` gains `export * from "./ocr";` and `packages/core/src/parsers/index.ts`
  gains the three new parser lines — §5's append-only rule for a barrel, with each line inserted where the

### What the rehearsal changed, and what it did not

The fixed command passed on its first run in the repository, and all twenty delivered tests passed on their first
run in the rehearsal — the two rehearsal failures that preceded the delivered files were both **this unit's own
test expectations**, not the code (a synthetic line 40 px below its neighbour is 20 px of whitespace away at a
30 px threshold and does not split; and `page.png`'s title is the first 60 characters of its first block, because
the heading and the first body line come back as one paragraph). Four of this unit's decisions were nevertheless
made by measurement rather than by assumption, and each would have failed **silently** — as wrong text rather than
as an error — if it had been guessed:

1. **What has to be asked of `recognize`.** With no `output` argument, `data.blocks` is `null` and there is no
   `lines` member, so an adapter that trusted the interface's name would have read zero lines from every image
   while looking correct. `{ blocks: true }` is what returns the geometry (section 2, measured twice: once bare
   and once with the flag).
2. **Where the language data comes from.** `langPath`'s default reaches a CDN, and `cachePath`'s default is the
   process's current directory — the first would have been a forbidden run-time download, the second a
   `.traineddata` file written beside the caller's working directory. Both were found by reading the installed
   worker script before the delivered file existed.
3. **How the data package must be reached.** Importing it is `error TS7016` (no declarations), so a delivered
   import would have failed the type-check step of the fixed command; `import.meta.resolve` is the form that
   compiles and needs no `@types/node`.
4. **What the OCR geometry means.** The paragraph rule's two readings differ on the fixtures (section 7's first
   proposal), so the delivered rule and the delivered tests were designed from measured boxes — 13 of them on
   `page.png`, 20 on `text.pdf` at 200 DPI — rather than from the spec's prose alone.

## 7. Deviation proposals

- [DESIGN → contract] **F§5.5's paragraph rule names two measurements and pins neither.** "A vertical gap > 1.5×
  the median line height" is unambiguous once the gap is the whitespace between two lines' boxes and the height
  is the median of those boxes — the reading U-007 already had to choose for F§5.4's PDF rule — but it can also be
  read as a distance between tops. The two readings differ in outcome: measured on `text.pdf` at 200 DPI, the
  whitespace reading separates ordinary leading (47–48 px) from paragraph starts (55–238 px) at a 54 px
  threshold, which is eight blocks for that page; on the tighter 1240×1754 `page.png` the same reading puts the
  fixture's own block break (34 px) *below* the threshold (39 px), so the scanned page comes out as one block
  plus the following one rather than five. Proposal: state the measure in F§5.5 (whitespace between boxes, median
  box height over the lines above the floor), so a later adapter or the Android path does not choose the other
  one.
- [DESIGN → contract] **`parseImage(bytes, ocr)` has no language, but `OcrEngine.recognize` requires one.** The
  contract fixes both signatures, so the language of an image or a scanned page can only be a constant; this unit
  makes it `OCR_LANG = "eng"` in `src/ocr.ts`, matching the only language data the hub installs. Proposal: name
  the hub's OCR language as an operator setting (F§7.1's environment block has `LECTERN_DATA_DIR` for the cached
  data but no language), or add a third parameter to `parseImage` in a patched contract — a hub serving a second
  language would otherwise have to edit F§5.5's adapter.
- [DESIGN → contract] **"One reusable worker" and multiple languages pull in opposite directions.** tesseract.js
  binds the language at worker creation and loading 10.9 MB of traineddata costs ~0.4 s, so an engine that
  terminated and re-created one worker per language change would pay that on every switch. This unit keeps one
  memoized worker **per language** and reuses each; `dispose` ends all of them. Proposal: say "one worker per
  language, reused" in F§5.5 so the contract and the code agree on what is cached.
- [DESIGN → contract] **An image parser has no title rule in the spec.** The contract requires a `title` from
  `parseImage`, and F§5.5 does not say where a scan's title comes from. This unit uses the first block's text cut
  to 60 characters — F§5.1's own fallback length, so `buildDocument` would have produced the same string had the
  parser declared no title at all — which makes the value a name for the library rather than a new rule. Proposal:
  state it (or state `""`), because the two differ for a caller that lists titles before parsing.
- [DESIGN → contract] **The scanned-PDF fallback re-opens the document it was just read from.**
  `rasterizePdfPage(bytes, pageNumber, dpi)` is fixed by the contract, so the page must be found again from the
  bytes: reading a 2-page scan costs an extra `getDocument` per OCR'd page (measured: 96–120 ms per page). A
  variant that took the already-open page (or that rasterized inside `parsePdf`) would halve the work on a long
  scan. Proposal: leave the signature for the camera path's sake but name the cost, or allow an internal
  `page`-taking form in a patched contract.
- [DESIGN → contract] **`@tesseract.js-data/eng` ships data with no declarations, and F§2.3's ledger does not list
  it at all.** The package is only resolvable as a path (`error TS7016` on any import), which is what makes
  `import.meta.resolve` the right tool here; its `index.js` also documents which directory the traineddata is in.
  Proposal: add the data package to F§2.3 with its version and a note that it is resolved, never imported, so the
  next unit that needs language data does not try to import it.
- [DESIGN → contract] **pnpm 12.18.0 refuses an install that ignores a dependency's build script, and refuses
  again on every later command.** The three installs succeed but `pnpm add` exits 1 with
  `ERR_PNPM_IGNORED_BUILDS` (tesseract.js's only script is an OpenCollective donation banner), so this unit
  passes `--config.strictDepBuilds=false` on the invocation — a per-run flag that writes no file. The same policy
  then appears *inside* the fixed command's output: pnpm's pre-script dependency check runs an install first, that
  install fails on the same ignored script, and the run prints
  `Error: ERR_PNPM_IGNORED_BUILDS` / `[WARN] The install that runs before scripts failed, so your node_modules may
  be out of sync with your lockfile. Set "verifyDepsBeforeRun": false to skip this install.` before the tests
  start (which still exit 0, against a `node_modules` that is in sync). Together with the `minimumReleaseAge` flag
  U-005/U-006/U-009 recorded, that is now four per-invocation or per-command facts a unit has to know about.
  Proposal: settle both policies once in the workspace (pnpm-workspace.yaml, which the operator has already added
  to the scope guard's always-allowed set) — `onlyBuiltDependencies` for the donation postinstall and
  `verifyDepsBeforeRun: false`, or a relaxed `minimumReleaseAge` — and state them in F§2.3's lineage, so each
  install and each verification run does not re-derive them.
