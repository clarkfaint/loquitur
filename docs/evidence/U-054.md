## 3. Architecture notes

The whole unit is one package's contract surface: three files of zod schemas plus their test. The design
questions the contract leaves open, and how they are settled:

**The change feed's first message.** F§8.3 writes the client's first frame as
`{ "type": "auth", "token": "…" }`, and U-057 authenticates the socket from it (a socket has no header).
The contract's *Forbidden Actions* say "Do not put the token in any schema", and F§11 keeps the token
opaque. The two are reconciled by validating the auth **envelope** loosely — `type` is pinned, nothing else
is declared — so the credential travels in the same message without any schema in this package naming it.
The `pong` answer stays strict and empty, and the hub's three messages (`ready`, `changed`, `ping`) carry
no record, no document and no token at all.

**The result schema is a function of the mode.** F§9 gives `brief` and `detailed` different validation
ceilings (≤ 1 200 characters / 3–6 takeaways against ≤ 4 000 / 6–12) and says the schema is deliberately
looser than the prompt. One shape cannot express both, and the mode is not a field of the result — F§8.4
keeps it in the `summaries` table's own column — so `SummaryResultSchema(mode)` builds the one schema the
caller's mode needs, and `AnySummaryResultSchema` is the union a *stored* status needs, because a status
does not carry the mode either.

**The two new code sets, and the shared envelope.** `SyncErrorCode` and `AiErrorCode` name failures the
thirteen codes in `common.ts` have no entry for, so each is a closed enum of its own. `SyncErrorSchema` and
`SummaryErrorSchema` are `ErrorBodySchema.shape.error.extend({ code })` — F§7.2's own `{ code, message }`
object with the new code set — so a phase-5 route can answer one of these codes and still hand a client a
shape it already parses. `common.ts` itself is U-018's frozen file and was not touched.

**Two limits, one source.** F§7.1's `LECTERN_MAX_UPLOAD_MB` default (100 MiB) is the only upload ceiling
the architecture states, so both the model and the original ceiling are that value in bytes, named
separately because U-056 enforces them on two different routes.

## 4. Lectern design

- [DESIGN] `PushRequestSchema` carries `{ deviceId, ops }` with `ops` 1–200 (F§8.2) and `deviceId` an
  opaque `z.string().min(1)` — no account, registration or permission field exists anywhere in it (F§5.9's
  LWW tie-break is the only use of a device id).
- [DESIGN] `PushResponseSchema` is `{ accepted: string[], rev }`; `accepted` lists every `opId` in the
  request, because F§8.2 returns the losers too, and `rev` is the change log's new position.
- [DESIGN] `PullQuerySchema` is `{ since, limit }` with `since` a non-negative integer and `limit` 1–500
  defaulting to 500 (F§8.2's page size); `PullResponseSchema` is `{ changes, nextRev, more }` over
  `@lectern/core`'s `OpSchema`, so a pulled op is one a store can `applyRemote` without translation.
- [DESIGN] Sync is record-level LWW and nothing else: no CRDT, vector clock or operational-transform
  structure appears in any shape (F§5.9), and the only ordering value on the wire is the change log's `rev`.
- [DESIGN] `WsClientMessageSchema` is `auth | pong` and `WsServerMessageSchema` is `ready | changed |
  ping`, both as `z.discriminatedUnion("type", …)` so runtime validation and the compile-time union cannot
  drift (F§8.3).
- [DESIGN] `DocIdParamSchema` is `^[0-9a-f]{32}$` — F§5.2's identifier, pinned as a whole-string pattern
  because the value becomes a path component under `{DATA_DIR}/library/` (F§8.4) and an upper-case or
  climbing value must be refused before a path is built.
- [DESIGN] `SummaryRequestSchema` is `{ docId, mode, document? }`, the optional model being F§5.1's own
  `DocumentModelSchema` imported from `@lectern/core` — F§7.2 stores an inline document as that document's
  model so a summary works without sync.
- [DESIGN] `SummaryStatusSchema` is `{ status, result?, error? }` with `status` the four F§9 states, the
  result validated by the mode-agnostic union, and the error by F§9's code set; a restart's `INTERRUPTED`
  is therefore expressible as data rather than as a sentence.
- [DESIGN] `SummaryModeSchema` is `brief | detailed`, and `SUMMARY_LIMITS` publishes F§9's per-mode ceilings
  as data so the hub, the tests and the prompt builder read one table.

## 7. Deviation proposals

1. **F§8.3's auth message and "Do not put the token in any schema".** F§8.3's first frame is
   `{ "type": "auth", "token": "…" }`; this unit's *Forbidden Actions* forbid modelling the token. The
   delivered `WsClientMessageSchema` therefore pins `type: "auth"` and validates the envelope loosely, so
   the credential rides in the message without appearing in any schema (F§11 keeps it opaque). If the
   operator intends the token to be a *declared* field of that one envelope — `token: z.string().min(1)` —
   a patched contract can say so and this file changes by two lines.
2. **`SummaryResultSchema` is a builder.** F§9 gives the two modes different ceilings and the mode is not
   part of the result, so the named export is `SummaryResultSchema(mode)` rather than a single const; the
   mode-agnostic union a stored status needs is exported beside it as `AnySummaryResultSchema`. A patched
   contract that prefers one const could name the mode field instead.
3. **`PullQuerySchema` carries numbers.** A query string delivers strings; a route converts `since` and
   `limit` before parsing, as it must for any typed query shape. Nothing in this unit coerces implicitly.
4. **The two upload ceilings are one number.** The contract asks for "size limits for model and original
   uploads" without values; F§7.1 states exactly one (`LECTERN_MAX_UPLOAD_MB`, default 100), so both named
   constants carry that default and a hub with a different configured value enforces its own.
