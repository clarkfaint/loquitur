## 3. Architecture notes

**The document model (`src/model.ts`).** F§5.1 is a closed set of nine names: two string unions
(`SourceKind`, `BlockKind`), six object shapes (`DocumentModel`, its inline `source`, `Block`,
`Sentence`, `Word`, `Position`, `PdfAnchor`), and two version literals (`schemaVersion: 1`,
`tokenizerVersion: 1`). The contract fixes the direction of definition: the zod schema is primary and
each TypeScript type is `z.infer` of it, so schema and type cannot drift. Five fields are optional —
`source.uri`, `source.mime`, `source.pageCount`, `Block.level` (restricted to 1–6) and `Block.page`.
The nesting is one-way: a document owns blocks, a block owns sentences, a sentence owns words, and
`Sentence.index` is a *global* index while `charStart`/`charEnd` are offsets into the **owning**
`Block.text` for sentences and into `Sentence.text` for words. Ordering fields (`index`, `blockIndex`)
are consequently redundant with position, and the model keeps them because F§5.1 declares them.

**The eight normalization steps (F§5.2).** The sequence is a pipeline whose order is load-bearing in two
places: line endings must be unified *before* per-line work, and whitespace inside lines must be
collapsed *before* lines are trimmed (otherwise a tab-only line would survive as a space). The
pipeline ends with a whole-string trim, so the fixed point of the function is a string that has no
leading or trailing whitespace, no run of two spaces or tabs, no run of three newlines, and no
`U+00A0`/`U+00AD`. Idempotence is a property of that shape rather than of the code: a second pass meets
a string in which every step is already satisfied, so it returns its input unchanged.

**Identifiers (F§5.2).** `docId` is the first 32 hex characters of the SHA-256 of the block texts joined
by a single `\n`, encoded UTF-8. Three consequences worth recording: the separator is part of the
input, so a block whose text ends in `\n` hashes differently from two blocks; the id is derived from
*normalized* text only indirectly (the caller passes `Block.text`, which F§5.1 defines as normalized);
and truncation is a prefix, not a re-hash, so the id is stable under any future change of digest
length only if that change were itself a format change.

**SHA-256 without a crypto library.** The algorithm is a fixed 64-round compression function over
64-byte blocks. The parts that a hand-written version must get exactly right are (a) the message
schedule `w[0..63]` — the first 16 words are the block's big-endian 32-bit words, the rest follow the
standard `σ0`/`σ1` recurrence; (b) the padding, `0x80` then zeros then the 64-bit big-endian bit
length, so the padded length is the next multiple of 64 of `length + 9`; (c) the eight working
variables and the two feeds `T1 = h + Σ1(e) + Ch(e,f,g) + K[i] + w[i]` and `T2 = Σ0(a) + Maj(a,b,c)`;
and (d) the output as the eight state words added into the previous state and written as 32 big-endian
hex characters each. All arithmetic is additions, XORs, bitwise AND/OR and rotates, so no operation
can exceed 2^35 — safe inside a double, and each step is reduced with `>>> 0`. Byte handling is the
one place where a JavaScript implementation can be silently wrong: text must be UTF-8 encoded with
surrogate pairs combined into a 4-byte sequence (and lone surrogates replaced, matching every other
encoder on this platform), and every 32-bit word must be read big-endian.

## 4. Lectern design

- [DESIGN] Every object schema is `z.strictObject`, so a document carrying a field F§5.1 does not declare is rejected rather than silently stripped. F§7 requires validating every external input and §6 keeps no room for a payload that grew fields somewhere upstream; the model is persisted and re-read, so an unrecognized key is a corruption signal, not forward compatibility — follows F§7 and F§5.1.
- [DESIGN] The five optional fields use `z.exactOptional()`, not `.optional()`. Under this repository's `exactOptionalPropertyTypes: true`, F§5.1's `uri?: string` means *absent or a string*, never *present and undefined*; `exactOptional()` infers exactly that, while `.optional()` would infer `string | undefined` and quietly widen five fields the contract forbids changing — follows F§5.1 and AGENTS.md §7 (installed types are the truth, R9).
- [DESIGN] Indices, offsets and counts are `z.int().nonnegative()`; `Block.level` is a union of the six literals `1..6` that F§5.1 names. Fractional or negative positions are unrepresentable in the model, and the level restriction is stated verbatim in F§5.1 — follows F§5.1.
- [DESIGN] `docId`, `title` and `lang` stay plain `z.string()`, and no length or hex-pattern refinement is added. F§5.1 types them as `string`; inventing a stricter shape would let the schema reject a value the contract's own type permits, and `docId`'s 32-character hex form is already pinned by F§5.2 and asserted in the id tests — follows F§5.1.
- [DESIGN] The two string unions are `z.enum([...])` of exactly the F§5.1 members, so `SourceKind` and `BlockKind` are the schema's inferred types and cannot list a member the contract does not.
- [DESIGN] `sha256Hex` is a synchronous, dependency-free TypeScript implementation (message schedule, compression, hex output) with its own UTF-8 encoder, and it accepts `string | Uint8Array`. The contract forbids `node:crypto`, `crypto.subtle` and hashing packages; the string path must therefore encode UTF-8 itself, and the encoder is written rather than taken from `TextEncoder` so that the module needs no global that a runtime might not provide — follows the contract's forbidden actions and AGENTS.md R8 (local, isomorphic core).
- [DESIGN] Every numeric read on bytes is a `DataView.getUint32(offset, littleEndian)` call rather than an array index. `noUncheckedIndexedAccess` types a variable index as `number | undefined`, and an algorithm that must read words at computed offsets cannot afford either a cast or a fallback that could hide a bug — measured in section 2.
- [DESIGN] `docIdFor(blockTexts)` joins with `"\n"` and truncates `sha256Hex` to 32 characters, staying a thin composition of the two functions F§5.2 defines, so the formula exists in exactly one place.
- [DESIGN] `normalizeText` is a direct transcription of the eight F§5.2 steps in order, as chained string operations, with each step testable on its own; the ordering rationale is recorded in section 3 — follows F§5.2.
- [DESIGN] The package exposes the three entry points the contract names through `exports`, and re-exports this unit's modules from `src/index.ts` only. `src/parsers/` and `src/testing/` are declared for later units and deliberately not created here: the contract's *Required File Outputs* does not list them, and an unbuilt entry that the isomorphic guard would have to walk is exactly what R5 forbids.
- [DESIGN] `vitest.config.ts` fixes the Node environment and `src/**/*.test.ts`, and the package's own `typecheck` script is `tsc --noEmit -p tsconfig.json`, so `pnpm -w run typecheck` now enters this package instead of skipping it: Turborepo reports `Running typecheck in 1 package` and `1 successful, 1 total` — follows AGENTS.md §7 (the tests are part of the unit's deliverable) and §2 Step 4.
- [DESIGN] The typecheck program is `include: ["src"]` with `exclude: ["src/__tests__/hash.test.ts"]`, and `vitest.config.ts` is deliberately outside it as well. The repository has no `@types/node` and R10 forbids adding one, so every declaration file that mentions Node's ambient types is unresolvable (section 2 measured the cascade); the two files that need them are vitest's own config typings and the one test file whose oracle the contract requires to be `node:crypto`. The library modules and the other three test files type-check cleanly, so the program keeps them and drops exactly the two files a dependency this unit may not add would be needed for. The boundary is also correct for an isomorphic package: with no Node ambient types inside the program, a stray `node:` import in library code cannot type-check at all, which reinforces what `scripts/check-isomorphic.mjs` guards from the other side.

## 7. Deviation proposals

- [DESIGN → contract] The contract's *Forbidden Actions* say *"Do not import from Node, the DOM, React,
  or React Native anywhere in this unit"*, while its *Required File Outputs* require
  `hash.test.ts` to assert a 1 000-character multi-byte string *"equals the value computed in the test
  with `node:crypto`"*. Read strictly the two cannot both hold, since a test file is a delivered file of
  this unit. Resolved in favour of the explicit, more specific output requirement, and on the
  forbidden-action bullet's own justification (*"`sha256Hex` is synchronous, pure TypeScript, and
  isomorphic"*): the prohibition governs the implementation, which contains no Node import and no
  hashing package — `node:crypto` appears once, in the test, as an independent oracle, which is the only
  way to make the required assertion meaningful rather than self-referential. Nothing in the isomorphic
  graph changes: `scripts/check-isomorphic.mjs` walks `src/index.ts`, and no test file is reachable
  from it. Proposal: state in the contract that test files may use Node built-ins as oracles.
- [DESIGN → contract] The contract requires `packages/core/package.json` to export `./parsers` and
  `./testing` while listing neither `src/parsers/index.ts` nor `src/testing/index.ts` under *Required
  File Outputs*. Both are exported and neither is created (R5), which leaves `package.json` pointing at
  two files that do not exist. That is harmless today — nothing imports them, `tsc` resolves only what
  is imported, and the isomorphic guard simply has a shorter walk — but it is worth a later contract
  naming the unit that fills them. Proposal: confirm in U-003 or the first parsers unit that those two
  entries are the intended target paths.
- [DESIGN → contract] This repository has no `@types/node`, and R10 forbids installing one, so no
  declaration file that mentions Node's ambient types can be in a `tsc` program: `vitest/config`'s own
  `.d.ts` alone cascades into dozens of errors, and the `node:crypto` oracle the contract requires in
  `hash.test.ts` is one `TS2591`. The unit resolves this inside the two files it owns — `tsconfig.json`
  and the test — by scoping the typecheck program (section 4), which is why `vitest.config.ts` and
  `hash.test.ts` sit outside it; everything else about the test file is unchanged, and it runs and passes.
  Two repairs are worth considering in a later contract: add `@types/node` to `F§2.3`, after which every
  test file in the repository — including this one — is type-checked rather than merely executed; or state
  explicitly which files a package's `typecheck` program must cover, so the boundary is the contract's
  choice rather than the executor's.
- [DESIGN → contract] The contract fixes no script names for `packages/core`, but its verification
  command runs `pnpm --filter @lectern/core run typecheck`, which requires a `typecheck` script in the
  manifest. Added, and nothing else: no `test`/`build` script was invented, so `turbo run test` remains
  a no-op for this package until a contract names those scripts. Proposal: state the expected script set
  for `packages/core` in a later contract if the turbo tracks are meant to pick the package up.
