## 3. Architecture notes

**The shape of one capture, in the order it happens.** F§10.3 gives the desktop shell one line for this feature
— "a transparent full-screen overlay window for drag selection → `desktopCapturer` screenshot → crop → PNG →
`POST /v1/parse` → play in the mini-player" — and the shell's half of it is a short chain of six steps that
begins with a trigger and ends with the app being handed bytes:

| # | Step | Where it happens |
|---|---|---|
| 1 | one action (`readRegion`) is raised on the shell's bus | F§10.3's triggers: the `Ctrl+Alt+S` hotkey, and the bridge's `captureRegion()` (U-038's `lectern:capture-region` channel raises the same action) |
| 2 | the mini-player is taken off the screen, so it is not in the frame | the shell's own `toggleMini` trigger |
| 3 | a transparent, frameless, always-on-top window covering the display under the cursor appears | the region overlay |
| 4 | the operator drags out a rectangle, or presses `Esc` | the overlay page |
| 5 | the display is captured, the rectangle cropped out of it, and the crop encoded as a PNG | `desktopCapturer` + `nativeImage` |
| 6 | the PNG is handed to the app as an import request (`Quick reads`, play at once) and the mini-player is put back | F§10.3's `lectern:import-request` |

Nothing in that chain parses anything, hashes anything, writes a file, or knows what a document is: the shell
produces an image and the app's ordinary import pipeline turns it into a document at the hub, exactly as a
dropped file or a read selection does (F§10.3's "go through the web app's normal import pipeline"). The OCR is
the hub's (F§5.5, U-020) — the shell never runs it, and this unit's *Forbidden Actions* say so.

**Two coordinate spaces, and the conversion between them.** The overlay page's drag is in the page's own CSS
pixels, and the page is the whole display, so one CSS pixel is one *device-independent* pixel of that display.
`desktopCapturer`'s thumbnail, on the other hand, is asked for at the display's *device* size
(`bounds.width × scaleFactor`), so a rectangle drawn at scale factor 1.25 or 2 covers more thumbnail pixels
than the drag covered page pixels. The conversion is one multiplication per edge, and it is the only piece of
this feature that is arithmetic rather than plumbing — which is why it is the piece the contract asks to be
pure and unit-tested (`region-math.ts`), and why `toDevicePixels` rounds the *edges* rather than the size: a
rounded size would leave a seam of un-captured or double-captured pixels along the selection's right and bottom
edges.

**Endings.** A capture has four ways to end and three of them are "nothing happened":

- a drag of at least 8×8 returns that rectangle;
- a drag smaller than that is discarded by the shell (`isTooSmall`), because a 3-pixel drag is a click, not a
  region;
- `Esc` (the page's own `cancel()`) returns `null`;
- a window that goes away for any other reason (the display changing under it, the operator's window manager)
  resolves with `null` too, so the trigger can never leave the shell waiting: F§10.3's trigger is a hotkey, and
  a hotkey that never returns is a hung action.

**Timing.** The contract's case gives the whole hand-off 60 seconds; the shell's own deadline is the pointer
drag (however long the operator takes) plus one screen capture and one PNG encode. Measured on this host, the
capture of a 1280×1024 display and its encode are tens of milliseconds (§6.1).

## 4. Lectern design

- [DESIGN] **The overlay's preload is shipped as an asset of the main bundle, and that is a measured
  necessity rather than a preference.** The contract's output list gives the overlay preload as
  `apps/desktop/src/preload/overlay.ts`, and this repository's build is U-038's `electron.vite.config.ts`, whose
  preload build has exactly one entry (`findLibEntry` resolves `src/preload/index.ts`; measured, §6.1 (a)) — so
  a second file in `src/preload/` is never emitted, and neither the config nor `src/preload/index.ts` is in this
  unit's scope (the contract states no `Patch scope`). electron-vite does provide the one supported way to ship
  a file *as written* and learn its path: the `?asset` import suffix, which emits the file beside the main
  bundle and compiles to `join(import.meta.dirname, "./chunks/<name>-<hash>.<ext>")` (measured, §6.1 (c)). So
  `overlay-window.ts` imports `../../preload/overlay.ts?asset` and hands the resolved path to the overlay
  window's `preload`. §7 (1) proposes the config change that would make the contract's own shape the natural one.
- [DESIGN] **The overlay preload is plain CommonJS, and says so.** An emitted asset is the file's own bytes, so
  `src/preload/overlay.ts` is written as JavaScript that is also valid TypeScript: no annotations, no imports,
  `require("electron")`, two members on `contextBridge`. That keeps the file the contract names as the single
  source of truth — and keeps `sandbox: true` (F§11) — where the alternative electron-vite mechanism for a
  shipped module (`?modulePath`) compiles the file as an **ES module**, which F§10.3/F§11's sandboxed preload
  cannot load (an ESM preload requires `sandbox: false`), and which the contract's own *Forbidden Actions*
  ("Do not bundle the overlay with a framework; it is one static HTML file and one script") do not ask for.
- [DESIGN] **The preload exposes two functions and nothing else, and the shell validates what they carry.**
  F§10.3's bridge is not available to the overlay page — it is a different window with a different job — and
  F§11's rule ("expose only the members it needs") is what the two members are for. What arrives is still
  untrusted: the rectangle is parsed against a zod schema before it is used (`overlay-window.ts`), because a
  renderer is a separate process with its own lifetime and a payload is whatever a script puts on the channel
  (§7 of AGENTS.md: "validate every external input … messages between extension contexts and Electron
  processes").
- [DESIGN] **The display is chosen by the cursor, and the capture is of that display alone.** F§10.3 says "a
  transparent full-screen overlay window"; the window that is *useful* covers the display the operator is
  looking at, so the overlay takes `screen.getDisplayNearestPoint(screen.getCursorScreenPoint())`'s bounds, and
  the capture asks `desktopCapturer` for the source whose `display_id` is that display's id, falling back to
  the first source when the ids do not match (measured: with one X screen the id matched, §6.1 (d)).
- [DESIGN] **The overlay is gone before the screen is read.** The dimmed overlay is *over* the pixels that are
  about to be captured, so closing it is part of resolving the selection, and the capture happens after the
  selection is complete. A frame's settle delay follows, because the window's own pixels must be off the screen
  before the screen is photographed; the delay is a named constant and not a slept guess.
- [DESIGN] **The mini-player is hidden through the shell's own trigger and only when it is really up.** The
  strip must not be in the frame, and the shell's only way to take it off the screen is F§10.3's `toggleMini`
  (U-039). Toggling it blindly would *create* a strip that the operator never asked for — U-039 makes the
  window lazily — so the handler asks first, and the predicate is U-039's own definition of the strip: the
  shell's always-on-top window of the mini-player's own size (`MINI_WINDOW_SIZE`, imported from the module that
  owns it). Exactly one `toggleMini` hides it before the capture and exactly one puts it back after the import
  request is sent, so a strip that was hidden stays hidden and a shell that had no strip gains none. §7 (3)
  proposes a `showMini`/`hideMini` pair, which is the same request U-041's evidence already filed.
- [DESIGN] **The bytes never touch the disk.** The PNG is produced by `nativeImage.toPNG()`, wrapped in a plain
  `Uint8Array`, handed over F§10.3's import channel, and dropped; nothing under the user-data directory is
  written, and nothing outlives the request (the contract's *Forbidden Actions*).
- [DESIGN] **The reading is played through the app, not by the shell.** The import request carries `play: true`
  and the folder `Quick reads`, so the app opens the document playing at `?autoplay=1` and the strip that was
  restored stands in for the window — F§10.3's "Screen-region readings are saved in the library folder
  `Quick reads` (newest 50 kept) and played at once".
- [DESIGN] **The handler takes its surfaces as arguments.** `useRegionCapture(ctx, surfaces)` is given the
  display lookup, the overlay, the capture, the strip's state and the import hand-off, and `captureRegionFeature`
  is the only place Electron's own objects are built — the shape U-041 used for the selection chain, and what
  keeps the handler's own decisions (what a too-small rectangle does, what is restored and when) readable
  without an application running.
- [DESIGN] **The overlay page is one HTML file and one script, and it is not a build.** No framework, no
  bundler, no asset pipeline: `resources/overlay/index.html` is a dimmed full-bleed page with a crosshair
  cursor, `resources/overlay/overlay.js` is a plain script that draws the rectangle the pointer describes and
  answers `Esc`, and the two of them are shipped exactly as written (U-043 packages the directory). The
  contract's *Forbidden Actions* put it that way, and it is also what a page whose whole job is one drag should
  be.

### 6.2 Rehearsal in a copy of the repository (2026-11-15)

The fixed command was run whole — all five of its steps — in a `cp -a` copy of the repository
(`~/.hermes/cache/scratch/u042-repo`, 920 MB) with the deliverables copied in and `cmp`-verified byte-for-byte,
before the official run, and the region cases were then re-run there until they were green. Its numbers: 101
unit tests in 6 files, `tsc` silent, 196 modules to the web build (`0.67 kB` `index.html`, `8.44 kB` stylesheet,
`867.61 kB` script), 140 modules to `out/main/index.js` (277.38 kB) **with the overlay preload emitted beside
it** (`out/main/chunks/overlay-BalSo9Fv.ts`, 2.29 kB) and 121 to `out/preload/index.cjs` (188.42 kB) — and then
the three cases green in 21.3 s (9.1 s for the drag, 5.2 s for `Esc`, 5.5 s for the strip).

Four findings, each measured, and all of them are in the deliverables or in the case that was wrong about them:

1. **An `ipcMain` listener's first argument is the message's event, not its payload.** The overlay's listener
   took its first argument as the rectangle, so Electron's event object reached the schema and was refused —
   `the region overlay sent lectern:overlay-submit a payload that is not a rectangle` in the shell's own log —
   which is the validation doing its job on the wrong value. Fixed by a wrapper that takes the payload (the
   second argument) and passes it on, and the two listeners are removed by that wrapper's own identity.
2. **A window asked for a display's exact size is given one pixel less on this host.** Measured for all four
   combinations of `useContentSize` and `transparent`: a 1280×1024 display gives a window a `contentSize` of
   `[1279, 1023]` and `bounds` `{x: 0, y: 0, width: 1279, height: 1023}`. The case's "is the overlay up"
   predicate required equality with the display, so it never matched and both required cases failed at their
   first step. The predicate now separates the shell's two extra windows by the mini-player's own height (a
   display is not 72 px tall), and the deliverable's own strip predicate compares with `<=` for the same reason.
3. **`Escape` closes the window during the key press.** The page's handler cancels the selection on `keydown`,
   the shell destroys the window with it, and Playwright's `press` then fails on the key-*up* with
   `Target page, context or browser has been closed` — with the overlay already cancelled by the press itself.
   The case presses the key and never releases it.
4. **The library list is drawn after a navigation.** A case that reads the rows in the same breath as its
   `#/library` navigation can read an empty list; the cases wait for a row before reading it.

Two more facts were measured while rehearsing, and they are what make the mechanism's shape a fact rather than a
hope: the overlay's own page answers `Object.keys(window.lecternOverlay)` with `["submit","cancel"]` — so the
preload really is the emitted asset, loaded by a sandboxed, context-isolated window — and a drag over a part of
the page that carries no text ends in the **hub** answering `422 the input holds no text the reader could read`,
which is F§5.5's OCR engine refusing an empty crop rather than a chain that stops short of the engine.

The whole desktop suite was run afterwards as a regression check, because this unit appends to the registry all
four earlier desktop units run through: **16 cases green in 1.2 min** — U-038's four, U-039's four, U-040's
three, U-041's two and this unit's three.

## 7. Deviation proposals

1. **The frozen build config emits one preload entry, and the contract asks for two.** The contract's outputs
   include `apps/desktop/src/preload/overlay.ts`, "the overlay preload", and U-038's `electron.vite.config.ts`
   is not in this unit's scope, so it cannot be made a second entry of the preload build: electron-vite resolves
   the preload entry with `findLibEntry(root, 'preload')`, which is `src/preload/index.ts`, and its validator
   refuses more than one *output* (measured, §6.1 (a)). This unit therefore ships the preload as an **asset of
   the main bundle** with electron-vite's `?asset` suffix (§6.1 (c)) — the same mechanism the tool provides for
   shipping a file as written — and keeps `sandbox: true`. Proposed: give the preload config an `input` object
   (`{ index: "src/preload/index.ts", overlay: "src/preload/overlay.ts" }`) with `build.isolatedEntries`, which
   is what electron-vite's own `isolateEntriesPlugin` exists for, and name the config under *Patch scope* for
   every unit that adds a preload; the deliverable then becomes a two-line change (`preload: join(__dirname,
   "..", "preload", "overlay.cjs")` instead of the asset path) and F§10.3 could name both preloads.
2. **`?asset` needs a types reference the desktop program does not carry.** electron-vite's `node.d.ts` is what
   declares `'*?asset'`, and U-038's `apps/desktop/tsconfig.json` references neither it nor `electron-vite`
   (its `compilerOptions` are `lib` and `jsx`), so the one file that uses the suffix declares the reference
   itself. Proposed: add `"types": ["electron-vite/node"]` to that tsconfig (a U-038 file this unit may not
   write), so every later unit that ships a file needs no per-file reference.
3. **F§10.3 has no action for hiding or showing the mini-player separately.** The contract asks the handler to
   "hide the mini-player" before the capture and to "restore" it after, and the shell's only trigger for the
   strip is the `toggleMini` action (U-039). A toggle is not a hide: it creates the strip when there is none, so
   the handler asks the window list whether the strip is really up (U-039's own `MINI_WINDOW_SIZE`) and toggles
   only when it is. Proposed: an idempotent `showMini`/`hideMini` pair on F§10.3's bus (or on
   `DesktopWindows`), the same request U-041's evidence already filed for this feature's neighbour.
4. **A screen capture is the one thing this unit cannot verify on Wayland here.** F§10.3's capture goes through
   `desktopCapturer`, and on a Wayland session that is a system picker with its own consent step. This host is
   X11 under `xvfb-run` and the contract says the Wayland path is not verified here, so the ledger says
   `wayland: unverified`.
5. **The overlay preload is a file the repository's own style would otherwise forbid.** Every other source file
   in this repository is typed TypeScript with ESM imports, and the overlay preload is plain CommonJS because
   the file that ships *is* the file that is written (§6.1 (b)). Its two members are therefore `any`-typed
   through `require`, and the payload they carry is validated where it arrives. Proposed: if the config change
   in (1) is ever made, this file becomes an ordinary preload entry and can be written as typed ESM like
   `src/preload/index.ts`.
6. **The contract's end-to-end case does not exercise the mini-player's own half of the handler.** The bullet
   for `capture-region.ts` asks the handler to "hide the mini-player … restore the mini-player", and F§10.3 has
   the strip stand in for the window while a region is read; the case the contract describes drags a region on a
   shell with no strip up, so the branch that hides and restores it would never run under this unit's own
   verification. This spec adds a third case for it — the strip is up, it is off the screen while the shell is
   asking for a region, and it is back once the region has been handed over — which is also what proves the
   strip's own identity (its height) is the right one. Proposed: name the strip in the contract's case list, so
   a later unit can tell whether that branch is still covered.
