## 3. Architecture notes

**A model's bytes are files, not rows (F§8.4).** `PUT /v1/library/documents/:docId/model` reads the request
body (Fastify's buffer parser hands it as a `Uint8Array` for every content type but JSON), decompresses it once
to prove it is a `DocumentModel`, and stores **the bytes the client sent** — U-055's `document-files.ts` writes
them into `{DATA_DIR}/library/{docId}/model.json.gz` through a temporary file and a rename. The route never
re-encodes, so a client that fetches the model back receives a byte-identical container (measured in §6.1).

**The path names the document, and the body has to agree.** The `docId` is validated against U-054's own
`DocIdParamSchema` (`/^[0-9a-f]{32}$/`) before any path is built, and the decompressed model's own `docId` must
equal the path's. A body that describes another document is `400 BAD_REQUEST` and writes nothing — the
contract's first *Forbidden Action*.

**Sizes are enforced while the body arrives.** Each route carries `bodyLimit: min(the library's ceiling for
that file, LECTERN_MAX_UPLOAD_MB)`; §2 measures that a route's `bodyLimit` is the one Fastify applies, so an
oversized upload is refused with 413 as it streams, never after being held whole. The decompressed side is
bounded by `maxOutputLength`, so a compressed body that would inflate past the ceiling is 413 as well.

**A missing file is `NOT_FOUND`.** Both `GET`s answer 404 with F§7.2's envelope when U-055's files hold no
model or no original, rather than an empty 200 that a reader could take for a document with no text.

**The sync round is push, then pull (F§8.2).** `POST /v1/sync/push` validates `{ deviceId, ops }` with U-054's
`PushRequestSchema` (1–200 ops over F§5.9's own `OpSchema`), hands the batch to U-055's repository — which
applies F§5.9's rule against one stored row per entity, records every `opId` in its ledger, and appends one
`changes` row per winning op — and answers `{ accepted, rev }` with **every** `opId` of the request, winners
and losers alike. `GET /v1/sync/pull?since=&limit=` reads the change log after `since`, one entry per changed
entity, each built from the record that currently wins, and answers `{ changes, nextRev, more }`; a client
stores `nextRev` and pulls again while `more` is true.

**The one side effect a record cannot carry.** A document's model and original are files, so a `document`
delete that wins must remove them. The removal is done from the hub's own change log rather than from the
request: the route remembers the `rev` before the batch, and after the repository's transaction has committed
it reads the changes after that `rev` — the page names, for every entity the batch moved, the stamp of the op
that now holds the record. An op is a winner exactly when that stamp is its own `(ts, deviceId)`, so a
tombstone that lost leaves the bytes alone, and nothing is removed from inside the write. Ids that are not
F§5.2's shape are skipped: they cannot name a directory, and U-055's `removeDocument` refuses them by design.

**A record never needs its model.** A winning `document` put whose model the hub has never been sent is stored
like any other op; F§8.2 has the client upload the model *before* the op that references it, and a client that
skipped that step must not be able to make the hub refuse a record the device holds. Measured in §6.1: the
record is stored, `GET …/model` is 404, and the model can be uploaded afterwards.

## 4. Lectern design

- [DESIGN] **The library routes are a thin skin over U-055's document files.** They own the HTTP shapes and the
  three refusals, and nothing else: the atomic writes, the directory layout and the id check all stay in the
  module that already owns them (F§8.4).
- [DESIGN] **The host's zlib is reached through a `string`-typed specifier**, with the part of its API this
  module uses declared beside it — U-019's boundary for `node:fs/promises`, reused for the same reason (no Node
  ambient types belong in this package's program, and U-055 measured what importing a `/// <reference
  types="node" />` declaration does to it).
- [DESIGN] **`PUT`s answer `204 No Content`.** F§7.2 gives the library routes no response body, and U-054's
  `library-api.ts` defines no answer schema for them, so the upload answers with the status alone and a client
  reads the effect back through the `GET`s.
- [DESIGN] **A model is served as `application/gzip`.** The stored bytes are a gzip container and are sent as
  they are (§3); F§7.2's "gzipped `DocumentModel` JSON" is read as the container, not as a `Content-Encoding`
  header, so no proxy or client can silently re-inflate what the hub promised to serve verbatim.
- [DESIGN] **An original is served under the type it arrived with** — the request's own `content-type`, or
  `application/octet-stream` when the declaration was empty — which is what U-055's `original.json` sidecar
  exists to remember.
- [DESIGN] **`TOO_MANY_OPS` is answered from the sync module, not raised as a hub error.** F§7.2's shared code
  set is closed at thirteen entries and has no code for "too many ops at once"; U-054's `SyncErrorSchema` is
  that envelope's own error object extended with the sync code set, so the route sends
  `{ error: { code: "TOO_MANY_OPS", message } }` itself rather than throwing a `HubError` whose body the shared
  handler's `ErrorBodySchema` would reject. The check runs before the schema parse so a 201-op body is named
  for its size, not for a generic shape failure.
- [DESIGN] **The pull query is read as text and converted.** F§7.2 writes `?since=&limit=`, and a query string
  arrives as strings while U-054's `PullQuerySchema` is written in integers, so the two keys it names are
  parsed as whole numbers; a value the client sent that is not one is passed through unchanged so the refusal
  names the value instead of reporting the field as absent. `since` stays required and `limit` keeps its 500
  default, exactly as U-054's schema declares.
- [DESIGN] **A malformed document id answers `BAD_REQUEST`.** F§7.2's closed code set has no document-id code,
  and inventing one would fail every client's own copy of `ErrorBodySchema`; this is the same choice U-055's
  `document-files.ts` already makes for the same id.
- [DESIGN] **No listing, search or admin route exists for library content** (the contract's third *Forbidden
  Action*): the module registers exactly the four library routes and the two sync routes, and a client learns
  of documents only through F§8.2's change log.

## 7. Deviation proposals

1. **The library routes' answer shape is not specified, so the `PUT`s answer `204` and a model is served as
   `application/gzip`.** F§7.2 gives `PUT`/`GET …/model` and `PUT`/`GET …/original` no answer body and U-054
   defines no response schema for them (§4). A patched contract could name a small JSON ack, or spell the
   model's content type as `Content-Encoding: gzip` over `application/json`; either would be a one-line change
   in `library.ts` plus its case in `sync-routes.test.ts`.
2. **The upload ceiling is `min(U-054's limit, LECTERN_MAX_UPLOAD_MB)`.** The contract's *Forbidden Action*
   says to enforce the limits from `library-api.ts` while streaming; those limits are the 100 MiB default of
   F§7.1's `LECTERN_MAX_UPLOAD_MB`, and a hub configured to accept less should not accept more than that
   either. A patched contract that wants U-054's constants to be the *only* ceiling can say so.
3. **A winning delete's files are removed inside the request, after the transaction.** The *Forbidden Action*
   forbids removing them "on a tombstone op in the request path"; the reading implemented here is that the
   prohibition is on acting for an op that merely *arrived* (a tombstone that lost must not touch the bytes),
   and that the removal belongs after `applyOps` has committed. It is awaited before the response, so a client
   that pushes a delete and then fetches the model sees the 404 the delete promised. A patched contract that
   wants the removal deferred to a background step can say so; the winner test (the change log's own stamp)
   would not change.
4. **The pull query's values are converted from text.** F§7.2 writes `?since=&limit=` and U-054's schema is
   written in integers; the hub reads whole numbers and passes anything else through so the refusal names it. A
   patched contract could instead fix the reading as `Number(value)` and let `NaN` be the normal failure.
5. **A malformed document id is `BAD_REQUEST`** (§4), the same code U-055's document files answer with. F§7.2's
   code set has no entry for it; a patched contract could add one, which would also need U-018's `common.ts`
   touched.
6. **`DELETE`/`HEAD` are not registered for the library routes.** F§7.2's table names `PUT` and `GET` only, and
   the contract's *Forbidden Actions* forbid adding routes for library content, so no `DELETE` exists — a
   document's body goes away through F§8.2's tombstone, which is what makes the removal replicate.
