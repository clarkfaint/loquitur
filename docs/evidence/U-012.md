## 3. Architecture notes

All three modules are pure functions over numbers and the document model. Nothing here holds state, so a
position restored from the library reports the same progress and the same remaining time it did before.
The quantities follow F§5.6 directly; the numbers below were produced by a scratch probe
(`node probe-goldens.mjs`, exit 0) that re-derives every golden value of the brief from the brief's own
formulas, and they are labelled `DESIGN` because they are arithmetic on the specification, not
observations of a reference product.

**Estimated timings — F§5.6(a).** A weighted apportionment of one chunk's duration over its words. Each
word carries `alnum(w)` (letters and digits, floored at 1) plus a pause of 3 after a sentence mark, 2
after a clause mark, or 0 — read *past* closing punctuation, so `"Stop."` is a sentence end and `Hello,`
is a clause end. The probe reproduces the brief's golden exactly: `['Hello,', 'world.']` at 1000 ms is
`[{i:0,s:0,e:333},{i:1,s:467,e:800}]` (weights 7 and 8 of 15). The pause is not spoken: it is the share
of the chunk a word holds, which is why the following word starts later than the previous word ends.

**Aligning engine timestamps — F§5.6(b).** A two-pointer walk with three states: *matched* (the run of
tokens equals the word, and the word keeps the engine's span), *unmatched* (a partial run consumes
nothing, and the token pointer may look ahead up to three tokens for one that starts the next word), and
*filled* (a maximal run of unmatched words is apportioned over the gap its matched neighbours leave, or
over the chunk start/end when a run touches an end). Two thresholds decide the outcome: `norm` compares
letters and digits only, so an engine that emits punctuation as its own token still matches; and fewer
than half the words matched means the engine's timestamps do not describe this text, so the whole chunk
falls back to `estimateTimings` as `estimated`. Both paths end clamped — `0 <= s <= e <= durationMs`,
with no start ever moving backwards — so `findActiveWord` can be a plain binary search.

**Active-word lookup — F§5.6(c).** `t` before the first start is word 0 and `t` after the last end is the
last word, so the highlight never leaves the chunk. The brief's four golden lookups on the golden timings
are `400 -> 0`, `467 -> 1`, `-5 -> 0`, `9999 -> 1`; the probe returns exactly those.

**Speed plan — F§5.6(e).** The synthesizer takes the rate the sink cannot reach, rounded up to a whole
0.25 and bounded to 1.0–4.0; the sink then takes what is left, capped by its own ceiling; the effective
rate is their product. The brief's five goldens reproduce exactly, including the two ceilings:
`(1.5, 16) -> {1.0, 1.5, 1.5}`, `(4.5, 2) -> {2.25, 2.0, 4.5}`, `(5.0, 2) -> {2.5, 2.0, 5.0}`,
`(3.0, 2) -> {1.5, 2.0, 3.0}`, `(5.0, 1) -> {4.0, 1.0, 4.0}`. The inequality that makes the plan safe
holds over the whole control: across all 91 rates from 0.5 to 5.0 in steps of 0.05 and all four sink
ceilings `{1, 2, 4, 16}`, the probe finds **0** cases where `effectiveRate` exceeds `rate` (worst excess
0.0), so the contract's sweep assertion is satisfiable exactly and needs no tolerance.

**Progress — F§5.6(f).** `fraction = (wordsBefore(sentenceIndex) + wordIndex) / wordCount`, and the
remaining time is the words still to read over `baseWpm · rate`, in minutes. The probe confirms the
case the test leans on: 340 words at 170 wpm is 120000 ms, and at twice the rate 60000 ms — an exact
halving, so the test can assert a doubled value with no rounding slack.

## 4. Lectern design

- [DESIGN] `estimateTimings` follows F§5.6(a) literally, with `Math.round` at exactly the two places the
  section names, so every output is a whole millisecond. `alnum` and `pause` are computed once per word.
- [DESIGN] `norm` strips everything that is not a Unicode letter or digit, so the comparison is
  punctuation-blind, diacritic-sensitive and script-independent, and an engine token with an empty `norm`
  is skipped exactly as step 2 requires.
- [DESIGN] A word whose own `norm` is empty (a bare dash, a lone bracket) can never be matched, because
  no token stream can equal it without consuming a token; it is treated as unmatched and interpolated.
  F§5.6(b) does not name this case.
- [DESIGN] A partial token run consumes nothing and the pointer stays where step 3 leaves it, so a later
  word can still match a token an earlier mismatch walked past.
- [DESIGN] Both paths end in the same clamp (step 6): every start and end inside `[0, durationMs]`,
  `s <= e`, and starts non-decreasing. `estimateTimings` output already satisfies this, and the clamp is
  applied anyway so `alignEngineTimings` has one guarantee rather than two.
- [DESIGN] `clampRate` is the only place the offered range is applied; `planSpeed` implements F§5.6(e)'s
  three lines verbatim and assumes its caller passes a rate inside the range (the contract's goldens and
  its sweep both do).
- [DESIGN] `progressFraction` is clamped to `[0, 1]` and answers 0 for a document with no words, so a
  position restored from a different document revision cannot produce a denominator of zero.
- [DESIGN] `remainingMs` returns 0 once nothing is left to read, and refuses a `rate` or a `baseWpm` that
  cannot carry words with a `RangeError` (the precedent `sentenceAt` in `playable.ts` set) rather than
  fabricating a number. F§5.6(f) does not name this case.
- [DESIGN] `updateBaseWpm` weighs the chunk just played and the average so far equally. See the deviation
  proposal in section 7: F§5.6(f) fixes the initial value (170) and the quantity averaged but not the
  weighting, and the signature `(previous, words, durationMs)` carries no sample count, so no exact
  arithmetic mean over all chunks is expressible.
- [DESIGN] The barrel `packages/core/src/index.ts` gains three export lines in the order Biome's
  import-organizer wants (`playable`, `progress`, `skip`, `speed`, `text`, `timing`, `tokenizer`); no
  existing line is touched, as §5 requires.

## 7. Deviation proposals

- **F§5.6(f) does not state the weighting of the running average.** It fixes the quantity
  (`60000 · words / durationMs`), the voice it belongs to, and the initial value (170), but not how a new
  chunk moves the average; and because `updateBaseWpm(previous, words, durationMs)` carries no sample
  count, an exact mean over all chunks played is not expressible from its arguments. This unit implements
  the newest chunk and the average so far at equal weight, which converges on a voice's real pace, ignores
  nothing, and needs no state beyond the average itself. Proposal: state the weighting in F§5.6(f)
  explicitly (an equal-weight blend, or an exponential average with its coefficient) so a later unit
  cannot pick a different one silently.
- **The contract's `progress.test.ts` asks for "fraction ... 1 at the last word".** F§5.6(f)'s formula
  `(wordsBefore(sentenceIndex) + wordIndex) / wordCount` reaches `1` only when the numerator equals the
  word count, which a position *on* the last word (0-based `wordIndex = wordCount - 1` in a
  single-sentence document) does not: it reads `(n-1)/n`. The test therefore asserts the three positions
  that pin the formula exactly — `0` on the first word, `(n-1)/n` on the last word, and `1` at the first
  position at or past the end, which is the position a player reports once the last word has been read —
  rather than weakening the assertion to a tolerance. Proposal: F§5.6(f) should say which of the two a
  position on the last word means, and the contract's one-line test description should name the
  end-of-document position it wants a `1` from.
