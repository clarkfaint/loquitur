## 3. Architecture notes

None from inspection. The behaviour this unit implements is F§9's, and it is recorded here as the design it is:

- **A summary is a job, not a reply.** `POST /v1/ai/summary` answers `202` with the job's state — `running` for a job the request started, the cached result when F§9's key `(docId, mode, LLM_MODEL, promptVersion)` already holds one — and the result is read back from `GET /v1/ai/summary/:docId?mode=`. Polling is therefore a route, not a connection.
- **The wait is a schedule**: one second, two, three, then every five, for at most ten minutes (F§9). Every wait is driven by an injected `Clock`, so the schedule is pinned in a test rather than waited out.
- **A summary becomes an ordinary document.** F§9's "listen to the summary" is `buildDocument` with `source.kind` `summary`: a heading, the summary, one list item per takeaway. It is read, highlighted and remembered by the same player and the same store as anything else.
- **`brief` and `detailed` are different jobs.** The mode is part of the hub's cache key and is not a field of the result, so a mode switch is a different question with a different answer.

## 4. Lectern design

- [DESIGN] `packages/api-client/src/ai-client.ts` — F§7.2's two AI routes as one typed client over an injected `fetch`, built the way U-021's hub client and U-058's sync client are. Its failure type is its own, because **F§9's code set is not F§7.2's shared one**: `AI_DISABLED`, `MODEL_MISSING` and `INTERRUPTED` have no place in the shared thirteen, and reporting them as `INTERNAL` with the code quoted in the message (what the sync client does with F§8.2's two codes) would hide exactly the distinction a screen acts on. `AiClientError.code` is therefore `ErrorCode | AiErrorCode`.
- [DESIGN] `waitForSummary` answers the last state the hub gave — `done` or `error` when the job finished, whatever it was still saying when the ten minutes were spent — and rejects with an `AbortError` when its signal aborts.
- [DESIGN] `packages/ui-web/src/components/SummaryPanel.tsx` — the four states, the mode switch, and the two actions, all as props and callbacks, so the panel owns no state (F§10.1's own rule for `PlayerBar`). F§9's shapes are imported from `@lectern/api-contract` rather than re-declared.
- [DESIGN] `apps/web/src/ai/summary-service.ts` — `generate` sends this device's model inline when it holds one (F§7.2 stores it as that document's model, which is what makes a summary work on a device that has never synced); `summaryDocument` builds F§9's document; `listen` files it in the folder `Summaries` and opens it with F§10.1's `?autoplay=1`.
- [DESIGN] `apps/web/src/ai/SummaryDrawer.tsx` — opening the drawer *reads* the hub's state and asks it for nothing, so a reader cannot spend a model call by looking; the mode switch reads the other mode's state; closing the drawer or switching mode aborts the wait in flight.

### 6.4 Rehearsal — the one real defect this unit had to fix, and how it was measured

The first full-suite rehearsal failed one case: `listening to a summary files it in Summaries and reads it` reached the summary document (`toHaveURL(/#\/read\/[0-9a-f]{32}\?autoplay=1/)` passed, and the page drew `Summary of Mill Notes`) but `getByRole("button", { name: "Pause" })` never appeared in 30 s.

Measured with a throwaway probe spec (since deleted) that reproduced the flow with **no summary code in it at all** — reader on document A, then `window.location.hash = "/read/<B>?autoplay=1"`, exactly what `navigate()` does — with the reader's own player state read back through two temporary `data-player-*` attributes (also since removed):

| ReaderPage autoplay guard | state at 400 ms | state at 1400 ms | requests after the hash change |
|---|---|---|---|
| U-029's shape: `if (snapshot.state !== "ready") return;` | `ready` | `ready` | `GET /v1/voices` only — **no chunk is ever asked for** |
| this unit: `if (snapshot.docId !== docId \|\| snapshot.state !== "ready") return;` | `playing` | `playing` | `GET /v1/voices`, `POST /v1/tts`, `GET /v1/tts/audio/<id>`, the chunk's blob URL |

The cause: `autoStarted` is a one-shot ref, and on a cross-document navigation the *previous* document's `ready` snapshot is still the one on screen while the new player is being built. The effect spent the one autoplay on that stale snapshot, dispatched `play` into a `controllerRef` that had just been nulled by the old build's cleanup, and then refused to fire again when the new controller really reached `ready`. F§10.1's own words are "starts playback **after load**", and the guard is that word: the snapshot has to belong to the document the route names. It is one condition inside a file this contract lists under *Patch scope*, and it is filed under §7 below.

## 7. Deviation proposals

1. **`ReaderPage.tsx` needed one condition beyond "gains a 'Summarize' button"** (measured in §6.4). The contract's *Patch notes* say "Change nothing else", but its own *Pass/Fail Verification Test* requires the summary e2e suite to exit 0, and that suite requires `Listen` to start playback — which F§10.1's `?autoplay=1` cannot do across a document change under U-029's one-shot guard. Following U-020's precedent (the test list decides when the prose and the tests disagree), the fix is the smallest one that makes the contract's own words true: the autoplay snapshot must be the routed document's. Proposed wording for a patched contract: "`ReaderPage.tsx` gains a 'Summarize' button that opens the summary drawer, and its `?autoplay=1` effect fires only for the document the route names."
2. **`@lectern/ui-web` gains `@lectern/api-contract`.** The contract's *Uses* line names `@lectern/api-contract` (`ai-api.ts`) and R10 permits "packages named in the contract or in F§2.3"; a workspace link is what keeps the panel's props F§9's own types rather than a re-declaration of them (AGENTS.md §7: "Use the types and names in `features.md` exactly"). `pnpm --filter @lectern/ui-web add -E "@lectern/api-contract@workspace:*"` exits 0, writes only the manifest and the lockfile, and leaves `pnpm-workspace.yaml` byte-identical.
3. **`ErrorBodySchema.shape.error` cannot carry an F§9 code.** F§7.2's thirteen-code set is closed and U-019's handler builds every shared envelope through it, so the AI routes answer the *extended* object (U-054's `SummaryErrorSchema`) and this unit's client unions the two when reading a refusal. No shared file needed changing; recorded so a later unit reading a refusal knows both shapes exist.
