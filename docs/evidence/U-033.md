## 3. Architecture notes

Inspection is unavailable, so nothing here is a claim about the reference product. What follows is the design
the contract and F§10.2 fix for *Lectern's* content script, and it is labelled as such:

- **What is read.** A page's readable text is the text of its text nodes, walked in document order, minus
  regions that are not prose: `script`, `style`, `noscript`, `template`, `nav`, `aside`, `footer`, a
  `header` carrying `role="banner"`, anything `aria-hidden="true"` or carrying the `hidden` attribute, form
  fields and `contenteditable` regions, and — only where the document has a layout engine, so the question is
  answerable at all — zero-size or invisible elements. The zero-size test is deliberately gated: it is a
  measurement, and a document without layout (the tests' jsdom, a service worker) cannot make it, so it must
  not be guessed.
- **Where reading starts.** Readability is asked for the article on a *clone* of the document, never on the
  live page. The clone's elements are tagged with their pre-order index before Readability runs, so the
  element it hands back can be located in the live tree by index even though the copy and the original share no
  object identity. The article root is the *lowest common ancestor* of the tagged elements that survived into
  Readability's content: pre-order numbering makes every element's subtree a contiguous index interval, so the
  smallest interval covering the surviving indexes is exactly that ancestor, and it is found by one pass over
  the index list. `main`, then `body`, is the fallback when there is no article.
- **Block boundaries come from block-level ancestors** (F§10.2): `h1`–`h6`, `p`, `li`, `blockquote` and
  `figcaption` each become one block, the *outermost* such ancestor winning so a `<blockquote>` holding a
  paragraph stays one quote; other block containers flush the text around them into paragraphs; inline elements
  join the block they sit in. A `<br>` is a line break inside the block it sits in, not a block boundary.
- **Offsets.** A block's text is the concatenation of the text nodes it holds, normalized by F§5.2's eight
  steps. Because that normalization collapses whitespace runs, deletes soft hyphens and trims lines, raw
  text-node offsets are not normalized offsets: the extraction therefore records, for every character of the
  normalized block text, which text node and which raw offset it came from. A `Range` is built from the point
  of the first character and the point *after* the last one, so a range is exact across inline element
  boundaries, across collapsed whitespace and across line breaks. The mapping is per block
  (`{ node, blockIndex, start, end }`), and `rangeFor(blockIndex, charStart, charEnd)` reads it.
- **Nothing is written to the page.** Extraction reads the live tree and returns data; the clone that Readability
  mutates is a copy, and the index attributes live only on that copy.
- [INFERRED] Because the extraction never adapts the page, the live document's serialized HTML must be
  byte-identical before and after it — which is one of the unit's own assertions, not an observation of the
  reference product.

## 4. Lectern design

- [DESIGN] `visibility.ts` answers the exclusion question in one place, as a predicate over an element plus a
  statement of what the caller can measure (`{ hasLayout: boolean }`), so the layout-dependent half of the
  rule cannot silently run where there is no layout (F§10.2).
- [DESIGN] `article-root.ts` clones the document, tags the clone's elements with their pre-order index, runs
  Readability over the clone with its `serializer` option so the returned `content` is the article *element* in
  the clone rather than a serialized string, takes the lowest common ancestor of the surviving indexes, and
  returns the live element at that index; `main`, then `body`, then the document element is the fallback chain
  (F§10.2).
- [DESIGN] `text-map.ts` walks text nodes, never `innerText` — the contract forbids it, and it is
  layout-dependent — and builds both halves of the map in one pass: the blocks with their normalized text, and
  the per-node offset entries the ranges are resolved from. Block indexes are the `DocumentModel`'s block
  indexes, so a block whose normalized text is empty is dropped here exactly as `buildDocument` drops it.
- [DESIGN] `page-document.ts` converts the map to a `DocumentModel` through core's own `buildDocument`
  (F§5.4), with `source.kind` `html` (and the page's own address as `source.uri`) for a page and `selection`
  for a selection, so the tokenizer, the ids and the sentence/word offsets are core's (F§5.2, F§5.3) and are
  not re-implemented for the extension.
- [DESIGN] Everything the extraction exposes is Lectern's own vocabulary; no reference-product wording or
  identifier appears in the module, and no page text leaves the function (the contract's *Forbidden Actions*).

### 5.1 `@mozilla/readability@0.6.0` — `index.d.ts`

```ts
export class Readability<T = string> {
  constructor(
    document: Document,
    options?: {
      debug?: boolean;
      maxElemsToParse?: number;
      nbTopCandidates?: number;
      charThreshold?: number;
      classesToPreserve?: string[];
      keepClasses?: boolean;
      serializer?: (node: Node) => T;
      disableJSONLD?: boolean;
      allowedVideoRegex?: RegExp;
    }
  );

  parse(): null | {
    title: string | null | undefined;
    content: T | null | undefined;
    textContent: string | null | undefined;
    length: number | null | undefined;
    excerpt: string | null | undefined;
    byline: string | null | undefined;
    dir: string | null | undefined;
    siteName: string | null | undefined;
    lang: string | null | undefined;
    publishedTime: string | null | undefined;
  };
}
```

`serializer` is what makes `content` a node: the shipped implementation stores it as `this._serializer` and
returns `content: this._serializer(articleContent)`, and `articleContent` is a fresh `DIV` the implementation
creates in the document it was given, into which the article's own (tagged) elements are moved. So `content`
is an untagged wrapper whose *descendants* are the clone's tagged elements — which is why the article root is
the lowest common ancestor of the surviving indexes rather than `content` itself.

Two findings, one of them a real defect in the deliverables and one a wrong fixture:

1. **`findArticleRoot` returned the copy's element, not the live page's.** The index table was built by the
   same walk that numbered the copy (`live.push(element)` inside the numbering walk), so `live[index]` was the
   copied node — visible in the failure above as a returned element still carrying `data-lectern-index="4"`.
   Fixed by listing the *live* document's elements in the same pre-order (`preOrderElements`) and using the
   index only to join the two lists, which is what the module's own doc comment already claimed. The
   byte-identical assertion had passed under the defect because reading from the copy leaves the page alone;
   it is the *region* that was wrong, and the fix is what makes the extraction read the live tree.
2. **The fallback fixture was wrong, not the code.** Measured before touching anything:
   `<div><p>Short.</p></div>` answers `content=div text="Short." len=6` — Readability returns the longest
   candidate it found even under its `charThreshold`, and answers `null` only when no attempt found text at all
   (`<body></body>` → `null`). "No article structure" therefore means a body whose text has no element
   structure, which is the fixture now used.
