## 3. Architecture notes

The shell this unit builds is stated by F§10.1 rather than measured, so every proportion below is Lectern's own
design (`[DESIGN]`), with the section it follows.

- **Layout hierarchy.** One column: a title bar across the full width at the top (wordmark, then the navigation
  links), a content outlet below it constrained to 52 rem and centred, and — from U-029 — the player bar fixed
  at the bottom, which is why the shell is a flex column with `min-height: 100vh` and nothing is absolutely
  positioned. Colours, spacing and radii are `@lectern/ui-web`'s tokens only (U-023's stylesheet), so the screen
  follows the light/dark theme.
- **Navigation areas.** The bar is not a written-out list: it is derived from the route registry, one link per
  registered route whose pattern has no parameter. In this unit that is `Settings` alone; the library, import
  and mini routes join it as later units register them, with no edit to `App.tsx`.
- **Routing.** A route is a pattern (`/settings`, and `/read/:docId` from U-029) and a location is the part of
  the address bar after `#`, so navigation is an `<a href="#/settings">` and the browser's back button works.
  Matching is a pure function of a pattern and a hash: equal segment counts, `:name` capturing exactly one
  non-empty segment, everything else compared literally, and the query parsed off the same string. A parameter
  is percent-decoded, and a malformed escape (`%zz`) is kept as written rather than thrown, so a hand-typed
  address cannot make routing fail.
- **Settings.** Two halves in two places, for two different reasons: the connection (hub URL, token) in
  `localStorage`, because the app must be able to read it on its first render and before any database is open;
  the preferences one `setting` record per field in the `LibraryStore` (F§5.9), so they travel with the rest of
  the library (F§8) and one device changing the speed cannot overwrite another's theme through the
  last-writer-wins rule — a single `preferences` record would make every setting a competitor of every other.
- **Connection check.** A probe is two calls, not one: `/healthz` (which F§7.2 exempts from authentication, so
  it proves only that the hub is there) and `/v1/voices` (which proves the token). One call would report a
  wrong token as connected. The saved connection is probed whenever it changes, including on the first render,
  and the form's own values are probed by "Test connection" — the point of testing before saving.
- **Composition.** `getStorage()` (the `lectern` database and the two stores over it) needs no hub, which is
  why the app can read its saved preferences before a connection exists; `getServices()` adds the hub client and
  F§5.8's chunk source for the saved connection and is rebuilt when that connection changes.

## 4. Lectern design

- [DESIGN] **No router package** — the contract forbids one — and no history library: `matchRoute`, `navigate`
  and `useHashRoute` are this unit's own, and F§10.1's routes are all hash routes, which is what lets the
  desktop shell load the same build from `file://` (F§10.3). `vite.config.ts` sets `base: "./"` for the same
  reason.
- [DESIGN] **`bootFeatures` run once a hub is configured**, from `main.tsx`, and not before: the contract's
  `Forbidden Actions` forbid a hard-coded hub URL and F§10.1 makes the default empty, so with no connection
  there is no client to hand a feature and the shell is on the settings screen anyway. The database is opened
  *before* that point, because the preferences live in it. The list is empty in this unit.
- [DESIGN] **Services are rebuilt when the connection changes, and only then.** The client and the chunk source
  are built from the saved connection and cached against its signature, so a reader who re-points the app at
  another hub talks to it from the next call on with no reload, while a screen that asks twice holds one client.
  The database, record store and cache are the app's own and are handed over again unchanged.
- [DESIGN] **`Services.db` is typed `Awaited<ReturnType<typeof openLecternDb>>`.** R10 gives `apps/web` no `idb`
  dependency (the contract names React, React DOM, zustand, the five workspace packages and six dev
  dependencies), so the connection's type is taken from `@lectern/ui-web`'s own function rather than named from
  a package this app may not import.
- [DESIGN] **Validation at the settings boundary** (AGENTS.md §7: validate every external input). Every stored
  value is checked field by field on the way in: a rate is clamped into F§10.1's 0.5–5.0 at a tenth of a step, a
  hub URL loses its trailing slashes (so `http://127.0.0.1:8787/` is stored as `http://127.0.0.1:8787`), a token
  is trimmed, and a record whose shape is not the one the app writes (a string where a number belongs, a
  negative lead, a theme that does not exist) is ignored in favour of the default rather than carried into the
  player.
- [DESIGN] **Defaults** — `voiceId` empty, `rate` 1, `skipFurniture` true and `skipCitations` true (F§5.8's
  policy, and the parser's `stripCitations`), `lookaheadMs` 0 (F§5.6(d) fixes 0 on web and 80 on Android),
  `theme` `system`, `cacheLimitBytes` 256 MiB.
- [DESIGN] **The theme is applied to the DOM**: `applyTheme` writes `data-lectern-theme` on the root element,
  which is the hook U-023's stylesheet documents for pinning light or dark, and removes it for `system` so the
  operating system's own preference is followed.
- [DESIGN] **`index.html` links the stylesheet** instead of `main.tsx` importing it: an asset import would need
  `vite/client`'s ambient types inside the type-check program, and Vite bundles a linked sheet into `dist/`
  either way. The build output confirms it (8.44 kB of CSS carrying the tokens).
- [DESIGN] **The browser tests drive the production build** (`vite build`, then `vite preview` on port 4174 —
  the ui-web harness owns 4173), against a real hub that `global-setup.ts` starts with F§7.1's mock engine on a
  port the operating system hands out (`listen({ port: 0 })`, read back from the socket) and releases with its
  temporary data directory. The hub's address and token are written to `e2e/.hub.local`, which `.gitignore`
  already covers through `*.local`.
- [DESIGN] **The unit-tested surface is framework-free.** `apps/web` has no component-testing library (the
  contract's install list does not name one), so the unit tests are pure logic plus one React root for the
  router hook: `router.test.ts` and `settings.test.ts` render nothing else, and the screens are proved in the
  browser instead.

## 7. Deviation proposals

1. **`ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` above every `pnpm` step** (pre-existing, recorded by U-019, U-023
   and U-026): U-019's lockfile carries `@fastify/cors@11.4.3`, published inside pnpm 12's minimum-release-age
   window, so each step of the fixed command prints the violation and a `[WARN] The install that runs before
   scripts failed …` line above its own output while still exiting 0. Every subsequent `pnpm` invocation in this
   repository prints the same block. Not editable from inside a unit (the command is fixed by R11, the policy
   file by §5).
2. **`pnpm-workspace.yaml`'s `allowBuilds` block still holds pnpm's scaffolding prose** (`esbuild: set this to
   true or false`). Left untouched: §5 makes that file read-only for units, and U-023's note already filed it.
3. **F§10.1's "Test connection" button calls `health()` — which F§7.2 exempts from authentication.** A hub that
   refuses every other route would still answer `health()`, so a wrong token would read as a working connection.
   This unit probes with `health()` **and** `voices()`, and shows the refusal's code. Proposal: say in F§10.1
   that the check proves the token as well as the address.
4. **F§10.1's boot features and an unconfigured app.** The contract's `bootFeatures` signature hands each
   feature a full `Services`, which cannot exist without a hub URL and token (both forbidden to hard-code, and
   empty by default), so `main.tsx` runs them once a connection is configured. Proposal: state that ordering in
   F§10.1, so a later unit that needs services before a connection (the desktop shell applying its own settings)
   knows to register its work against the settings rather than against a client.
5. **The theme setting's DOM hook is U-023's, not this unit's.** `applyTheme` writes `data-lectern-theme`, which
   `packages/ui-web/src/styles.css` documents but no contract names as the place a theme is applied. Proposal:
   name that attribute in F§10.1's settings list, so the next platform that offers a theme (Android, F§10.4)
   uses the same name.
