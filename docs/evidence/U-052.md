## 3. Architecture notes

Nothing below is a claim about the reference product; it is the platform behaviour the scripts read, measured on
this device (§2.1) and quoted from F§10.4.

**The media-session state machine the check reads.** Android publishes one `PlaybackState` per media session, and
`dumpsys media_session` prints it either numerically (`state=PlaybackState {state=3, position=…}`) or by name
(`state=PLAYING(3)`), depending on the platform build. The three answers the contract names map onto it as: a
session for `dev.lectern.app` whose state is `PLAYING`/`3` is `playing`; `PAUSED`/`2` is `paused`; no session for
that package, or a state of `NONE`/`0`, `STOPPED`/`1`, `ERROR`/`7` or `CONNECTING`/`8`, is `none`. The transient
transport states the queue itself produces while it moves between chunks — `BUFFERING`/`6`,
`SKIPPING_TO_NEXT`/`10`, `SKIPPING_TO_PREVIOUS`/`9`, `FAST_FORWARDING`/`4`, `REWINDING`/`5` — are reported as
`playing`, because a session in one of them has been told to play and is advancing; a reader who pressed play and
saw `none` because a chunk was loading would be reading a false negative, and the check's whole point is whether the
reading survives leaving the app.

**Timing.** The contract fixes four numbers and the scripts use exactly them: `playing` within 20 s of the tap;
still `playing` 30 s after the Home key; `playing` again 20 s after the screen is switched off; and the
diagnostics run is given 180 s. The state is therefore polled rather than sampled once — a session that has been
told to play reaches `PLAYING` after the first chunk has been prepared, not at the instant of the tap.

**Layout and controls.** F§10.4 fixes the control set: "Lock-screen and notification controls map to play/pause and
previous/next sentence". `apps/android/src/audio/audio-session.ts` declares exactly that —
`showPreviousTrack: true, showNextTrack: true, showSeekBackward: false, showSeekForward: false` — so the unit's own
question about seek buttons is answered by the code that configures the session, and the device run proves the
session itself is published and controllable. The reader's transport is reachable by name from the accessibility
tree: the play/pause control carries `accessibilityLabel` `Play` / `Pause`, the two skips `Previous sentence` /
`Next sentence`, and those labels are what `uiautomator dump` prints as `content-desc`, which is why the scripts
locate the transport by label rather than by a coordinate.

**The connection.** The device reaches the hub over `adb reverse tcp:8787 tcp:8787`, so the app's
`lectern://setup?hubUrl=http://127.0.0.1:8787&token=…` link names an address that resolves on the device itself and
is forwarded to the host's hub. Nothing else about the device's network state is touched, and the reverse is
removed when the run ends (the contract's Forbidden Actions).

## 4. Lectern design

- [DESIGN] **Five POSIX shell files, no framework.** `adb` plus `uiautomator dump` is what the contract allows; no
  Appium, Maestro or Detox enters the repository, and no new dependency is installed (R10).
- [DESIGN] **Runtime state lives under `data/`**, which `.gitignore` already excludes ("Runtime data
  (`LECTERN_DATA_DIR` default)"). The hub's data directory, its log, its PID file and the UI dump are all written
  under `data/device-run/`, so a run leaves no untracked path for `check-scope` to see and nothing outside the
  repository is written or deleted (AGENTS.md §7).
- [DESIGN] **The test token is the repository's own test token** — the string
  `apps/server/src/__tests__/engine-routes.test.ts` already uses, 32 characters, meeting F§7.1's floor. It is not a
  credential: it authenticates a mock-engine hub this unit starts on `127.0.0.1` and stops again, and it never
  reaches anything but that process (R16).
- [DESIGN] **`media_state` reads the session, not the screen.** It parses `dumpsys media_session` for
  `package=dev.lectern.app`, takes the *inner* `{state=…}` of the matched line — the line also carries
  `error state=0`, so a naive last-`state=` match would read the error state — and prints one of the three words
  the contract names, using the mapping in §3.
- [DESIGN] **`media_dispatch` prefers `cmd media_session dispatch`** and falls back to `media dispatch` only when
  the former is unavailable, which is the order the contract gives. On this device only the first exists (§2.1).
- [DESIGN] **`ui_has_text` matches containment, not equality.** The contract needs it for two different jobs —
  "the visible sentence has advanced" and "the first words of the text visible" — and a React Native text node
  carries a whole block, so an exact match would fail the case it exists for. The argument is matched against a
  node's `text` and its `content-desc`, which is also how the transport's `Play` label is found.
- [DESIGN] **Each verify script stands alone.** `run-all.sh` runs them in the contract's order, but
  `verify-media-session.sh` opens the reader itself (it re-sends the same share intent) rather than assuming the
  previous script left a document on screen: a script that only works when its predecessor ran is not a
  verification, and the contract's phrase "with the shared document open" describes the state it needs, which it
  therefore establishes.
- [DESIGN] **Cleanup is unconditional.** `run-all.sh` runs `stop_hub` and removes the port reverse whatever
  happened, including when a verify script fails, so the hub process and the device's forward list are as they
  were found (contract's Forbidden Actions).
- [DESIGN] **A failing check is reported, never repaired.** This unit may not touch application source, so a check
  that cannot pass is a `BLOCKED` entry with the script's own output (contract's Forbidden Actions).

### 6.3 The first two official runs, and the two harness defects they exposed

The fixed command was run three times in this session. Run 1 was killed by this session's own process management
during its gradle configuration phase, so it is not a result and is recorded only so the log's `build_release_apk:
gradle exited non-zero` line is not mistaken for one. Run 2 (`EXIT=1`) failed **in the harness**, and both
defects are worth recording because they were mine:

1. **`ui_nodes` merged a container with its first child.** `uiautomator` writes a container as `<node …>` with
   its children after it, and the parser split the tree on `/>`, so a container and the child that followed it
   landed on one line and the child's own text was read as the container's empty `text=""`. The reader's own
   paragraph and the setup screen's Connect button were both invisible to the harness while being plainly on
   screen. Splitting at every `<node` fixes it; the measurement is that the same dump that reported 2 text nodes
   reports 12 after the fix.
2. **The provisioning sequence assumed a cold deep link works.** Measured: a cold start whose initial address
   carries a query string draws nothing, while `lectern://setup` alone draws the screen and the same address
   delivered to the running app fills it in — and whichever screen a deep link does open is replaced by the
   entry route's own redirect a few seconds later. The script now opens the bare link, then the link carrying
   the address and token, presses the button while it is on screen, and retries the whole sequence up to three
   times.

Both are harness fixes; neither changes what the contract requires the run to prove, and the authoritative run
in §6.1 is the final scripts.

## 7. Deviation proposals

1. **The contract's target and the inspection string name different targets.** The contract's *REA Inspection
   Target & Method* is `T-SHOTS` (`targets/shots/android/`), while the `UNAVAILABLE` reason this session was asked
   to record names `targets/android/base.apk` (that is `T-APK`, another unit's target). Both are absent from this
   host, so nothing about the unit's work changes; the wording is filed for the operator to reconcile.
2. **`dumpsys media_session` cannot show the notification's own action buttons.** It reports the session's
   transport state, its metadata and its queue, which is what the platform's lock screen and its media
   notification are both drawn from — so the run proves the session is published, controllable and still playing
   with the app in the background and the screen off, and the *set* of buttons remains F§10.4's declaration
   (`audio-session.ts`'s four options) rather than an observed count. A patched contract could name a screenshot of
   the notification as the evidence for the button set.
3. **`adb shell media` does not exist on this device**, so the contract's fallback form (`media dispatch`) cannot be
   exercised here; the primary form (`cmd media_session dispatch`) is the one that runs. The fallback stays in
   `media_dispatch` for platforms that have the older command.
4. **`run-all.sh` installs a release APK, so the diagnostics run and the playback run are two builds of the same
   commit.** The contract fixes `build_release_apk` and `install_apk`, and `--clean` means the prebuild the script
   runs is the one the verified APK was built from; the install therefore cannot drift from the source it claims to
   verify.
5. **The audio queue sink does not play on this device, and this is the unit's blocker.** `FAIL audio-sink`: 5 of 7
   conformance cases fail, positions never advance, and chunks never finish with durations of `0 ms`, while the
   mock engine's own WAV is valid (§6.4). The contract requires `PASS audio-sink`, and the sink is
   `apps/android/src/audio/expo-queue-sink.ts` — U-047's frozen file, which this unit may not touch. A patched
   contract should either own that repair (a U-047-P1 with `Patch scope`) or scope this check to the four rows that
   do hold.
6. **The tab group's routes render nothing.** `lectern://settings` and `lectern://library` draw no content at all
   on this device, while every root-level route (`setup`, `diagnostics`, `read/[docId]`) draws normally. The route
   context is complete in the built bundle (every route path, including `.(tabs)/settings.tsx` and
   `.(tabs)/_layout.tsx`, is in `assets/index.android.bundle`), so the files are bundled and it is the tab
   navigator that renders nothing. No check in this unit depends on it — the harness was moved off the settings
   screen for exactly that reason — but it is a defect a reader would meet immediately, and F§10.4's navigation is
   "tabs Library, Scan, Settings".
7. **The entry route replaces a deep-linked screen a few seconds after it appears** (§6.4, last row). The harness
   works around it by opening the contract's link twice and retrying the sequence; a patched contract could either
   fix the app (the redirect should not replace the screen a deep link opened) or bless the workaround in the
   contract's own words.
8. **`dumpsys media_session` prints the session's metadata positionally on this platform** —
   `metadata: size=4, description=…, …, null` — not as `artist=…`, so the step that requires "the visible sentence
   has advanced" reads the positional form. It could not be exercised in this run: the check stops at the state
   before it, because playback never starts.
9. **R8 minification damages reflection-based libraries in the release build.** Logcat for the installed APK
   carries `ComponentDiscovery: y32: Could not instantiate com.google.mlkit.common.internal.CommonComponentRegistrar`
   and the same for `com.google.mlkit.vision.text.internal.TextRegistrar`, both `Caused by:
   java.lang.NoSuchMethodException: … <init> []` — R8 removed constructors those libraries discover by reflection.
   The release build enables it (`android.enableMinifyInReleaseBuilds=true` in the generated
   `apps/android/android/gradle.properties`, with the template's default `proguard-rules.pro`), which means the
   on-device scanner U-051 built is likely broken in a release APK even though its debug build was fine. This is
   outside this unit's file scope; it is filed because this unit is the first to run a release build at all.
10. **A connection to the harness URL was already in the app's secure store when this session first read the
    diagnostics screen**, so `hub-health` passed before this session had pressed anything. How it was written is
    `UNKNOWN` — the setup screen's button is the only writer and this session did not press it before then. It
    changes nothing about the run (the script provisions the connection itself, and `hub-health` is what proves it
    landed), but it is recorded rather than left unexplained.
