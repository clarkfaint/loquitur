## 3. Architecture notes

### 3.1 The client (F§7.2)

One typed call per phase-1 route, over the injected `fetch`. Every request is built from three things — the
hub's origin, F§11's token, and the transport — so nothing reads a global and the package stays isomorphic.
The token is written into an `authorization` header on every request and never into a URL or a query string.

- `GET /healthz` and `GET /v1/voices` are plain reads.
- `POST /v1/tts` sends `{ text, voiceId, synthSpeed }` with `synthSpeed` defaulting to `1` — the speed the
  hub's cache is shared at (F§7.3), so a caller that names none gets the cached chunk.
- `GET /v1/tts/audio/:chunkId` reads the bytes; the id is percent-encoded on the way into the path.
- `POST /v1/parse` has its three forms: raw bytes with `Content-Type` plus F§7.2's `x-lectern-filename`
  header, JSON `{ url }`, and JSON `{ text, title? }` (the `title` key is absent, not `undefined`, when the
  caller states none — F§7.2's schema is `exactOptional`).

Every answer is parsed with the `@lectern/api-contract` schema that owns that route, so the two ends of a
request cannot drift: `HealthResponseSchema`, `VoicesResponseSchema`, `TtsResponseSchema`,
`ParseResponseSchema`. A refusal is read back through `ErrorBodySchema`, so the code a caller switches on is
the hub's own.

### 3.2 The caching chunk source (F§5.8, F§5.9, F§6)

`get({ text, voiceId, synthSpeed })` splits the voice id into F§6's two halves and computes the chunk id
locally with `chunkIdFor`, so the cache can be consulted before anyone is asked anything. The cache is keyed
by the chunk id for the audio and by `<chunkId>.json` for its metadata (mime, duration, timings, timing
source — the same fields, spelled with the contract's own `WordTimingSchema` and `TimingSourceSchema`).

- **Hit** = both halves present and the sidecar readable as that shape. The answer is the cache's URI, so the
  bytes are played locally.
- **Miss** = the client calls `tts`, downloads `ttsAudio`, stores the audio and then the metadata, and answers
  with the URI `put` returned.
- **One request per chunk**: a `Map` of in-flight promises keyed by chunk id. A second caller for the same
  chunk while the first is in flight awaits the same promise, so a play and a prefetch of one sentence cost
  one synthesis between them. The entry is removed when the load settles, at which point the chunk is cached.

`prefetchDocument(doc, voiceId, opts)` walks `playableSentences(doc, { skipFurniture })` in document order,
awaits `get` for each sentence's text, and yields `{ done, total }` after every sentence — plus one step of
`{ done: 0, total }` before the first, so a caller can show the bar immediately. The default `skipFurniture`
is `true`: a prefetch caches what playback will read. `isCached(text, voiceId, synthSpeed)` answers the same
question the hit rule does, without touching the network.

### 3.3 Measured facts that shaped the code

1. **`inject` JSON-encodes a payload it does not recognise as bytes.** `light-my-request`'s
   `lib/request.js:219`: `if (payload && typeof payload !== 'string' && !payloadResume && !Buffer.isBuffer(payload)) payload = JSON.stringify(payload)`.
   A plain `Uint8Array` is *not* a `Buffer`, so the first rehearsal's `parseFile` arrived at the route as the
   string `{"0":76,"1":101,…}` — the JSON of the array's own index object — and the document hashed to
   `11df8e4c…` where the same text stated as JSON hashed to `c2ef47d9…`. The adapter now converts bytes to a
   Node `Buffer` at that boundary.
2. **`BodyInit` admits only `ArrayBuffer`-backed views.** A probe compiled against this repository's
   `tsconfig.base.json` with the repository's own compiler: `{ body: bytes }` for a bare `Uint8Array` fails
   (`TS2322 … is missing the following properties from type 'URLSearchParams'`), `new Uint8Array(bytes)`
   compiles, and `bytes.slice()` compiles. Both byte boundaries therefore hand over a fresh
   `ArrayBuffer`-backed copy.
3. **`inject` sets `content-length` itself when none is given** (`lib/request.js:227-234`, from
   `Buffer.byteLength` for a string and `payload.length` for bytes), which is why the adapter copies every
   answer header except `content-length` and `transfer-encoding` and lets `Response` decide its own.
4. **A real `FastifyInstance` satisfies a structural app type.** The rehearsal compiled
   `const structural: InjectingApp = app;` and `fetchFromFastify(app)` for an instance returned by
   `buildApp`, so the adapter needs no `fastify` type — and the package declares no `fastify` dependency,
   which R10's install list does not name.
5. **The delivered test files are the only thing the official program excludes.** With the second program
   (`include: ["src"]`, `exclude: []`) the complete diagnostic list is 7 `TS2591`s, one per `node:` specifier
   in the two test files — no `TS7006`, and nothing else.

## 4. Lectern design

- [DESIGN] A transport failure is `code: "ENGINE_UNAVAILABLE"`, `status: 0`, `offline: true`. F§7.2's set is
  about what a hub answered and holds no code for a hub that was never reached, so the one code about an
  unreachable backend carries it and `offline` is the field that makes it unambiguous.
- [DESIGN] A `2xx` whose body is not the route's schema is `code: "INTERNAL"` with the status the hub
  answered: the exchange worked and the two ends disagree about the shape.
- [DESIGN] A cache hit needs both halves. A sidecar that is absent, unreadable or not the metadata shape
  counts as a miss and is replaced, because a chunk whose timings cannot be trusted is worth re-synthesizing.
- [DESIGN] `prefetchDocument`'s options are `{ synthSpeed?, skipFurniture? }` defaulting to `1` and `true`,
  and its first step is `{ done: 0, total }` (the contract fixes the progress shape, not the option names).
- [DESIGN] `isCached` answers `false` for an id that is not an `engine:voice` pair rather than throwing:
  nothing can be cached under an id no chunk id can be computed from. `get` does throw for it
  (`UNKNOWN_VOICE`, `offline: false`), because a request was made and cannot be honoured.
- [DESIGN] The testing adapter takes an `InjectingApp` — the one capability it uses — instead of Fastify's
  own type, so `packages/api-client` needs no dependency R10 does not name; `fetchFromFastify` is typed as
  `typeof fetch` while its domain is the URL-plus-init form the client uses.
- [DESIGN] Writes to the cache use the chunk id the hub answered with, reads use the locally computed one.
  The two are equal by construction (both are F§6's formula over the same four fields) and the test pins the
  equality rather than trusting it.

## 7. Deviation proposals

- **`prefetchDocument`'s options are not specified.** The contract gives the signature as
  `prefetchDocument(doc, voiceId, opts)` and the yielded shape as `{ done, total }`, but not the option
  names, the defaults, or whether a `0` step is reported. The implementation chose
  `{ synthSpeed?, skipFurniture? }` with defaults `1` and `true`, and a first step of `{ done: 0, total }`.
  Proposed wording for F§5.8: *"`prefetchDocument(doc, voiceId, { synthSpeed = 1, skipFurniture = true })`
  caches every sentence `playableSentences` returns and yields `{ done, total }` once before the first
  sentence and once after each."*
- **The client does not clamp `synthSpeed`.** F§7.2's TTS body accepts 1.0–4.0 and F§6's engines accept
  0.25–4.0; a caller that hands the client a value outside the body's range is refused by the hub with
  `BAD_REQUEST`, which is the honest answer (the hub is the owner of its own limits). If the client should
  clamp instead, that belongs in F§5.6(e)'s wording.
- **`@lectern/server`'s `exports` map names a path that does not exist.** `apps/server/package.json` declares
  `"./testing": "./src/testing/index.ts"`, and `apps/server/src/testing/` is absent (U-019's manifest). No
  module imports it today; a later unit that does will fail to resolve. Not touched — R6 freezes that file,
  and this unit's contract does not list it under *Patch scope*.
