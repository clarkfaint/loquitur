# Evidence — U-018 api-contract: engine route schemas
Date: 2026-11-14 · Target: N/A · Inspection: N/A

## 1. Questions
The contract's *REA Inspection Target & Method* is `Target: N/A — the hub API is a Lectern design. Never inspect
or record the reference product's network API. Do not call REA.`, so no behavioural question is put to a target
and this session made no REA call. The questions the unit's schemas answer, all of them design questions, are:

- what each phase-1 route's request and answer bodies are, field by field (F§7.2);
- which of those fields already have an owner elsewhere, so this package imports them instead of re-spelling
  them (F§5.1's `DocumentModel` and `PdfAnchor`, F§6's `Voice`);
- how a route reports a failure, and whether the code set is closed;
- how the TTS request's optional engine speed behaves when it is absent, and what a TTS answer carries;
- how the JSON half of the parse route says which source it means.

## 3. Architecture notes
The package is one isomorphic barrel (`src/index.ts`) over two modules: `src/common.ts` holds the error envelope
and the code set every route shares, `src/engine-api.ts` holds phase 1's seven shapes. It imports zod, the
isomorphic `@lectern/core` entry and `@lectern/core-tts` — nothing from Node, the DOM or React — so the hub that
answers a route, the browser client, the extension and the desktop app all validate the *same* schema object.
That is the point of the package: one side builds a request with a schema, the other validates the answer with
it, and neither can drift without a test failing.

**Error envelope.** `ErrorBodySchema` is `{ error: { code, message } }`, strict at both levels, and the code is a
closed zod enum of the thirteen names F§7.2 lists. A route that answers with a code outside the set fails its own
response check rather than reaching a reader as an unexplained failure.

**Health and voices.** `HealthResponseSchema` carries F§7.2's `{ ok, version, engines }`. `VoicesResponseSchema`
is the bare `Voice[]` F§7.2 writes — the route table says `Voice[]` for this route where it writes `{ … }` for the
TTS and parse answers, so the array is normative rather than an envelope.

**TTS.** `TtsRequestSchema` is `{ text, voiceId, synthSpeed? }`: the text is 1–1 000 characters (a JavaScript
string's own length), `voiceId` is a non-empty `engine:voice` string, and `synthSpeed` is a number in 1.0–4.0
that **defaults to 1** — so a parsed request always carries a speed, and the ordinary playback path (F§5.6(e)
keeps `synthSpeed` at 1.0 until the sink cannot reach the rate alone) asks for the same chunk as the cached one.
`TtsResponseSchema` is the six fields F§7.2 names: the chunk id, the container (F§6's two mimes), the integer
duration, the word timings with their source, and the path that serves the bytes.

**Parse.** One route, two body kinds. `ParseJsonRequestSchema` is the JSON half — a URL to fetch or text to read,
exactly one of the two — while raw bytes travel in the request body with their name in `FILENAME_HEADER`. The
answer, `ParseResponseSchema`, carries F§5.1's whole `DocumentModel` and the `PdfAnchor`s a paged source gave its
sentences; a pageless source has none, so `anchors` is optional.

**Strictness.** Every object here is `z.strictObject`, so a field this design does not define is refused at the
boundary instead of being silently carried: these are the shapes the hub and its clients agree on, and an
unlisted field is exactly the kind of drift a shared schema exists to catch.

## 4. Lectern design
- [DESIGN] `ErrorCode` is `z.infer` of `ErrorCodeSchema`, a closed zod enum of F§7.2's thirteen codes — the same
  schema-derives-the-type pattern every earlier unit used for F§5.1's types (U-002), so the runtime set and the
  compile-time union cannot diverge. The set is re-spelled here rather than imported because its only existing
  owner, `ParseErrorCode` (`packages/core/src/parsers/dispatch.ts:91`), lives under the **Node-only**
  `@lectern/core/parsers` entry, which an isomorphic package may not reach (AGENTS §7).
- [DESIGN] `ErrorBodySchema` is strict at both levels; the contract's own words are `{ error: { code, message } }`
  and nothing beside it.
- [DESIGN] `FILENAME_HEADER` is the lower-case `x-lectern-filename`; F§7.2 spells the header
  `X-Lectern-Filename`, and a header name is case-insensitive, so the constant exists to keep one spelling
  between the hub and a client rather than to assert a case.
- [DESIGN] `HealthResponseSchema` types `ok` as a boolean and `version`/`engines` as non-empty strings and a
  list of them. `engines` is a list of engine ids rather than a hard union of `kokoro | piper | mock`, because
  F§6 types `TtsEngine.id` as `string` and F§7.1 leaves which engines exist to configuration; a hard union here
  would refuse a hub that enables an engine F§6's prose does not enumerate. Section 7 proposes saying so.
- [DESIGN] `VoicesResponseSchema` is F§7.2's bare array, and the delivered test pins that by refusing an
  enveloped body — the one place the two readings differ.
- [DESIGN] `WordTimingSchema` and `TimingSourceSchema` re-spell F§5.6's two wire values (`{ i, s, e }` in integer
  milliseconds, `'engine' | 'estimated'`) because F§5.6 declares them as TypeScript interfaces only, with no
  schema anywhere to import. Their field names and units are F§5.6's, not invented, and the test drives
  F§5.6(a)'s golden timings through them.
- [DESIGN] `TtsRequestSchema.text` is `z.string().min(1).max(1000)`: F§7.2's "Text limit 1 000 characters",
  measured the way a JavaScript string counts (`length`), which is what the hub will slice and tokenize.
- [DESIGN] `synthSpeed` is `z.number().min(1).max(4).default(1)`. The range is F§5.6(e)'s clamp for the engine
  speed; the value is **not** restricted to quarter steps, because F§7.2 states a range while the quarter-step
  rounding belongs to `planSpeed` on the client (U-012), and a schema that demanded the grid would refuse a
  request the hub can serve.
- [DESIGN] `voiceId` is a non-empty string and nothing more: which engines and voices exist is the hub's
  question, and F§7.2 answers `UNKNOWN_VOICE`. Checking the `engine:voice` shape here would turn a missing voice
  into `BAD_REQUEST` and a malformed one into `UNKNOWN_VOICE` for no gain; `parseVoiceId` (U-015) stays the only
  place that splits an identifier.
- [DESIGN] `TtsResponseSchema.mime` is the union of F§6's two containers, and `durationMs` and every timing are
  `z.int().nonnegative()`, because F§5.6 states that all times are integer milliseconds of media time. `chunkId`
  is a non-empty string rather than a 40-character hex: F§6 fixes the length of what `chunkIdFor` produces, and a
  schema that repeated it would be a third place the length lives. The test quotes F§6's golden id verbatim.
- [DESIGN] `audioPath` is a non-empty string — the path that serves the bytes (F§7.2's
  `GET /v1/tts/audio/:chunkId`) — deliberately not pinned to a prefix or to a filesystem form, so a hub mounted
  under a prefix or answering an absolute URL is not refused by its own contract. Section 7 proposes wording.
- [DESIGN] `ParseJsonRequestSchema` puts `.exactOptional()` on all three fields (so a parsed body never carries
  an explicit `undefined`, matching `exactOptionalPropertyTypes`) and adds one `refine` that exactly one of `url`
  or `text` is present, reported at `["url"]`. The refinement passes zod 4's current `error` key — `message` is
  deprecated in the installed build (section 5).
- [DESIGN] `title` stays optional and unrestricted. F§7.2 lists `{ text, title? }` for the text form and `{ url }`
  for the fetch form, but states no rule that a title may not accompany a URL, and the contract states exactly
  one rule ("exactly one of `url` or `text`"); a second, unstated refinement would refuse a body the route can
  serve. Section 7 proposes the sentence that would settle it.
- [DESIGN] `ParseResponseSchema` imports `DocumentModelSchema` and `PdfAnchorSchema` from `@lectern/core` rather
  than re-spelling F§5.1's model: that model has one owner (U-002), and a copy here could drift from it.
- [DESIGN] `packages/api-contract/vitest.config.ts` runs in the Node environment, as the contract asks, and
  includes `src/**/*.test.ts`. The manifest mirrors `packages/core-tts`'s shape: `"type": "module"`, an `exports`
  map onto TypeScript source, one `typecheck` script, and **no declared test runner** — `pnpm --filter
  @lectern/api-contract exec vitest` finds the workspace root's binary, which keeps R10's dependency list to the
  three packages the contract names (zod 4.6.7, and both workspace packages).
- [DESIGN] No exported barrel line was added anywhere: this unit *creates* its barrel rather than appending to an
  existing one, so §5's append-only rule has nothing to protect here.

## 7. Deviation proposals
1. **`F§7.2` writes `Voice[]` for `GET /v1/voices` and `{ … }` for the other two answers.** The schema follows
   the bare array, and its own test refuses an enveloped body. Proposal: say in `F§7.2` whether a bare array is
   normative, so a later hub that wants a revision or an `etag` beside the list knows it is a contract change.
2. **`F§7.2` states no rule for `title` beside `url`.** `{ text, title? }` and `{ url }` are listed, but a body
   carrying both a URL and a title is neither forbidden nor described; the schema accepts it and the fetch path
   would ignore the title. Proposal: state whether a `title` with a `url` is refused with `BAD_REQUEST` or
   ignored.
3. **Which layer refuses a URL's scheme.** `F§7.2` says the `{ url }` fetch follows only `http:`/`https:` and
   refuses loopback, link-local and private hosts unless `LECTERN_ALLOW_PRIVATE_FETCH=1`, and the schema checks
   only that the value is a non-empty string — so a `file:` URL reaches the route and is answered
   `FETCH_REFUSED`/`BAD_REQUEST` rather than failing validation. Proposal: name the layer that refuses a scheme
   (this is also how section 4's missing `url` format check should be read).
4. **The five parser codes have an owner only under the Node-only entry.** `ParseErrorCode`
   (`packages/core/src/parsers/dispatch.ts:91`) is exactly the five codes the hub must map a parser failure to,
   but it sits under `@lectern/core/parsers`, which an isomorphic contract package may not import — so this unit
   re-spells them in `ErrorCodeSchema`, and the two lists can drift. Proposal: move the shared code union into
   the isomorphic entry (`@lectern/core`) and have both the parsers and the API contract import it.
5. **`OCrEngineErrorCode`'s `OCR_RESPONSE_INVALID` has no place in `F§7.2`'s error set.**
   `packages/core/src/parsers/ocr-tesseract.ts:37` defines a code for an unreadable OCR answer, while the
   contract's thirteen codes (and therefore `ErrorCodeSchema`) have none for it, so a hub must fold an OCR
   engine fault into `PARSE_FAILED` or `ENGINE_UNAVAILABLE`. Proposal: either add the OCR fault to `F§7.2`'s
   list or state in `F§7.2` which of the thirteen an OCR engine failure is reported as.
6. **Every `pnpm --filter … exec` fixed command prints a policy failure that is not one.** The pre-script
   dependency check runs an install first, which refuses `tesseract.js`'s ignored build script and prints
   `Error: ERR_PNPM_IGNORED_BUILDS` plus `[WARN] The install that runs before scripts failed …` above the run,
   while the command still exits 0 (section 6.2). It is noise from U-010's dependency and a reader can mistake it
   for this unit's failure. Proposal: set `verifyDepsBeforeRun: false` (or approve the build script) in the
   workspace configuration so a fixed command's output carries only its own result.
