# Evidence — U-019 Hub: server skeleton, authentication, voices and TTS routes
Date: 2026-11-14 · Target: N/A · Inspection: N/A

## 1. Questions
The contract's *REA Inspection Target & Method* is `Target: N/A — the hub is a Lectern design. Do not call REA.`,
so no behavioural question is put to a target and this session made no REA call. The questions this unit's files
answer are Lectern's own design questions:

- how F§7.1's environment table becomes one validated configuration, and what happens to a value the table does
  not allow — the token's 32-character floor, a port that is not a whole number, and a `0`/`1` flag that is
  neither;
- what the hub's one failure type is, and how every failure — a route's own, a framework refusal, an
  unclassified crash — leaves as F§7.2's `{ error: { code, message } }`;
- how F§7.2's exemption for `/healthz` and for a browser's preflight is expressed, and how the token is compared;
- which engines F§7.1's variables enable, and how a route reaches the engine behind a voice id when F§6's
  registry exposes only a merged voice list;
- what F§7.3's on-disk cache holds, how a chunk is written so an interrupted write is never read, and how
  concurrent readers share one synthesis;
- which files F§7.3's layout names, and what a byte-range request answers;
- what this package's type-checking program can contain on a host where `@types/node` is absent and R10 forbids
  adding it, given that the hub is the one piece of Lectern that reads the environment and writes to disk.

## 3. Architecture notes
**Module map.** `src/index.ts` is the registry: it re-exports `buildApp`, `loadConfig` and their types, and
nothing else. `src/app.ts` builds the instance; `src/config.ts`, `src/errors.ts`, `src/auth.ts`,
`src/context.ts` and `src/tts-cache.ts` are the pieces it is assembled from; `src/routes/index.ts` is the route
registry, and `src/routes/health.ts`, `voices.ts` and `tts.ts` are the three modules it lists. `src/main.ts` is
the only file that reads a process global or opens a socket.

**Request lifecycle.** Fastify routes, then runs `onRequest` hooks in registration order, and the CORS plugin's
hook answers a preflight (`OPTIONS`) before anything else. The auth hook is the next thing a request meets and
the only place the token is examined. A handler that returns a value has it serialized; a handler that throws
reaches `setErrorHandler`, and a path no route matches reaches `setNotFoundHandler` — both of which answer
through F§7.2's envelope, so a client parses one shape whatever happened. `buildApp` never listens: the entry
point owns the socket, and a test injects straight into the instance.

**The token check.** One pre-shared token (F§11), compared by `constantTimeEquals`: the loop runs to the longer
string's length, out-of-range positions read as zero, and the length difference is folded into the accumulator
rather than answered first, so a caller cannot learn the token's length or how far a guess got. `OPTIONS` is
exempt because a browser's preflight carries no `Authorization` header, and `/healthz` because a probe that
answered `401` could not tell an operator the hub is up. A missing or malformed header and a mismatched token
both answer `401 UNAUTHORIZED`; a token presented with a different length still walks the whole comparison.

**The engine set.** `enabledEngines(config)` builds exactly the engines F§7.1 enables, in the table's order
(`KOKORO_URL` → kokoro, `PIPER_URL` → piper, `LECTERN_ENABLE_MOCK=1` → mock) and nothing else: an unset variable
means the engine is not offered, so an unconfigured hub has no engine that could reach a network. F§6's
`createEngineRegistry` merges the voice lists and keeps the answers that arrived, so one backend that is down
costs only its own voices. Because the registry exposes just `listVoices` and `resolve`, `createHubEngines` adds
the two lookups the hub itself needs: `ids()` for the health probe — taken from the engine set the context
actually holds, so a hub whose engines were replaced reports what it really has — and `targetFor(voiceId)`,
which walks an id to the engine and voice behind it and answers `404 UNKNOWN_VOICE` for a malformed id, an
engine nobody enabled, and a voice no engine offers.

**Chunk identity and the cache.** A chunk is named by F§6's `chunkIdFor(engine, engineVoiceId, synthSpeed, text)`
over 40 hexadecimal characters, computed by the route as its cache key and again inside `synthesizeChunk`, from
the same four values — so the id the cache files a chunk under is the id the client is answered with, and the
route's own path never touches the filesystem with anything else: the audio route tests the parameter against
`^[0-9a-f]{40}$` before the cache is reached. F§7.3's layout is `{DATA_DIR}/tts-cache/<first two characters of
the id>/<id>.wav|.mp3` beside `<id>.json`. A write goes through a uniquely named temporary file and a rename,
audio first and sidecar second, so an interrupted write leaves a file no reader treats as complete: a read
begins at the sidecar, validates it, and only then reads the audio it names; a sidecar that is missing,
unparsable, or of a shape this design does not define is a miss, and audio missing beside a sidecar it can read
is a miss too. The cache is never the truth — every entry can be synthesized again.

**Concurrency.** The cache holds one promise per chunk id. A request reads the disk first; on a miss it looks for
an in-flight synthesis and shares it if there is one, and otherwise starts one and records it before yielding.
Ten concurrent requests for one chunk therefore reach the engine once, and the second identical request is
answered from the file the first one wrote (measured in section 6.1). A failed synthesis releases its map entry
in a `finally`, so a later request tries again rather than inheriting the failure.

**Byte ranges.** `Range: bytes=start-end`, `bytes=start-` and `bytes=-suffix` are answered `206` with
`Content-Range: bytes start-end/size` and exactly the requested slice of bytes; anything else — a malformed
header, a multi-part range, or one that does not fit the chunk — is `416`, because answering the whole chunk
would hide that the client asked for something this chunk cannot satisfy. `Content-Length` is left to Fastify,
which derives it from the payload it is given.

**The host boundary.** The hub is Node-only, but this host has no `@types/node` and R10 forbids installing one,
so the program is written to need no Node ambient type: `loadConfig` takes the environment as an argument,
`src/tts-cache.ts` reaches the file API through a specifier held in a `string`-typed variable (so the compiler
does not try to resolve a built-in it cannot resolve), and `main.ts` — the only file that needs the process —
declares the two globals it uses at module scope. Nothing else in the package reaches for a global. The package's
`tsconfig.json` keeps the test directory out of the program for the same reason: the delivered test file reads
`node:fs/promises`, `node:os` and `node:path`, which no file this unit may write can declare.

## 4. Lectern design
- [DESIGN] `ConfigSchema` is F§7.1's table as one strict zod object, and `Config` is `z.infer` of it — the same
  schema-derives-the-type pattern U-002 and U-018 used, so the validated shape and the compile-time type cannot
  drift. `strictObject` refuses a field the table does not name.
- [DESIGN] The token is required and at least 32 characters, checked before the schema runs so the refusal names
  the variable and the received length rather than a zod path (`LECTERN_TOKEN must be at least 32 characters
  (F§7.1), received <n>`). F§7.1 marks it required in its own table and F§11 makes it the whole authentication
  story, so a hub without one must not start.
- [DESIGN] `LECTERN_ENABLE_MOCK` and `LECTERN_ALLOW_PRIVATE_FETCH` accept exactly `0` and `1`, and anything else
  fails configuration instead of falling back to the default. F§7.1 writes `1` enables / `0` disables for both;
  treating `true`, `yes` or a typo as "off" would leave an operator believing a feature is on.
- [DESIGN] An empty environment value counts as unset: `LECTERN_DATA_DIR=` yields the default `./data`, and
  `KOKORO_URL=` leaves the engine off. A variable that a shell or a compose file sets to nothing is the usual
  way an operator removes a value, and the alternative is an engine adapter built on an empty base URL.
- [DESIGN] `LECTERN_PORT` is `z.int().min(1).max(65535)`, and a non-integer value is refused by name before the
  schema sees it; `LECTERN_MAX_UPLOAD_MB` is `z.int().min(1)`. F§7.1 states no ranges beyond its defaults, so the
  only bounds here are the ones a socket and a size can physically have.
- [DESIGN] `HUB_VERSION` is `"0.0.0"`, the workspace's own version (`package.json`), and lives in `config.ts`
  beside the configuration it describes. F§7.2's probe carries `version` but no section says where it comes
  from; a constant read from one place keeps the answer stable, and a later unit that wants the manifest's value
  changes one line. Section 7 proposes saying so.
- [DESIGN] `HubError(code, message, status?)` carries F§7.2's code from `@lectern/api-contract`'s closed set and
  defaults its status to `STATUS_FOR_CODE[code]` — one table, `UNAUTHORIZED` 401, `BAD_REQUEST` 400,
  `NOT_FOUND`/`UNKNOWN_VOICE` 404, `PAYLOAD_TOO_LARGE` 413, `UNSUPPORTED_FORMAT` 415, `INVALID_EPUB`/
  `DRM_PROTECTED`/`EMPTY_DOCUMENT` 422, `PARSE_FAILED`/`INTERNAL` 500, `FETCH_REFUSED` 400 and
  `ENGINE_UNAVAILABLE` 502 — so a route names a code and gets a coherent status unless it passes one. The status
  is a parameter because an unsatisfiable byte range needs `416` with a code from the closed set, and F§7.2 has
  no code for "the range does not fit".
- [DESIGN] Every answer, including every error, is produced by parsing through the contract's own schema
  (`ErrorBodySchema`, `HealthResponseSchema`, `VoicesResponseSchema`, `TtsRequestSchema`, `TtsResponseSchema`),
  so the hub cannot answer a shape its own contract refuses. The parse sits before `reply.send`, which is also
  where a design mistake in a handler would surface as an `INTERNAL` rather than as a malformed body.
- [DESIGN] An unclassified failure answers `INTERNAL` with the fixed message `the hub could not complete this
  request`, discarding the caught value's text: a stack trace or an engine's own words are not a client's
  business (F§11). A framework refusal that carries a 4xx status keeps that status and is reported as
  `BAD_REQUEST` — the client's own fault — except the two content-type faults, which map to
  `UNSUPPORTED_FORMAT` 415, and `FST_ERR_CTP_BODY_TOO_LARGE`, which maps to `PAYLOAD_TOO_LARGE` 413. The codes
  and their statuses are quoted from the installed build in section 5.
- [DESIGN] `setNotFoundHandler` answers the same envelope for a path no route matches, so a client parses one
  shape. It is registered in `app.ts`, not in a route module, because a not-found handler is not a route; the
  contract's "do not register routes in `app.ts`" is honoured by the loop over `routes`, which is the only place
  a path is declared.
- [DESIGN] Authentication is `constantTimeEquals`, this package's own comparison over UTF-16 code units, with no
  `node:crypto` anywhere: `timingSafeEqual` needs equal-length buffers and throws on a length mismatch, which is
  itself an oracle for the token's length, and reaching it would mean the same built-in-specifier problem the
  file API has. The comparison folds the length difference into its accumulator and reads both strings to the
  end, which is what F§7.2's "constant-time comparison" needs. AGENTS §7's ban on non-null assertions is
  respected throughout: `HubEngines.targetFor` narrows by hand rather than asserting.
- [DESIGN] CORS is `{ origin: true, credentials: false }` and explicitly lists the headers a client may send
  (`authorization`, `content-type`, `range`, `x-lectern-filename`) and may read (`accept-ranges`,
  `cache-control`, `content-length`, `content-range`). F§7.2 requires any origin with the `Authorization` header
  and no credentials, because authentication is header-based and cookie-free; `exposedHeaders` is needed for a
  browser to read `Content-Range` at all, which is what makes F§7.2's range support usable from the page client.
- [DESIGN] `buildApp(config, overrides)` takes the pieces a caller may replace (`engines`, `ttsCache`) plus a
  logger, and defaults to `logger: false`. The contract defines `overrides?` without saying what may be
  overridden; the engines are what the delivered test observes, and the cache is the other half of F§7.3's
  behaviour. A hub built by a test is silent, and the entry point decides what its log carries.
- [DESIGN] `main.ts` asks for `{ level: "info", redact: ["req.headers.authorization"] }`: Fastify's default
  request line carries method, url, host and remote address and no headers at all, and the redaction is the
  belt-and-braces for the one header a token ever travels in. Measured in section 6.1: a live run with a valid
  token logs nine lines and contains the token zero times.
- [DESIGN] Shutdown is once-only and idempotent: the first `SIGTERM` or `SIGINT` closes the instance and exits,
  and a second signal cannot interleave two closes. The entry point is the only place a signal is handled, and
  nothing in the hub installs a handler of its own.
- [DESIGN] The audio route answers `Cache-Control: public, max-age=31536000, immutable`, `Accept-Ranges: bytes`
  and the chunk's own mime exactly as F§7.2 prescribes for this route, and `reply.send` is given a
  `Uint8Array` (a `subarray` view for a range) — the installed build converts one to bytes without a copy
  (section 5), so no `Buffer` is named anywhere in this package and no ambient Node type is needed to send audio.
- [DESIGN] `apps/server/package.json` exports `"."` and `"./testing"` as the contract requires. The `./testing`
  target, `./src/testing/index.ts`, is this unit's contract text but not one of its *Required File Outputs*, so
  no such file is created here; the subpath is declared and resolves once the unit that delivers the hub's test
  helpers adds it. Section 7 records it.
- [DESIGN] `apps/server/vitest.config.ts` runs in the Node environment, as the contract asks, and includes
  `src/**/*.test.ts`. The manifest mirrors the packages' shape — `"type": "module"`, an `exports` map onto
  TypeScript source, `typecheck` as `tsc --noEmit -p tsconfig.json`, `test` as `vitest run` — and declares **no
  test runner**: `pnpm --filter @lectern/server exec vitest` finds the workspace root's binary, which keeps R10's
  dependency list at exactly the packages the contract names (fastify 5.12.8 and zod 4.6.7 from F§2.3,
  `@fastify/cors` 11.4.3 and `tsx` 4.23.15 at the registry's current versions, and the three workspace packages).
- [DESIGN] The engines and cache are built per `buildApp` call and reach the routes only through the context
  object, so the hub holds no module-level state except the cache's temporary-file serial; two hubs in one
  process cannot share a cache or a registry by accident.
- [DESIGN] `docs/status.md` is appended exactly once, after the fixed command and all four standing gates exited
  0, and the ledger row's commit is the `feat(U-019)` commit read from `git rev-parse --short HEAD` — never a
  placeholder, because that commit cannot name itself.

## 7. Deviation proposals
1. **The contract's `apps/server/tsconfig.json` is described as "extends the base config, Node types", and
   "Node types" cannot be honoured on this host.** `@types/node` is not installed anywhere in the repository
   (no `node_modules/@types`, no `@types+node` in the virtual store — U-018's evidence recorded the same), and
   R10 allows only the packages a contract or F§2.3 names, which this contract's *Installs* line does not extend
   to it. The file therefore extends the base config with `include: ["src"]` and excludes the test directory,
   and the program is written to need no Node ambient type at all — an environment argument instead of a global,
   a specifier held in a `string`-typed variable for the file API, and two module-scope declarations in the one
   file that needs the process. Two `TS2591`s remain, and only in the excluded test file. Proposal: either name
   `@types/node` in this contract's *Installs* line (which would also let the test file into the program), or
   reword the file's description to "extends the base config; holds no Node ambient types" so a later executor
   does not read a missing dependency as a missing deliverable.
2. **`F§7.3`'s `{chunkId[0..2]}` is read as the first two characters.** The shard directory is
   `<id>.slice(0, 2)` (the layout git uses), which the delivered test pins by reading exactly
   `<dataDir>/tts-cache/3b/` for the golden chunk. Proposal: write "the first two characters of the id" in
   F§7.3, since the slice notation could equally be read as the first three.
3. **`F§7.3` does not say what an interrupted write leaves behind.** The sidecar is written second and a read
   begins at the sidecar, so audio without metadata is invisible and metadata pointing at missing audio is a
   miss. Proposal: state that order in F§7.3 (audio, then metadata) and that a reader treats a half-written
   entry as absent, so a later implementation that writes the sidecar first is a contract change rather than an
   implementation detail.
4. **No section fixes the HTTP status of a code.** `F§7.2` names `ENGINE_UNAVAILABLE`, `BAD_REQUEST`,
   `UNKNOWN_VOICE` and the rest but never a status; this unit chose the table in section 4 (`ENGINE_UNAVAILABLE`
   → 502, because the hub is a proxy for the engine that failed) and `416` with `BAD_REQUEST` for an
   unsatisfiable byte range, a code the closed set has no entry for. Proposal: add a status column to F§7.2's
   table, or state that a client switches on `code` and treats `status` as advisory.
5. **`GET /healthz`'s `version` has no owner.** `F§7.2` lists `{ ok, version, engines }` without saying whether
   the version is the package's (`0.0.0`), the API's, or a release tag. This unit answers the workspace's own
   version from one constant in `config.ts`. Proposal: say which version F§7.2 means, so a later bump does not
   leave two hubs answering different things.
6. **Resolving a voice id costs a voice-list call per synthesis.** `HubEngines.targetFor` asks the registry for
   the merged voice list to confirm that the id is served, which for a real engine is its own voices route
   (`GET /v1/audio/voices`, `GET /voices`) — so a hub with Kokoro or Piper enabled asks its engine for its voice
   list on every `POST /v1/tts`, and engine conformance (U-016, U-017) defines no cache for it. The mock engine
   makes it free and the delivered test counts `synthesize` calls only, which is what the contract's "call it
   once" is about. Proposal: state a voice-list refresh policy in F§6 or F§7.2 (a short time-to-live, or a
   resolution path that does not need the list), so the hub's per-chunk cost does not depend on an engine's
   voice route being cheap.
7. **The TTS route has no body-size limit of its own.** `F§7.2` caps the text at 1 000 characters and F§7.1's
   `LECTERN_MAX_UPLOAD_MB` governs uploads and URL fetches, so `POST /v1/tts` is bounded only by Fastify's
   default 1 MiB body limit — 1 001 characters are refused by the schema, but a megabyte of JSON is parsed
   first. Proposal: name the limit that applies to a JSON route body (and to the later sync routes) in F§7.2.
8. **`pnpm --filter … exec` fixed commands print a policy failure that is not one.** The pre-script dependency
   check runs an install first, which this unit's install now also trips over — `tsx` brings `esbuild`, whose
   build script pnpm ignores (`Ignored build scripts: esbuild@0.28.2, tesseract.js@7.0.0`) — and a reader can
   mistake the block for this unit's failure. Proposal: set `verifyDepsBeforeRun: false` (or approve the build
   scripts) in the workspace configuration, as U-018's evidence proposed.
9. **A package F§2.3 does not pin can land inside pnpm's `minimumReleaseAge` window and make every later pnpm
   invocation print a policy failure.** `@fastify/cors@11.4.3` — the current registry version when this unit
   installed it, which is what the contract prescribes for a package the ledger does not name — was published
   hours before this session, so pnpm 12's pre-script dependency check now rejects the committed lockfile with
   `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` on *every* `pnpm` run in this repository, including the standing
   gates, while each command still exits 0 (section 6.2). The lockfile is not stale and nothing was bypassed: the
   install used `--config.minimumReleaseAge=0`, a per-run flag that writes no file, and `pnpm-workspace.yaml` is
   byte-identical. Proposal: either pin `@fastify/cors` in `F§2.3` (and choose a version outside the window),
   name `minimumReleaseAge` handling in the workspace configuration, or set `verifyDepsBeforeRun: false` — so a
   fixed command's output carries its own result rather than a policy complaint about a dependency the contract
   asked for.
