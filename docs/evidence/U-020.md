# Evidence — U-020 Hub: parse route and safe URL fetch

Date: 2026-11-14 · Target: N/A · Inspection: N/A

## 1. Questions

The contract's *REA Inspection Target & Method* is `Target: N/A — the hub is a Lectern design. Do not call REA.`,
so no behavioural question is put to a target and this session made no REA call. The questions this unit's files
answer are Lectern's own design questions:

- how F§7.2's one parse route tells its three request forms apart — raw bytes with a declared type and an
  optional `X-Lectern-Filename`, JSON `{ url }`, and JSON `{ text, title? }` — when the body Fastify hands a
  handler is an object for one form and bytes for the other two;
- what F§7.2's URL fetch is allowed to do: which schemes, how many redirects, how long, how large, and what it
  must never carry to the site it reads;
- how "refuses hosts that resolve to loopback, link-local, or private ranges unless
  `LECTERN_ALLOW_PRIVATE_FETCH=1`" becomes a check on the *resolved address* rather than on a name, and what
  "re-check after every redirect" means for a fetch that a fetched page can steer;
- which status each of F§5.4's five refusal codes answers with, given that the hub's own status table (U-019)
  gives `PARSE_FAILED` a different one;
- how the OCR engine F§5.5 requires reaches a route without being built by a hub that never parses an image;
- where the upload limit comes from, and what a body past it answers before a parser sees it;
- what this package's type-checking program can contain for a route that reads files, fetches URLs and opens a
  stub socket — on a host where `@types/node` is absent and R10 forbids adding it.

## 3. Architecture notes

**Module map.** Two files are new. `src/fetch-url.ts` holds `safeFetch` and the address rule; it knows nothing
about documents, so the rules F§7.2 states for a URL can be exercised without a parser. `src/routes/parse.ts`
holds `POST /v1/parse` and the mapping from F§5.4's codes to F§7.2's statuses; it decides which of the three
request forms arrived, and hands the bytes to the *dispatcher* rather than choosing a parser itself. Three
existing files change: `src/context.ts` gains the OCR member (F§5.5), `src/app.ts` gains the binary body parser
and its limit, and `src/routes/index.ts` (U-019's registry) gains one entry.

**Which form arrived.** Fastify parses `application/json` itself, so a JSON body reaches the handler as an
object and every other content type reaches it as bytes — that is the whole discriminator, and it is why R5's
ban on multipart parsing costs nothing: a file is the body. The catch-all parser is registered for
`["text/plain", "*"]` rather than `"*"` alone, because Fastify's own plain-text parser is registered by default
and would answer a `.txt` upload with a *string*; naming it beside the catch-all makes the bytes arrive as
bytes (`lib/content-type-parser.js:75-77` maps `*` to the empty key, and `getParser` reaches it only after the
exact type and the media type both miss — measured, see section 5).

**The document's own evidence decides.** The route passes what the request *claims* — the `Content-Type` and
F§7.2's `X-Lectern-Filename` — to `parseDocument` as hints, and the dispatcher's precedence (F§5.4) puts the
bytes' signatures first. Measured through the route: `text.pdf`'s bytes uploaded under `text/plain` come back
as `source.kind: "pdf"` with `source.mime: "application/pdf"`, and a bare `<p>…</p>` fragment with no name hint
comes back as `txt` where the same bytes named `page.html` come back as `html` — the header is a hint the
dispatcher can use and never a claim that overrides the bytes.

rehearsal workspace; the numbers are this host's, quoted so later units can compare):

(`Lighthouse Notes The first tower was little more than a ston…`).

**OCR recovery, measured.** The image's 181 words are the 181 words `expected.json` lists for its page, and the
route's engine read **181 of 181** back (the delivered test asserts a floor of 175, so it tests the wiring

engine is built per hub rather than per request.

**The OCR engine is built on first use, not at start-up.** The context holds an accessor (`OcrProvider`), not an
engine: `createTesseractOcrEngine` returns a closure whose worker does not exist until `recognize` is called on
a page, so a hub that parses only text never starts one — and the route asks for the engine only for the two
forms that can need it, never for `{ text }`, which the route read itself.

**The type-checking program.** `apps/server/tsconfig.json` (U-019's, unchanged — it is not in this unit's
outputs) keeps `include: ["src"]` with `exclude: ["src/**/__tests__"]`, and the contract's `typecheck` step runs
it. `tsc --noEmit -p tsconfig.json --listFiles` shows the program holds exactly the package's **14** non-test
modules, including this unit's `src/fetch-url.ts` and `src/routes/parse.ts`. A second probe program
(`{"extends": "./tsconfig.json", "include": ["src"], "exclude": []}`, built in the scratch tree and never
delivered) reports **12** diagnostics, all of them the one pre-existing class `TS2591` — `node:fs`,
`node:fs/promises`, `node:http`, `node:module`, `node:os`, `node:path` and two `Buffer`s in this unit's two test
files, plus the three `node:` imports in U-019's test file. Nothing else is reported in the unit's own files:
the earlier version of these tests, which typed its helpers with `Parameters<FastifyInstance["inject"]>[0]` and
left the stub callbacks' parameters for inference, added 28 more diagnostics of its own (of 40 in the program, 12 of them the `TS2591` class) and every one of them was removed
(the type is `InjectOptions`, exported by fastify, and the callbacks are annotated).

**What a URL fetch costs a hostile page.** One request in flight at a time, with `redirect: "manual"` so the
loop owns every hop: the address is judged, then the request is made, then a `3xx` with a `location` becomes the
next target (resolved against the answer that named it, and refused if it is not a URL). The deadline is one
timer over the whole exchange, and the size limit is counted *as* the body arrives — a stub that writes 4 KiB
and then stalls is refused with `PAYLOAD_TOO_LARGE` in milliseconds where a buffering implementation would have
sat until the deadline and answered `FETCH_REFUSED` instead. Measured in the rehearsal: 38 tests in 13 s, the
two OCR cases 1.9 s and 3.4 s of that.

## 4. Lectern design

- [DESIGN] **The address rule is F§7.2's, read literally, with one narrowed exception** (F§7.2). Every hop's
  *resolved* addresses are checked before the hop is fetched: a literal address is checked as itself and a name
  is resolved first (the host's own `node:dns/promises`, or the `lookup` an option supplies). Loopback,
  link-local, the private ranges, carrier-grade NAT and "this network" are `local`; the unspecified address,
  multicast, broadcast and the reserved ranges are `unusable`. `LECTERN_ALLOW_PRIVATE_FETCH=1` opens `local`
  addresses **for the URL the caller supplied**, and a *redirect* may revisit an address that URL already led to
  — which is what keeps the flag useful for a service that moves a path or switches to https — but a redirect
  to a *different* local address is refused, and `unusable` is refused whatever the flag says. The measured
  reason for the exception: with a plain "the flag never applies to a hop" rule, the first rehearsal run failed
  two of its own tests, because an ordinary `302` between two paths of the operator's own stub was refused.
  Recorded as a deviation proposal (section 7, item 2).
- [DESIGN] **`PARSE_FAILED` answers `422`, not the hub's table's `500`** (F§7.2's parse row, the contract's own
  mapping). A document a client sent that Lectern could not read is the client's answer to read, and the
  contract names the status explicitly; `HubError`'s third argument exists for exactly this, so the table in
  `errors.ts` — U-019's file, and not in this unit's patch scope — is left untouched. Recorded as a deviation
  proposal (section 7, item 1).
- [DESIGN] **The upload limit is one function, used twice** (F§7.1's `LECTERN_MAX_UPLOAD_MB`). `maxUploadBytes`
  lives in the parse route (the only route that uploads) and `app.ts` imports it for the body parser's
  `bodyLimit`, so the limit a body is refused at and the limit a URL fetch is read to are the same arithmetic
  rather than two spellings of it. The route also refuses an oversized body itself, which the parser's limit
  makes unreachable in practice — it is the second line, for a transport that ever hands the route bytes the
  parser did not count.
- [DESIGN] **The stated title is stamped after the dispatcher, inside the validated answer** (F§5.1's title
  rule, F§5.2's `docId`). F§5.1 prefers a title the caller states, and `{ text, title? }` is exactly that; the
  dispatcher's text branch has no title to pass to `buildDocument`, and `docId` hashes the *block texts alone*,
  so stamping the title onto the built model cannot move the identity. The whole answer then leaves through
  `ParseResponseSchema.parse`, so what a client receives is validated whatever was stamped.
- [DESIGN] **The OCR member lives in the context, and the app factory owns the parser** (the contract's patch
  note, F§5.5). The note asks for "an OCR engine member in the context" and, in the app factory, "a binary body
  parser … and create the OCR engine lazily on first use"; the laziness is therefore expressed where the
  context is built — `buildApp` calls `createHubContext`, which hands the accessor in — so the app factory adds
  the parser and passes the caller's overrides through, and no route knows how an engine is built. An
  `HubOverrides.ocr` entry lets a later unit replace the engine, which is how a test can exercise a scan without
  running one.
- [DESIGN] **The route is stateless, and the fetch carries nothing** (the contract's *Forbidden Actions*,
  F§11). Nothing is written to disk, no parsed document is stored, and the request a fetch makes sets exactly
  one header (`accept: */*`) with `credentials: "omit"`: the hub's bearer token and any cookie stay with the
  hub, and the delivered test asserts that the stub saw neither.
- [DESIGN] **A JSON `{ text }` is handed to the same dispatcher** (F§5.4). The text form is bytes the route read
  itself (`TextEncoder`), so the document it produces is normalized, skip-classified, tokenized and identified
  by the same code path as an upload — measured: `{ text: "Hello, world." }` answers F§5.2's golden `docId`
  `f8c3bf62a9aa3e6fc1619c250e48abe7` (F§5.2's table entry for one block `Hello, world.`) with `sentenceCount: 1` and `wordCount: 2`, and
  an HTML-looking `{ text }` would be read as markup by the dispatcher's own rules rather than by a route-level
  special case.
- [DESIGN] **`fetch`, `Response`, `AbortController` and `URL` come from the platform, not from a package** (R9,
  R10). They are declared by the DOM library TypeScript injects by default at `target: ES2022` — measured in a
  scratch probe that compiles them with the repository's own compiler options, and confirmed by the fact that
  the rest of the hub's own `main.ts` still has to declare `process` because no Node ambient type exists. No
  typings package is installed or needed, and the one host module this unit reaches for (`node:dns/promises`) is
  named by a `string`-typed variable, the form that compiles without a Node declaration and still loads the real
  module under vitest.

## 7. Deviation proposals

1. **No section fixes the HTTP status of a code, and two of the hub's own answers disagree with the table
   U-019 chose.** `errors.ts` gives `PARSE_FAILED` `500`, while this contract's *Required File Outputs* line for
   `routes/parse.ts` maps `PARSE_FAILED` to `422` beside `INVALID_EPUB`, `DRM_PROTECTED` and `EMPTY_DOCUMENT`.
   The route follows the contract (it is the more specific and the higher-precedence document) and passes the
   status explicitly, and the delivered test pins `422` for a text that normalizes to nothing. Proposal: add a
   status column to F§7.2's error table — or say that a parse's refusals are `422` while the hub's default for
   `PARSE_FAILED` stays `500` — so the two do not read as a contradiction to the next executor.
2. **F§7.2's address rule, as written, cannot be satisfied by the contract's own test list, and this unit
   states the reading it implements.** "Do not fetch private, loopback, or link-local addresses unless
   `LECTERN_ALLOW_PRIVATE_FETCH=1`; … re-check after every redirect" reads as *the flag opens every hop*; but
   the parse-route test list asks for a loopback stub to work with the flag on *and* for "a redirect to a
   private address" to be refused — and with the flag opening every hop, no redirect can ever be refused once a
   loopback first hop has been allowed, because a test cannot serve a *public* address. This unit therefore
   implements: the flag opens the addresses the caller's URL led to, and a redirect may only revisit those.
   Every sentence of the prohibition is still honoured (nothing local is fetched that the flag does not cover),
   and the narrowing is what prevents a public page from walking into the hub's own network. Proposal: write
   that reading into F§7.2 — "a redirect is followed to a local address only when the URL the operator supplied
   already resolved there" — and, if the operator meant the flag to open every hop, say so and add a test that
   does not need a second local address.
3. **F§7.2 does not say what a fetched page's size limit counts.** The size limit is enforced on the bytes that
   arrive (`PAYLOAD_TOO_LARGE` the moment the total passes `LECTERN_MAX_UPLOAD_MB`), not on a `Content-Length`
   header, because a header is a claim a server can be wrong about and can be absent entirely. Proposal: state
   that in F§7.2, and say whether the deadline covers a body that never finishes (this unit's does — the answer
   is `FETCH_REFUSED` at the deadline, which is the only way a stalled body can be refused without holding a
   reader open).
4. **The parse route's title stamp is an implementation detail F§5.1 leaves open.** `buildDocument` takes an
   explicit title, but `@lectern/core/parsers`' `parseDocument` exposes no way to pass one for its text branch,
   so `{ text, title? }` — a form F§7.2 defines — has no supported route to F§5.1's first preference. This unit
   stamps the title onto the built model and re-validates the whole answer. Proposal: either give
   `parseDocument` an optional `title` on its input (the smallest fix, and the one that would remove the stamp)
   or state in F§5.1/F§7.2 that a stated title is applied after building and never affects `docId`.
5. **`@types/node` is still absent, and this unit's two test files cannot be typed without it.** R10 forbids
   adding it, `apps/server/tsconfig.json` excludes `src/**/__tests__`, and the second program therefore reports
