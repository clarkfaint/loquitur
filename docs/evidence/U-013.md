## 3. Architecture notes

**State machine — F§5.7.** One machine with eight states: `idle`, `loading`, `ready`, `buffering`, `playing`,
`paused`, `ended`, `error`. The load path is `idle → loading → ready`; the play path is `ready | paused |
ended → buffering → playing`, where `playing` is entered by the sink's `play()` once the first chunk of the
window is enqueued. `playing → paused` is the sink's `pause()`. `playing → ended` happens when the last
sentence of the playback order ends; the position is left on that last sentence. `stop` from any state is
`sink.clear()` and back to `idle`. A chunk or sink failure enters `error` while keeping the position, and a
later `play` retries. `seek`, `skip` and `setVoice` clear the queue, reposition and refill, resuming only if
the player was playing; `setRate` recomputes the speed plan and clears and refills only when the plan's
`synthSpeed` actually changed.

**Prefetch window — F§5.7 rule.** The window is the current sentence plus the next three *non-skipped*
sentences, i.e. four entries of the playback order. Because the order is built once per load from
`playableSentences(doc, { skipFurniture })`, "non-skipped" falls out of the order itself: with
`skipFurniture` on the furniture blocks contribute no sentences, and with it off every sentence is present.
As playback advances, the window slides one sentence at a time and the newly exposed sentence is requested.

**Sentence boundaries and the sleep timer — F§5.7 rule.** A chunk-end is a sentence boundary. The sleep
timer only marks itself expired when its deadline passes; the machine stops at the *next* chunk-end after
that, so a timer that expires mid-sentence finishes the sentence first. `sleepRemainingMs` is derived from
the deadline against the injected clock, so a snapshot taken after expiry reads 0 and a snapshot taken after
the stop reads `null`.

**Rate plan — F§5.6(e), used by F§5.7's `setRate` row.** `planSpeed(rate, sink.maxRate)` splits the user rate
into a synthesis speed (the part the sink cannot reach, rounded up to a quarter and bounded to 1.0–4.0) and
a sink rate (the rest, capped by the sink's ceiling). Only a change in `synthSpeed` invalidates cached
audio, which is why only that change forces a clear-and-refill.

**Highlight clock — F§5.6(d), used by `activeWord()`.** The word under the highlight is the one whose timing
span contains `sink.current().positionMs + lookaheadMs`, found by `findActiveWord` (the F§5.6(c) binary
search) over the timings of the chunk the sink is currently on. `lookaheadMs` is a per-platform constant
held in settings (0 on web and desktop, 80 on Android).

## 4. Lectern design

- [DESIGN] The protocol types are the `z.infer` of their schemas, so the runtime shape and the compile-time
  shape cannot drift; the schemas use `z.strictObject` and `.exactOptional()` exactly as `model.ts` does
  (F§5.1 precedent), and every command is validated with `PlayerCommandSchema.safeParse` before it acts.
- [DESIGN] The controller is pure TypeScript over four injected boundaries (F§5.8): `AudioQueueSink`,
  `ChunkSource`, `Clock`, `DocumentProvider`. It never reads `window`, `document`, `Audio` or a timer; all
  time comes from `Clock`, and no test plays audio.
- [DESIGN] A chunk is one sentence: `ChunkSource.get` is asked once per sentence with the sentence's text
  (with `stripCitations` applied when `skipCitations` is on), the voice (or the empty string when no voice
  has been chosen) and the plan's `synthSpeed`.
- [DESIGN] `queued` (sentence indexes requested or enqueued) and `chunkMeta` (chunkId → sentence and timings)
  are the only bookkeeping; `generation` is bumped by every clear/refill so an in-flight fill from an older
  queue can never enqueue a stale chunk.
- [DESIGN] The playback order is snapped to a playable sentence on load and on seek, so a position restored
  from the library that sits inside furniture starts at the next playable sentence (F§5.7's "sentences in
  skip blocks are passed over").
- [DESIGN] `ended` leaves the position on the last sentence; a `play` from `ended` restarts at the first
  playable sentence, and `stop` clears the document so `idle` means "nothing loaded". F§5.7 does not name
  either behaviour — see the deviation proposals.
- [DESIGN] `dispose()` is idempotent: it bumps the generation, clears the sleep timer, detaches every sink
  listener and clears the sink. The injected sink's own lifetime belongs to its host, so the controller does
  not call `sink.dispose()`.
- [DESIGN] The fake sink models the sink contract in memory and is driven entirely by `FakeClock`; the fake
  chunk source is deterministic (chunk ids from a counter, timings from `estimateTimings`) with a
  clock-driven delay and a failure count. `runAudioQueueSinkConformance` is runner-agnostic: it takes a
  factory and a `wait`/`makeChunk` environment and returns one `{ name, ok, error }` per case.

## 7. Deviation proposals

- **F§5.7 does not say what `play` does from `ended`.** The table's row is `ready, paused, ended | play |
  buffering`, and its only position rule is that `ended` leaves the position on the last sentence. This unit
  restarts from the first playable sentence, because replaying the last sentence and immediately ending
  again is not a useful control. Proposal: state the intended `ended → play` position.
- **F§5.7's `stop` action is only `sink.clear()`.** It does not say whether the document stays loaded. This
  unit clears the document too, so `idle` consistently means "nothing loaded" and `load` is the only way back
  in. Proposal: say whether `stop` keeps the document.
- **F§5.7 does not name the voice used before `setVoice`.** `PlayerSnapshot.voiceId` is `string | null` and
  `ChunkSource.get` needs a string, so this unit passes the empty string as "no voice chosen" rather than
  inventing a voice identifier. Proposal: name the default-voice rule.
