## 3. Architecture notes

### 3.1 Measurements made in this session
Everything below was measured on this host, in a `cp -a` copy of the repository, with Playwright driving the *built* extension and F§7.1's real hub (the run's own `e2e/global-setup.ts`). They are facts about this host, this Chrome and this extension — not about the reference product.

- [OBSERVED] **A manifest shortcut is not delivered under Playwright's input.** Pressing `Alt+Shift+R` on the article page (`Alt+Shift+R` is U-032's `read-page` binding) left the extension untouched: the worker recorded no message of any kind, no snapshot, and no offscreen document was created (`{state: "none", offscreen: 0, message types: []}`). — Playwright probe case, rehearsal copy.
- [OBSERVED] **A tab's address is not readable.** `chrome.tabs.query({})` answered every tab with `url: null` (two tabs: an `about:blank` and the `https` PDF page), while `chrome.permissions.getAll()` answered `origins: ["<all_urls>"]` and `permissions: ["activeTab","contextMenus","storage","scripting","offscreen"]`. Reading `Tab.url` needs the `tabs` permission, a host permission or an `activeTab` grant, and `activeTab` is granted only by an *invocation* — a toolbar click, a menu item or a shortcut. — Playwright probe case, rehearsal copy.
- [OBSERVED] **A host permission cannot be granted in this rig either.** `chrome.permissions.request({origins: [...]})` from the service worker rejects with `This function must be called during a user gesture`, and the same call made from a real click inside the popup page never settled at all (Chrome's prompt cannot be dismissed headlessly): three seconds later `__probeGrant` was still `no answer`, and `chrome.permissions.contains({origins: ["https://harbour.example.invalid/*"]})` was `false` with the tab's `url` still `null`. — Playwright probe case, rehearsal copy.
- [OBSERVED] **A wrong token fails the reading the way F§5.7 says.** With `configure({ token: "wrong…" })` and the widget's own play control, the worker received `{state: "error", error: {code: "CHUNK_FAILED", message: "the bearer token is not valid"}, sentenceIndex: 0, wordIndex: 0}` and never a `playing` state. — Playwright probe case, rehearsal copy.
- [OBSERVED] **The worker's session records its reading tab *after* the load it relays has answered** (`apps/extension/src/background/session.ts`: `const answer = await relay(reading); if (answer.ok) active = target;`). On a first failing attempt the counters read `{active: null, seen: 5, forwarded: 0}` — the five snapshots published while the document was loading, the error among them, were not forwarded to the tab, and the instrumented content script had seen only `[ext/read-active-tab]`. After a second press the same counters read `{active: <tab id>, seen: 11, forwarded: 6}` and the tab then received `ext/snapshot:error:CHUNK_FAILED`. — Playwright probe case with an instrumented rehearsal copy.
- [OBSERVED] **The error banner this unit mounts reads, in the widget's shadow root:** `{"count": 1, "text": "This page could not be read aloud. the bearer token is not valid"}` with the attribute `data-lectern-widget-error="CHUNK_FAILED"`, and Playwright's CSS locator `lectern-widget [data-lectern-widget-error]` resolves inside the open shadow root and reports it visible. — Playwright probe case, rehearsal copy.
- [OBSERVED] **A second reading session answering `ext/read-selection` is not a second answer, it is a second relay.** Built as the contract's literal wording describes (an own session whose `startSelectionReading()` runs on the same message), one menu click sent `ext/read-document` twice and the two relays raced each other's offscreen document: the menu reply came back `{ok: false, code: "OFFSCREEN_UNAVAILABLE", message: "Only a single offscreen document may be created."}`. The delivered code does not do this — see §7 (1). — Playwright probe case, rehearsal copy.
- [OBSERVED] **The offscreen document cannot be inspected from a case.** It is a `chrome.runtime.getContexts` context (`contextType: "OFFSCREEN_DOCUMENT"`, `documentUrl: …/offscreen.html`, `tabId: -1`), not a page: `context.pages()` held only `about:blank` and the article. And the sink's two elements are never attached to any document (`packages/ui-web/src/audio/html-audio-queue-sink.ts`: "The elements never join the document"), so "no audio plays" cannot be read off a DOM.
- [OBSERVED] **A wrong token is refused by the hub itself.** `fetch(`${hubUrl}/v1/voices`, {headers: {authorization: "Bearer <wrong>"}})` from the extension's own popup page answers `401` — which is what the delivered failing case asserts, and what makes "no audio plays" a fact about the hub as well as about the player.
- [INFERRED] Therefore a browser case can assert an error state in the tab only after the worker has forwarded one, and it can assert the hand-off address only if the tab's address is supplied — hence the two seams and the shape of §6's sixth case; both are recorded in §7.

### 3.2 What the delivered design does about each
- The two routes a browser would raise *for* the extension — a context-menu click and a shortcut — cannot be raised by a test, so `installContextMenu` and `installCommands` publish the functions the browser calls on the worker's own global (`lecternMenuClick`, `lecternCommand`), and `installPdfHandoff` publishes `lecternPdfHandoff`, which supplies the one value the platform would have supplied (the tab, and its address) to the same handler. Everything downstream of each seam is the extension's real code.
- The extension's own command surface is U-032's four manifest commands (`toggle-play`, `read-page`, `next-sentence`, `previous-sentence`); the first three are F§5.7 player commands (`toggle`, `skip ±1`) and the fourth is the page-reading request U-035's feature already binds.

## 4. Lectern design
- [DESIGN] `context-menu.ts` creates exactly two items on install, of Lectern's own ids, and removes the previous set first, so a reinstalled worker cannot leave duplicates in the reader's menu; a click routes the item's message to the active tab's content script and answers with what that tab said (`NO_ACTIVE_TAB` when there is none, `NO_CONTENT_SCRIPT` when nothing answered). Follows the contract and F§10.2's background row.
- [DESIGN] The page item asks for the page reading (`ext/read-active-tab`) because `chrome.contextMenus.OnClickData` carries no hit point — there are no coordinates in it — and the frozen message protocol has no request that carries a start sentence for a page. Filed in §7 (5).
- [DESIGN] `commands.ts` is the mapping table (all four manifest commands) plus one listener and one dispatch. The listener runs the three player commands through the reading session, so a keystroke with nothing being read is refused with `NO_SESSION` rather than waking the audio host; `read-page` is left to U-035's feature, which already binds it — a second binding would answer one keystroke with two page-reading requests (filed in §7 (3)).
- [DESIGN] `pdf-handoff.ts` keeps detection, address building and the handler in one file. `isPdfUrl` reads the URL's *path* only, so a query string that ends in `.pdf` is not a PDF and neither is a path with `.pdf` in the middle; `handoffUrl` builds `{webAppUrl}/#/import?url=<encodeURIComponent(pdf)>` with a trailing slash trimmed. The handler decides in a fixed order — the address's eligibility (`LOCAL_FILE` for a non-`http(s)` address or a private window), then whether it is a PDF (`NOT_A_PDF`), then whether there is a reader to open it in (`NO_WEB_APP`) — and opens the tab with `chrome.tabs.create`. No PDF is ever fetched or parsed by the extension (F§10.2, and the contract's *Forbidden Actions*).
- [DESIGN] The handler is added to the registry at *installation* rather than written into `handlers.ts` (U-032's file, whose frozen test asserts the registry as declared refuses every type but `ext/get-status`), which is the pattern the operator ratified in U-034 and U-035. The contract's "registered in `handlers.ts`" is met in the sense that the entry lives in that registry — see §7 (2) for the wording.
- [DESIGN] `selection-feature.ts` owns the widget's error state: when a snapshot carries `PlayerSnapshot.error`, the failure is mounted inside the widget's own *open* shadow root as one block styled from the widget's `--lectern-*` tokens, updated when the error changes, and removed when it clears. It reads no file U-036 owns (R6) and adds nothing to the page's own DOM. Its listener answers no message, so the page keeps exactly one responder — U-036's measured lesson about a second responder winning a reply race.
- [DESIGN] It does *not* start a second selection reading. The request is already answered by U-035's reading session, and a second session is measured to relay the document twice and to race the offscreen document (§3.1, §7 (1)).
- [DESIGN] The full suite (`e2e/full.spec.ts`) drives the six numbered behaviours against the run's real hub, page server and built extension, and asserts the extension's own numbers (the worker's snapshots, the offscreen document count, the replies the extension's handlers gave). No earlier spec was weakened or edited.

## 7. Deviation proposals
1. **`selection-feature.ts` does not answer `ext/read-selection`; U-035's reading session does.** The contract lists this unit's file as an answerer, but `apps/extension/src/content/reading-session.ts` (U-035, frozen by R6) already answers that message with the same extraction, and that file is not in this unit's patch scope. Built as the contract's wording describes, one click relayed `ext/read-document` twice and the second relay raced the first for the offscreen document, answering `OFFSCREEN_UNAVAILABLE: Only a single offscreen document may be created.` (measured, §3.1). The request is therefore served by the file that owns it, and this file owns the widget's error state — the other half of what the reader sees. Proposed fix: one patched contract either removing U-035's `ext/read-selection` branch or moving the whole selection path into U-037's file.
2. **`ext/open-pdf` is registered at installation rather than as a literal entry in `handlers.ts`.** U-032's frozen `messages.test.ts` asserts that the registry *as declared* refuses every type but `ext/get-status`; adding the key to that object literal would break it, and R11 forbids weakening the test. The pattern (install-time registration into the same registry from the unit's own file) is U-034's and U-035's, ratified by the operator in `docs/evidence/U-034.md` §7. Proposed fix: the contract's wording, or a patch to U-032's test.
3. **`commands.ts` maps all four commands but binds three.** U-035's `installReadActiveTab` already binds `read-page` to the same page-reading request; binding it again would answer one keystroke with two requests and start the tab's reading twice. The map and the dispatch cover the fourth command (that is what the suite's seam drives, because the accelerator itself cannot be delivered — §3.1). Proposed fix: a patched contract naming which unit owns the `read-page` binding.
4. **The failing-reading case presses play twice, and the reason is U-034's session.** The service worker records its reading tab only after the relay answers, so the snapshots published while a document is loading — the error among them — never reach the tab (measured: `{seen: 5, forwarded: 0}` on the first attempt, `{seen: 11, forwarded: 6}` after the next state). Proposed fix: assign the tab before relaying, or forward to the tab that sent the document.
5. **The page-context menu item asks for the page reading, not for the sentence under the cursor.** `chrome.contextMenus.OnClickData` has no coordinates, and the message protocol (U-032, frozen) has no page-reading request that carries a start sentence, so "Read from here" cannot name a hit point. Proposed fix: a message that carries one, in a later contract.
6. **Three test seams are published on the service worker's global.** `lecternMenuClick`, `lecternCommand` and `lecternPdfHandoff` exist because a browser test cannot click browser chrome, cannot make the browser deliver a manifest shortcut, and cannot grant an `activeTab`/host permission (§3.1); each seam runs the same function the browser or the platform would call, and each is documented at its declaration. Proposed fix: name them in the contract, or record in `features.md` that the extension exposes them for end-to-end driving.
7. **One `F§10.2` wording** (carried over from U-036, not acted on): the widget's mount rule is measured to add exactly one element to a page.
