## 3. Architecture notes

### 3.1 What the page supplies and what the engine does not

U-058's engine reads no platform API — its own comment says so — so the five platform facts arrive as
arguments from `apps/web/src/sync/sync-service.ts` and nowhere else:

| Fact | Supplied as |
|---|---|
| time and timers | F§5.7's `Clock` over `Date.now`/`window.setTimeout` |
| the change feed | F§8.3's `GET /v1/sync/ws` over the browser's `WebSocket`, authenticated with F§11's token as the socket's first message |
| reachability | `navigator.onLine`, kept current by the window's `online`/`offline` events |
| F§7.2's model bodies | gzip and gunzip over `CompressionStream`/`DecompressionStream` |
| the reader's own progress | a store write plus `notifyLocalChange()` (the reader's only change) |

### 3.2 The doorbell, which is what makes a frozen screen's write travel

F§5.9's `LibraryStore` has no change event, and the screens that write to it are frozen. Measured shape of
the mechanism that replaces them: a 1 s timer reads `pendingOps(1)`, and a non-empty answer calls F§8.2's
`notifyLocalChange()`, whose own debounce is 2 s. A write is therefore on the hub **~3 s** after it lands
(measured in the browser cases: a document imported in A is in B's library in **3.4 s**, the whole case
including both devices' start).

### 3.3 Where a device starts: the one decision this unit had to make

`[DESIGN]` — measured, twice, and the second measurement is why the rule exists at all.

The first implementation followed F§8.2 literally: a device that has never pulled asks for changes after
`rev 0`, so its first round replays the hub's whole change log. In the browser suite that broke a **frozen**
case: `e2e/import-library.spec.ts:89` imports two documents of its own and asserts
`expect(rows(page)).toHaveCount(1)` after deleting one of them. Measured: the page reached **4** rows (its own
2, plus the 2 documents the run's *previous* case had pushed to the same hub), and the assertion read **3**
where it wrote 1. That spec belongs to U-028 and is not in this unit's *Patch scope*, and the contract forbids
modifying Phase 2 end-to-end specs; a faithful full-log pull therefore cannot coexist with the contract's own
Pass condition.

The rule the delivered service makes instead, once per device and per hub:

- **a device that already holds documents** keeps them and follows the hub from the moment it joins: its
  cursor starts at F§8.3's `ready` `rev`, so the log that predates the join is not replayed into a library the
  reader built. Its own records still travel up (push is unchanged), and everything after the join travels
  both ways.
- **a device that holds no documents** takes the hub's library: its first pull is the whole log, which is what
  makes pointing a fresh install at a hub useful.

Measured after the change: the frozen case passes again (2 rows), and the six sync cases pass with two fresh
devices. The decision is remembered per hub in `localStorage` (the same place F§10.1 keeps the connection), so
a reconnect never re-decides and a cursor a pull earned is never moved back.

### 3.4 What the reader sees

- The badge is in the shell's navigation and is a view of the service's own state: **synced**, **syncing**,
  **offline**, **error**, with the last clean round's time as its `title`. With sync off, or with no hub, it
  renders nothing — a mark that said "synced" for a page that is not syncing would be a lie.
- The settings section is one switch, the engine's state and pending count, the last-synced time and a
  "Sync now" button that calls the engine's own `syncNow()`. Flipping the switch really stops the engine: no
  round, no socket, no doorbell — measured as the whole of case 6 (an import made with sync off never reaches
  the other device, and the badge is gone).

### 3.5 The rehearsal's own three findings

`[DESIGN]` — each of these cost an iteration and each is fixed in the deliverable:

1. **A wrong import made an infinite loop that no test timeout could end.** `outboxDepth()` widens
   `pendingOps(limit)` until the page comes back short, the same arithmetic U-058's `status()` uses. The
   delivered module first imported `MAX_PUSH_OPS` from `@lectern/api-client` (which does not export it) instead
   of `@lectern/api-contract`: the constant was `undefined`, `page.length < undefined` was false, `limit` became
   `NaN`, `pendingOps(NaN)` answered `[]`, and the loop ran forever. Because the loop *awaits* each empty page
   it never yields to the macrotask queue, so vitest's own 5 s timeout never fired and the file simply hung —
   measured three times, and bisected with throwaway probe files until `status()` was isolated. The import now
   comes from the package that declares it.
2. **The bookmarks panel is a switch, not an opener.** A retrying helper that clicks "Bookmarks" before each
   read closes the panel it opened on the previous pass; measured, the second pass found no panel at all. The
   deliverable's helper reads `aria-expanded` and clicks only when the panel is closed.
3. **Playwright serves the build, not the sources.** An e2e run after editing `src/sync/sync-service.ts` still
   exercised the old bundle, which made the join decision look broken when it had never been built. The unit's
   fixed command builds before it tests (`vite build && … playwright test`), which is why the delivered order is
   the contract's order and not a shortcut.

### 3.6 The browser cases: a browser context *is* a device

The two devices are two `browser.newContext()` instances: separate `localStorage` (the connection and this
device's switch), separate IndexedDB (F§5.9's records, cursor and outbox), one hub from `global-setup.ts`. Each
device is connected through the settings screen and reloaded once, because F§10.1's start-up features run for
the connection the page already had — after that no case reloads anything, and a library that must show a
remote record is re-read by re-entering the route (a hash navigation), never by reloading the page.

## 4. Lectern design

- `[DESIGN]` **The engine is built only when a hub is configured and this device's switch is on**, and every
  failure is a state rather than an exception, so sync is never a requirement (F§8.2's failures, F§10.1's
  default: on).
- `[DESIGN]` **The switch lives in `localStorage`, not in a `LibraryStore` setting** (F§5.9): syncing is a
  property of *this* device's connection, exactly like the hub URL and F§11's token that F§10.1 keeps there, and
  a `setting` record is the kind of thing F§8 carries to the reader's other devices.
- `[DESIGN]` **A local write reaches the hub without a wire from every frozen screen**: a one-second look at
  the outbox calls F§8.2's `notifyLocalChange()`, and the reader — whose progress write is the one change this
  unit may announce directly — rings the same bell (§3.2).
- `[DESIGN]` **The page pulls when it comes back to the foreground and when the network returns** (F§8.3),
  which is one `syncNow()` call for both.
- `[DESIGN]` **The cursor starts where the hub is for a device that holds documents; a device that holds none
  takes the hub's library** (§3.3), with the decision remembered per hub.
- `[DESIGN]` **The badge and the section read the service, never the hub**: one subscription carries
  `{ running, status }`, so no screen can show a state the sync code does not believe.
- `[DESIGN]` **The reader asks for a document's body when its store has no model for it** (F§8.2's lazy
  download): `use-player.ts` calls `ensureModel(docId)` and treats `null` — a device with sync off, or a hub
  that holds no model — as the `notFound` it was before this unit.
- `[DESIGN]` **The e2e's two devices re-read their library by re-entering the route**: `LibraryPage` is frozen
  and reads the store when it mounts, so "appears in B's library within 10 s without a reload" is measured
  without reloading any page (the contract's own words for what must not happen).

## 7. Deviation proposals

1. **A device that holds documents does not adopt the hub's older records** (§3.3). This is the one place the
   delivered behaviour is narrower than a literal reading of F§8.2 (a device with no cursor asks from `rev 0`).
   It is forced by the contract's own Pass condition: with the full-log pull, the frozen
   `e2e/import-library.spec.ts:89` reads 3 rows where it wrote 1, and neither that spec nor `LibraryPage` is in
   this unit's *Patch scope*. A patched contract could instead: (a) give each e2e case its own hub or data
   directory, (b) let the library screen re-read on a sync change so a case can assert what it likes, or
   (c) add an explicit "adopt this hub's library" action to the sync section, which is the one case the
   delivered rule cannot serve: a device that already holds documents joining a hub that already holds others.
2. **F§8.2's initial cursor is now a stated decision, not an omission.** If the operator's intent is the
   opposite of (1) — every device adopts the whole log on first join — the change is one branch of
   `joinHub()` and the four lines above it.
3. **The library screen is frozen, so "appears in B's library" is observed by re-entering the route.** The
   record arrives live (F§8.2's pull applies it), but the screen reads the store when it mounts; a future unit
   could subscribe the library to the service's own `{ running, status }` view or to a change notification.
4. **U-058's `fetchFromFastify` harness limitation** (a `204` response cannot be built by its `Response`
   constructor) does not reach this unit: the web app uses the page's own `fetch`, measured by the two
   document-file routes the round exercises in case 2 (the model is fetched, stored and played).
