## 3. Architecture notes

Generic names, and no claim about the reference product — the reference's permission list is `UNKNOWN`.

**A download for offline** is two records and one loop. The loop walks a document's playable sentences and asks
the chunk source to synthesize each one; the chunk source caches both halves of every chunk — the audio and the
metadata beside it — before it answers. The two records are the cached bytes and one *pin*: the pin is the
record that says which document the bytes belong to and what voice and engine speed they were synthesized at.
A pin without coverage is a document whose audio is partly there; coverage without a pin is audio the cache may
throw away. The three states a row can be in follow from those two facts: `none`, `partial`, `complete`.

**Eviction is a size limit plus a predicate.** The cache is asked to bring itself under a byte limit while
sparing every key a pinned document occupies. Because that predicate is asked synchronously about one key at a
time, the pin set is materialized first: every pinned document's model is read and its chunk ids are computed
from the text, the voice and the engine speed the pin holds. A document whose model is gone pins nothing, which
is what lets a deleted document's audio be dropped.

**Timing.** Nothing here is clock-driven; a pack is a burst of requests, and each sentence's pair of cache
writes completes before the next sentence is asked for. The reader sees a percentage that moves one sentence at
a time.

**The permission list is a build artifact, not a source file.** The APK's manifest is the merge of the app's own
generated manifest (from `app.json` and the config plugins) with every linked Android library's manifest, so a
permission can enter the shipped app from a dependency's own manifest without any file in the repository naming
it. That is what the audit exists to catch, and it is why the audit reads the built APK rather than `app.json`.

## 4. Lectern design

- [DESIGN] The pin is F§5.9's `setting` entity under the key `offline:<docId>`, holding `{ voiceId, synthSpeed }`
  — the same record, key, and meaning the web app's own "download for offline" writes (F§10.1, U-031). A value
  that is not an object with a non-empty string `voiceId` and a finite `synthSpeed` is not a pin, which is how a
  removal (`null`) and a damaged row both read as "not pinned" — F§5.9's `LibraryStore` has no setting delete.
- [DESIGN] **The pin is written before the sentences are fetched, not after.** The web app has no cancellation
  and writes it last; this unit's contract requires the opposite observable outcome — "cancel leaves a `partial`
  state" — and `partial` is exactly "a pin whose coverage is incomplete". Writing the pin first is also what
  makes an interrupted pack identifiable and protected from eviction while it is still being filled, and the
  row's own "Finish" affordance is the reader's answer to it. Nothing claims the document is readable offline
  until every sentence is cached: that is `offlineState`'s `complete`, which is recomputed from the cache.
- [DESIGN] The pack covers **every** sentence (F§10.1's "every sentence"), so the reader's own reading mode
  cannot find a gap, and it is synthesized at engine speed 1 (F§5.6(e)): Android's sink ceiling is the
  platform's own time-stretcher, so no reader-chosen rate has to be split off to the synthesizer.
- [DESIGN] Cancellation is a consumer-side stop, because the hub client takes a base URL, a token and a `fetch`
  and exposes no abort signal (measured at U-049, F§7.2's routes have no cancel) — the loop stops asking for
  further sentences and reports the cancel as such; a request already in flight is not claimed to be aborted.
- [DESIGN] The audit reads the APK's merged manifest with the SDK's `aapt2 dump badging`, falling back to
  `apkanalyzer manifest permissions`, and passes only when the package is `dev.lectern.app` and every
  `uses-permission` is one of the contract's eight or is the app's own — a permission whose name is namespaced
  to the application id, which is how the manifest merger names a library's signature-level permission.
- [DESIGN] `verify-offline.sh` does the contract's steps with the harness attached. It downloads through the
  library row's own control, stops the hub (which also removes the `adb reverse` that is the app's only route to
  it), enters airplane mode, and — because this host's transport is Wi-Fi only and airplane mode takes Wi-Fi
  down with it (§2) — restores Wi-Fi on the device immediately afterwards so that the observation the contract
  asks for is possible at all. Airplane mode is still on (`airplane_mode_on` is read and reported), the hub is
  still stopped and the reverse is still gone, so the app is offline with respect to its hub; the script always
  disables airplane mode on the way out, on every path, including a failure.

## 7. Deviation proposals

1. **The release APK declares three permissions outside the allowlist, and no file this unit may write can
   remove any of them.** `MODIFY_AUDIO_SETTINGS` is declared by `expo.modules.audio:expo.modules.audio:58.0.12`'s
   own Android manifest and written into the app's generated manifest by its config plugin;
   `USE_BIOMETRIC` and `USE_FINGERPRINT` are added by `androidx.biometric:biometric:1.1.0`, a transitive
   Android library (the manifest-merger report in §2 names both origins, and `aapt2` and `apkanalyzer` agree on
   the result). None of the three is microphone, billing, advertising-identifier, location, contacts or
   external-storage; each is a normal-protection-level permission that a linked library asks for, and each is
   removable **only** by a `tools:node="remove"` directive, which comes from either
   `apps/android/app.json`'s `android.blockedPermissions` (the mechanism U-047 used for `RECORD_AUDIO`, and the
   one `app.json` already uses for the two storage permissions) or a config plugin — both outside this unit's
   patch scope. Two repairs, both the operator's:
   (a) add `android.permission.MODIFY_AUDIO_SETTINGS`, `android.permission.USE_BIOMETRIC` and
   `android.permission.USE_FINGERPRINT` to `apps/android/app.json`'s `blockedPermissions`, which the audit would
   then see gone from the APK (F§10.4's list is unchanged and nothing the app does needs any of the three);
   (b) patch this contract's allowlist to name them, which is the smaller change but leaves three permissions
   the app never uses in the shipped APK.
   This session takes neither: AGENTS.md R6/R5 leave `app.json` to the operator, and R11 forbids editing the
   fixed command's expectations.
2. **`verify-offline.sh` cannot enter airplane mode and keep driving the device on a Wi-Fi-only transport.**
   Reported with its measurement in §2 and §6.3. The repair this unit implements is to restore the device's
   Wi-Fi immediately after the toggle, so that airplane mode is on, the hub is stopped and the app is hub-less,
   while the harness stays attached to observe the reading; the alternative repair — observing the app from the
   device side and reading the result back after the radio returns — would put the whole check inside a shell
   one-liner and leave the failure mode (a phone stuck in airplane mode with no transport) to the operator.
