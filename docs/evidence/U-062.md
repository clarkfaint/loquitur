## 3. Architecture notes

**One completion, as a small state machine (F§9).** A provider built from a configuration is inert — it holds an address,
a model, an optional key and an optional transport, and touches nothing until it is asked. `complete(req)` moves it to one
*in flight* state: exactly one `POST` to `{baseUrl}/chat/completions`, carrying the two prompt messages. It settles in one
of two terminal states. *Answered*: the first choice's `message.content` is the result and is what the caller receives —
the adapter does not interpret it, because only the summarisation step knows whether it asked for JSON. *Refused*: one
`LLM_UNAVAILABLE` error, from any of six causes — this host has no `fetch` and none was injected; the deadline passed; the
endpoint answered a non-2xx status; the answer's JSON has no readable `choices` array or no `message.content`; the choice
list is empty; the transport rejected, or the body could not be read. Six causes, one terminal state, so a caller has one
failure to handle and one state to record rather than a taxonomy to switch on.

**Timing.** The deadline is not a socket option here, it is a race, and the two halves do different jobs. A promise that
resolves `null` after `timeoutMs` — and aborts the controller that travelled with the request — is raced against the call
itself. The abort is what a real `fetch` obeys and what releases the socket; the race is what still holds for a transport
that ignores the signal, which is why both exist. The deadline's own timer is cleared in the `finally`, so an answer that
arrives in time leaves no timer behind. Measured in this session's suite: a transport that never settles, at
`timeoutMs: 20`, refuses with `did not answer within 20 ms` — the deadline is arithmetic, not a race with a scheduler.

**The mock's decision table.** One server, one route, one reply per prompt, chosen by searching the *user* message and
nothing else. The order matters and is fixed: `FORCE_ERROR` first (a 500, whatever else the prompt says), then
`FORCE_INVALID_ONCE`, then `FORCE_INVALID` — the second marker is a *prefix* of the first, so a single `includes` test for
the long marker has to happen before the short one or the "once" prompt would be invalid for ever. Then the classification
that is not a marker at all: a prompt whose text, stripped to letters and digits, contains `keytakeaways` is F§9's reduce
step, and everything else is the map step — F§9 names the reduce output as `keyTakeaways`, so a prompt that asks for that
output says so in some spelling of it, and a map prompt that asks for notes cannot match. Both surviving branches build
their text from the segment's first six words, which is what makes a reply deterministic and yet derived from what the hub
actually sent. `FORCE_SLOW` is orthogonal: it never changes the reply, only delays it by two seconds, so a case can either
wait for it or let a provider's own deadline fire first.

**Where the boundary sits.** Two imports could have leaked Node's ambient types into `apps/server`'s program — which
compiles `packages/core`'s parsers, where U-023, U-055 and U-057 each measured the same two frozen lines breaking the
moment `Buffer` became a real type. Neither does. The provider reaches `fetch` as a host global (declared by TypeScript's
injected DOM library) behind an interface it owns, and the mock reaches `node:http` through a `string`-typed specifier with
the four members it uses declared locally. Measured: `tsc --listFiles` over the package program names **0** `@types/node`
files, and the three non-test modules this unit delivers are exactly the ones in the program.

## 4. Lectern design

- [DESIGN] `LlmProvider` is F§9's interface exactly — `complete(req: { system; user; json; maxTokens }): Promise<string>`.
  F§9's inline parameter is given one name, `LlmCompletionRequest`, so a route, a test and the adapter refer to one type
  instead of repeating the shape three times; the fields and their order are F§9's.
- [DESIGN] The request body is F§9's list and nothing beside it: `model`, `messages` (one `system`, one `user`), the
  caller's `max_tokens`, `temperature: 0.2`, and `response_format: { type: "json_object" }` **only** when `json` is true.
  Proven by key set rather than by a field check: `["max_tokens","messages","model","temperature"]` without it, the same
  list plus `response_format` with it.
- [DESIGN] The credential is a header and only a header: `authorization: Bearer <key>` when a key is configured, and no
  `authorization` key at all when one is not, so an endpoint that wants no credential is sent nothing rather than an empty
  bearer. The key is F§7.1's `LLM_API_KEY` and is never written into a request body or a URL.
- [DESIGN] The transport is an injected `LlmFetch`, defaulting to the host's `fetch` — U-016's and U-017's engine boundary
  one layer up. It is what lets the suite produce a socket that never settles, a refused connection and a choice-less
  answer without a network, and it keeps `AbortController` typing out of the adapter's own signature.
- [DESIGN] The deadline is 60 000 ms when an operator names none; `timeoutMs` overrides it. F§9 names no deadline, the
  engine adapters are bounded at 30 s, and a completion is slower than a chunk of speech (§7 (2)).
- [DESIGN] The one refusal is `LlmError`, carrying `code: "LLM_UNAVAILABLE"`. That code is U-054's `AiErrorCode` — F§7.2's
  closed thirteen-code set has no entry for it, which is why the context's AI routes carry their own set — and the literal
  is bound to that set with `satisfies AiErrorCode`, so a rename in the contract breaks this compile rather than drifting
  silently.
- [DESIGN] The mock is a `node:http` server on an operating-system-chosen loopback port, published as
  `@lectern/server/testing` (`startMockLlm(): Promise<{ baseUrl, requests, close }>`): the second entry the package's
  `exports` map already declared, and the reason no AI unit needs a model, a GPU or a network (P6).
- [DESIGN] Its reply rules are the four markers plus the map/reduce classification, all string searches over the user
  message, so a case steers the endpoint by writing its prompt: `FORCE_ERROR` → HTTP 500; `FORCE_INVALID` → the message
  content is text that is not JSON; `FORCE_INVALID_ONCE` → the same, once; `FORCE_SLOW` → the answer is delayed two
  seconds; a prompt naming F§9's reduce output → the reduce reply; anything else → the map reply.
- [DESIGN] A map reply is `{ notes: [...3] }` with each note quoting the segment's first six words; a reduce reply is
  `{ summary, keyTakeaways }` with 5 takeaways in `brief` and 9 in `detailed` — F§9's own prompt counts, which also sit
  inside the modes' validation ranges (3–6 and 6–12), so the same reply is valid at both the prompt's request and the
  stored result's ceiling.
- [DESIGN] Every request that arrives is recorded in `requests` — method, path, lower-cased headers and the parsed body —
  whether it was answered or 404'd, so a case can assert the request the hub built and not only what came back.
- [DESIGN] F§9's provider is created in the app factory: `buildApp` builds it from `LLM_BASE_URL` + `LLM_MODEL` and it is
  **absent** from the context when either is unset, which is what leaves a hub with no AI routes configured without a
  provider to call. The key comes from `LLM_API_KEY` and is passed only when it is set.
- [DESIGN] `HubOverrides.llm` is the injection seam beside `engines`, `ttsCache` and `ocr` — the same shape the hub has
  used since U-019 — because a route's own tests must be able to drive an AI route without an endpoint (§7 (4)).
- [DESIGN] Nothing logs a prompt or a completion: neither file writes to a console, and the hub's logger is off unless a
  caller asks for one, so neither half of an exchange can reach a log by default.
- [DESIGN] `node:http` is reached through a `string`-typed specifier, the boundary `src/db/database.ts` documents, because
  `src/testing/mock-llm.ts` is a *delivered* module inside the package's own type-check program. A static `node:` import
  there would be `TS2591` and, worse, a static import of a package whose declarations reach `@types/node` would re-break
  the frozen `packages/core` parser lines one unit later.

## 7. Deviation proposals

1. **`FORCE_INVALID_ONCE` is identified by its marker, not by the exact message.** The contract says "invalid on the first
   call for that message, valid afterwards", but F§9's own retry appends the validation error to *that same message*, so a
   key on the message text would answer the retry invalidly as well and the marker could never do the one thing it exists
   for. The mock therefore answers the first call that carries the marker invalidly and every later one validly, which is
   recorded in `replyFor`'s own comment. Proposed wording: "invalid on the first call that carries the marker".
2. **F§9 names no LLM deadline and no temperature.** The contract requires `temperature: 0.2`, and `features.md` §9's
   adapter line lists `{ model, messages, max_tokens, response_format }` without it. The deadline is this unit's own
   choice (60 s, `timeoutMs` overriding). Proposed: add both to F§9's adapter line.
3. **A reduce reply is F§9's `{ summary, keyTakeaways }`, not a stored `SummaryResult`.** U-054's `SummaryResultSchema(mode)`
   also requires `model`, `promptVersion` and `createdAt`, which the model does not produce and the mock cannot invent
   deterministically — the hub adds them when it stores a job's result. The mock builds the reply to the *mode's* ceilings
   instead, so "a valid result for the requested mode" holds at both the prompt's request and the schema's range.
4. **`HubOverrides.llm` is an addition the patch note does not spell out.** It says "add an optional `llm` member to the
   context, created in the app factory"; the provider is created in `buildApp` as written, and the override is the seam a
   later unit's route test needs to drive an AI route without an endpoint — the same shape `engines`, `ttsCache` and `ocr`
   have carried since U-019. Nothing else in either patched file changed.
5. **The map/reduce classification is made from the prompt's own text.** The contract names the two replies but not how a
   prompt is recognised as one or the other. The mock uses F§9's reduce output field name (`keyTakeaways`, matched with all
   punctuation and case removed) as the reduce signal and treats everything else as a map prompt. If a later unit's reduce
   prompt does not name that output, this rule needs restating — it is the one place where a future prompt and this mock
   must agree.
