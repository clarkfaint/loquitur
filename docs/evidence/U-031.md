4. What engine speed does the web player actually request, so a pack is synthesized at the speed it will be
   read at?

## 3. Architecture notes

**A pack's state machine.** `none` — no pin under `offline:<docId>`, or a value that is not a pin. → *download*
synthesizes every sentence (furniture included, because F§10.1 says "every sentence" and a reader who turns
furniture on must not find a gap), writes the pin `{ voiceId, synthSpeed }`, adopts the voice, then enforces the
cache limit → `complete` when every sentence's audio **and** its metadata sidecar are cached. A pin whose audio
is incomplete reads `partial`, which is what an interrupted download and a pack whose document was deleted both
look like. → *remove* writes `null` under the pin key and enforces the limit.

**The pin is derivable, not remembered.** A chunk's id is `sha256([engine, engineVoiceId,
synthSpeed.toFixed(2), text])` (F§6), and a pin holds the voice and the speed, so `pinnedPredicate()` recomputes
every key from the document's own model rather than storing a key list. Two consequences the tests pin down:
both halves of a chunk (`<id>` and `<id>.json`, U-021's layout) are protected, and a document whose model is
gone contributes no keys — which is how F§5.9's "deleting a document unpins its audio" is honoured without a
second write path.

**`evictLru` asks a synchronous predicate**, so the pin set is materialized before the eviction rather than
during it (`pinned: (key: string) => boolean`). The limit is the reader's saved one unless a caller names
another; the settings section's "clear unpinned audio" is the same call with `0`.

**Sizes and arithmetic measured in the unit tests** (a 4-sentence document, 40 bytes per sentence for both
halves): a pack is 160 bytes; with a 120-byte limit the eviction frees the two 256-byte unpinned blobs (512
bytes) and leaves all 160 pinned bytes, which is `evictLru` stopping at "nothing left to take" rather than at
the limit.

**Layout of the shell.** The worker owns one cache (`lectern-precache-v1`, prefix-matched so `activate` can
retire an earlier generation). `install` reads `precache-manifest.json` and caches every path it names, failing
the install (and deleting the half-filled cache) if the list cannot be read; `fetch` answers a same-origin `GET`
only — a navigation, `/` or `index.html` network-first with a cache fallback, everything else cache-first — and
lets non-`GET`, other origins and `/v1/` through untouched, so F§7.2's hub traffic is never cached.
`main.tsx` registers `./sw.js` only when the build is production and the protocol is `http:` or `https:`, after
the shell has mounted.

## 4. Lectern design

- [DESIGN] **The manifest is a directory listing taken in `closeBundle`** (F§10.1's app shell), because
  `index.html` is written around the bundle rather than inside it and the shell is the one file the worker
  cannot do without. It lists the worker itself too — "every emitted file path" is the rule, and the few
  kilobytes cost nothing — and leaves out only the list being written.
- [DESIGN] **`cache.match(request, { ignoreVary: true })`** in both branches of the fetch handler (§2's
  measurement). The app serves one variant per URL, so `Vary` distinguishes nothing it should respect.
- [DESIGN] **Unpinning writes `null`** under `offline:<docId>` (F§5.9 has no delete for a setting), and a pin
  that is not an object with a non-empty `voiceId` and a finite `synthSpeed` reads as no pin at all.
- [DESIGN] **The pack adopts its voice as the reader's own** (`useSettingsStore.update({ preferences: {
  voiceId } })`), because a reader who comes back with no network cannot ask the hub which voices exist, and
  F§6 refuses a chunk with no voice. The end-to-end case proves it without ever typing a voice: the pack is
  prepared with the hub's first voice and the offline reading uses it.
- [DESIGN] **Removal unpins and enforces the reader's own limit; it does not empty the cache.** Evicting to
  zero on a per-row action would silently drop another document's cached audio. The reader who wants the space
  back has the section's own action, which says what it does.
- [DESIGN] **`downloadForOffline` pins before it enforces the limit**, and writes nothing until every sentence
  is cached — a pin that outlived a half-finished download would claim a document is readable offline when it
  is not.
- [DESIGN] The offline control is one component per row (`OfflineButton`), the cache section is one registry
  entry (`OfflineSection`), and the service's own dependencies arrive as an argument with the app's wiring as
  the default, which is what lets the unit tests drive it with memory stores and a stub chunk source
  (AGENTS.md §7's "tests use the mock engine" in its web form).

## 7. Deviation proposals

1. **F§5.9 has no way to remove a setting.** `LibraryStore` declares `setSetting`/`getSetting` and no delete,
   while the schema's `deleted` flag is only ever written by `applyRemote`. This unit writes `null` under the
   pin key; a `deleteSetting(key)` member (or a documented convention) would say it properly.
2. **`sections.ts`'s own doc comment is now stale** ("Empty in this unit"), and AGENTS.md §5 makes a registry
   append-only ("never rewrite existing lines"), so it was left as it stands — the same state `routes.ts` is in
   after U-028 and U-029. A later unit that may edit the file could correct the sentence.
3. **`index.html` is not in the Rollup/Rolldown bundle object**, so "every emitted file path" cannot be taken
   from `generateBundle` alone; this unit reads the output directory in `closeBundle`. Worth saying in the
   contract's patch note, because the obvious implementation silently ships a worker that cannot serve the
   shell.
4. **`Cache.match` and `Vary`**: a build that marks its own assets `crossorigin` and a server that answers
   `Vary: Origin` together make every precache lookup miss. Worth a line in F§10.1's offline bullet so the
   extension and desktop units do not each rediscover it.
