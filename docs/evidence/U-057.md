## 3. Architecture notes

**The feed carries no data (F§8.3).** A `changed` message only tells a client that `rev` moved; the client
answers it with an ordinary pull over U-056's HTTP routes. That is why the module is small: it owns
authentication, the `ready` handshake, the `changed` subscription, the ping clock and shutdown, and nothing
else. No record, document text or token ever crosses the socket in either direction — the server set is
`ready`/`changed`/`ping`, and the client set is `auth`/`pong` (§2).

**Authentication is a first message, never the address.** A socket cannot carry F§11's bearer header before it
is upgraded, and F§8.3 forbids the token in the URL, a cookie or a subprotocol header. So the first frame must
be `{ "type": "auth", "token": "…" }` inside the configured deadline (5 s by default), and the comparison is
`constantTimeEquals` — the same function U-019's HTTP hook uses (`auth.ts:43`) — so a guess cannot be read off
the timing. Every failure closes with `4401`: a wrong token, a first message that is not an authentication, or
silence past the deadline.

**`ready` and the subscription are taken in one synchronous step.** `startFeed` clears the deadline, starts the
ping clock, subscribes to `onChange`, and only then sends `ready` with `currentRev()`. Because the subscription
is registered before the read is announced, a commit cannot slip between the two unnoticed: a commit that lands
after the subscription is announced as `changed`, and a commit that landed before it is already in the `rev`
`ready` carries.

**A ping that goes unanswered is counted, and the second one closes the socket.** Each interval sends `ping`
and marks an outstanding ping; the next turn counts it first, so two unanswered pings close with an application
code beside `4401` (this hub uses `4408`, §4). A `pong` clears both the count and the outstanding flag. The
clock is `setInterval`, and both timers are cleared on `close`.

**Every socket closes with the hub.** The plugin closes the server's own clients as the server stops; the
sockets this module opened are closed here as well, through an `onClose` hook that walks the `live` set with
`1001` and a shutdown reason. A hub that shuts down leaves no feed socket open (§6.1, the last case).

**A request without an upgrade is refused, not left to the plugin.** The route registers an ordinary `handler`
beside its `wsHandler`: an upgrade reaches `feed`, and a plain HTTP GET — a probe, a health check, a client that
forgot to upgrade — reaches the handler and is answered `426 Upgrade Required` with `upgrade: websocket` and
F§7.2's envelope, so a client that probed the path still parses one shape.

**The plugin's declarations are the trap, and the module is reached through a string.** See §2's measured
finding and §4's boundary. The route's own socket surface is declared locally as `FeedSocket` (three members:
`send`, `close`, `on`), and the route options are typed as `RouteOptions & { wsHandler: (socket: FeedSocket) => void }`,
so neither the route nor its cases load the plugin's declarations — but the plugin registered by `app.ts` is the
real module at runtime.

## 4. Lectern design

- [DESIGN] **The plugin is registered in `app.ts` before the route registry runs.** F§8.3's feed is a socket,
  and the upgrade has to be dispatched through Fastify's own router for a socket to run the hooks and reach the
  route it named; the plugin reads the route table as routes are added, so it is registered first. A route
  declaring a `wsHandler` is a socket route, and every other request to that path stays an ordinary HTTP request.
- [DESIGN] **The plugin is reached through a `string`-typed specifier, with its one used member declared
  beside it.** `const WS_PLUGIN_SPECIFIER = "@fastify/websocket" as string;` plus
  `type WebSocketPlugin = (instance: FastifyInstance) => Promise<void>;`, then
  `const { default: websocket } = (await import(WS_PLUGIN_SPECIFIER)) as { default: WebSocketPlugin };`. This is
  the boundary U-019 used for `node:fs/promises` and U-046/U-055 used for a native addon: a specifier typed as
  `string` is not resolved by the compiler, so the declarations never enter the program, and the module
  registered at runtime is the real plugin. Measured both ways in §2: 83 `@types/node` files and two frozen
  errors with the static import, against 0 and a clean exit without it.
- [DESIGN] **The route's socket surface is declared locally.** `FeedSocket` names the three members F§8.3's feed
  touches — `send`, `close`, `on` — rather than importing `ws`'s `WebSocket` type, for the same reason: the
  plugin's declarations are what reach `@types/node`, and the object at runtime is still the plugin's own socket.
- [DESIGN] **The auth exemption is a named path beside the health probe.** `auth.ts` gains
  `export const WS_FEED_PATH = "/v1/sync/ws"` and `EXEMPT_PATHS` becomes `new Set([HEALTH_PATH, WS_FEED_PATH])`.
  The feed's exemption is its own reason — a socket cannot carry a header before it is upgraded — and a request
  that arrives on the path without an upgrade is refused by the route itself and reads nothing.
- [DESIGN] **The two clocks are configuration, not literals.** `wsAuthTimeoutMs` (default 5000) and
  `wsPingIntervalMs` (default 30000) join F§7.1's always-present fields, read from
  `LECTERN_WS_AUTH_TIMEOUT_MS` and `LECTERN_WS_PING_INTERVAL_MS` through the same `asInteger` helper as the
  port and the upload limit. A test drives the feed's clocks in milliseconds instead of waiting out thirty
  seconds.
- [DESIGN] **`4408` is the no-pong close code.** F§8.3 names only `4401` for a failed authentication and no code
  for a socket that stopped answering pings, so this hub uses the application code beside it rather than a
  generic `1008`; the reason string says "two pings went unanswered (F§8.3)" for a log.
- [DESIGN] **A first message that is not an authentication is `4401`, not `400`.** F§8.3's failure is the
  close; a socket that sends `{"type":"pong"}` before authenticating has not authenticated, so it gets the same
  close a wrong token gets, and it is told nothing first.
- [DESIGN] **The route's HTTP handler is a `426`, not a `400`.** F§8.3's path is a socket endpoint; a request
  without an upgrade is answered with the status that names what the client must do and the `upgrade` header
  that names the protocol, inside F§7.2's envelope. The contract's case allows "400 or 426"; `426` is the one
  that tells a client what to do.
- [DESIGN] **The feed's messages are built through the contract's own schemas.** `WsServerMessageSchema.parse`
  runs on every outbound frame, so a `ready` or `changed` that did not carry a non-negative integer `rev` would
  throw here rather than reach a client; `WsClientMessageSchema.safeParse` validates every inbound frame before
  its `type` is read.
- [DESIGN] **`textOf` reads a frame as text or as bytes.** `ws` hands a message over as bytes by default, and a
  client of this feed speaks JSON, so a frame that is not text at all reads as the empty string — which no
  message of F§8.3 parses as, and so fails authentication rather than being answered.

## 7. Deviation proposals

1. **The no-pong close code is `4408`, not a code F§8.3 names.** F§8.3 names only `4401` for a failed
   authentication and says "close after two unanswered pings" without a code. A patched contract could name one
   — `4408` is the application code beside `4401` — or ask for `1008`; either is a one-line change in
   `sync-ws.ts` plus its case.
2. **The HTTP refusal is `426`, not `400`.** The contract's case allows "400 or 426"; `426 Upgrade Required`
   with `upgrade: websocket` is the one that tells a client what to do. A patched contract that wants `400` can
   say so.
3. **The first message that is not an authentication is `4401`, not a protocol error.** F§8.3's failure is the
   close, and a socket that has not authenticated has not authenticated; a patched contract could instead name
   a separate code for "malformed first frame".
4. **The feed's two clocks are environment settings.** The contract asks for `wsAuthTimeoutMs` (default 5000)
   and `wsPingIntervalMs` (default 30000) in the config; they are read from `LECTERN_WS_AUTH_TIMEOUT_MS` and
   `LECTERN_WS_PING_INTERVAL_MS`. A patched contract could name the environment variables explicitly in F§7.1's
   table, which would also need `spec.md` touched.
5. **The plugin's declarations are avoided by a string-typed specifier.** F§8.3's *Forbidden Action* forbids a
   library beyond `@fastify/websocket`, and the module is installed and registered exactly as named; the
   specifier is typed `string` only so its `@types/node`-reaching declarations stay out of the program (§2,
   §4). A patched contract could instead allow `skipLibCheck` in `apps/server/tsconfig.json`, which is outside
   this unit's writable set and would not repair the frozen `packages/core` lines anyway.
6. **The auth exemption is a named export in `auth.ts`.** The path is `WS_FEED_PATH` beside `HEALTH_PATH`, so
   the route and its cases share one string. A patched contract could keep the literal in both places.
