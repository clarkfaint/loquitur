## 3. Architecture notes

**The feed carries no data (F§8.3).** A `changed` message only tells a client that `rev` moved; the client
answers it with an ordinary pull over F§8.2's HTTP routes. The module therefore owns four things and nothing
else: authentication, the `ready` handshake, the `changed` subscription, and the ping clock.

**Authentication is a first message, never the address.** A socket cannot carry F§11's bearer token before it
is upgraded, and F§8.3 forbids the token in the URL, a cookie or a subprotocol header. A client's first
message must be `{ "type": "auth", "token": "…" }` inside the configured `wsAuthTimeoutMs` (5 s by default);
the comparison is `constantTimeEquals`, so a guess cannot be read off the timing. Every failure — a wrong
token, a first message that is not an authentication, or silence past the deadline — closes the socket with
`4401`. The path is exempt from the HTTP header hook for exactly this reason: a request that arrives without
an upgrade is refused by the route itself and reads nothing.

**`ready`, and then every `changed`.** The current `rev` is read and the `onChange` subscription is taken in
one synchronous step, before `ready` goes out, so no commit can slip between the two unnoticed. F§8.2's
`onChange` then sends `changed` with the new `rev` for every commit that moved it. The subscription is
released on the socket's own `close` event, so a client that disconnects leaves no listener behind.

**`ping`, and a socket that stops answering is closed.** A `ping` goes out every `wsPingIntervalMs` (30 s by
default) and a `pong` clears both the count and the outstanding ping. Two pings may go unanswered before the
socket is closed. The ping clock starts when the socket authenticates, not when it connects, so the
authentication deadline and the liveness clock cannot race each other.

**Every socket closes with the hub.** The plugin closes the server's own clients as the server stops; the
sockets this module holds are closed by its own `onClose` hook, so a hub that shuts down leaves none of them
open. A request to the path without an upgrade is answered `426 Upgrade Required` through F§7.2's envelope
with an `upgrade: websocket` header, so a client that probed the path still parses one shape.

**The plugin must be registered before the registry runs.** It reads the route table as routes are added, so
`app.ts` registers it before `for (const route of routes) route(app, context)`; a route declaring a
`wsHandler` is then a socket route, and every other request to that path stays an ordinary HTTP request.

## 4. Lectern design

- [DESIGN] **The feed is one route module with a `wsHandler` beside its handler.** `syncWsRoutes` registers
  `GET /v1/sync/ws`; the `wsHandler` owns the socket lifecycle and the handler refuses a non-upgrade request.
  The module is registered in U-019's `(registry)` list like every other route module.
- [DESIGN] **The plugin and the socket type are reached through `string`-typed specifiers.** In `app.ts` the
  module is imported as `(await import(WS_PLUGIN_SPECIFIER))` and its default export typed locally as
  `WebSocketPlugin`; in `sync-ws.ts` the socket's four used members are declared as `FeedSocket` rather than
  imported from the plugin's typings. This is U-055's repair for the transitive-`@types/node` trap (§2), and
  the module registered at runtime is the real plugin.
- [DESIGN] **The auth exemption lives in `auth.ts` beside the probe's.** `WS_FEED_PATH` is exported from
  `auth.ts` and used both in `EXEMPT_PATHS` and by `sync-ws.ts` (as `SYNC_WS_PATH`), so the path the hook
  exempts and the path the route registers cannot drift apart. The contract's *Patch scope* names `auth.ts`
  for exactly this change.
- [DESIGN] **The two feed intervals are configuration, not constants.** `wsAuthTimeoutMs` (default 5000) and
  `wsPingIntervalMs` (default 30000) are optional settings read from `LECTERN_WS_AUTH_TIMEOUT_MS` and
  `LECTERN_WS_PING_INTERVAL_MS`, added to the strict `ConfigSchema`, so a test can drive the feed's clocks in
  milliseconds instead of waiting out thirty seconds.
- [DESIGN] **A socket that stops answering pings closes with `4408`.** F§8.3 names no close code for that case
  — only `4401` for a failed authentication — so this hub uses the application code beside it; the contract's
  *Forbidden Action* is satisfied by closing, not by the code's value.
- [DESIGN] **A non-upgrade request is `426` with `upgrade: websocket`.** The contract's test accepts 400 or
  426; 426 is the status that names what the client must do, and the header repeats it for a client that only
  reads headers.
- [DESIGN] **The auth message is read beside the schema, not out of it.** U-054's `WsClientMessageSchema`
  deliberately models no token field (`auth` is a `looseObject` pinned to the discriminator), so the message is
  validated by that schema and the credential is taken from the value the schema accepted. Nothing about the
  token is modelled or logged.
- [DESIGN] **Every send is built through `WsServerMessageSchema`.** A message the contract's own schema would
  reject is never put on the wire, and a parse failure is a programming error rather than a client-visible one.

## 7. Deviation proposals

1. **A socket that stops answering pings closes with `4408`.** F§8.3 names only `4401` for a failed
   authentication; the contract's *Forbidden Action* requires closing after two unanswered pings but does not
   name a code. A patched contract could name one, or accept `1001`; the delivered constant is
   `WS_NO_PONG_CODE = 4408`.
2. **A non-upgrade request is `426` with `upgrade: websocket`.** The contract's test accepts 400 or 426; the
   delivered status is 426 because it names what the client must do. A patched contract could fix 400.
3. **The auth exemption is implemented in `auth.ts`'s `EXEMPT_PATHS`, with the path exported as
   `WS_FEED_PATH`.** The contract's *Patch notes* say to exempt only `/v1/sync/ws`; the delivered change keeps
   the probe's exemption and adds the feed's beside it in one set. A patched contract could instead move the
   exemption into the route's own `config`.
4. **The two feed intervals are read from `LECTERN_WS_AUTH_TIMEOUT_MS` and `LECTERN_WS_PING_INTERVAL_MS`.**
   The contract names the settings `wsAuthTimeoutMs` and `wsPingIntervalMs` but not their environment
   variables; the delivered names follow F§7.1's `LECTERN_` convention. A patched contract could name them.
5. **The plugin is reached through a `string`-typed dynamic import in `app.ts`.** This is the repair for the
   transitive-`@types/node` trap the static import caused (§2), not a contract instruction; it is the same
   boundary U-055 established. A patched contract that wants the plugin statically imported would need the
   frozen `packages/core` parser lines unfrozen or `skipLibCheck` widened.
6. **The ping clock starts when the socket authenticates, not when it connects.** F§8.3 gives no ordering;
   starting it after `ready` keeps the authentication deadline and the liveness clock from racing. A patched
   contract could start it at connect.
