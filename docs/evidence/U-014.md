## 2. Observations

- [UNKNOWN] How any other store implementation behaves on a device — the three implementations F§5.9 names (`MemoryLibraryStore`, `IdbLibraryStore`, `SqlLibraryStore`) are only made comparable by the conformance suite this unit adds.
- [OBSERVED] `zod@4.6.7` refuses an explicit `undefined` for an `.exactOptional()` field — `{ uri: undefined }` fails with `expected string, received undefined` while the same object with the key absent passes — measured with `node -e` against the installed package in `packages/core/node_modules/zod`. - [OBSERVED] `z.strictObject` refuses an unrecognized key — `{ …meta, ownerId: "user-1" }` fails to parse — measured the same way. This is what makes the contract's "no user, account, owner or tenant fields" rule structural rather than a comment.

## 3. Architecture notes

**Last-writer-wins.** Two records of the same `(entity, entityId)` are ordered by `ts` first and by `deviceId` as a plain string second; equal stamps are not newer, so re-applying an op is a no-op and two devices cannot rewrite a record back and forth. The device comparison is lexical, so `dev-10` sorts *before* `dev-9`.

**The outbox.** Every local mutation (put document, folder, bookmark, progress, setting; delete document, folder, bookmark) appends exactly one `Op`. Two operations are deliberately *not* mutations of a synced entity: `setCursor` (local sync bookkeeping) and `applyRemote` (a change that arrived from the network). Neither appends, which is what keeps a store from echoing what it just received.

**Version bookkeeping.** The outbox carries the comparison's inputs, but the queue is drained by `ackOps`, so the store keeps one `{ ts, deviceId }` per `(entity, entityId)` separately. That map is what `applyRemote` compares against, and it survives acknowledgement.

**Tombstones.** A delete writes `deleted: true` into the record itself, appends a `delete` op carrying that tombstone, and drops the document's model. A tombstoned document answers `null` from `getDocumentMeta` and `getDocumentModel` and is absent from `listDocuments` — the tombstone exists for sync, not for the reader.

**Convergence.** Because every applied record is written verbatim from the op (and a delete op's record is applied as its tombstone), two stores that hand each other their pending ops end in the same state whatever order they apply them in: the op's stamp is the only thing that decides a winner.

**The model is not in an op.** `Op.record` carries a record; a document's `DocumentModel` travels as its own payload (F§8.2), so a device that applies a remote `document` op holds the metadata and has no model until the file arrives — `getDocumentModel` answers `null` for it, and applying the op does not disturb a model the device already has.

## 4. Lectern design

- [DESIGN] F§5.9's record set and sync envelope are implemented verbatim as strict zod schemas (`DocumentMeta`, `Folder`, `Bookmark`, `Progress`, `Op`), with `SourceKind` taken from `model.ts` rather than re-declared.
- [DESIGN] A fifth record, `SettingRecord` (`key`, `value`, `updatedAt`, `deleted`), gives F§5.9's `setting` entity kind a body: `setSetting` writes one, a delete op carries its tombstone, and `getSetting` answers `null` for a missing or tombstoned key. F§5.9 declares the entity kind and the two methods but no record type.
- [DESIGN] The store owns the clock: each mutation sets the record's `updatedAt` to the injected `now()` and stamps its op with the same number, so a record's timestamp and the op's `ts` agree on every device that applies it, and no store code reads the wall clock.
- [DESIGN] `deleteDocument` removes the model and the reader's view of the record; it cannot unpin audio, because `BlobCache` has no pin registry — pinning is the `pinned` predicate the caller passes to `evictLru`. The caller therefore unpins by reading the store (see §7).
- [DESIGN] `deleteFolder` tombstones the folder alone. F§5.9 authorises no cascade, so documents keep their `folderId` and an orphaned folder id is the library's problem, not the store's.
- [DESIGN] A delete of an unknown or already-deleted record appends nothing, because a tombstone needs a record to tombstone.
- [DESIGN] `pendingOps` answers queue order and `Math.max(0, limit)` entries; `listDocuments` answers insertion order and filters by an exact `folderId` (where `null` selects the documents at the root) and by a case-insensitive substring of the title. F§5.9 fixes neither order, so the conformance suite sorts before comparing.
- [DESIGN] `evictLru` answers the number of bytes it removed, and recency in the memory cache is a counter incremented by every read, write and `uri` request — not a clock, so two caches fed the same calls evict the same entries.
- [DESIGN] The memory cache copies bytes in on `put` and out on `get`, so a caller's buffer cannot corrupt a cached chunk.
- [DESIGN] Both conformance suites take a factory that receives the store's identity and clock (`{ deviceId, now, newId }`) or nothing (`() => BlobCache`), return one `{ name, ok, error? }` per case, and are exported from `@lectern/core/testing` beside the existing sink suite.

## 7. Deviation proposals

1. **"Deleting a document … unpins its audio" (F§5.9) has no API to call.** `BlobCache` exposes `has`/`put`/`get`/`uri`/`delete`/`sizeBytes`/`evictLru(maxBytes, pinned)`; pinning is a predicate the *caller* supplies, so a store cannot unpin anything. Current behaviour: `deleteDocument` removes the model; the caller's `pinned` predicate reads `getDocumentMeta` (a tombstoned document is `null`, hence unpinned). Proposal: add a sentence to F§5.9 that says the pin predicate is the caller's, or add `pin(key)`/`unpin(key)` to `BlobCache`.
2. **F§5.9's `Op.record: unknown` is not expressible as a required schema key.** `z.unknown()` infers an optional property (`record?: unknown`) while the schema requires the key at runtime, so `Op`'s inferred type is the stricter of the two in one direction and the looser in the other. Proposal: state that `record` is `unknown` and always present, which is what both the schema and every producer here do.
3. **F§5.9's `setting` entity has no record type.** Proposal: add `interface SettingRecord { key: string; value: unknown; updatedAt: number; deleted: boolean }` to the F§5.9 block so every implementation and the hub's repository agree on the body of a `setting` op.
4. **F§5.9 does not say whether a record's `updatedAt` or the store's `now()` wins.** Implemented as the store's clock (`updatedAt = now()` on every mutation, the op's `ts` equal to it), which is what makes a record's timestamp comparable across devices. Proposal: say so in F§5.9.
5. **`evictLru`'s return value is untyped prose.** Implemented as the number of bytes freed. Proposal: name the quantity in F§5.9.
