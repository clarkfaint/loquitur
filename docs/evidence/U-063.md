## 3. Architecture notes

**State machine (one row per document and mode).** `none` — no row has ever been written. `running` — a job was
enqueued, or is being executed. `done` — a result was written, and the row carries it. `error` — the job
failed, and the row carries the code and the sentence. Transitions: `request` moves `none`/`error`/a stale
`done` to `running`; the job moves `running` to `done` or `error`; `recoverInterrupted` moves `running` to
`error` with `INTERRUPTED` at start-up. There is no transition out of `done` other than a new `request`.

**The cache key.** `(docId, mode, model, promptVersion)` — the row's own `(doc_id, mode)` primary key plus the
two provenance columns. A `done` row whose model or prompt version is not the current one is not a cache hit:
`request` starts a new job over it, which is what makes a wording change in `prompts.ts` a real change rather
than a stale answer.

**One job at a time.** A single-slot queue in the job factory: `request` appends and starts the pump if the
slot is free, and the pump drains the queue in order. Two documents requested in the same instant are
summarized one after the other — measured in the route suite by a provider that records when each call starts
and ends (`start:A, end:A, start:B, end:B`, never interleaved).

**Segmentation.** Non-skipped blocks, in document order, packed whole into pieces of at most 12 000
characters, joined by a blank line inside a segment. A block that does not fit is split at its own sentence
boundaries (F§5.3's offsets into the block's text), which is the only case in which a block spans two segments.
A document that fits is one segment; a document with no reading matter is no segments.

**Map-reduce and the retry ladder.** One segment skips the map step and is sent as the reduce material
directly. Otherwise each segment is a map call, and the notes they return are the reduce material. Every call
has three attempts: the reply is parsed as JSON and validated, and a reply that fails either step is answered
again with `Your previous reply was rejected: <validation error>` appended to the *original* user message, so
three attempts cost three messages of a known size. A third failure is `LLM_INVALID_OUTPUT`; a provider that
cannot be reached at all (`LLM_UNAVAILABLE`) is not retried, because no wording fixes it.

**Timing and size.** F§9 names no token ceiling, so the pipeline's own are 512 tokens for a map call (at most
eight short notes) and 2 048 for a reduce call (F§9's loosest result ceiling is 4 000 characters). Nothing here
reads a clock except the injected one.

## 4. Lectern design

- [DESIGN] `prompts.ts` states both of F§9's limits and the exact JSON shape in the *user* message, so a case
  can read back what the model was told and a model needs no repair pass (F§9).
- [DESIGN] `PROMPT_VERSION = "1"` names the wording, and the result records it; the row's cache key includes it
  (F§9).
- [DESIGN] The map step is mode-independent — F§9 asks the same notes of every segment — and the reduce step's
  message names the mode and that mode's own limits, so the two modes cannot be confused for one another
  (F§9).
- [DESIGN] `segmentDocument` reads a block's sentences through the offsets F§5.3 already recorded, rather than
  re-tokenizing text that has been tokenized once (F§5.3, F§5.4).
- [DESIGN] Skipped blocks are dropped from a segment and their absence is not mentioned to the model, so the
  model summarizes reading matter rather than a document with holes in it (F§5.4, the contract's *Forbidden
  Actions*).
- [DESIGN] A reply is validated against the mode's ceilings taken from `SUMMARY_LIMITS` in the contract rather
  than written out again here, and the finished result is validated against `SummaryResultSchema(mode)` before
  it is returned (F§9, the contract's *Forbidden Actions*).
- [DESIGN] A job's failure is a row, not a rejection: `request` answers `running` before any work has happened,
  so the promise the job runs on is nobody's to await (F§9).
- [DESIGN] `recoverInterrupted()` is called when the AI route module registers, which is inside `buildApp` —
  the hub's start-up — and only when a provider is configured, because a hub with no AI has no summaries to
  recover (F§9).
- [DESIGN] A `running` row is written with F§8.4's two provenance columns `NULL`, following the migration's own
  comment that a pending summary has neither a model nor a prompt version yet.
- [DESIGN] Both routes answer `AI_DISABLED` (503) when F§7.1's `LLM_BASE_URL`/`LLM_MODEL` are unset, in F§9's
  own error shape rather than the shared thirteen-code envelope, exactly as U-056's sync routes answer their
  own codes (F§7.2, F§9).
- [DESIGN] `POST /v1/ai/summary` answers `202` with the status whether it started a job or found a cache, which
  is what F§7.2's row for that route says.
- [DESIGN] An inline `document` is stored gzipped through U-055's `putModel`, the same way F§7.2's library
  route stores one, and a document whose own `docId` is not the request's is refused (F§7.2, F§8.4).
- [DESIGN] `GET /v1/ai/summary/:docId?mode=` defaults to `brief`, the shorter of F§9's two modes, when the
  caller names none.

## 7. Deviation proposals

1. **`summarize`'s signature has no room for two of the result's fields.** The contract writes
   `summarize(provider, doc, mode): Promise<SummaryResult>`, and `SummaryResult` carries `model` and
   `createdAt` (F§9) — neither of which the model answers, and neither of which the three named parameters can
   supply: U-062's `LlmProvider` exposes `complete` alone, and AGENTS.md §7 forbids a real clock in a test. The
   delivered function is `summarize(provider, doc, mode, options)` with
   `options: { model: string; now: () => number }`, supplied by the pipeline that owns both (`jobs.ts`).
   Proposed wording: name the fourth parameter in the contract.
2. **The map step's mode-independence.** The contract asks for "functions building the system and user messages
   for the map step and for the reduce step in `brief` and `detailed` modes". F§9 defines the map step once
   (*"each segment → up to 8 bullet notes"*) and gives the mode-dependent limits to the reduce step, so the map
   messages take no mode and the reduce messages do. Proposed wording: state which of the two the modes apply
   to.
3. **`AI_DISABLED` on the read route.** The contract says `GET /v1/ai/summary/:docId?mode=` is
   `{ status, result?, error? }` and names `503 AI_DISABLED` only for `POST`. Both routes answer 503 here when
   no provider is configured, because a hub that cannot summarize is not the place to ask about a summary —
   but that does hide a stored result on a hub whose LLM was configured earlier and is not now. Proposed
   wording: say whether a disabled hub still reports a stored state.
4. **`202` for a cached result.** F§7.2's row for `POST /v1/ai/summary` says `202 { status }`, and the contract
   says a second request "returns the cached result". The route answers `202` in both cases, so a client that
   wants the distinction reads `status`, not the HTTP code. Proposed wording: confirm that reading.
5. **A pending row records no provenance.** F§8.4's migration comment says a pending summary has neither a
   model nor a prompt version yet, so a `running` row is written with both columns `NULL`. That means a row
   left running by a *previous* model is indistinguishable from one started by the current model; the recovery
   rule treats both as `INTERRUPTED`, which is right either way. Proposed wording: say whether provenance
   should be recorded while pending.
6. **A `(registry)` file's array literal had to be wrapped.** `apps/server/src/routes/index.ts` is marked
   `(registry)` by U-019, and §5 allows a registry entry to be added but never an existing line rewritten. The
   single-line array literal is 137 characters before this unit's entry and 147 after it, past
   `biome.json`'s `lineWidth: 140`, so the standing lint gate cannot pass unless the literal is wrapped over
   one line per entry. The wrap changes whitespace only: no entry was removed, reordered or renamed, and
   `aiRoutes` is appended last, after `syncWsRoutes`, in F§7.2's own table order. Proposed wording: note that a
   registry's array literal may be re-wrapped to satisfy the formatter.
