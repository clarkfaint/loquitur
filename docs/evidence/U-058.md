## 3. Architecture notes

Written in my own words for Lectern's own engine; there is no reference behaviour to describe for this unit.

**The round as a state machine.** A round has four steps in F§8.2's order and answers whether it reached the hub
at all. States: `syncing` while a round is in flight; `idle` when the last round finished against the hub;
`offline` when the hub could not be reached (a transport failure, or the injected online signal saying no);
`error` for any other failure. Events that *start* a round: `start()` (one round immediately), a local change
notified (`notifyLocalChange`, 2 s later), the periodic clock (every 5 minutes), a `changed` frame on the feed,
and an explicit `syncNow()`. A round never throws: a failure is a state, and the outbox and the cursor stay
where they were.

**One round at a time, one follow-up at most.** A request that arrives while a round is running is not a second
round: it sets one flag, and the round in flight runs exactly one more before it finishes. The promise a caller
awaits is the whole chain, so a caller that asks during a round still sees the change it made pushed by the time
it returns. Measured: three overlapping requests produced two rounds and no third (§1, question 7).

**Timing math.** Local-change debounce 2 000 ms (a burst of edits is one round; a second `notifyLocalChange`
inside the window does not add a timer). Periodic round 300 000 ms, rescheduled from each tick so the interval
cannot drift with the engine's own work. Reconnect ladder `min(1 000 × 2^n, 60 000)` ms from n = 0 over
consecutive feed failures, so the waits are 1, 2, 4, 8, 16, 32, 60, 60 s (the sixth rung is 64 s clamped to 60 s,
the seventh 128 s to the same ceiling). A `ready` frame resets n to 0 — measured, a feed that fails once and
then authenticates asks for 1 s again, not 2 s (§1, question 8). `lastSyncedAt` is the injected clock's reading at
the end of a round that reached the hub.

**What moves and what never moves.** Ops leave the outbox only for the `opId`s the hub's answer listed in
`accepted`; the cursor is stored only after `applyRemote` has resolved; `lastSyncedAt` only after the whole
round. A push whose answer is lost leaves the outbox untouched and the cursor alone, which is then repaired by
the op ledger on replay (case 5). A pull whose page fails halfway leaves the cursor where the store's records
really are, and the re-applied page is a no-op under LWW.

**The two clocks a client has.** The engine's own three triggers (debounce, periodic, reconnect) and the hub's
`socket factory` handshake, which a caller supplies and which is where F§8.3's first-message authentication
belongs, because the engine is handed a client and never a credential.

## 4. Lectern design

- [DESIGN] **Compression is a text codec, injected.** `SyncGzip` is `(text) => Promise<Uint8Array>` and
  `SyncGunzip` is `(bytes) => Promise<string>`, so the model's JSON goes in and the container comes out. Keeping
  the seam at *text* keeps `TextEncoder`/`TextDecoder`/`CompressionStream`/`node:zlib` out of the package
  entirely, which is the same rule U-021 followed for `fetch` (F§5.8's isomorphic package).
- [DESIGN] **The socket factory owns F§8.3's handshake.** `openSocket()` answers a socket that is already
  pointing at the hub's feed with `send(text)`, `close()`, `onMessage(handler)` and `onClose(handler)`. The
  engine owns the *protocol* — it parses every frame with `WsServerMessageSchema` and answers `ping` with
  `pong` — and the *credential* stays where F§11 puts it, with the caller that holds the token.
- [DESIGN] **The device id comes off the outbox.** `F§5.9`'s `LibraryStore` exposes no identity, and every op
  the store queues is stamped with the device that made it, so a round pushes under the `deviceId` of the op it
  is sending. A store's outbox holds one device's ops by construction.
- [DESIGN] **An empty outbox is not a push.** `F§8.2` carries 1–200 ops, and `PushRequestSchema` refuses zero, so
  a round with nothing to send skips the push and still pulls.
- [DESIGN] **`ensureModel` stores what it fetches.** The store's only model writer is `putDocument`, so a fetched
  model is written through it (with the meta the store already holds); the consequence is recorded in §7 (3).
- [DESIGN] **`status().pending` is a count, not a page.** `pendingOps(limit)` answers a page and no count, so the
  count is read by widening the page until it comes back short — bounded, and the only way to answer a number
  F§8.2's 200-op cap would otherwise disguise.
- [DESIGN] **A frame that is not F§8.3's is dropped.** The feed carries no data, so an unparseable frame or an
  unknown `type` costs nothing by being ignored; a socket that is closed under the engine's feet is what
  schedules a reconnect.
- [DESIGN] The engine's `gzip`/`gunzip` options are declared and unused (§7 (2)); the barrel gains the two
  export lines §5 allows (`./sync-client`, `./sync-engine`), inserted in the sort order Biome's organizer wants.

## 7. Deviation proposals

1. **`packages/api-client/src/testing/fastify-fetch.ts` cannot carry a null-body status.** Measured: the model
   upload through the adapter raises `Response constructor: Invalid response status code 204` — `new
   Response(new Uint8Array(answer.rawPayload), { status: 204 })` is refused because a `204` may not have a body,
   and U-056's two document-file `PUT`s answer `204` (`routes/library.ts:118`, `:139`). The file is frozen by
   R6 and is not in this contract's *Patch scope*, so this unit's test reads the two null-body answers as an
   empty `200` through a documented one-method decorator (`readableApp` in the test file); the client under
   test acts on `ok` and never on the difference. **Proposed repair for a future contract:** give that adapter
   `init: answer.statusCode === 204 || answer.statusCode === 205 || answer.statusCode === 304 ? null : new
   Uint8Array(answer.rawPayload)`. Every later unit that exercises F§7.2's library routes through that adapter
   will hit this.
2. **The engine's `gzip`/`gunzip` options have no engine-side consumer.** `F§8.2`'s compression happens in the
   client, which the contract's own parenthetical puts there ("`putModel` (gzips the JSON)"), and the engine
   performs no compression of its own in any reading of the contract. They are declared (optional) so a caller
   can hand one pair to both halves and so a later unit's literal still compiles, and they are documented in
   place. **Proposed wording:** move `gzip`/`gunzip` out of the engine's option list, or say what the engine is
   expected to compress.
3. **`ensureModel` re-queues one `document` op.** The store's only model writer is `putDocument` (F§5.9) and
   `applyRemote` deliberately carries no body, so storing a fetched model appends a local op with a fresh
   `updatedAt`. It converges (the record is unchanged apart from the stamp, and LWW makes the hub's answer a
   no-op), but it is a write to the outbox that a reader's first open of a synced document causes. **Proposed
   repair:** a store method that writes a model without queuing, or an explicit statement that this re-queue is
   intended.
4. **`SyncStatus.pending` costs a widened page.** `pendingOps(limit)` answers at most `limit` ops and the
   interface has no count, so `pending` is read by doubling the page until it comes back short. **Proposed
   wording:** say whether `pending` may be capped at one push (200) instead.
5. **The socket factory owns F§8.3's handshake.** The contract's option list gives the engine no credential and
   `sync-api.ts` deliberately models no token, so the first-message authentication cannot be the engine's.
   That is a design conclusion, stated here so a later unit does not read the omission as an oversight.
6. **`start()` awaits its first round.** The contract lists `start()` without saying whether it settles before
   or after the round it triggers; it settles after, which is what makes a caller's very next read of the store
   meaningful. `stop()` is synchronous and cancels the three timers and closes the socket.
