## 3. Architecture notes

No behavioural evidence was gathered, so this section carries the contract's own structure and the architecture the implementation follows, not a claim about the reference product.

- **Where the summary is reached from.** The reader screen (`apps/android/app/read/[docId].tsx`, U-048's file, in this unit's *Patch scope*) gains one control — "Summarize" — which pushes the summary route for the document the reader is on. The screen is a route of its own (`app/summary/[docId].tsx`), so it is a full screen in the stack rather than an overlay: expo-router registers one route per file and the root layout's stack carries no per-screen entry (U-048/U-049).
- **What the screen shows.** Four states, one at a time: nothing yet (with the button that asks), running (a spinner and how long the job has been running), done (the summary paragraph, its takeaways numbered, the model that wrote them, and "Listen to summary"), and a failure (its F§9 code, its message, and a retry).
- **Who does the work.** The hub alone (F§9): the prompts, the map-reduce, the retries and the cached row live there, and the device's two calls are F§7.2's two AI routes. The device never reaches the operator's LLM endpoint and runs no model of its own (the contract's *Forbidden Actions*).
- **Timing.** F§9's schedule is the client's: one second, then two, then three, then every five seconds, for at most ten minutes — U-064's `waitForSummary`, reused unchanged. The screen adds one thing of its own: a one-second tick that redraws the elapsed time while a job is in flight.
- **A summary that is listened to is an ordinary document.** F§9's `summaryDocument` builds it with the same `buildDocument` every parser's output goes through, so the player, the highlighter and the library need to know nothing about summaries.

## 4. Lectern design

- [DESIGN] The service is `apps/android/src/ai/summary-service.ts` with the three doors the contract names — `generate(docId, mode)`, `summaryDocument(result, title)`, `listen(docId, mode)` — plus `aiClient()`, which the screen needs twice (reading the hub's state, and waiting on a job) and which the web app's own service exposes the same way (F§10.1's `apps/web/src/ai/summary-service.ts`). F§9.
- [DESIGN] `summaryDocument` builds F§9's document exactly as the web app's does: a level-1 heading (`Summary of <title>`, or `Summary` when the document has no title), the summary as a paragraph, and one `list-item` per takeaway — so F§5.2's hash of the block texts makes the same summary the same `docId` on every platform. F§5.1, F§5.2, F§9.
- [DESIGN] `listen` files the document in the folder `Summaries` (the web app's own folder name and lookup rule: a root folder with that name, made the first time one is) and opens the reader at `/read/<docId>?autoplay=1`, which is the flag F§10.4's reader already reads. F§9, F§10.1, F§10.4.
- [DESIGN] `generate` sends this device's copy of the document when it holds one, so a document imported on the phone can be summarized before it has ever synced (F§7.2's inline document). F§7.2, F§9.
- [DESIGN] No platform module is evaluated when the service is imported: the connection, the app's stores, `expo/fetch`, `expo-crypto` and expo-router are each reached inside the function that needs them. That is what lets the package's own Node test program import the module and test `summaryDocument`, and it is the rule U-046, U-047 and U-061 established. AGENTS.md §7.
- [DESIGN] The screen's failure is F§9's own error object (`{ code, message }` with F§9's closed code set) when the hub sent one, and `LLM_UNAVAILABLE` when the failure was the client's own — the reading U-064's drawer uses, so the two platforms name a failure the same way. F§9.
- [DESIGN] Nothing was added to `app.json`, no permission was touched, and no `Platform.OS` branch exists: the app is Android-only (F§10.4, AGENTS.md §6).
