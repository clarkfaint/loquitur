## 3. Architecture notes

Everything here was measured against the installed toolchain on this host, not read out of any reference artifact.

**electron-builder reads one configuration, and a `build` key wins over the file.** `app-builder-lib@26.18.0`'s `out/util/config/load.js`:

```js
async function loadConfig(request) {
  …
  const data = packageMetadata == null ? null : packageMetadata[request.packageKey];
  return data == null ? findAndReadConfig(request) : { result: data, configFile: null };
}
```

`packageKey` is `"build"`, and `findAndReadConfig` — which is what looks for `electron-builder.yml` — is reached **only** when the application's `package.json` has no `build` key. Measured twice: with `apps/desktop/package.json` unchanged, a run logs `loaded configuration file=package.json ("build" field)` even with `apps/desktop/electron-builder.yml` present; with the `build` key removed, the same run logs `loaded configuration file=…/apps/desktop/electron-builder.yml`.

**electron-builder refuses to run at all when `electron` is a production dependency.** `out/util/packageMetadata.js`:

```js
const deps = ["electron", "electron-prebuilt", "electron-rebuild"];
if (process.env.ALLOW_ELECTRON_BUILDER_AS_PRODUCTION_DEPENDENCY !== "true") { deps.push("electron-builder"); }
for (const name of deps) {
  if (name in dependencies) {
    errors.push(`Package "${name}" is only allowed in "devDependencies". …`);
  }
}
```

`checkDependencies` is called from `checkMetadata` for every run, before any platform is chosen, and it reads the application package's own `dependencies`. Measured: `⨯ Package "electron" is only allowed in "devDependencies".` and exit 1, with `pnpm recursive run` reporting `ERR_PNPM_RECURSIVE_RUN_FIRST_FAIL`. The environment variable only exempts `electron-builder`; `electron` is unconditional.

**A Linux package's executable name comes from the package *name* by default.** `out/appInfo.js` declares `get sanitizedName() { return sanitizeFileName(this.name); }` over `get name() { return this.info.metadata.name; }`, and `out/linuxPackager.js` opens with

```js
const executableName = this.platformSpecificBuildOptions.executableName ?? info.config.executableName;
this.executableName = executableName == null ? this.appInfo.sanitizedName.toLowerCase() : sanitizeFileName(executableName);
```

For a workspace-scoped package (`@lectern/desktop`) that default is `@lecterndesktop`, which app-builder refuses: `executableName contains characters that cannot be safely used in file paths: @lecterndesktop`. `productName` does **not** feed this default — it names the AppImage (`dist/Lectern-0.0.0.AppImage`) and nothing else. Measured: naming it explicitly in the config produces `dist/linux-unpacked/lectern` and lets both targets finish.

**The `.deb` target needs three things a library-only package does not have.** `out/targets/FpmTarget.js`:

```js
const projectUrl = await packager.appInfo.computePackageUrl();
if (projectUrl == null) { errors.push("Please specify project homepage, …"); }
let author = options.maintainer;
if (author == null) { const a = packager.info.metadata.author; if (a == null || a.email == null) { errors.push(errorMessages.authorEmailIsMissed); } … }
```

and `AppInfo.computePackageUrl()` reads `this.info.metadata.homepage || this.notNullDevMetadata.homepage`, then a github `repository`. So the `.deb` needs a project URL from the application's `package.json`, and a maintainer — the latter from `linux.maintainer` or from an `author` that carries an email. Measured both refusals in one run:

```
⨯ Please specify project homepage, see https://www.electron.build/configuration#metadata
Please specify author 'email' in the application package.json
It is required to set Linux .deb package maintainer. Or you can set maintainer in the custom linux options.
```

**The same target's default file name is `${name}_${version}_${arch}.${ext}`, and a scoped name breaks it.** With `name` = `@lectern/desktop` the target writes `dist/@lectern/desktop_0.0.0_amd64.deb`, and fpm then refuses: `Parent directory does not exist: …/dist/@lectern — cannot write to …/dist/@lectern/desktop_0.0.0_amd64.deb`. `FpmTarget`'s own options are `deepAssign({}, packager.platformSpecificBuildOptions /* linux */, packager.config[this.name] /* deb */)`, so `deb.packageName` and `deb.artifactName` are the two keys that fix the internal name and the file name; `packageName` is **not** a key the schema accepts under `linux` (measured: `Invalid configuration object … configuration.linux should be one of these: null` for the version that carried it there, and the scheme's `LinuxConfiguration` properties are the authority).

**Production dependencies are copied into the package unless a negated pattern stops them.** electron-builder appends a node-module file set of its own (`out/platformPackager.js`: `if (!this.info.isPrepackedAppAsar && !this.info.areNodeModulesHandledExternally) { … getNodeModuleFileMatcher(…) … computeNodeModuleFileSets(…) }`), and `getNodeModuleFileMatcher` "grabs only excludes" — it keeps only patterns from `files` that start with `!`. With no negation it is empty, `NodeModuleCopyHelper` is then constructed with `matcher.isEmpty() ? null : matcher.createFilter()`, and a null filter copies everything. Measured before the negation existed: **5 018 files, 194 533 928 bytes**, including `node_modules/pdfjs-dist/build/pdf.worker.mjs.map` — a source map inside the application archive. With `"!node_modules/**"` in `files`: the archive carries **24 paths** and 2 779 510 bytes, and nothing under `node_modules` at all.

**An asar is two pickles followed by the files**, which is what lets a script see what the archive really holds without a dependency:

```
bytes 0..3   length of the outer pickle's payload (the constant 4)
bytes 4..7   length of the header pickle
bytes 8..11  the header pickle's payload size
bytes 12..15 the JSON directory's length
bytes 16..   the JSON directory itself
```

Measured on the archive this unit produces, in this layout: `04 00 00 00 | 2c 06 14 00 | 28 06 14 00 | 21 06 14 00 | 7b 22 66 69 6c 65 73 22 …` — the `{"files":…` directory begins at offset 16. Reading the length at offset 8 (the header pickle's payload size) and the JSON at 12 yields `!\u0006\u0014{"file"…` and a parse failure, which is the mistake this file's parser first made.

## 4. Lectern design

- [DESIGN] **The config file is the packaging config** (F§10.3's packaging line). `apps/desktop/electron-builder.yml` carries `appId: dev.lectern.desktop`, `productName: Lectern`, `directories.output: dist`, `files` (`out/**`, the resource trees, and the `!node_modules/**` negation), the three `extraResources`, Linux `AppImage` + `deb` with category `Utility`, Windows `nsis` per-user with no elevation, and **no `publish` entry** (§1's no-update-feed rule; §6's exclusion of telemetry and self-updating).
- [DESIGN] **The reader page is carried twice, on purpose.** `out/**` goes into `resources/app.asar`; the page is also inside the archive at `resources/web`, because `apps/desktop/src/main/index.ts` resolves it as `join(__dirname, "..", "..", "resources/web/index.html")` and inside a packaged application `__dirname` is inside the archive (measured: `app.getAppPath()` ends with `app.asar`, and the window's own URL contains `app.asar`). The same three trees are *extra resources* beside the archive, at `resources/web`, `resources/overlay` and `resources/icons`, where the overlay window, the tray icon and an operator's inspection can reach them. The map is `{ from: resources, to: resources }` inside `files` plus three `extraResources` entries with `to: web|overlay|icons` — a string entry in `extraResources` is instead a *pattern* on the default matcher, which would have written `resources/web` to `resources/resources/web`.
- [DESIGN] **`scripts/verify-package.mjs` checks two trees, because a package is two trees.** The loose files beside the archive and the files inside it; a walk of the unpacked directory alone cannot see anything the archive carries, which is exactly where a stray test or source map hides. It exits 1 naming the path and the one command that produces it.
- [DESIGN] **The packaged case is small and separate.** `e2e/packaged.spec.ts` launches `dist/linux-unpacked/lectern` through Playwright's `_electron` with `executablePath` and asserts the facts only a package can supply: the application path ends in `app.asar`, the window's title is `Lectern` (in the page and in the main process), the window's URL contains `app.asar`, and the bridge reports `linux` with F§10.3's seven members. The behavioural suite keeps running against the build directory, where a failure points at one unit's code rather than at the packaging step. No `.skip` and no conditional pass: a missing package is a failure that names the command to run.
- [DESIGN] **`docs/desktop-windows-build.md` is the operator's recipe and checklist**, including the ten manual checks (install, launch, each default hotkey, selection from a browser and from a text editor with the clipboard restored, region OCR, mini-player, watched folder, tray quit) and the explicit statement that Windows artifacts stay `unverified` until those steps have really run on Windows (§1: "Do not claim Windows artifacts are verified unless the Windows steps were actually run on Windows").
- [DESIGN] **The `.deb` is built with the project's own non-resolving identity** — `maintainer: Lectern Executor <executor@lectern.invalid>` — because F§10.3 wants a `.deb` and Debian wants a maintainer, and Lectern has no operator email to give it. Nothing is contacted; `.invalid` cannot resolve.

## 7. The blocker, and the repairs it needs

The contract's fixed command **cannot exit 0 against the repository as it stands**, and every remaining cause is in a file this unit may not write. Measured, in the rehearsal copy, in the order the command meets them:

| # | File | What the run says | What it needs |
|---|---|---|---|
| 1 | `apps/desktop/package.json` | `⨯ Package "electron" is only allowed in "devDependencies". Please remove it from the "dependencies" section in your package.json.` — `dist:linux` exits 1 before anything is packaged | move `electron` (and `electron-builder`) from `dependencies` to `devDependencies`. U-038's contract *Installs (`apps/desktop`, exact): `electron`, `electron-vite`, `electron-builder`, `zod`` put them in `dependencies`, and electron-builder's own metadata check refuses to run on that manifest — there is no flag and no environment variable that exempts `electron`. |
| 2 | `apps/desktop/package.json` | with (1) repaired: `loaded configuration file=package.json ("build" field)` — the file this contract requires is never read | remove the `build` key. `loadConfig` consults `electron-builder.yml` only when the application's `package.json` has no `build` key, so every value this contract pins — `category: Utility`, the three `extraResources`, `output: dist`, `syncDesktopName` — lives in a file that is currently dead. |
| 3 | `apps/desktop/package.json` | with (1) and (2) repaired: `⨯ Please specify project homepage …` — the `deb` target refuses to build | add `homepage` (or a github `repository`). Measured: adding `"homepage": "https://lectern.invalid/"` to the copy's manifest lets the `.deb` finish. |

`apps/desktop/package.json` is owned by `U-038`, which is `DONE`; `U-044`'s *Inputs & Dependencies* carries no `Patch scope:` line at all, and §5 lets a unit only **add** dependencies and scripts to a manifest, never remove or change an existing entry — so all three edits are outside this unit's file scope (R6, R15). They are not adjudications of taste: (1) and (2) are each independently fatal to the contract's own fixed command.

Two things are worth recording beside them:

- The repairs are additive and behaviour-preserving elsewhere. In the copy, nothing else changed: the four `dist:linux`/`dist:win`/`build`/`e2e` scripts are untouched, and the whole chain — including U-038's, U-039's, U-040's, U-041's, U-042's and U-043's cases — exits 0 on the first run.

**Fix attempts spent:** one, as the protocol counts them — the rehearsal established the full repair set before the official run, and no attempt can be made against the repository because every remaining cause is in `apps/desktop/package.json`. The unit's own four deliverables are complete and are the artefacts a patched contract would close on; the rehearsal above is the proof that they are sufficient.
