## 2. Observations

Inspection is `N/A`, so no statement below is a claim about the reference product and none carries an
`OBSERVED`, `INFERRED` or `UNKNOWN` label — there is no target evidence to label. What this unit decides
is Lectern's own, and each decision is recorded as `[DESIGN]`:

- [DESIGN] The layout lives in exactly one file. `openLecternDb` is the only declaration of the database
  name and version, and it creates all ten stores in one upgrade step, so no store module can disagree
  with another about the layout.
- [DESIGN] `outbox` is keyed by an auto-incrementing number with an `opId` index, so insertion order *is*
  the outbox's order and `ackOps` removes through the index rather than by rewriting the queue.
- [DESIGN] The per-entity last-writer-wins stamp is kept in the already-declared `meta` store under
  `version:<entity>:<id>`. F§5.9 gives the layout no store for it, and a stamp held in a module variable
  would be lost on reload, which would let an older remote record overwrite a newer local one after a
  refresh.
- [DESIGN] `blobMeta` rows carry `mime` beside `size` and `lastUsed`, because `uri` must hand back a
  *playable* URL and a URL built from bytes alone plays the wrong container after a reload.
- [DESIGN] One object URL per key. It is created when the key is written, remembered, handed back by
  `uri`, and revoked on `delete` and on eviction — measured with a spy on `URL.revokeObjectURL`.
- [DESIGN] The test gives each conformance case a database of its own, because a suite case expects to
  start from a store that holds nothing (a shared database would let an earlier case's document appear in
  a later case's unfiltered list).

## 3. Architecture notes

**Schema** — database `lectern`, version 1, ten stores. Keyed stores: `documents` (`docId`), `models`
(`docId`), `folders` (`id`), `bookmarks` (`id`), `progress` (`docId`), `settings` (`key`). Keyed from the
outside: `outbox` (auto-increment, plus an `opId` index), `meta`, `blobs`, `blobMeta`.

**One transaction per mutation.** A record's write, its `models` change and its outbox entry commit
together, with the entity's new version stamp in the same transaction. A record written without its op
would be a change no other device hears about; an op written without its record would be one they cannot
apply.

**Last-writer-wins.** Applying a remote op reads `meta`'s stamp for that entity; the op wins only when
`A.ts > B.ts`, or `A.ts === B.ts` and `A.deviceId > B.deviceId` (F§5.9, via `@lectern/core`'s `isNewer`).
`applyRemote` never appends to the outbox. A document op writes its metadata and leaves any model already
on hand alone — a model arrives as its own payload (F§8.2) — and a delete op removes the model.

**Blob cache.** `lastUsed` comes from the injected `now()`, and `evictLru` removes the coldest unpinned
rows until the total fits, returning the bytes freed. `sizeBytes` sums the `blobMeta` sizes, so replacing
a key replaces its contribution rather than adding to it.

Measured locally in this session's rehearsal copy (`~/.hermes/cache/scratch/u026-repo`), all by running
the code rather than by reading a doc:

- `fake-indexeddb/auto` installs `indexedDB` (an object) and `IDBKeyRange` (a function) over the

## 4. Lectern design

- [DESIGN] `openLecternDb(name = "lectern")` returns the connection; the four modules this unit adds
  never open a database of their own, which is what keeps the schema in one place (F§5.9).
- [DESIGN] `createIdbLibraryStore({ db, deviceId, now, newId })` is the contract's factory with the
  contract's options; the store takes its clock and its op ids from the caller, so a test can name every
  timestamp and every op id (F§5.9).
- [DESIGN] `createIdbBlobCache({ db, now })` keeps only the object URLs it has handed out; the bytes and
  the recency live in the database (F§5.9).
- [DESIGN] `getDeviceId(db)` creates the identifier inside the read-write transaction that reads it, so
  two tabs opening at once cannot mint rival identities and turn every later write into a tie (F§5.9's
  `deviceId` tie-break).
- [DESIGN] `packages/ui-web/src/index.ts` gains four export lines, inserted in their sorted positions
  with no existing line moved — the append-only barrel §5 allows and the two preceding ui-web units did
  (U-024, U-025).
- [DESIGN] Both `@lectern/core/testing` conformance suites run unmodified against the real
  implementations; the test asserts every case is `ok` and pins the case counts (9 library, 3 cache).

## 7. Deviation proposals

1. **F§5.9 says nothing about the MIME type a cache's `uri` builds a URL with.** `put(key, bytes, mime)`
   is handed the type, but the record the cache keeps is described only as tracking "size and last
   access", and `BlobCache` has no method that returns it. After a reload a cache therefore holds bytes
   with no way to learn their container, and a `blob:` URL built without one plays the wrong format.
   Implemented: `blobMeta` carries `mime` as a third field. Proposed: F§5.9 name the field, or add a
   `mime(key)` accessor to `BlobCache`.
2. **F§5.9's layout has no store for the per-entity version the LWW rule compares.** The reference
   `MemoryLibraryStore` keeps it in a `Map`, which a durable store cannot. Implemented: `meta` — a store
   the contract's own list already contains — under the key `version:<entity>:<id>`. Proposed: F§5.9 name
   that key space (or the layout gain a `versions` store) so a later store implementation cannot pick a
   different key.
3. **pnpm's minimum-release-age policy is noisy on this lockfile and quiet about ignored builds.**
   Every `pnpm` invocation here prints `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` for
   `@fastify/cors@11.4.3` — and `[WARN] The install that runs before scripts failed …` — above its own
   output while still exiting 0, including both steps of this unit's fixed command. Installing the two
   packages the contract names needed `--config.minimumReleaseAge=0`, and `pnpm add` also reported
   `Ignored build scripts: esbuild@0.28.2.` while exiting 0. Recorded, not acted on: the contract's
   command is run unmodified and no policy file is edited (`pnpm-workspace.yaml` is byte-identical before
   and after the two installs). The same observation stands in U-019, U-021, U-022 and U-023.
