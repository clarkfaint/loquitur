## 3. Architecture notes

**Reading order is geometry, and it is decided per page.** pdfjs reports a page as a flat item list in
content-stream order, which is not reading order. The layout groups items into *lines* by baseline (an
item joins the line being built while `|Δy| ≤ max(1, 0.2 × size)`), lines into *paragraphs* by the
whitespace between them, and marks a line a *heading* when its type is at least 1.25 × the page median.
Nothing is grouped across a page boundary: the page a block belongs to then has one answer, and a break
between pages separates paragraphs in any case.

**The paragraph arithmetic, with the fixture's numbers.** The rule F§5.4 states is "vertical gap >
1.5 × the median line height". The vertical gap is the whitespace between two baselines, i.e. the
baseline distance minus the line height, and the line height is the median type size of the lines being
grouped. The fixture sets 14 pt type on 30 pt leading with a 45 pt distance between paragraphs, so the
within-paragraph gap is `30 − 14 = 16` and the between-paragraph gap is `45 − 14 = 31`, against a
threshold of `1.5 × 14 = 21`: 16 stays, 31 splits. The comparison is strict, so a 35 pt baseline
distance — exactly `2.5 × 14` — still stays one paragraph, which the unit test pins. The reading is
deliberate: taken as "baseline distance > 1.5 × the *baseline* distance", no paragraph break in a
double-spaced document can ever fire, and the fixture's own 45 pt break would not fire either.

**Headings are their own blocks; a heading level is a rank.** A heading line never joins a paragraph —
F§5.4 marks it by type size, not by the gap around it — and the document's distinct heading sizes, from
largest to smallest, become levels 1, 2, … capped at 6. The fixture has one heading size, so its three
chapters are one level, which is what the test asserts rather than inventing a distinction the document
does not draw.

**Every rule reads the same two ratios.** `yRatio = (pageHeight − baseline) / pageHeight`, measured from
the top of the page, and `fontRatio = size / pageMedian`. They are the *only* geometry a `RawBlock`
carries (F§5.4, and `RawBlock`'s own fields), and they are what `classifySkip` — U-004's frozen module,
untouched here — needs for the top/bottom bands and the footnote size test.

**Provenance, not a second guess.** Each block's text is assembled from the items together with, for
every character, the item it came from and the offset inside that item's string; a character the
assembly inserted (a space between two items of a line, or between two lines of a paragraph) records
`null`. The parser then tokenizes that same text with F§5.3's tokenizer — the one `buildDocument` uses —
so a word's range in the block text maps directly onto the characters of the item that drew it. The
de-hyphenated word is the interesting case: the break hyphen is dropped from the text, so the word's
characters run from the middle of one item to the start of the next, and the anchor names the item the
word starts in and stops where that item stops.

**One guard makes the offsets honest.** Normalization (F§5.2) can change text length — it removes soft
hyphens and applies NFC — and any such change would move every offset after it. Rather than reimplement
those rules, `parsePdf` asks `normalizeText` whether the assembled block text is already what
normalization would produce, and gives a block no anchors at all when it is not. A pointer computed
against text that is about to shift is worse than no pointer, and the delivered test asserts the
invariant for every block of the fixture.

**The page walk.** `getDocument` is given a copy of the bytes, the options that exist (`useWorkerFetch:
false`, `disableFontFace: true`, `verbosity: VerbosityLevel.ERRORS`), the document's own `Title` if it
declares one, and each page's items; the loading task is destroyed in a `finally`, so the in-process
worker is released whatever happens. `page.cleanup()` is called after a page's strings have been
extracted into plain data — the layout consumes only `str`, `x`, `y`, `width`, `height` and the item's
index, so nothing depends on the proxy afterwards.

**The item shapes pdfjs actually returns are checked, not assumed.** A page's items are external input —
they come out of a file the user supplied — so each is validated with a zod schema
(`str`, `transform`, `width`, `height`) before any of it is read: marked-content entries, which carry no
string, fail the schema and are dropped, and an item whose string is empty is dropped as well, since it
holds no word and no geometry worth grouping. `transform` is declared `Array<any>` by pdfjs, so its
entries are read as `unknown` through a finite-number coercion rather than trusted; the type size is the
scale `hypot(a, b)` of that matrix, falling back to `height` when it is zero.

## 4. Lectern design

- [DESIGN] `pdf-layout.ts` is pure data in, pure data out: it imports nothing, so F§5.4's four layout
  rules can be read and tested without a PDF or a library at hand, and `pdf.ts` holds everything that
  touches pdfjs — follows the contract's split into "pure functions over `{ str, x, y, width, height,
  fontSize, itemIndex }[]`" and the module that owns the library.
- [DESIGN] Lines are grouped with a tolerance of `max(1, 0.2 × size)` rather than exact equality: real
  writers emit baselines that differ in the last decimal, and a fifth of the type size is far below any
  leading a document uses — follows F§5.4's "grouped into lines by baseline".
- [DESIGN] The paragraph gap is `baselineDistance − lineHeight` compared strictly against
  `1.5 × lineHeight`, with the line height the median type size of the lines being grouped (section 3
  gives the arithmetic and why the alternative reading cannot fire) — follows F§5.4.
- [DESIGN] Headings are detected per page against the *page* median, as F§5.4 says, and are never merged
  into a paragraph; heading levels are the document's distinct heading sizes ranked largest-first, capped
  at the six levels F§5.1 allows.
- [DESIGN] `RawBlock`s carry `page`, `yRatio` and `fontRatio` and nothing else about their geometry, and
  the parser sets no `kind` beyond `heading`/`paragraph`: furniture is `classifySkip`'s decision (U-004),
  not the parser's — follows F§5.4's "buildDocument normalizes, classifies `skip`, tokenizes".
- [DESIGN] `parsePdf` copies the caller's bytes into a fresh `Uint8Array` before handing them to pdfjs,
  because pdfjs transfers — and therefore detaches — the buffer it is given (section 2). A parser that
  quietly empties its caller's array is a footgun for the units above it (the dispatcher hashes and
  re-reads the same bytes), and the copy also makes a `Buffer` argument acceptable, which pdfjs refuses.
  The cost is one copy of a document that is read once.
- [DESIGN] The returned `wordAnchors` is a list of one entry per word of each block, carrying the word's
  range in the block's text and the item and item-character range that drew it; `anchorsFor` turns that
  into F§5.1's `PdfAnchor[]` by matching a word's block offset, in reading order (block, sentence, word).
  A word the parser could not locate is left out rather than anchored to a guess.
- [DESIGN] A word split across two items is anchored to the item it starts in, covering the characters of
  that word which lie in that item (section 3). One anchor per word is what F§5.1's `PdfAnchor` — a
  single `itemIndex` with a single `charStart`/`charEnd` — can express; a second anchor for the tail of
  the same word would break "one anchor per word" for no gain.
- [DESIGN] `RawBlock`'s text for the fixture already satisfies F§5.2, and the parser *proves* that per
  block with `normalizeText` before it anchors anything (section 3), instead of reimplementing NFC or
  the soft-hyphen rule — follows AGENTS.md §7 (use the module that owns the rule) and R14 (a block with
  no anchors is honest; a guessed offset is not).
- [DESIGN] The parser passes only pdfjs options that exist in the installed version: `useWorkerFetch:
  false`, `disableFontFace: true` and `verbosity: VerbosityLevel.ERRORS`. `isEvalSupported`, which older
  pdf.js releases document, is **not** passed (section 2) — follows R9. No worker is started: pdfjs's
  Node path disables it itself, which is the contract's "disable the worker for Node" without inventing
  a flag for it.
- [DESIGN] The parser is `async` and destroys its loading task in a `finally`; it renders nothing, creates
  no canvas and reads no image — follows the contract's *Forbidden Actions* and leaves page rendering to
  U-010.
- [DESIGN] `packages/core/src/parsers/index.ts` gains two export lines, `./pdf` and `./pdf-layout`, which
  sort after the two lines U-006 added, so the barrel stays append-only in the order the standing lint
  gate wants — follows AGENTS.md §5.

### Defects found and fixed in the rehearsal (all three before this commit)

1. **`DataCloneError` on a second parse of the same bytes** — `getDocument` was given the caller's array
   directly, and pdfjs transfers that array's buffer to its worker, so the second call with the same
   array fails (section 2). Fixed by copying the bytes in `parsePdf`, which the test now pins by parsing
   the same array twice.
2. **`TS2741: Property 'getMetadata' is missing`** — the structural document interface the parser reads
   through did not list `getMetadata()`, which `declaredTitle` calls. Fixed by adding it; the
   `pnpm --filter @lectern/core run typecheck` step is what caught it, which is the second step of the
   fixed command doing its job on the unit's own code.
3. **A JSDoc comment closed itself**: the header comment of `__tests__/pdf.test.ts` contained
   `src/**/__tests__`, whose `**/` sequence ends a block comment, and the standing lint gate reported a
   page of parse errors against text that was still inside a comment. Fixed by rewording the comment —
   no rule was disabled and no frozen file was touched.

## 7. Deviation proposals

- [DESIGN → contract] **`RawBlock` has no field for "below a horizontal rule"**, which F§5.4's footnote
  rule names as an alternative arm; U-004 recorded the same gap and the fixture's footnote is decided by
  its font size. Unchanged here because this unit cannot add the field: the contract's *Required File
  Outputs* are four files under `src/parsers/`, and `builder.ts` (which declares `RawBlock`) is U-004's
  frozen file and is not in this contract's `Patch scope`. The rule is implemented as the font-size arm
  alone.
- [DESIGN → contract] **The PDF row's paragraph rule cannot fire as written for a double-spaced
  document.** "Vertical gap > 1.5 × the median line height" is implemented as
  `baselineDistance − lineHeight > 1.5 × lineHeight` (section 3). If "line height" is instead read as the
  baseline-to-baseline distance — which is the other natural meaning of the phrase — then no gap a
  document's own leading produces can ever exceed `1.5 × that`, since paragraph breaks are only half a
  line wider in the fixture and less than that in ordinary typesetting, and the fixture's own paragraph
  breaks would not be detected. Proposal: state the comparison's two operands in F§5.4 (whitespace gap
  against type size), so a later parser does not have to rediscover which reading works.
- [DESIGN → contract] **A word can span two text items, and F§5.1's `PdfAnchor` can only name one.** For
  the fixture two words do (the de-hyphenated `lighthouse`, and `flame. -`, which F§5.3's punctuation
  merge creates across a line break). The anchor names the item the word starts in and covers that
  word's characters within it (section 3). Proposal: either accept that a word's highlight may be partial
  in one item (state it in F§5.1), or let `PdfAnchor` carry a short list of item/character runs.
- [DESIGN → contract] **The fixture's footnote line is drawn truncated** — 107 of its 115 characters
  reach the text layer, ending mid-word (section 2). `packages/fixtures/generate.mjs` draws the footnote
  unwrapped (`buildTextPdf`, the `document.footnote.text` draw), and U-005's `--check` asserts only that
  the marker is present. It does not affect this unit, and U-005 is `DONE` and frozen (`generate.mjs` is
  not in this contract's *Required File Outputs* or *Patch scope*). Proposal: wrap the footnote in the
  generator, and have `--check` read the footnote's full text back, so a later unit can assert on a
  complete footnote.
- [DESIGN → contract] **No target is available for the whole PDF-reading path.** This contract, like
  U-003, U-004 and U-006 before it, found its inspection tools absent and its target directory empty, so
  questions 1, 2, 4 and 5 of section 1 stay `UNKNOWN` and will stay so for every later unit that
  inherits them. Proposal: name, in the unit that owns reader behaviour (not a parser), the target and
  the tools that will actually be present when it runs.
